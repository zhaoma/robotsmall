## 0. 一页纸结论

| 决策点 | 结论 | 一句话理由 |
|---|---|---|
| 分层 | 4 项目严格单向依赖，`Api` 是唯一组合根，端点方法体只做 `Model → Command → Service → Response` | 业务规则只有一个落点，AI 生成代码时没有第二个可漂移的位置 |
| 事务边界 | **一个用例一个事务**，由 `IUnitOfWork.ExecuteAsync()` 显式包裹，事务只存在于 Application 层 | 端点开事务 = 事务边界随 HTTP 抖动；仓储开事务 = 隐式嵌套不可控 |
| 领域事件 | 进程内**同步、在事务内**派发；订阅者**只允许写库（含写 Outbox 行）**，绝不直接调外部 | 外部副作用在事务内会让回滚变成谎话；只写库则"回滚 = 什么都没发生"成立 |
| 库存语义 | `StockItem(OnHand, Reserved, Sold)`；**`Available = OnHand − Reserved`**；`Reserve` 加 Reserved、`Commit` 减 OnHand/Reserved 增 Sold、`Release` 减 Reserved | DB `CHECK(Reserved <= OnHand)` 是不超卖的**最后防线**（AC-08），领域校验只做友好提示 |
| 并发令牌 | 全实体统一 **`long Version` + `IsConcurrencyToken()` + SaveChanges 拦截器** | `UseXminAsConcurrencyToken` 是 provider 专有开关，切 SQLite 直接失效；`Session` **例外**（不加令牌，用单调 UPDATE） |
| 支付一致性 | Order 与 Payment 不同聚合，`SettleAsync()` 是**唯一支付状态写入点**，回调/手动刷新/对账三路共用 | 三条路径各写一份幂等逻辑 = 必然有一条是错的（AC-06/AC-07 同时要过） |
| 金额 | 唯一金额类型 `Money(long minorUnits, currency)`；JSON 形态 **`{amountMinor, currency}`** | 裸 `decimal` 跨层是本项目最贵的 bug 来源（架构 §7 风险 8） |
| 价格结构 | **`ProductVariant` 内联 `PriceAmountMinor / CompareAtMinor / Currency` 三列**，不建 1:N 价格表；二期加币种走"新增 `VariantPrice` 表 + 回填 + 双写 + 切换读" | **Currency 列存在且不得省略**（否则二期回填只能靠猜，而配置期间可能被改过）。这是定论，不是技术债 |
| 退款 | 幂等键 **`refund:{RefundId}`**；一律**异步**（事务内建 `Pending` + Outbox）；通道无 `Refund` 能力 → `Provider=manual` + `Status=AwaitingManual` + 必填凭证号 | 一单可多次部分退款，用订单 ID 作幂等键会把第二笔退款当重放吞掉 |
| `canSell` | **落库派生值**：`已填凭据 && 最近测试通过 && 通道启用`；`canSellReason ∈ {ok,noCredentials,testFailed,channelDisabled}`；**无写入口**；连续 2 次探测失败才翻 false、单次成功立即恢复 | 能手工翻转 → "能下单但通道是错的" → 僵尸订单；一次抖动就关闭 → 商家无过错却被停业 |
| 安装向导 | **一次性安装令牌**（`/data/setup-token.txt` 或 `OPENSTORE_SETUP_TOKEN`）保护**所有写端点** | 部署完到向导完成之间的窗口是开放的，任何扫到 IP 的人都能改支付凭据把货款收进自己账户 |
| 鉴权 | 两套 Cookie（`os_admin_sid` / `os_shop_sid`）+ DB Session（存 token 哈希）+ 权限点策略 `perm:*` | 权限点策略比 `[Authorize(Roles="Admin")]` 可持续：员工权限要能细到"不可退款" |
| 越权防护 | 落点在 **Application 查询入口**（`OwnedQuery` 强制过滤 + 统一返回 NotFound） | 落在 Controller 会被新端点绕过；落在 DB 行级安全 SQLite 不支持 |
| 幂等 | **四层**：`WebhookEvent(Provider, DedupeKey)` 唯一 → `Payment(OrderId) WHERE Succeeded` 唯一 → 支付状态守卫 + Version → `(Provider, ProviderTransactionId)` 唯一 + Outbox `DedupeKey` 唯一 | 单靠任一层都会漏；而"先查再写"在并发 5 次时 5 个全漏（AC-06 加严） |
| SEO 归属 | 页面级 `canonical`/`noindex` **归 storefront**；后端只出 `sitemap.xml` 绝对 URL 与 `/api/*` 的 `X-Robots-Tag`；`robots.txt` 只一行 | 两处各输出一份必然互相矛盾；"robots Disallow + noindex 双保险"是已被作废的错误（W9/W12） |
| 工程门禁 | `scripts/check.sh` 14 步 + `scripts/verify-gates.sh` 自动注入 **12 处违规**并断言红灯 | 客户要的不是"有检查脚本"，是"能证明检查脚本会拦住违规" |

### 1.2 端点方法体的标准形态

固定四段，中间不许插入业务逻辑：

```csharp
// Endpoints/Admin/CatalogEndpoints.cs —— 8 行，这是全部内容
group.MapPost("/products", async (
    CreateProductRequest req, ICurrentUser me,
    IValidator<CreateProductCommand> validator, CatalogService svc, CancellationToken ct) =>
{
    var cmd = req.ToCommand(me.SubjectId, me.Locale);                    // ① Model → Command
    var v = await validator.ValidateAsync(cmd, ct);
    if (!v.IsValid) return Results.ValidationProblem(v.ToDictionary());  // ② 校验（Application 的 Validator）
    var result = await svc.CreateProductAsync(cmd, ct);                  // ③ Service（内部一个事务）
    return Results.Created($"/api/admin/products/{result.Id}", result.ToResponse()); // ④ Response
})
.RequireAuthorization(Permissions.CatalogWrite)
.Produces<ProductDetailResponse>(201).ProducesProblem(400).ProducesProblem(403)
.WithOpenApi();
```

**`ToCommand` / `ToResponse` 放在 `Api/Mapping`，是纯函数**（无 DI、无 IO），所以可以被单元测试穷举字段映射——这是防止"admin 字段泄漏到 storefront"最经济的手段：storefront 的 `ToResponse` 只接受 `StorefrontProductDto`，两者在编译期就是不同类型。

### 1.3 Application Service 的边界

| 它做的事 | 它绝不做的事 |
|---|---|
| 编排：按顺序调用仓储读聚合 → 调聚合方法 → 调领域服务 → 写仓储 → 提交事务 | **绝不**包含业务规则（"库存不足要怎样"属于 `StockItem.Reserve`；"总额怎么算"属于 `Pricing`） |
| 事务边界声明（`IUnitOfWork.ExecuteAsync`） | **绝不**拼 SQL、绝不 `FromSqlRaw`、绝不 `Include` 到 3 层以上（复杂读走专用 Query 类 + 投影） |
| 跨上下文编排（Order 创建 = 读 Catalog 快照 + Stock.Reserve + Payment 创建） | **绝不**直接 new 另一个上下文的聚合根来做"顺手写一下"——必须走那个上下文的 Service 或领域事件 |
| 把领域异常翻译成 `Result`/`AppException`（带 `ProblemCodes`） | **绝不**调 `IPaymentGateway` / `IEmailSender`（外部副作用一律写 Outbox 行；唯一例外是「结算提交时创建支付意图」需要在事务内确定支付 URL，见 §5 备注） |
| 输出持久化无关的 DTO | **绝不**做 HTTP 相关判断（读 header、拼 url、看 `HttpContext`）。需要请求上下文的一律走 `ICurrentUser` 抽象 |

> **唯一的"事务内调外部"例外**：`CheckoutService.ConfirmAsync` 必须在创建订单的同一事务语义内拿到 `PaymentIntent` 的客户端密钥。做法是**两阶段**：阶段 ① 本地事务创建 Order(PendingPayment) + StockHold，提交；阶段 ② 调 `IPaymentGateway.CreateAsync` 成功则回写 `Payment.ProviderIntentId`，失败则进入"待支付但无支付意图"状态，由 `Payments` 的"重试创建意图"用例兜底（幂等键 `intent:{orderNumber}`）。这样"回调丢失/意图创建失败"都不会留下不一致的订单，代价是存在一个极短窗口的"订单已建但用户看不到支付页"——用 `GET /orders/{n}/pay-url` 幂等重取解决。

#### 1.3.1 下单前置校验流水线（顺序写死，不许分散）

AC-17⑦ 的 TOCTOU 要求：**页面渲染时 `canSell=true`，随后凭据被改坏，用户提交——服务端必须拒绝且不建单**。这与库存/价格的二次校验是**同一类模式**，因此放进同一个流水线，顺序固定：

```
① CanSell 可用性    → 503 CANNOT_SELL（+ details.reason）      ← 最便宜、失败原因最确定，放最前
② 幂等键检查        → 命中则直接回放原响应；body 不同 → 409
③ 库存预占         → 预占成功才允许建单；失败 → 409 INSUFFICIENT_STOCK（必须指到具体变体）
④ 价格有效性       → quoteToken 金额与服务端重算不一致 → 409 CHECKOUT_PRICE_CHANGED + amountChanged
⑤ 建单 + Payment + Outbox
```

| 约束 | 说明 |
|---|---|
| ① 必须是方法体**第一条语句**（在打开事务、读购物车、读库存之前） | 保证"不建单、不占库存"（AC-17②） |
| **重新支付路径（`POST /orders/{n}/pay` 与 `GET /orders/{n}/pay-url`）走同一个 ①②** | 否则凭据失效后用户点"重新支付"仍会创建支付意图（主理人专门点名过这条） |
| ③ 失败时事务必须已回滚 | 预占与建单在同一事务；任一步失败整体回滚，不留半张订单 |
| ④ 与 ③ 的顺序不可交换 | 先占库存再判价，才能保证"价格变了但库存已占"不会发生（占库存是短事务，价格检查在提交前完成） |

### 1.4 领域事件分发器

**注册表形态：显式、无扫描。** 与"不用 MediatR"的理由一致：编译期可见、可 grep、AI 不会猜错。

```csharp
// Application/Events/HandlerRegistry.cs —— 22 行
public sealed class HandlerRegistry
{
    private readonly Dictionary<Type, List<Func<IDomainEvent, IServiceProvider, CancellationToken, Task>>> _map = new();
    public void Add<TEvent>(Func<TEvent, IServiceProvider, CancellationToken, Task> handler) where TEvent : IDomainEvent
    {
        if (!_map.TryGetValue(typeof(TEvent), out var list)) _map[typeof(TEvent)] = list = new();
        list.Add((e, sp, ct) => handler((TEvent)e, sp, ct));          // 注册顺序 = 执行顺序（确定性）
    }
    public IReadOnlyList<Func<...>> For(Type t) => _map.TryGetValue(t, out var l) ? l : Array.Empty<...>();
}

// DI 装配处（Program.cs）
registry.Add<PaymentSucceeded>(async (e, sp, ct) =>
{
    // 订阅者只允许写库：改 Order 状态 + 写 Outbox 行
    await sp.GetRequiredService<IOrderSettlementHandler>().OnPaymentSucceededAsync(e, ct);
});
```

**语义（写死，不留解释空间）**

| 项 | 决定 | 理由 |
|---|---|---|
| 同步还是异步 | **同步 await，在事务内**。订阅者抛异常 = 用例失败、事务回滚 | 让"订单已支付但库存没扣"这种状态在物理上不可能出现 |
| 派发时机 | `UnitOfWork.SaveChangesAsync()` 内：`SaveChanges → 派发（订阅者可能再 SaveChanges）→ 再次 SaveChanges → Commit` | 订阅者要能读到主聚合的最新持久化状态（如 Order 的 Id） |
| 订阅者能做外部调用吗 | **不能**。需要外部效果就写 Outbox 行（`OutboxMessage` 是普通表，同事务） | 事务内的 HTTP 调用会：① 阻塞全局吞吐 ② 外部成功但事务回滚 → 假成功 ③ 事务持有时间不可控 |
| 失败怎么办 | 异常直接上抛，无自动重试 | 重试必须在"整用例"粒度（调用方/用户重试），局部重试会产生半个事务 |
| 重复派发防护 | 派发后 `aggregate.ClearEvents()`；`UnitOfWork` 持有本轮事件列表，Commit 成功后丢弃 | 防"SaveChanges 多次调用导致同一事件派发两次" |
| 顺序 | 同聚合内按加入顺序；跨聚合按 `SaveChanges` 时 `ChangeTracker` 遍历顺序（按实体类型名排序后固定） | 确定性是可测试的前提 |
| 是否可以跨上下文 | 可以，但**只允许订阅方是 Application 层的编排端口**（如 `IOrderSettlementHandler` 由 `OrderingService` 实现），Domain 之间零引用 | 保住 §2.1 上下文边界 |

**事件清单与订阅关系（全部为进程内，无外部投递）**

| 事件 | 发布方 | 订阅方 | 订阅方动作 |
|---|---|---|---|
| `PaymentSucceeded` | Payments | Ordering | `Order.MarkPaid()` + 写 `OrderPaid` 事件 + Outbox（确认邮件） |
| `PaymentFailed` | Payments | Ordering | 记 `PaymentAttempt` 失败原因，订单保持 PendingPayment |
| `PaymentRefunded` | Payments | Ordering | `Order.ApplyRefundSucceeded()` + Outbox（退款邮件） |
| `OrderPlaced` | Ordering | Content / Settings | 无（仅审计）；Outbox（下单邮件）由 Application 直接写，不走事件 |
| `OrderCancelled` | Ordering | Inventory | `StockItem.Release(holdId)` |
| `StockDepleted` | Inventory | Catalog | bump `catalog` 缓存版本（商品从"有货"变"售罄"） |
| `ThemeActivated` / `ThemeConfigChanged` | Content | — | bump `content` 缓存版本 |
| `SetupCompleted` | Settings | Api（运行时） | 熔断 `/api/setup/*` 写路由（进程内 flag） |

### 1.5 事务边界

**硬约束：事务只允许出现在 Application 层的 `IUnitOfWork.ExecuteAsync` 内部，且一个用例恰好一个事务。**

```csharp
// Infrastructure/Persistence/UnitOfWork.cs（关键骨架，18 行）
public async Task<T> ExecuteAsync<T>(Func<CancellationToken, Task<T>> work, CancellationToken ct)
{
    if (_ambient is not null) return await work(ct);          // 嵌套：复用外层，内层不提交
    await using var tx = await _db.Database.BeginTransactionAsync(ct);
    _ambient = tx;
    try
    {
        var result = await work(ct);
        await SaveAndDispatchAsync(ct);                       // SaveChanges → 派发事件 → SaveChanges
        await tx.CommitAsync(ct);
        return result;
    }
    catch { await tx.RollbackAsync(ct); throw; }
    finally { _ambient = null; }
}
```

| 场景 | 是否开事务 | 说明 |
|---|---|---|
| 命令型用例（Create/Update/StateChange） | 是，`ExecuteAsync` | 唯一形态 |
| 查询型用例 | 否 | `AsNoTracking` + 投影，绝不 `SaveChanges` |
| 跨上下文用例（下单） | 是，**一个** | Order + Stock + Payment 同 DbContext 同事务（架构 §2.4 一致性策略） |
| 后台任务单条处理 | 是，**每条一个事务** | 批量扫描在事务外，逐条 `ExecuteAsync`；一条失败不影响其它条 |
| 安装向导 A8 应用阶段 | 是，**一个长事务** | 架构 §5.3.3 阶段 B；失败 = 整库重置（§2.7） |
| 外部副作用 | 否 | 写 Outbox 行（在事务内），由 Job 在事务外执行 |

`IUnitOfWork` 只暴露三个方法（`ExecuteAsync` / `ExecuteAsync<T>` / `SaveChangesAsync`），**不暴露 `DbContext`**——Application 层根本拿不到 DbContext 类型，从编译期堵住"Application 直接写 SQL"。

### 2.1 Catalog 上下文

#### 聚合根 `Product`（**重点**）

**不变量**

**事件**：`ProductCreated` `ProductPublished` `ProductArchived` `VariantPriceChanged` `VariantsRegenerated`

**关键设计点**

1. **变体矩阵的"归属"**：变体是产品内实体，所以轴组合唯一性（INV-P05）能在**内存里**校验完再落库——DB 约束只能兜底，不能作为唯一防线（否则错误信息是"唯一索引冲突"，用户体验是"保存失败"）。
2. **价格/库存/图的归属**：价格与图在 `ProductVariant` 上（`PriceAmountMinor` / `PrimaryImageMediaKey`，为空则继承商品级默认）；**库存在 `Inventory.StockItem`，Product 完全不含库存字段**（架构 §2.4）。前台"是否有货/最多可买 N 件"由 Application 用 `IStockQuery.GetAvailabilityAsync(variantIds)` **一次批量查**后合并，绝不 N+1。
3. **启停变体不影响历史订单**：`OrderLine` 存的是快照（`SkuSnapshot`、`NameSnapshot`、`UnitPriceSnapshot`），订单详情渲染完全不回查 Product。这是 US-E2-06 "变体状态不影响历史订单展示" 的落地方式。
4. **变体矩阵重算不删有销量的变体**：`VariantMatrixPlan` 分四桶 `ToAdd / ToKeep / ToDisable / ToDelete`，`ToDelete` 仅包含"无销量且不在新组合中"的变体。

#### 聚合根 `Category`

不变量：树无环（INV-C01）、深度 ≤ 5（INV-C02，需求要求 ≥3 级支持）、同父下 `SortOrder` 唯一（INV-C03）、per-locale slug 全局唯一（INV-C04，DB 唯一索引 + 领域预检）、**有子分类或已挂商品时不可删除**（INV-C05，返回计数供提示）、父分类删除不影响子分类的 `Path` 一致性（`Path` 为物化路径，随移动重算，INV-C06）、继承的属性集只能追加不可移除（只能 `IsHidden=true`，INV-C07）。

方法：`Create` `Rename` `Move(parentId, sortOrder)` `AttachAttributeSet(setId)` `HideInheritedAttribute(attrId)` `EnsureDeletable(childCount, productCount)` `Delete`。
事件：`CategoryTreeChanged` `CategorySlugChanged`（触发 SlugHistory 写入 → 301）。

#### 聚合根 `AttributeDefinition` / `AttributeSet`

`AttributeDefinition` 不变量：`Code` 全局唯一且符合 `^[a-z][a-zA-Z0-9]{1,39}$`（INV-A01）；多语名默认语言必填（INV-A02）；**已被商品使用时 `DataType` 与 `Scope` 不可变更**（INV-A03，US-E2-02 的硬要求，`ChangeDataType()` 内部检查 `UsageCount`，由 Application 传入）；`Scope=Variant` 时只允许 `Enum` 类型（INV-A04，否则矩阵无法枚举）；`Enum` 必须 ≥1 个 option（INV-A05）。

`AttributeSet` 不变量：`Code` 唯一（INV-AS01）、成员属性 `Code` 不重复（INV-AS02）、`Scope=Variant` 的成员数 ≤ 3（INV-AS03，与 INV-P04 呼应但在定义层就拦住）。

### 2.2 Inventory 上下文

#### 聚合根 `StockItem`（**重点**）

**构成**：`StockMovement`（实体，只追加）、`StockHold`（实体，临时预占凭据）

**核心三元组语义（与 `docs/02-数据模型.md` 对齐，`Available` 不落库）**

| 字段 | 含义 | 谁改 | 何时改 |
|---|---|---|---|
| `OnHand` | 物理在库（管理员认知的"库存"） | 管理员调整、`Commit`、退款回补 | 补货/盘亏 /**支付成功减**/退款回补加 |
| `Reserved` | 已预占但未支付 | `Reserve` / `Release` / `Commit` | 下单加 / 取消减 / 支付成功减 |
| `Sold` | 已支付净售出（报表与退款回补对账用） | `Commit` / `RestockFromRefund` | 支付成功加 / 退款回补减 |
| `Available`（**计算属性，不落库**） | **`OnHand − Reserved`** | — | 前台可售、加购上限、`maxOrderQuantity` |

**为什么 `Available = OnHand − Reserved` 而不是 `OnHand − Reserved − Sold`**：`Commit` 同时做 `OnHand −= q, Reserved −= q, Sold += q`，两种写法的数值结果完全相同，但前者只依赖两个字段，因此 DB 可以写成 `CHECK (Reserved <= OnHand)` —— 这是一个**单表内可判定的约束**，成为不超卖的**最后防线**。`Sold` 仅用于报表与"退款回补是否已做过"的对账，不参与可售计算。

**不变量**

| 编号 | 不变量 | 说明 |
|---|---|---|
| INV-S01 | `OnHand ≥ 0 && Reserved ≥ 0 && Sold ≥ 0` | 任一分量不得为负（DB `CHECK` 兜底） |
| INV-S02 | **`OnHand ≥ Reserved`**（即 `Available ≥ 0`） | **"不超卖"的形式化表达**。领域层 `Reserve` 先校验并抛 `INSUFFICIENT_STOCK{variantId,sku,requested,available}`；DB `CHECK (Reserved <= OnHand)` 是并发/重试绕过领域校验时的最后防线（AC-08 要求"库内永不出现负数"） |
| INV-S03 | 每次变更写一条 `StockMovement`（`OccurredAt, OperatorKind, OperatorId, Delta(OnHand/Reserved/Sold 三元组), Reason, RelatedOrderNumber?, RelatedHoldId?`），**不可改不可删** | US-E2-08 流水要求；超时释放也必须留痕（AC-08：回补要能对账） |
| INV-S04 | `Commit(holdId)` / `Release(holdId)` **按 holdId 幂等**：hold 状态已非 `Active` 时返回 `AlreadyApplied`，不产生任何变更 | AC-06 "库存只扣一次"的落点 |
| INV-S05 | `Reserve` 必须创建 `StockHold{HoldId, Qty, ExpiresAt, Status=Active}`；同一 `orderLineId` 只能有一个 Active hold | 超时释放的扫描对象（索引 `(Status, ExpiresAt)`） |
| INV-S06 | 并发控制：**`long Version` 乐观锁**（`IsConcurrencyToken`），冲突时 Application 重试 **1 次**，再冲突返回 `STOCK_CHANGED_RETRY` | 统一 `Version` 而非 `rowversion`/`xmin`：后者是 provider 专有，切 SQLite 失效 |
| INV-S07 | `AdjustOnHand(newOnHand)` 不得使 `Reserved > OnHand` | 防"管理员把 100 改成 0 导致已售订单的账不平" |

**公开方法**

```csharp
StockItem CreateStockItem(VariantId id, int initialOnHand, IClock clock);
StockHold Reserve(int qty, OrderLineRef line, DateTimeOffset expiresAt, IClock clock);   // 失败抛 INSUFFICIENT_STOCK
HoldOutcome Commit(HoldId holdId, IClock clock);     // OnHand−q, Reserved−q, Sold+q（Available 不变）
HoldOutcome Release(HoldId holdId, string reason, IClock clock); // Reserved−q（Available 回升）
void AdjustOnHand(int newOnHand, string reason, AdminId by, IClock clock);
void RestockFromRefund(int qty, string orderNumber, RefundId refundId, IClock clock); // OnHand+q, Sold−q
void ExpireHold(HoldId holdId, IClock clock);         // 超时释放 = Release(reason="hold_expired")
```

**事件**：`StockReserved` `StockCommitted` `StockReleased` `StockAdjusted` `StockDepleted`（Available 由 >0 变 0 时发布，供 Catalog 失效缓存）

### 2.3 Cart 上下文

聚合根 `Cart`：`CartLine`（`VariantId, Qty, AddedUnitPrice(Money), AddedAt`）。

不变量：同一变体合并为一行（INV-CT01）；行数量 ∈ [1, 99]（INV-CT02）；`Currency` 必须等于店铺币种（INV-CT03）；`Status ∈ {Active, CheckedOut, Merged, Abandoned}`，仅 `Active` 可修改（INV-CT04）；登录合并时按 `VariantId` 累加并裁剪到 `min(99, Available)`（INV-CT05，不静默丢行，超出部分写 `CartMergeNotice` 供前端提示）。

方法：`AddLine` `ChangeQty` `RemoveLine` `MergeInto` `MarkCheckedOut` `Revalidate(prices, availability)`。
事件：`CartLineAdded` `CartCheckedOut` `CartMerged`。

> **不缓存、不预占**：Cart 行**不下单就不占库存**。`Revalidate` 在进入结算页与提交订单时各执行一次（US-E5-07 的"停留 10 分钟后提交"）。
> 匿名身份：Cookie `os_cart={cartId}:{hmac}`（HttpOnly，SameSite=Lax，180 天）。HMAC 防止伪造 cartId 遍历他人购物车。

### 2.4 Ordering 上下文

#### 聚合根 `Order`（**重点**）

**构成**：`OrderLine`（实体，快照）、`OrderStatusHistory`（实体，只追加）、`Address`（VO）、`ReturnRequest`（**独立聚合根**，不放进 Order）

**金额快照结构（MVP 折扣位恒 0，二期加券不动结构）**

```
Subtotal      : Money   // Σ line.UnitPrice × line.Qty，精确无舍入
Discount      : Money   // MVP = 0
ShippingTotal : Money   // Pricing 计算
TaxTotal      : Money   // Pricing 按行计算后求和
Total         : Money   // Subtotal − Discount + ShippingTotal + TaxTotal（价外税）
                        // 或 Subtotal − Discount + ShippingTotal（价内税）
RefundedTotal : Money   // 累计已成功退款
Currency      : string  // 落库快照，不随后续设置变更
```

**不变量**

| 编号 | 不变量 |
|---|---|
| INV-O01 | 状态转换必须命中 §4.1 白名单，否则抛 `ORDER_INVALID_TRANSITION(current, action)` |
| INV-O02 | 金额快照在 `Place()` 之后**不可变**（除 `RefundedTotal`、`PaidAt`、`ShippedAt` 等时间戳） |
| INV-O03 | 恒等式：`Total == Subtotal − Discount + ShippingTotal + TaxTotal`（价外）或 `Total == Subtotal − Discount + ShippingTotal`（价内，且 `TaxTotal ≤ Subtotal − Discount`）；构造时与每次 `BeginRefund` 前校验 |
| INV-O04 | `RefundedTotal + 本次退款额 ≤ Total` |
| INV-O05 | 单行累计退款数量 ≤ 该行 `Qty`；单行累计退款额 ≤ 该行 `LinePaid = UnitPrice×Qty − 已退该行合计` |
| INV-O06 | `OrderNumber` 全局唯一、生成后不可改，格式 `{Prefix}-{yyMMdd}-{6 位 Crockford Base32 随机}`（对齐 Q8 建议，非顺序号防枚举） |
| INV-O07 | 每条 `OrderStatusHistory` 必须含 `From, To, Actor(Kind+Id), Reason`；**人工变更（Admin）时 `Reason` 必填** |
| INV-O08 | `Cancelled` / `Refunded` 终态后不可 `Ship()` |
| INV-O09 | `Place()` 时 `OrderLine` 必须携带 `SkuSnapshot / NameSnapshot(locale, 下单语言) / UnitPriceSnapshot / Qty`，且每个变体都有 `HoldId` |
| INV-O10 | 下单必须记录 `Locale`（邮件与状态文案按此语言，US-E6-06） |
| INV-O11 | **投影列同事务维护**（不允许异步补算）：`PaidMinor`（支付成功时写，等于 `Total`）、`RefundedMinor`（每次退款成功累加，恒等于 `Σ Refund.Succeeded.AmountMinor`）。每日对账 Job 校验 `RefundedMinor == Σ refunds` 与 `PaidMinor == Total IF Paid`，不一致即告警 | 报表与运营列表不能靠 join 聚合实时算，但也不能容忍投影漂移 |
| INV-O12 | `Version`（`long`，`IsConcurrencyToken`）由 SaveChanges 拦截器自增；两条并发支付回调只有一个能提交 | 与全库统一令牌方案一致 |

**公开方法**

```csharp
static Order Place(OrderDraft draft, PricingResult pricing, IReadOnlyList<OrderLineDraft> lines, IClock clock);
void MarkPaid(PaymentId paymentId, Money paidAmount, DateTimeOffset paidAt);   // 幂等：已 Paid 直接返回
void Cancel(CancelReason reason, Actor actor, IClock clock);                    // 仅 PendingPayment 允许
void Ship(CarrierCode carrier, string trackingNo, Actor actor, IClock clock);
void MarkCompleted(Actor actor, IClock clock);
void BeginRefund(RefundId id, IReadOnlyList<RefundLineRequest> lines, Actor actor, IClock clock);
void ApplyRefundSucceeded(RefundId id, Money amount, IClock clock);            // 重算 Status 投影
void ApplyRefundFailed(RefundId id, string failureCategory, IClock clock);
void ApplyRefundPending(RefundId id, IClock clock);
```

**事件**：`OrderPlaced` `OrderPaid` `OrderShipped` `OrderCompleted` `OrderCancelled` `OrderRefundPending` `OrderPartiallyRefunded` `OrderRefunded` `OrderRefundFailed`

**关键设计点**

1. **取消与退款的关系**（US-E7-02 的精确落地）：`PendingPayment` 取消 = `Cancel()` → `Cancelled` + 释放 hold（无资金动作）；`Paid`/`Shipped` 取消**不是** `Cancel()`，而是管理员发起退款 → `BeginRefund()` → `RefundPending` → 成功后才可能进 `Refunded`。**退款失败时订单必须回到原位（`Paid`/`Shipped`），不是 `RefundFailed` 终态**——`RefundFailed` 是"当前有一次退款失败"的投影，见 §4.1 的禁止转换说明。
2. **`RefundedTotal` 与 `Status` 的关系**：`Status` 里的 `PartiallyRefunded` / `Refunded` 由 `ApplyRefundSucceeded` 内部按 `RefundedTotal == Total` 重算，**绝不接受外部传入目标状态**。
3. **`ReturnRequest` 是独立聚合根**：退货申请不涉及资金，与 Order 生命周期解耦；审批通过后由 Application 调 `RefundService`（跨上下文），失败不回滚退货申请（它已审批，重试退款即可）。

聚合根 `ReturnRequest`：`Create(orderId, lines, reason)` `Approve(adminId, note)` `Reject(adminId, reason)`；不变量：行数量 ≤ 订单行数量、同一订单行不能有两个 `Pending` 申请、`Rejected` 终态。

### 2.5 Payments 上下文

聚合根 `Payment`：`PaymentAttempt`（实体，每次调通道留痕）。

不变量：`Amount` 必须等于 Order 应付额（下单时快照，INV-PM01）；`(Provider, ProviderTransactionId)` 全局唯一且**非空时**才参与唯一约束（INV-PM02，AC-06）；**同一订单最多一条 `Succeeded` 支付**（INV-PM05，DB 唯一索引 `(OrderId) WHERE Status=Succeeded` —— 一单两付是资金事故，靠索引而非代码拦住）；`Status=Succeeded` 后 `Amount` 不可改（INV-PM03）；`Succeeded` 是终态，退款在 `Refund` 聚合表达（INV-PM04）。

方法：`Create(orderId, orderNumber, amount, provider)` `AttachIntent(providerIntentId, clientSecret)` `MarkSucceeded(transactionId, paidAt)`（幂等）`MarkFailed(code)` `MarkCanceled()`。

事件：`PaymentSucceeded` `PaymentFailed` `PaymentIntentCreated`。

聚合根 `Refund`：`RefundLine`（订单行 + 数量 + 金额）。

| 字段 | 说明 |
|---|---|
| `Status ∈ {Pending, Processing, AwaitingManual, Succeeded, Failed}` | `AwaitingManual` = 等运营线下打款（仅 `Provider=manual`） |
| `Provider` | 通道标识；**线下退款固定为 `manual`** |
| `ProviderRefundId` | 线上=通道退款号；**线下=线下凭证号**（银行流水/转账单号）；唯一索引 `(Provider, ProviderRefundId)`（过滤 NULL） |
| `ManualRefundDate` / `ManualOperatorAdminId` / `MarkedSucceededAt` | 线下路径必填（`CHECK`：`Provider='manual' → ManualRefundDate NOT NULL`；`Status=Succeeded → MarkedSucceededAt NOT NULL`） |
| `ReturnRequestId` | 可空；**唯一索引**保证"一次退货申请最多一张退款单" |
| ~~`IdempotencyKey`~~ | **删除该列**。幂等键由主键派生：`refund:{Refund.Id}`（见 §4.2.4）。存一列独立 IdempotencyKey 的最大风险是有人真去填订单 ID |

不变量：`Amount ≤ Order.Total − Order.RefundedTotal`（INV-RF01）；`RefundLine.Amount ≤ 该行 LinePaid`（INV-RF02，AC-19「超出其行实付金额时保存被拒」）；`Status` 转换见 §4.2；`Succeeded` 终态不可重试（INV-RF04）；**线上退款只有通道确认才能进 `Succeeded`**（INV-RF05）；**线下退款必须填 `ManualRefundDate` + `ProviderRefundId`（凭证号）才能进 `Succeeded`**（INV-RF06，US-E7-07 / AC-19）；**凭证号允许修改，但每次修改必须写审计（原值→新值 + 操作人 + 时间）**（INV-RF07，否则对账时无法解释同一笔退款换过凭证号）。

方法：`Create(orderId, paymentId, lines, amount, reason, operatorId, provider)` `MarkProcessing(providerRefundId)` `MarkAwaitingManual()` `MarkSucceeded(providerRefundId, markedAt)` `CorrectVoucher(newVoucherNo, adminId, clock)` `MarkFailed(code, category)` `CanRetry()`

**退款路径由通道能力位决定（AC-19 / US-E7-07）**

| `Capabilities` | Provider | 首个状态 | 通道调用 | 部分退款入口 |
|---|---|---|---|---|
| 含 `Refund` + `PartialRefund` | 通道标识（如 `stripe`） | `Pending` | 有（经 Outbox，§4.2.3） | 可用 |
| 含 `Refund`，无 `PartialRefund` | 通道标识 | `Pending` | 有 | **禁用并说明原因**（不是隐藏，US-E7-07） |
| **无 `Refund`** | **`manual`** | **`AwaitingManual`** | **零调用**（AC-19 逐字断言） | 按 `PartialRefund` 决定 |

> **能力位是静态声明，不是运行时探测**：`GatewayCapabilities`（`[Flags] Webhook | Query | Refund | PartialRefund`）在适配器里写死，`FakeGateway` 的 `SupportsRefund` 做成**构造参数**（供 AC-19 两条路径的测试编排）。运行时探测会让"退款"带上网络不确定性，而且探测失败到底是"没能力"还是"临时故障"永远说不清。
> **边界**：只有在"通道**不具备**该能力"时才走线下；**具备能力但调用失败时必须重试，不允许人工降级**（否则"退款失败"就成了绕开通道的通用后门，通道对账永久不平）。退出机制是显式改能力声明（配置变更 + 审计，留下人和理由）—— 这条提示语要写在 admin 的退款失败界面上，否则运营第一反应是找"人工完成"按钮。

事件：`RefundRequested` `RefundSucceeded` `RefundFailed` `RefundAwaitingManual`。

实体 `WebhookEvent`（幂等凭据）：`{Provider, **DedupeKey**, ReceivedAt, SignatureValid, ProcessingResult}`，唯一键 **`(Provider, DedupeKey)`**。`DedupeKey` 的取值规则见 §4.3.1（**不用签名 hash**、不用业务组合键）。

实体 `PaymentGatewayConfig`（单行）：`Provider, IsEnabled, SecretConfigEncrypted, CapabilitiesJson, LastTestSucceededAt?, LastTestFailedAt?, LastTestFailureCode?, LastTestMerchantId?, ConsecutiveProbeFailures`。

实体 `PaymentChannelHealth`（单行）：`LastVerifiedAt?, LastVerifyResult ∈ {Ok, Failed}, LastProbeFailedAt?, ConsecutiveProbeFailures` —— 供"连续 2 次探测失败才翻 false"的防抖计数（§2.7 INV-SS06）。

### 2.6 Customers 上下文

`Customer`：`Email`（规范化小写，全局唯一）、`PasswordHash`（`PasswordHasher<Customer>` 产出的不透明字符串 + 参数版本）、`Name`、`DefaultAddress`、`Status`、`LastLoginAt`。不变量：密码策略（长度 12–128、非纯数字、非 Top-1000 弱口令）（INV-CU01）；邮箱唯一（INV-CU02）；删除账户 = 匿名化 `Email/Pii` 但保留 `Orders` 归属为 `AnonymousCustomerId`（INV-CU03，架构 §6 数据合规）。

`AdminUser`：`Email`（唯一）、`PasswordHash`、`Role ∈ {Admin, Staff}`、`FailedAttempts`、`LockedUntil`、`SecurityStamp`、`Status`。不变量：连续 5 次失败锁 15 分钟（INV-AD01，`LockedUntil` 由聚合自己算）；改密/停用必须轮换 `SecurityStamp` → 所有 Session 失效（INV-AD02）；**系统内至少保留 1 个 Admin**（INV-AD03）。

`SessionRecord`（实体，由 Auth 服务直接操作，不是聚合根）：见 §6.2。

事件：`CustomerRegistered` `AdminUserSuspended` `AdminPasswordChanged`。

### 2.7 Settings 上下文

#### 聚合根 `SetupState`（**重点**）

单行表（`Id` 固定为 1，`CHECK(Id = 1)`）。字段：`Status ∈ {Draft, Applying, Failed, Completed, Resetting}`、`CurrentStep`、`DraftPayload`（JSON，8 步草稿）、`SelectedTemplateKey`、`AttemptCount`、`AppliedTemplateKey`、`CompletedAt`、`LastErrorCode`、`LastError`、`Version`。

**状态机**

| 当前 | 动作 | 目标 | 谁触发 | 前置/副作用 |
|---|---|---|---|---|
| Draft | UpdateDraft | Draft | 商家（每步保存） | 无事务，逐次 upsert；改模板 = 覆盖 `SelectedTemplateKey` + 清空模板相关草稿 |
| Draft | BeginApply | Applying | 商家点"开始初始化" | 前置：8 步全通过（`IsReadyToApply`）+ **安装令牌校验通过**；`AttemptCount+1` |
| Applying | Complete | Completed | 系统（A8 事务提交后） | 写 `AppliedTemplateKey` + `CompletedAt`；发布 `SetupCompleted`；**安装令牌立即作废** |
| Applying | Fail | Failed | 系统（事务回滚/异常） | 写 `LastErrorCode` + `LastError`；**不自动回退到 Draft** |
| Failed | ResetToDraft | Draft | 运维（CLI `reset-setup`，二次确认） | 见下方"两档重置" |
| Completed | BeginReset（仅逃生口开启时） | **Resetting** | 运维 | 期间所有写端点 **503 + `Retry-After: 30`** |
| Resetting | ResetDone | Draft | 系统 | 清库 + 重跑迁移 + 令牌重新生成 |
| Completed / Resetting | — | — | — | 终态语义：仅 `OPENSTORE_ALLOW_SETUP_RESET=true` 才可能离开 |
| Applying（进程崩溃遗留） | Reap | Failed | 启动自检 | 条件：`Status=Applying && Version 未变 && 无活动连接` → 标记 Failed，提示"上次安装未完成" |

**不变量**

| 编号 | 不变量 |
|---|---|
| INV-SU01 | `Status=Completed` 时 `AppliedTemplateKey` 与 `CompletedAt` 必填 |
| INV-SU02 | **只有 `Draft` 可以 `BeginApply`**；`Failed` 必须先进 `ResetToDraft`；`Applying` 期间重复 `BeginApply` → **409 `SetupInProgress`** |
| INV-SU03 | `Draft` 阶段允许反复改模板（需求 §2.1「A8 之前可反复改选」），改选即覆盖 `DraftPayload.template` |
| INV-SU04 | `BeginApply` 前必须 8 步齐备（environment / storeInfo / locale / currency / taxShipping / payment / admin / ready），失败返回缺失步骤列表 |
| INV-SU05 | 单一真源：任何地方判断"是否已初始化"只读 `SetupState.Status`，不读文件/配置 |
| INV-SU06 | **`Completed` 后所有安装写端点返回 409 `SetupAlreadyCompleted`**（不是 404，见 §13 冲突 1）；`Resetting` 期间返回 503 + `Retry-After: 30` |

**三层锁定 + 三档状态码（不是一档）**

| 层 | 机制 |
|---|---|
| 数据层 | `Status` 单一真源 |
| 应用层 | `SetupLockMiddleware` 首行判定，按下表返回 |
| 端点层 | `Program.cs` 决定是否注册 `/api/setup/*`（**页面**层收敛攻击面由前端返回 404；**接口**层必须给语义化状态码，否则运维误诊） |

| 阶段 | 读端点 | 写端点 | 语义 |
|---|---|---|---|
| `Draft` / `Failed` | 200 | 200（需令牌） | 正常 |
| `Applying`（含崩溃残留） | 200 | **409 `SetupInProgress`** | 别插队 |
| `Completed`（未开逃生口） | 200 | **409 `SetupAlreadyCompleted`** | 已经装完了，别再调 |
| `Completed` + 逃生口开 + 重置中（`Resetting`） | 200（`status=resetting`） | **503 + `Retry-After: 30`** | 正在重置，暂时不可用 |

> **409 = 别插队；409 `SetupAlreadyCompleted` = 已完工；503 = 正在重置。** 三者的区分意义在于运维读日志时的判断：看到 409 知道"商家已经装完"（放弃排障），看到 503 知道"等一下再试"。把 `Completed` 做成 404 会让运维以为"部署漏了路由"。

**`Failed → Draft` 的重置分两档（对齐架构 §5.3.3「失败即整库重置」但避免过度破坏）**

| 情形 | 重置动作 | 判定依据 |
|---|---|---|
| 应用阶段事务已干净回滚 | **轻量重置**：只把 `SetupState` 归零（`Status=Draft`、`AttemptCount` 保留、清 `LastError*`） | `LastErrorCode` 由本进程写入且事务确认回滚 |
| 进程在 `Applying` 中崩溃（无法证明无残留） | **整库重置**：删 SQLite 文件（或 `DROP SCHEMA public CASCADE`）→ 重跑迁移 → `Draft` | 启动自检（§7 #10） |


理由：首次部署时库内不存在任何真实业务数据，两种重置都不会造成用户数据损失；而"能证明事务已回滚"时做整库重置属于无谓的重建成本（尤其 PG 上 `DROP SCHEMA` 会带走迁移历史）。**两者对用户的观感一致：向导回到第 1 步，之前填的表单仍在 `DraftPayload` 中。**

#### 聚合根 `StoreSettings`

单行（`Id=1`）。字段：`StoreName(LocalizedText)`、`Country`、`TimeZone`、`SupportEmail`、**`PublicSiteUrl`（`string(300)`，必填、绝对 URL、无尾斜杠）**、`Currency`（3 位 ISO）、`WeightUnit`、`DefaultLocale`、`EnabledLocales[]`、`OrderNumberPrefix`、`SessionIdleMinutes`(120)、`GuestCheckoutEnabled`、`SmtpSettings(encrypted)`、`BackupEnabled`、**`TaxMode ∈ {None, SingleRate}` + `SingleTaxRateBasisPoints`**、**`CanSell(bool)` + `CanSellReason`**（投影列，见下）、`Version`。

**税率：收敛到"统一税率 + 分类级覆盖 + 含税开关"（PM v1.6，明确不做多辖区）**

| 概念 | 落点 |
|---|---|
| 全局是否含税 | `StoreSettings.TaxInclusive(bool)` |
| 统一税率 | `StoreSettings.SingleTaxRateBasisPoints`（0 = 不征税，即 `TaxMode=None`） |
| 分类级覆盖 | 窄表 `CategoryTaxRate(CategoryId PK, RateBasisPoints)`：**有行 = 覆盖，无行 = 用统一税率**（一张表表达两种语义，不需要再做 `TaxRule` 的 `CountryCode/RegionCode`） |

**`canSell`：派生 + 落库 + 无写入口（主理人 Q8 / PM ①④ / AC-17）**

```
CanSell = PaymentGatewayConfig.IsEnabled
       && PaymentGatewayConfig.SecretConfigEncrypted IS NOT NULL
       && PaymentGatewayConfig.LastTestSucceeded == true      // 最近一次结果（不是"曾经成功过"）
CanSellReason ∈ { ok, noCredentials, testFailed, channelDisabled }
```

| 规则 | 说明 |
|---|---|
| INV-SS05 | **`CanSell`/`CanSellReason` 是只读投影列**：无 setter、无 API 写入口、管理端**不出现**"开启/关闭支付"的开关（AC-17 ⑤）。它们可以被"重算流程"写，但不能被任何 endpoint 写 |
| INV-SS06 | **重算时机（三处，缺一不可）**：① 支付配置变更（存/清凭据、切通道、启停）→ **同一事务内**重算 ② 连接测试成功/失败 → 同事务重算 ③ **定时健康探测** → 见下。凭据失效自动回 false，不需要人工干预 |
| INV-SS07 | 写凭据/启停通道时**必须**清空 `LastTestSucceeded` → `canSell` 立即变 false，直到重测通过（防"改了凭据但沿用旧结论"） |
| INV-SS08 | `CanSell=false` 时 `CheckoutService.ConfirmAsync` 与重新支付（`/pay`、`/pay-url`）的**第一条语句**抛 `CannotSellException`（503 `CANNOT_SELL` + `details.reason`），在任何读库存/建单/建支付意图之前（AC-17②⑦） |
| INV-SS10 | **`CanSellReason` 只允许是 4 个枚举值**：绝不返回凭据内容、通道原始报文、异常栈（PM 明确约束：诊断信息最容易被顺手做成把 `Exception.Message` 抖给前台） |
| INV-SS11 | `CanSell=false` 期间**不改任何既有订单/购物车数据**，只拦截"新的可售动作"（已下单的支付回调仍要正常入账） |

**定时健康探测（Must，但必须防抖）**

| 项 | 决定 | 理由 |
|---|---|---|
| 载体 | **并入 §7 #2 的对账 `BackgroundService`**，按 `Payment:HealthProbeIntervalHours` 节流触发。**不新开定时器** | 少一个定时器就少一处运维面（PM + 主理人一致） |
| 探测动作 | **只读、无副作用**（查余额/查账户状态）。**绝不能是"创建一笔测试支付"** | 有副作用的探测会污染对账与账单 |
| 防抖 | **连续 2 次探测失败**才置 `CanSell=false`；**单次失败只写 `LastProbeFailedAt` + 日志**，不翻转 | 通道抖动/网络瞬断/限流都会造成单次失败；一次失败就停业比晚发现更糟 |
| 恢复 | **任意一次探测成功立即恢复 `CanSell=true`**（不等连续 2 次） | 恢复要比关闭更灵敏 —— 不能让商家等两天才能重新收钱 |
| 失败重试 | **不重试**（下一周期再说） | 通道故障时重试只会加剧问题 |
| 只读探测端点缺失时 | 退化为"用真实调用的认证类错误反推"（`GatewayAuthException`），并记 `canSell.probe.unavailable` 告警 | 有些通道没有只读端点；这时至少还有第二信号 |

> **不对称设计（谨慎关闭、立即恢复）的理由**：错误的关闭 = 损失生意；错误的开启 = 损失一笔钱；但**持续关闭两天会失去商家信任**。三者取衡，防抖 + 立即恢复是最优。

**`CanSell` 一致性校验（回应数据模型"用 EXISTS 不落列"的意见）**：读路径用落库列（省 TTFB 且保证"首页说能买、结算也说能买"），**每日对账 Job 用 EXISTS 重算一次并与落库值比对**，不一致 → 写 `canSell.drift` 告警日志 + 以 EXISTS 结果为准回写。这样既拿到落库的读性能，又不失"派生值永远是事实的函数"这个性质。

不变量：`Currency` 在存在任何订单后不可变更（INV-SS01）；`DefaultLocale ∈ EnabledLocales` 且默认语言不可停用（INV-SS02，US-E3-01）；`TaxInclusive`/税率变更不影响历史订单（INV-SS03，快照已定格）；凭据字段以 `IDataProtector` 加密后落库（INV-SS04，AC-16 "导出不含凭据明文"）；**`PublicSiteUrl` 是 canonical / og:url / hreflang / sitemap / 邮件链接 / 支付回跳的<u>唯一</u>来源**（INV-SS09，AC-10：**禁止读请求 `Host` 头**，Host 注入可把整站索引权重送人）。

`ShippingRule`（`Mode ∈ {Flat, FreeOverThreshold, WeightBands}`、`FlatAmount`、`ThresholdAmount`、`Bands[]`）——作为 `StoreSettings` 的子实体（低并发、单店主）

### 2.8 Content 上下文

#### 聚合根 `ThemeInstance`（**重点**）

**关键认知：覆盖值必须按主题分区存储**，否则 US-E4-02「切回 A 时恢复 A 的编辑值」做不到。

```
ThemeInstance {                                     // 单行
  ActiveThemeId : string
  Version       : long
  // 覆盖值按主题分区存储（US-E4-02「切回 A 恢复 A 的编辑值」的前提）
  Tokens  : IReadOnlyCollection<ThemeTokenOverride> // 行表：(ThemeInstanceId, ThemeId, TokenKey, Value, UpdatedByAdminId)
  Blocks  : IReadOnlyCollection<ThemeBlockOverride> // 每主题一整套 block 配置
  Texts   : IReadOnlyCollection<ThemeTextOverride>  // (ThemeId, Locale, Key, Value)
}
```

**为什么 token 用行表而不是 JSON 列**（三件 JSON 列做不好的事）：① 单项重置 = `DELETE` 一行；② 按页签重置 = `DELETE WHERE TokenKey LIKE 'color.%'`；③ "哪些键被改过" = `SELECT TokenKey`（JSON 要读整块再与主题默认做差集，且读-改-写有丢失更新）。
**对外形状不变**：`ThemeInstance.TokenOverrides` 仍是扁平 `TokenMap` 投影（EF `HasMany` 映射，**不是** `HasConversion(JSON)`）；写入口只暴露 `SetToken(key,value)` / `ResetToken(key)` / `ResetTokenGroup(prefix)`。

**token 三层合并：后端不做，只提供原始三层值**

```
主题默认（theme.tokens 的 default）  →  行业模板 preset.themeTokens  →  商家 override（本表）
```

| 决定 | 理由 |
|---|---|
| **合并唯一实现在 storefront**（`packages/theme`，SSR 期执行并注入 CSS 变量） | 后端与前端各写一份合并必然分叉；而 CSS 变量只有 SSR 输出 HTML 时才需要 |
| 后端 `GET /admin/themes/{id}/config` 返回**三层原始值 + schema 原样** | 编辑器需要"当前值 / 默认值 / 是否被覆盖"三者，合并后的结果反而丢失信息 |
| 合并顺序写进本文作为**契约**，前端实现必须与此一致 | 顺序 = `默认 ← preset ← override`，后者胜；键名 `replace('.', '-')` 成 CSS 变量，**不做任何值转换** |
| 后端**保留** `TokenMap.Merge` 纯函数但**仅用于草稿预览的一致性测试与邮件/OG 场景**（不参与 storefront 渲染） | 需要有一处"权威实现"可供测试比对，但不能让它成为第二条渲染路径 |

**theme manifest 字段（架构 v1.3 #4，替换旧字段名）**：`tokensSchema` / `blocksSchema` 取代旧的 `tokens` / `editable` —— 把"默认值"与"可编辑白名单"合并成一个 JSON Schema，避免双文件漂移。`GET /api/admin/themes` 必须**原样透传**这两个字段（`JsonElement`），因为里面带 `default` / `x-control` / `x-group` / `x-a11y` 等注解，**它们是编辑表单渲染的唯一数据源**；映射成强类型 DTO 会静默丢字段，表现为"主题编辑器页面空着但不报错"。

**不变量**

| 编号 | 不变量 |
|---|---|
| INV-TI01 | `ActiveThemeId` 必须是 `IThemeCatalog` 已注册主题，且 `formatVersion` 在宿主支持范围，`supports.storefront` 满足；否则抛 `THEME_INCOMPATIBLE`（拒绝激活，不静默降级） |
| INV-TI02 | `TokenKey` **必须**在主题 `tokensSchema` 声明的白名单内（清单外一律拒绝：`THEME_TOKEN_NOT_EDITABLE`）；值必须通过该键的 schema 校验（颜色格式、字号范围、字体枚举）。校验点落在 `SetToken` |
| INV-TI03 | `Blocks[].blockKey` 必须在 `manifest.blocks` 内（`THEME_BLOCK_UNKNOWN`）；`order` 为连续整数 1..n（`THEME_BLOCK_ORDER_INVALID`）；**至少 1 个 `visible=true`**（全隐藏时保留最小布局并告警，架构 §7 风险 9） |
| INV-TI04 | 切换主题**不清空**任何主题的 override 行（US-E4-02）；切回时恢复 |
| INV-TI05 | 主题升级（`version` 变化）：保留全部 override 行；新增 token 键以默认值生效；新增 block 追加到末尾且默认 `visible=true`；新增文案键用主题默认值（US-E4-05）。校验点落在 `ResetTokenGroup` 之外的一次性迁移 |
| INV-TI06 | 对比度检查（WCAG AA 4.5:1）**只警告不阻断**，返回 `warnings[]` 给前端 |
| INV-TI07 | `ResetTokenGroup(prefix)` 只删匹配前缀的**覆盖行**，不触碰其它键；删除后再读该键 = 回落到 preset/主题默认（**只有后端知道该键在 preset 里存不存在**，所以重置必须由前端调 `DELETE` 而不是"删 map 键再整份提交"） |

方法：`ActivateTheme(themeId, IThemeCatalog)` `SetToken(key, value, adminId)` `ResetToken(key)` `ResetTokenGroup(prefix)` `SetBlocks(list)` `SetTexts(locale, map)` `ValidateAgainst(manifest)`。

事件：`ThemeActivated` `ThemeConfigChanged` `ThemeTokensChanged`。

#### 聚合根 `StaticPage`

不变量：per-locale slug 唯一（INV-SP01）；`Draft` / `Published` 两态（INV-SP02）；富文本入库前必须经 sanitize（白名单标签 `p,b,strong,em,ul,ol,li,a,img,h2,h3,br`，`a[href]` 仅 http/https/相对路径），存储 sanitized 结果而非原文（INV-SP03，AC-15）。

### 2.9 值对象清单与运算规则

#### `Money` —— 全项目唯一金额类型

```csharp
public readonly record struct Money(long MinorUnits, string Currency)   // Currency 必须 3 位大写 ISO
{
    public static Money Zero(string currency);
    public static Money Of(long minorUnits, string currency);           // 唯一构造入口
    public Money Add(Money other);      // 币种不同 → CurrencyMismatchException
    public Money Subtract(Money other); // 结果可为负（内部用于调整），负值不代表合法余额
    public Money Multiply(int quantity);            // 精确，无舍入
    public Money MultiplyBy(decimal rate);          // 舍入：AwayFromZero，到最小单位
    public Money Allocate(IReadOnlyList<int> weights); // 按比例拆分，余数按最大余数法分配，Σ 精确等于原值
    public static Money RoundToMinor(decimal major, string currency, MidpointRounding m = MidpointRounding.AwayFromZero);
}
```

| 规则 | 决定 | 理由 |
|---|---|---|
| 币种不匹配 | **抛 `CurrencyMismatchException`**（`DomainException` 子类，`Code=CURRENCY_MISMATCH`），绝不隐式取左操作数币种 | 隐式取左币种是本项目最隐蔽的资金错误：`tax(CNY) + ship(USD)` 会静默变成 CNY |
| 加法/减法 | 精确，无舍入 | 只有"乘比率"和"按行算税"两个点允许舍入 |
| 乘以整数 | 精确 | 行小计不能舍入，否则 Σ 行 ≠ 总额 |
| 乘以比率 | `AwayFromZero` 到最小单位 | 税务惯例；且 `MidpointRounding.ToEven` 会让相邻两行差额方向随机，客服无法解释 |
| 拆分（折扣/分摊） | 最大余数法，Σ 必须精确等于原值 | 否则"部分退款"会因分摊余数出现 1 分差额，触发 INV-O04 误报 |
| 序列化 | 全局 `JsonConverter<Money>` → **`{"amountMinor": 29900, "currency": "CNY"}`** | 字段名 `amountMinor`（不是 `amount`）由前端 §11.3 定稿；永不返回预格式化字符串（前端用 `Intl` 按 locale 渲染） |
| 反序列化 | 拒绝小数（`amountMinor` 必须是整数）、拒绝未知币种 | 前端传 `299.00` 直接 400，防"元/分"混用 |
| 禁止 | 任何 `decimal` / `double` 跨层传递；任何 `ToString()` 参与业务判断 | `Money.ToString()` 仅用于日志 |

#### 价格结构：（本期）内联三列 + Currency，**不建 1:N 价格表**

| 项 | 定稿 |
|---|---|
| 存储 | `ProductVariant.PriceAmountMinor` / `CompareAtMinor?` / **`Currency`（`string(3)`，ISO 4217，必填不得省略）**；`CHECK(PriceAmountMinor > 0)`、`CHECK(CompareAtMinor IS NULL OR CompareAtMinor >= PriceAmountMinor)` |
| 聚合 | `Variant.Price` 便捷属性读内联列（无需 join），缺失/未初始化时抛 `VariantPriceMissingException` 而非返回 null |
| API DTO | **只暴露单一价格**：`price: {amountMinor, currency}` + `compareAtMinor`（同级扁平）。**绝不做币种数组、绝不包成对象数组** |
| 二期加币种 | **新增 `VariantPrice(VariantId, Currency)` 表 + 回填 + 双写 + 切换读**（纯新增不 ALTER，可在线可回退）—— `docs/02-数据模型.md` §6.4 有 5 步 |
| 为什么不在本期建表 | 单值拆 1:1 子表会让列表页/详情页/下单每次读价都 join，而这是热路径；为一次未来迁移先付永久利息不划算。反过来"改主键"才是破坏性变更（drop PK + 重建表 / 全表复制），所以二期的演进路径必须是"新增表"而不是"改现有表" |
| `Currency` 为什么必须现在就存 | 若等到二期才加，回填只能靠"从当前配置推算"——而配置可能在期间被改过，历史价格就再也无法确定币种。**这列现在不写，等于把二期变成不可做** |

| 值对象 | 结构与规则 |
|---|---|

| `Slug` | per-locale；`^[a-z0-9]+(-[a-z0-9]+)*$`，长度 1–120；生成时从标题 slugify + 去重后缀 `-2`；**变更必须写 `SlugHistory(from, to, entityType, entityId, locale)` 供 301** |

## 3. 领域服务（纯函数优先）

四个服务全部满足：**无 DB、无 IO、无 DI、无 `DateTime.Now`（时间由参数传入）、无 `new` 随机（id/序号由 `IIdGenerator` 参数传入）**。因此 `tests/OpenStore.Domain.Tests` 里可直接 `new Pricing(settingsSnapshot)` 断言全部用例，不需要任何 fixture 或 mock。

### 3.1 `VariantMatrix`（笛卡尔积 + 唯一性 + SKU 推导）

```csharp
public sealed class VariantMatrix
{
    public VariantMatrixPlan Plan(
        string productSkuRoot,
        IReadOnlyList<VariantAxis> axes,                  // 每个 axis: attributeCode + optionCodes[](可 >1)
        Func<IReadOnlyList<AxisOption>, Money> priceFor,   // 定价策略由调用方给（模板/复制默认/统一价）
        IReadOnlyDictionary<string, ExistingVariant> existing, // 组合键 → 现有变体
        int maxVariants = 100);
}
public sealed record VariantAxis(string AttributeCode, IReadOnlyList<AxisOption> Options);
public sealed record AxisOption(string AttributeCode, string OptionCode, int SortOrder);
public sealed record VariantMatrixPlan(
    IReadOnlyList<VariantDraft> ToAdd, IReadOnlyList<VariantDraft> ToKeep,
    IReadOnlyList<VariantId> ToDisable, IReadOnlyList<VariantId> ToDelete,
    IReadOnlyList<string> Warnings);
```

**算法（顺序即步骤）**

1. **轴校验**：`axes.Count ∈ [1,3]` 否则 `AXIS_LIMIT_EXCEEDED`；轴 `AttributeCode` 不重复（`AXIS_DUPLICATE`）；每轴 `Options.Count ≥ 1`（`AXIS_EMPTY`）；轴属性必须 `Scope=Variant`（`AXIS_SCOPE_INVALID`）。
2. **规模预检**：`∏ options.Count ≤ maxVariants(100)`，否则 `VARIANT_LIMIT_EXCEEDED` 并**回传实际组合数**让商家知道要减哪一维。
3. **笛卡尔积生成**：按轴声明顺序做**惰性左折叠** `acc = acc.SelectMany(a => axis.Select(o => [..a, o]))`，保证顺序稳定（轴 1 变化最慢）。稳定顺序是快照测试可用的前提。
4. **组合键**：`key = string.Join("|", options.Select(o => o.OptionCode.ToUpperInvariant()))`（按轴顺序，不排序——轴顺序本身是语义）。重复 → `VARIANT_COMBINATION_DUPLICATE`（理论上笛卡尔积不会重复，除非同一轴内 option 重复，步骤 1 已拦；此处为防御性断言）。
5. **SKU 推导**（**给出完整算法**）：

```
sku = Normalize($"{productSkuRoot}-{axis1Code.Take(4)}{opt1Code.Take(6)}[-{axis2...}[-{axis3...}]]")
```
   - 段内只保留 `[A-Z0-9]`，其余丢弃；`axisCode` 取前 4 字符，`optionCode` 取前 6 字符；
   - 例：`TSHIRT` + `color=WHITE` + `size=M` → `TSHIRT-COLO-WHITE-SIZE-M`；单轴 → `TSHIRT-COLO-BLACK`；
   - 超长截断到 64 字符（从尾部截），截断后若发生碰撞 → 追加 `-{序号}`（`-2`、`-3`，序号按本 plan 内顺序）；
   - **SKU 的唯一性是"纯函数生成 + DB 唯一索引 + 冲突重试"三段式**：纯函数只保证"同输入同输出、plan 内不重复"；全局唯一由 Application 在 `SaveChanges` 捕 `DbUpdateException`（唯一索引）后，把冲突 SKU 加后缀重试，最多 5 次，仍失败返回 `SKU_GENERATION_EXHAUSTED`。**不查库**是刻意的——查库会让这个服务无法单测。
6. **与现有变体合并**：`existing[key]` 存在 → `ToKeep`（保留其 id/价格/库存绑定/启用状态）；不存在 → `ToAdd`（价格来自 `priceFor`，库存由 Inventory 侧懒创建为 0）；`existing` 中有但新组合无 → 有销量则 `ToDisable`，无销量则 `ToDelete`。
7. **警告**：`ToDisable.Count > 0` 时警告"X 个变体有历史销量，已停用而非删除"。

### 3.2 `TemplateCompiler`（JSON 模板 → 聚合集合）

```csharp
public sealed record CompileResult(
    IReadOnlyList<Category> Categories,
    IReadOnlyList<AttributeDefinition> Attributes,
    IReadOnlyList<AttributeSet> AttributeSets,

// 例：("/products/3/variantAxes/1", "AXIS_SCOPE_INVALID", "属性 size 的 scope 必须为 variant", "在 attributes 中把 size 的 scope 改为 variant")
```

**编译过程（8 步，每步失败都返回带 JSON 路径的诊断，不抛裸异常）**

| 步 | 做什么 | 失败诊断 |
|---|---|---|
| 1 | **Schema 校验** `template.json ↔ template.schema.json`（`JsonSchema.Net`，纯内存） | `{jsonPointer}` 来自校验器，直接就是 `/products/0/key` 这种路径 |
| 2 | **属性定义**：`attributes[]` → `AttributeDefinition` + `AttributeOption`；`code` 全局唯一 | `/attributes/2/code` `TEMPLATE_DUPLICATE_CODE` |
| 3 | **属性集**：`attributeSets[]` 引用属性 `code`，必须已存在 | `/attributeSets/0/members/3` `TEMPLATE_UNKNOWN_REF` |
| 4 | **分类树 —— 解鸡生蛋**：两遍法。第一遍按 `categoryTree` 的**深度优先路径**为每个节点生成**确定性 Id**：`Id = DeterministicGuid(templateKey + "|" + nodePath)`（`nodePath` 如 `tops/knitwear`，实现为 SHA-256 前 16 字节转 Guid）；第二遍按同一路径建父子关系与 `Path` 物化路径。**因为 Id 由路径决定，父 Id 在子节点处理前就已可知**，不需要"先插父再查父 Id"（这正是架构 §5.3.4 说的天然解法） | `/categoryTree/1/children/0/key` `TEMPLATE_DUPLICATE_SLUG` |
| 5 | **分类挂属性集**：`category.attributeSet` 引用第 3 步的 code | `/categoryTree/0/children/1/attributeSet` |
| 6 | **商品 + 变体**：`products[]` → 每个商品按 `variantAxes` 调 `VariantMatrix.Plan`，`priceFor` 用 `product.basePrice`（± `variantPriceDelta`） | `/products/5/variantAxes` `AXIS_LIMIT_EXCEEDED` |
| 7 | **初始库存**：`products[].initialStock`（缺省 0）→ `StockItem` 并写一条 `Setup` 来源的 `StockMovement` | `/products/5/initialStock` `TEMPLATE_NEGATIVE_STOCK` |
| 8 | **主题与设置预设**：`defaults.{currency,locale,themeId,themeTokens}` → `ThemeActivationDraft` + `StoreSettingsDraft`；`themeId` 必须在 `IThemeCatalog` 已注册（这是编译期唯一的外部依赖，通过参数注入只读清单，仍是纯函数） | `/defaults/themeId` `THEME_NOT_REGISTERED` |

**确定性 Id 的三个收益**（这是本设计最值得强调的一点）
1. 同一模板重复编译产出的聚合**Id 完全相同** → 快照测试可以直接断言完整对象图而不用忽略 Id；
2. 幂等性由数据结构保证，不需要 `SeedBatchId`（对齐架构 §5.3.3 "重跑 = 整库重置"的取向）；
3. 编译一份模板的 diff 可读（`id` 稳定，改动只出现在真正改动的字段），PR review 有意义。

**错误定位契约**：`Diagnostics` 按 `JsonPointer` 字典序排序返回；任一 `Code` 以 `TEMPLATE_` 开头即视为"模板数据错误"（可修 JSON），非 `TEMPLATE_` 前缀视为"宿主问题"（需运维），前端据此分别提示"改模板"或"联系支持"。

### 3.3 `Pricing`（计算顺序写死）

**顺序不许改，理由是每一步的输入都依赖上一步的输出，任意调整都会改变法律意义上的"应付金额"。**

```
① LineUnitPrice_i  = variant.Price（含税模式下视为含税单价）
② LineSubtotal_i   = LineUnitPrice_i.Multiply(qty_i)                    精确，无舍入
③ Subtotal         = Σ LineSubtotal_i                                   精确
④ Discount         = Money.Zero(currency)                              MVP 恒 0（保留结构）
⑤ LineDiscount_i   = Discount.Allocate(LineSubtotal_i 权重)             最大余数法，Σ 精确
⑥ LineNet_i        = LineSubtotal_i − LineDiscount_i                    精确
⑦ NetGoods         = Σ LineNet_i = Subtotal − Discount                  精确
⑧ ShippingTotal     = ShippingRule.Evaluate(NetGoods, totalWeight)      ← 门槛判 NetGoods
⑨ TaxTotal          = 价外：Σ Round(LineNet_i × rate_i)
                      价内：Σ Round(LineNet_i × rate_i / (1 + rate_i))  逐行舍入后求和
⑩ Total             = 价外：NetGoods + ShippingTotal + TaxTotal
                      价内：NetGoods + ShippingTotal                    税已含在 NetGoods 内
```

| 规则 | 决定 | 理由 |
|---|---|---|
| **包邮门槛用什么判** | `NetGoods`（商品小计 − 折扣，**不含运费、不含税**） | 若含税，商家改税率会突然改变包邮与否；若含运费，会出现"运费让订单达标"的循环依赖。US-E5-04 例子（满 200 包邮）语义就是商品金额 |
| **税按行算还是按总额算** | **按行算完再求和** | 分类级税率覆盖（裁决 4b）要求不同行不同税率，按总额算无法表达；且逐行舍入后求和与逐行开票金额一致 |
| **价内税怎么算** | `tax = round(net × r / (1+r))`，`Total` 不含税 | 含税价是商家对消费者的承诺价，不能因为加税而变 |
| **运费是否计税** | MVP **不计税**（`ShippingTotal` 不进税基） | 简化 + 与"统一税率"口径一致；如需计，是 `TaxRule.ApplyToShipping` 开关（登记为 T+1） |
| **最高精度** | 中间量全为 `long` minorUnits，只在第 ⑨ 步与 `MultiplyBy` 处舍入 | 避免"多次舍入累积偏差" |
| **舍入模式** | `MidpointRounding.AwayFromZero` | 见 §2.9 |
| **总价必须自校验** | 返回前断言 INV-O03 恒等式，不成立抛 `PRICING_INVARIANT_BROKEN`（这是"计价 bug 立即暴露"而非"算错 1 分上线"） | |

```csharp
public sealed record PricingResult(Money Subtotal, Money Discount, Money NetGoods, Money ShippingTotal,
                                   Money TaxTotal, Money Total, IReadOnlyList<LineAmount> Lines,
                                   bool FreeShippingAchieved, string? FreeShippingHintKey);
public PricingResult Calculate(PricingInput input);   // 纯函数：settings snapshot + lines + address + rules
```

**怎么做到脱离 DB 单测**：`PricingInput` 里只放`PricingSnapshot`（`TaxInclusive, DefaultRateBps, CategoryRateOverrides, ShippingRule, Currency`）——全部是值对象，由 Application 从事务里读好后传入。单测直接构造 snapshot，覆盖：`0 税`、`分类覆盖`、`含税/价外`、`刚好等于门槛`、`门槛差 1 分`、`25 行 × 0.5 分余数`、`币种不匹配抛异常`。

### 3.4 三个服务"可脱离 DB 单测"的统一理由

| 手段 | 说明 |
|---|---|
| 构造函数无依赖 | 只有 `VariantMatrix` 需要 `maxVariants` 之类常量参数；`Pricing` 需要 snapshot；`TemplateCompiler` 需要只读主题清单 |
| 时间是参数 | `IClock` 只在 **Domain 聚合方法**里出现（`Product.Publish(clock)`），服务本身不取时间 |
| Id 是参数/确定性 | 变体 Id 由 `IIdGenerator` 在 Application 层给；模板 Id 由路径确定性推导 |
| 无仓储 | 服务只"算"，返回 plan / result / diagnostics，**不落库**。落库是 Application 的事 |
| 快照测试 | `TemplateCompiler` 对 3 个内置模板各一份 `verified.json`（`Verify` 库），任何编译行为变化都会 diff 出来 |

## 4. 订单与支付状态机

### 4.0 先解决一个建模陷阱：为什么"一个 status 字段"不够

需求原文列了 9 个订单状态（待支付、已支付、已发货、已完成、已取消、部分退款、已退款、退款处理中、退款失败），它们**混了两个正交维度**：履约（Fulfillment）与资金（Refund）。如果用一个枚举直接赋值，必然遇到"已发货 + 部分退款后又要发货"、"已支付 + 退款失败该显示哪个"这类不可解冲突——运维中真实会出现（先退了一行坏货，剩下的货照发）。

**所以 `Order` 内部持有两个正交子状态，对外 `status` 是它们的纯函数投影。**

| 内部字段 | 取值 | 谁能改 |
|---|---|---|
| `FulfillmentStatus` | `PendingPayment` / `Paid` / `Shipped` / `Completed` / `Cancelled` | 只由 `MarkPaid / Ship / MarkCompleted / Cancel` 改 |
| `RefundStatus` | `None` / `Pending` / `PartiallyRefunded` / `Refunded` / `Failed` | 只由 `BeginRefund / ApplyRefundSucceeded / ApplyRefundFailed` 改 |
| `RefundedTotal` | `Money` | 由 `ApplyRefundSucceeded` 累加 |
| `status`（对外，只读） | 9 值枚举 | **没有任何方法可以赋值**，`ProjectStatus()` 纯函数计算 |

**`ProjectStatus()` 优先级（高 → 低，顺序即规则）**

| 序 | 条件 | 对外 status | 排序理由 |
|---|---|---|---|
| 1 | `Fulfillment == Cancelled` | `Cancelled` | 终态，一切信息让位 |
| 2 | `RefundStatus == Refunded` | `Refunded` | 钱全退，履约意义消失 |
| 3 | `RefundStatus == Pending` | `RefundPending` | 客户在等钱，必须最显眼（US-E7-05） |
| 4 | `RefundStatus == Failed` | `RefundFailed` | "不允许静默失败"，失败必须压过履约态 |
| 5 | `Fulfillment == Completed` | `Completed` | |
| 6 | `Fulfillment == Shipped` | `Shipped` | 物流是客户最关心的信息 |
| 7 | `RefundStatus == PartiallyRefunded` | `PartiallyRefunded` | 已发货+部分退款时优先展示物流，退款金额在 `refundSummary` |
| 8 | `Fulfillment == Paid` | `Paid` | |
| 9 | `Fulfillment == PendingPayment` | `PendingPayment` | |

> **API 响应必须同时返回三个字段**：`status`（上面这个投影，用于列表与状态标签）、`fulfillmentStatus`、`refundSummary{status, refundedAmount, lastFailure}`。前端订单详情页**必须分区渲染**：状态标签用 `status`，物流区块用 `fulfillmentStatus`，退款区块用 `refundSummary`。
> **⚠ 待与 PM 确认**：序 4 的位置与 US-E7-02 措辞"退款失败则保持已支付"存在可争议的读法。本文的取向是"失败优先暴露"（对齐 US-E7-05"不允许静默失败"），并在 `fulfillmentStatus` 里保留"已支付"的事实。若 PM 要求 `status` 严格保持 `Paid`，只需把序 4 移到序 7 之下，**实现零改动**（只改一个纯函数与一个测试）。见 §12.2 Q1。

**一个订单行在一个订单内的两个独立进度**（同样禁止挤在一个字段里）：`FulfillmentQty`（已发数量，MVP 恒 0 或全量）与 `RefundedQty`（已退数量）。MVP 不做部分发货，`FulfillmentQty ∈ {0, Qty}`。

### 4.1 订单状态机

#### 4.1.2 明确禁止的转换（附理由，不可协商）

| # | 禁止 | 错误码 | 理由 |
|---|---|---|---|
| F1 | `PendingPayment → Shipped` | `ORDER_NOT_PAID` | 未收到钱就发货是最直接的资损。无例外、无"信任客户"开关 |
| F2 | `PendingPayment → Completed` | `ORDER_NOT_PAID` | 同上 |
| F3 | `PendingPayment → RefundPending` | `ORDER_NO_PAYMENT_TO_REFUND` | 没付过款不能退款（防"退款套现"+ 通道侧必失败） |
| F4 | `Paid → Cancelled` | `ORDER_MUST_REFUND_TO_CANCEL` | US-E7-02 硬要求：已付款的取消 = 退款，钱必须先回来。若允许 `Paid → Cancelled`，库存会回补而钱没退，形成"卖了又没卖也没退钱"的账 |
| F5 | `Shipped → Cancelled` | `ORDER_SHIPPED_CANNOT_CANCEL` | 货已出库，只能走退款（US-E7-02） |
| F6 | `Paid → Completed` | `ORDER_MUST_SHIP_FIRST` | MVP 无虚拟商品，跳过发货等于绕过履约留痕 |
| F7 | `Refunded → Paid` | `ORDER_REFUNDED_TERMINAL` | AC/US-E6-05 明令禁止。终态回退意味着"钱退了但订单说已付"，任何报表与对账都无法收口 |
| F8 | `Refunded → RefundPending` | `ORDER_REFUNDED_TERMINAL` | 二次退款会直接造成资金损失（第一笔已全退） |
| F9 | `Cancelled → 任何` | `ORDER_CANCELLED_TERMINAL` | 库存已释放，重激活会导致"同一份库存卖两次" |
| F10 | `Mode=Gateway` 的 `Refund` 从 `Failed` 人工直接置 `Succeeded` | `REFUND_FAILED_CANNOT_MARK_REFUNDED` | US-E7-05 明令禁止。钱没退就标已退 = 伪造财务事实 |
| F11 | **`Mode=Gateway` 的 `Refund` 在通道能力存在时被"降级"为 `Mode=Offline`** | `OFFLINE_FALLBACK_NOT_ALLOWED` | 若允许，"通道退款失败"就成了绕开通道的通用后门，且退款与通道对账永久不一致。**正确做法：能力存在 → 只能重试**（US-E7-05）。通道**不具备**退款能力时系统**在创建时就**选 `Mode=Offline`（§2.5），不存在"中途降级"这个动作 |
| F11b | `Mode=Offline` 的 `Refund` 未填 `OfflineVoucherNo` 就置 `Succeeded` | `OFFLINE_VOUCHER_REQUIRED` | US-E7-07 / AC-19：「未填凭证号不可置成功」。凭证号是线下退款的唯一对账依据 |
| F12 | 任何状态的 `RefundedTotal > Total` | `REFUND_EXCEEDS_ORDER_TOTAL` | INV-O04 |
| F13 | `Succeeded` 的 `Payment` 被改回 `Failed` / 新建第二个 `Succeeded` Payment | `PAYMENT_ALREADY_SUCCEEDED` | 一问一付；多付由退款处理，不由支付状态表达 |
| F14 | `RefundStatus=Succeeded` 的 `Refund` 再 `MarkSucceeded` 或被重试 | `REFUND_ALREADY_SUCCEEDED` | INV-RF04，同一退款单幂等 |

> 全部禁止转换在代码里是**状态机白名单表 + 穷举测试**：`OrderStatusMachine.Transitions` 是一张静态表，`Theory` 把 9×动作 = 全部组合跑一遍，断言"表内允许、表外抛 `ORDER_INVALID_TRANSITION`"。新增动作必须先改表（会红），不允许在聚合方法里 `if (status == X)` 打洞。

### 4.2 支付与退款状态机

#### 4.2.1 `Payment`（订单 ↔ 支付一对一，多次尝试在一对一内）

| 当前 | 动作 | 目标 | 触发者 | 副作用 | 允许 |
|---|---|---|---|---|---|
| — | `Create`（下单事务内） | `Created` | 系统 | 写 `Amount = Order.Total` 快照 | ✅ |
| `Created` | `AttachIntent(providerPaymentId, clientSecret)` | `RequiresAction` | 系统（提交订单阶段②） | 写 `PaymentAttempt#1` | ✅ |
| `Created` | 创建意图失败 | `Failed` | 系统 | `PaymentAttempt{category=ProviderDown}` | ✅ |
| `RequiresAction` | 用户跳转后提交支付 | `Processing` | 通道回调（部分通道有 intermediate 通知） | 仅记录，不动订单 | ✅ |
| `RequiresAction` / `Processing` | 通道成功通知（三路共用） | `Succeeded` | 系统 | 见 4.1.1 #1 | ✅ |
| `RequiresAction` / `Processing` | 通道失败通知 | `Failed` | 系统 | 记 `Attempt`，订单不变 | ✅ |
| `RequiresAction` | 用户放弃（30 分钟超时） | `Canceled` | 系统（随 `UnpaidOrderExpiryJob`） | 与订单取消同事务 | ✅ |
| `Failed` | 用户重试支付 | `RequiresAction`（`AttemptNo+1`） | 消费者 | 新 `Attempt`，**Payment.Id 不变** | ✅ |
| `Succeeded` | 任何 | — | — | — | ❌ F13 终态 |
| `Canceled` | 任何 | — | — | — | ❌ 订单已取消，只有新订单能付款 |

**不变量**：`Succeeded` 后 `Amount`/`Provider`/`ProviderTransactionId` 全部不可变；`Attempts` 只追加；`AttemptNo` 单调递增且 `(Payment.Id, AttemptNo)` 唯一。

#### 4.2.2 `Refund`

| 当前 | 动作 | 目标 | 触发者 | 副作用 | 允许 |
|---|---|---|---|---|---|
| — | `Create(...)` | `Created` | 管理员 | 校验 INV-O04/RF02 + 写 `IdempotencyKey` | ✅ |
| `Created` | 通道同步成功 | `Succeeded` | 系统 | 订单 `RefundedTotal += amount`；库存回补（若选回补） | ✅ |
| `Created` | 通道受理（异步） | `Pending` | 系统 | 写 `ProviderRefundId` | ✅ |
| `Created` | 通道拒绝 | `Failed` | 系统 | 记分类 + 原因 | ✅ |
| `Pending` | 对账/回调确认成功 | `Succeeded` | 系统 | 同上 | ✅ |
| `Pending` | 对账/回调确认失败 | `Failed` | 系统 | 同上 | ✅ |
| `Pending` | 通道持续受理（> 24h，可配） | `Pending` + `StaleFlag` | 系统 | 管理端显示"需人工核查"，**不自动改状态** | ✅ |
| `Failed` | `CanRetry()` → 管理员重试 | `Pending` | 管理员 | `AttemptNo+1`，幂等键不变 | ✅ |
| `Succeeded` | 任何 | — | — | — | ❌ 终态 |

**线下退款模式（`Mode=Offline`，US-E7-07 / AC-19）**

| 当前 | 动作 | 目标 | 触发者 | 副作用 | 允许 |
|---|---|---|---|---|---|
| — | `Create(mode=Offline)`（由 `SupportsRefund==false` 自动决定） | `RequiresManualSettlement` | 管理员 | 写 `Refund{Mode=Offline}`；**零通道调用** | ✅ |
| `RequiresManualSettlement` | `MarkSettledOffline(voucherNo, settledBy, note)` | `Succeeded` | 管理员 | 订单 `RefundedTotal += amount` + 库存回补（若选）+ Outbox 退款邮件（文案含"线下退款"）+ 审计（含凭证号） | ✅ |
| `RequiresManualSettlement` | 未填 `voucherNo` 就置成功 | — | — | — | ❌ `OFFLINE_VOUCHER_REQUIRED`（F11b） |
| `RequiresManualSettlement` | 改为 `Mode=Gateway` | — | — | — | ❌ 创建后不可改模式（否则"退两次"风险） |
| `Succeeded`（Offline） | 任何 | — | — | — | ❌ 终态（与 Gateway 一致） |

> **AC-19 的对账要求**：`Mode=Offline` 与 `Mode=Gateway` 在 `Order.RefundStatus`、`Order.RefundedTotal`、报表口径上**完全一致**，唯一差别是 `Refund` 上有 `Mode/OfflineVoucherNo/SettledBy` 三个字段可审计。这是"降级路径不产生第二套账"的关键。

**`Refund.Status` 与 `Order.RefundStatus` 的关系**：一对多（一个订单可有多笔部分退款）。`Order.RefundStatus` 由 `RefundService`（Application）按"最高优先级的活跃退款 + 累计金额"推导后调聚合方法，**聚合不接受外部传入目标状态**（§2.4 关键设计点 2）。`RequiresManualSettlement` 在订单层映射为 `RefundPending`（订单页额外置 `refundSummary.requiresManualSettlement = true` 并显示"需线下退款"表单），**不新增第 10 个订单状态**（对齐需求列出的 9 个状态）。

#### 4.2.3 退款为什么走 Outbox（与"创建支付意图"不同）

AC-19 要求"管理员发起退款后订单**先为退款中**，通道回调成功后才变已退款/部分退款"。这天然要求退款动作是**异步**的：

```
管理员 POST /admin/refunds
 事务内：Create Refund(Pending) + Order.BeginRefund() + Outbox{Kind=Refund, DedupeKey="refund-request:{refundId}"} + 审计
 提交 → 202 {refundId, status:"Pending"}
OutboxDispatcherJob（5 秒内）→ IPaymentGateway.RefundAsync
 → 同步成功：SettleRefundAsync(eventId="refund:{refundId}:succeeded") 幂等入账
 → 受理中：Refund.MarkPending(providerRefundId)，等回调/对账
 → 失败：Refund.MarkFailed(category)
```

对比：**创建支付意图**必须同步（用户要立刻跳转支付页，不能等 5 秒轮询），所以 §1.3 才写了那个两阶段例外。**退款没有这个约束**（管理员点完可以等），所以一律走 Outbox——这也顺带消掉了"退款接口等通道 3 秒超时"的问题。**判断准则：外部副作用是否需要把结果同步返回给当前用户；不需要就一律 Outbox。**

### 4.3 幂等设计（AC-06 / AC-07 的可通过性论证）

#### 4.3.1 三层防线，缺一不可

| 层 | 机制 | 拦住的场景 | 单靠它会漏什么 |
|---|---|---|---|
| L1 | `WebhookEvent (Provider, ProviderEventId)` 唯一索引 | 通道重投**同一个** event（AC-06 的 5 次重放） | 通道重投时换了新 eventId（Stripe 的 `retry` 可能生成新事件 id）→ 漏 |
| L2 | `Payment` 状态守卫 + `RowVersion` 乐观锁 | 不同 eventId 指向同一笔支付；并发双投递 | 慢速重放（前一事务已提交，Status 已是 Succeeded）→ 这把也拦住了，但若 L2 被绕过（例如手动 SQL 改状态）则漏 |
| L3 | `(Provider, ProviderTransactionId)` 唯一索引 + 领域方法内幂等（`Commit(holdId)` 按 hold 状态幂等、Outbox `dedupeKey` 唯一索引） | 已进到副作用阶段才重复 | — |

**AC-06 逐步推演：同一成功回调重放 5 次**

| 次 | L1 | L2 | L3 | 结果 | 支付记录 | 库存 | 邮件 |
|---|---|---|---|---|---|---|---|
| 1 | 插入成功 | `RequiresAction` → `Succeeded` | Commit 1 次；Outbox 插入 1 行 | `Settled` | **1** | **扣 1 次** | **1 封** |
| 2 | 唯一键冲突 → `DuplicateEvent` | 不再执行 | 不执行 | `DuplicateEvent` → 200 | 1 | 1 次 | 1 封 |
| 3-5 | 同上 | — | — | 200 | 1 | 1 次 | 1 封 |
| 3'（假设换 eventId） | 插入成功 | `Status==Succeeded` → `AlreadySettled` | 不执行 | `AlreadySettled` → 200 | 1 | 1 次 | 1 封 |

> 关键：**任何一条路径都必须返回 200**。返回 4xx/5xx 会让通道不停重投，把小问题放大成风控事件。

#### 4.3.2 并发重放（v1.3 #18，AC-06 新增"并发 5 次"）

**这一条是本设计里最容易"看起来对、实际漏"的地方**，必须先说清为什么会漏：

```csharp
// ❌ 错的写法：读-判断-写（read-then-check）在并发下全部漏
if (await db.WebhookEvents.AnyAsync(e => e.EventId == n.EventId)) return Duplicate;   // 5 个并发请求都读到 false
db.WebhookEvents.Add(new(...));                                                       // 5 个都 Add
await db.SaveChangesAsync();                                                          // 靠唯一索引才会炸，但此时业务已执行一半
```

**正确做法：让数据库唯一约束做仲裁，把"冲突"当正常分支处理。**

```csharp
// Application/Payments/PaymentSettlementService.cs —— 并发安全的骨架（20 行）
public Task<SettlementResult> SettleAsync(PaymentNotification n, CancellationToken ct) =>
    _uow.ExecuteAsync(async t =>
    {
        try { await _webhooks.InsertAsync(n.Provider, n.EventId, n.SignatureValid, t); }
        catch (DbUpdateException ex) when (IsUniqueViolation(ex))          // ← 仲裁点：并发下只有 1 个能进来
        { return SettlementResult.DuplicateEvent; }                        //   其余 4 个走这里，事务回滚但无副作用

        var pay = await _payments.GetByOrderNumberAsync(n.OrderNumber, forUpdate: true, t)!;
        if (pay.Status is PaymentStatus.Succeeded) return SettlementResult.AlreadySettled;

        pay.MarkSucceeded(n.TransactionId!, n.Amount, n.PaidAt, _clock);   // 内部再查一次 Status（双保险）
        await _uow.SaveChangesAsync(t);   // Stock.Commit(holdId) 幂等 + Outbox(dedupeKey) 唯一索引
        return SettlementResult.Settled;
    }, ct);
```

**并发 5 次的实际时序（以 PostgreSQL 为例，SQLite 写串行化效果相同）**

| 时刻 | T1 | T2–T5 | 说明 |
|---|---|---|---|
| t0 | `INSERT WebhookEvent` | `INSERT` 同键 | T2–T5 在唯一索引上**阻塞**等 T1 |
| t1 | 提交，`Payment → Succeeded` | 仍在等 | T1 是唯一赢家 |
| t2 | 200 `Settled` | 唯一索引冲突 → `DuplicateEvent` → **事务正常回滚**（不报错） | 4 个 loser 不产生任何写 |

**四条必须遵守的实现约束**

| # | 约束 | 违反后果 |
|---|---|---|
| 1 | `WebhookEvent` 插入必须是事务内**第一个**写操作 | 后置插入会让业务副作用先执行，冲突时回滚已晚（虽然能回滚，但事务持有时间变长，冲突率上升） |
| 2 | 唯一冲突必须识别为**业务分支**而非 500 | `DbUpdateException` 冒泡到全局处理器 → 返回 500 → 通道无限重投 → 风控 |
| 3 | **不允许**在任何路径上用"先查再插"判断是否已处理（可以查，但只能用于日志/返回不同文案，不能作为控制流） | 并发全漏 |
| 4 | 同一订单的 `Payment` 行必须带 `RowVersion`；`MarkSucceeded` 内部先断言当前状态 | 两条不同 eventId 的并发结算都能过 L1，靠 L2 的乐观锁 + 状态再断言才拦得住第二条 |

**AC-19 的退款并发重放同理**：`Refund` 的成功入账用 `RefundSettlementService`，`(Provider, ProviderRefundId)` 唯一索引 + `Refund.RowVersion` + `Status` 再断言；库存回补走 `RestockFromRefund` 并以 `(refundId, orderLineId)` 幂等（见 §2.2 INV-S03 的流水去重键）。

**AC-07 论证：回调丢失 + 手动刷新 + 定时对账**

三条路径**共用一个方法** `PaymentSettlementService.SettleAsync(PaymentNotification, ct)`。`PaymentNotification` 是内部统一契约（`provider / eventId / orderNumber / transactionId / amount / paidAt / rawStatus`），由三个适配器分别构造：

| 入口 | 构造 `PaymentNotification` 的方式 | `eventId` 从哪来 |
|---|---|---|
| Webhook | 验签后解析原始 body | 通道给的 event id |
| 手动刷新 `/orders/{n}/refresh-payment` | 调 `IPaymentGateway.GetStatusAsync(orderNumber)` 后**合成** | `manual:{orderNumber}:{status}:{transactionId}` |
| 定时对账 `PaymentReconciliationJob` | 同上，批量 | `recon:{orderNumber}:{status}:{transactionId}` |

合成 `eventId` 的价值：**手动刷新点 3 次也只产生一条 `WebhookEvent`**，天然幂等，不需要额外分支。这直接满足 AC-07"不产生重复支付记录"。

#### 4.3.3 关键骨架（≤20 行）

```csharp
// Application/Payments/PaymentSettlementService.cs —— 三路唯一入口
public Task<SettlementResult> SettleAsync(PaymentNotification n, CancellationToken ct) =>
    _uow.ExecuteAsync(async t =>
    {
        if (!await _webhooks.TryRecordAsync(n.Provider, n.EventId, n.ProviderTxnId, t))   // L1
            return SettlementResult.DuplicateEvent;

        var pay = await _payments.GetByOrderNumberAsync(n.OrderNumber, forUpdate: true, t)
                  ?? throw AppException.NotFound(ProblemCodes.PAYMENT_NOT_FOUND);
        if (pay.Status is PaymentStatus.Succeeded) return SettlementResult.AlreadySettled; // L2

        if (!n.IsSuccess) { pay.MarkFailed(n.FailureCode!); return SettlementResult.Failed; }
        pay.MarkSucceeded(n.TransactionId!, n.Amount, n.PaidAt, _clock);                  // L3 领域幂等
        await _uow.SaveChangesAsync(t);   // → PaymentSucceeded → Order.MarkPaid + Stock.Commit(hold)
                                          //   + Outbox(dedupeKey="order-confirmation:{orderNumber}")
        return SettlementResult.Settled;
    }, ct);
```

`Outbox` 去重键（唯一索引）：`order-confirmation:{orderNumber}` / `order-shipped:{orderNumber}:{trackingNo}` / `refund-succeeded:{refundId}`。**邮件这一环的幂等靠 DB 唯一索引而不是内存标记**，所以进程重启后依然成立。

#### 4.3.4 下单接口的幂等（另一处必需的幂等）

`POST /checkout/submit` 携带 `Idempotency-Key`（前端每次进入结算页生成一个，重试不变）。

| 场景 | 行为 |
|---|---|
| 首次 | 计算 → 创建 Order + Hold + Payment → 保存响应体到 `IdempotencyKey{Key, Scope, RequestHash, ResponseJson, StatusCode, ExpiresAt}` |
| 同 Key 重放且 `RequestHash` 相同 | 直接返回缓存的 `ResponseJson` + 原 `StatusCode`（**不重复建单**） |
| 同 Key 但 `RequestHash` 不同 | `409 IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_BODY` |
| 首次请求未完成（`Status=InFlight`） | `409 REQUEST_IN_FLIGHT`（前端 1s 后重试） |
| 保留期 | 7 天（`IdempotencyKeyCleanupJob` 清理） |

### 4.4 失败分类（通道错误码 → 用户能懂的三类）

**只暴露分类，不暴露通道原文**。通道的英文错误（`Your card was declined.`）对中文客户无意义，且原文里常含通道名（泄露技术栈）。

| 分类 `FailureCategory` | i18n key（前端渲染） | 常见通道码（映射表的左侧） | 前端动作 |
|---|---|---|---|
| `Retryable` | `payment.failed.retryable` "支付未成功，可稍后重试" | `processing_error` `network_timeout` `rate_limit` `try_again_later` `insufficient_funds`（余额不足，客户可充值） | 显示"重试支付"按钮，订单保留 30 分钟 |
| `ChangeMethod` | `payment.failed.changeMethod` "该支付方式不可用，请换一种方式" | `card_declined` `do_not_honor` `expired_card` `incorrect_cvc` `currency_not_supported` `amount_too_large` | 显示"换支付方式"；订单保留 |
| `ContactIssuer` | `payment.failed.contactIssuer` "请联系发卡行后重试" | `fraud_suspected` `stolen_card` `pickup_card` `card_not_supported` | 显示客服邮箱 + 订单号，**不显示重试按钮**（重试必失败） |
| `Canceled` | `payment.failed.canceled` "支付已取消" | `user_canceled` `payment_abandoned` | 回购物车/订单页，可重试 |
| `Unknown` | `payment.failed.unknown` "支付未完成，请稍后重试或联系客服" | 未识别的一切 | 显示订单号 + 客服邮箱 + 重试按钮 |

**映射表形态**（纯函数，可单测，可配置覆盖）

```csharp
public sealed record FailureMapping(string ProviderCode, FailureCategory Category, bool IsRetryableByUser);
public static class PaymentFailureClassifier
{
    private static readonly Dictionary<string, (FailureCategory Cat, bool Retry)> Map = new(StringComparer.OrdinalIgnoreCase) { ... };
    public static FailureClassification Classify(string provider, string? providerCode, string? providerMessage)
        => Map.TryGetValue(Normalize(provider, providerCode), out var m) ? m.ToResult()
         : new(FailureCategory.Unknown, IsRetryableByUser: true, MessageKey: "payment.failed.unknown");
}
```

| 规则 | 说明 |
|---|---|
| 通道原文只给管理员 | 管理端订单详情显示 `providerCode + providerMessage`（便于对账），storefront **永不返回** |
| 未识别一律 `Unknown` 且可重试 | 宁可让客户多试一次，也不要因为漏映射把可恢复的失败判成死局 |
| 分类影响重试按钮 | `ContactIssuer` 隐藏重试按钮（US-E6-04 的三类展示） |
| 分类进审计 | 每次失败写 `PaymentAttempt{FailureCategory, ProviderCode}`，用于统计"卡被拒率" |
| AC-14 联动 | 全是 i18n key，英文站不会漏出中文（反之亦然） |

## 5. API 契约

### 5.1 全局约定（先立规矩，再列端点）

| 约定 | 内容 |
|---|---|
| Base path | `/api/storefront/*`、`/api/admin/*`、`/api/webhooks/*`、`/api/setup/*`；健康检查在根（`/health/*`）供反代直取 |
| 版本 | 路径不带版本号（单实例同版本部署，前后端同仓同步发版）。破坏性变更靠"新增字段、旧字段保留 1 个 minor"处理；`openapi.json` 的 `info.version` 跟随后端语义化版本 |
| 金额 | **一律** `{"amount": 29900, "currency": "CNY"}`（minorUnits 整数）。禁止 `"29.90"`、禁止裸数字 |
| 时间 | ISO-8601 带偏移 `2025-11-15T16:34:00+08:00`；服务端统一 UTC 存储，按 `StoreSettings.TimeZone` 或订单 `Locale` 渲染 |
| 分页（统一） | 请求 `?page=1&pageSize=24`（`pageSize` 默认 24、上限 100，超限返回 400 `PAGE_SIZE_EXCEEDED`）；响应固定 `{ "items": [], "page": 1, "pageSize": 24, "total": 137, "totalPages": 6 }`。**不用 cursor**（小店数据集 + 后台需要跳页） |
| 排序 | `?sort=priceAsc\|priceDesc\|newest\|relevance`（storefront）／`?sort=createdAtDesc\|totalDesc\|status`（admin），非法值 400 |
| locale | 所有含内容的读接口接受 `?locale=zh\|en`，缺省 `DefaultLocale`；非法 locale → 400 `LOCALE_NOT_ENABLED` |
| 幂等键 | 会创建资金/订单类资源的 POST 必须带 `Idempotency-Key` 头（`/checkout/submit`、`/admin/refunds`）；缺失 → 400 `IDEMPOTENCY_KEY_REQUIRED` |
| 认证 | Cookie（见 §6）；storefront 匿名可用的端点标 `Public` |
| 错误 | `application/problem+json`（RFC 7807）+ 扩展字段 `code` / `correlationId` / `errors` / `details` |
| 成功码 | 创建 `201 + Location`；纯状态变更 `200` + 最新资源；删除 `204`；异步受理 `202` |
| **绝对 URL** | canonical / `og:url` / `og:image` / `hreflang` / 邮件链接 / 支付回跳 **只允许由 `StoreSettings.PublicSiteUrl` 生成**，禁止用 `HttpContext.Request.Host` 或 `X-Forwarded-Host`（AC-10：「不随请求 Host 头漂移」）。后端所有 DTO 里出现的 URL 字段都是绝对 URL，前端**不做拼接** |
| **`canSell`（派生）** | 见 §2.7。storefront 的 `bootstrap` 与 admin 的 `dashboard/summary` 必须返回它；`CheckoutService` 在**任何写操作之前**断言它，false → `503 CANNOT_SELL` |
| **数据不可用 ≠ 空结果**（AC-10 负向断言） | `200` + `items: []` **只允许**在"确实没有匹配数据"时返回（`total` 为真实 0）。任何内部异常（DB 不可用、查询报错、缓存后源数据读失败）必须返回 **503** + `ProblemDetails`，**禁止**把异常吞成空列表——因为"200 的空白商品页被索引比不索引更糟"。实现约束：查询类端点不得 `try/catch → return [];`，全局异常中间件是唯一出口 |
| 空结果与降级的判别 | 响应必带 `total`（真实计数）。前端约定：`total === 0` 才渲染空态；任何 5xx 渲染"暂时不可用"页并带 `Retry-After: 30`，且该错误页 SSR 输出 `<meta name="robots" content="noindex">` |

**storefront 数据隔离（安全边界，非风格问题）**

| 绝不返回 | 替代 |
|---|---|
| 成本价 / 毛利 / 供应商 | 无（不存在于 storefront DTO 类型上） |
| 内部备注 / 员工备注 / 审计原因 | 无 |
| 库存内部分解（`OnHand` / `Reserved` / `Sold` / 流水） | `availability: { "inStock": true, "maxOrderQty": 7 }` |
| 其他客户的任何信息、订单是否存在的判断依据 | 见 §6.5 越权防护 |
| 通道原文错误、`providerTransactionId`、`providerPaymentId` | 分类 + i18n key（§4.4） |
| 未上架/已归档商品（除 410 语义提示） | 404/410，不带详情 |
| 管理员账号、Session、审计日志 | 无 |

> 强制手段：`StorefrontProductDto` / `StorefrontOrderDto` 是**独立类型**，与 admin DTO 无继承、无共用基类。架构测试反射扫描 storefront 命名空间下所有 DTO 的属性名，命中黑名单（`Cost|Margin|Note|OnHand|Reserved|Sold|ProviderTxn|Email` 等，允许白名单例外）即 CI 红（§9）。

### 5.5 Webhooks 与 Health

| 方法 | 路径 | 用途 | 鉴权 | 主要请求字段 | 主要响应字段 | 备注 |
|---|---|---|---|---|---|---|
| POST | `/api/webhooks/payments/{provider}` | 支付**与退款**回调 | **签名校验**（无 Cookie） | 原始 body + `Stripe-Signature` 等头 | `200 {result}` 恒 200（除验签失败 400） | 验签失败 → 400 + 落 `WebhookEvent{SignatureValid=false}` + 告警计数（AC-15）。支付事件走 `PaymentSettlementService`，**退款事件走 `RefundSettlementService`**（AC-19：退款串行/并发各重放 3 次 → 退款记录 1 条、库存回补 1 次）。`Mode=Offline` 的退款不会产生任何回调（本来就没调通道） |
| GET | `/health/live` | 存活探针 | Public（仅内网） | — | `200 {status:"live"}` | **不查 DB**，进程能响应即可 |
| GET | `/health/ready` | 就绪探针 | Public（仅内网） | — | `200/503 {checks:{db,migrations,mediaDir,templatesDir}}` | **不检查是否已完成安装**（新部署未初始化也是 ready）；任一失败 503 + 明细 |

## 6. 鉴权与权限

### 6.1 两套 Cookie

| Cookie | 用途 | HttpOnly | Secure | SameSite | Path | 有效期 | 值 |
|---|---|---|---|---|---|---|---|
| `os_admin_sid` | 管理端会话 | ✅ | ✅（生产；HTTP 下拒绝设置） | `Lax` | `/api/admin` | 会话 Cookie（浏览器关闭即失）+ 服务端 120 分钟空闲 / 7 天绝对 | 32 字节随机 base64url（DB 只存 SHA-256） |
| `os_shop_sid` | 商城端客户会话 | ✅ | ✅ | `Lax` | `/` | 30 天空闲 / 90 天绝对 | 同上 |
| `os_admin_csrf` | CSRF double-submit | ❌（JS 必须可读） | ✅ | `Lax` | `/` | 与会话同寿命 | 32 字节随机 base64url；`Session.CsrfHash` 存其哈希 |
| `os_cart` | 匿名购物车标识 | ✅ | ✅ | `Lax` | `/` | 180 天 | `{cartId}:{HMAC-SHA256(cartId, serverKey)}`（防遍历） |
| `os_locale` | 语言偏好（仅用于根路径 302 与语言切换） | ❌ | ✅ | `Lax` | `/` | 1 年 | `zh` / `en` |

**为什么两个 Path 不同**：`os_admin_sid` 限定 `Path=/api/admin`，商城页面的任何请求（含 SSR 内部调用之外的浏览器请求）都拿不到管理员会话，减少被 XSS 或第三方脚本带走的面积。代价是 `/admin` 静态页面导航时没有 Cookie——但 admin 是纯 SPA，靠 `/api/admin/auth/me` 判断登录态，不受影响。

**为什么 Cookie 而不是 JWT**：架构 §3 已裁决。补充一句落地理由：**"管理员封禁/改密立即生效"是 AC-15 与 US-E8-01 的隐含要求**，JWT 需要黑名单（等于又做一个 Session），而 Session 表 `RevokedAt` 一行就够。

### 6.2 Session 表结构与过期策略

> 表由 data-engineer 定稿，此处只给**字段语义契约**（§11 已登记对齐项）。

| 字段 | 类型 | 语义 |
|---|---|---|
| `Id` | string(26) | ULID |
| `TokenHash` | bytea(32) | `SHA-256(cookie 值)`；**唯一索引**；DB 泄露也无法直接用 |
| `Kind` | smallint | 1=Admin 2=Customer |
| `SubjectId` | string(26) | AdminUser.Id / Customer.Id |
| `CsrfHash` | bytea(32)? | 仅 Admin 有 |
| `CreatedAt` / `LastSeenAt` | timestamptz | `LastSeenAt` **节流写**：仅当 `now - LastSeenAt > 5min` 才 UPDATE（避免每请求一写） |
| `IdleExpiresAt` | timestamptz | 滑动：`LastSeenAt + IdleMinutes`（Admin 120，Customer 30 天） |
| `AbsoluteExpiresAt` | timestamptz | 绝对：创建时定死（Admin 7 天，Customer 90 天） |
| `RevokedAt` / `RevokeReason` | timestamptz? / smallint? | `Logout` / `PasswordChanged` / `AdminSuspended` / `ReuseDetected` |
| `IpFirst` / `UserAgentHash` | string? / bytea? | 仅审计，**不做会话绑定**（家宽 IP 变化会误杀，收益低） |
| `RowVersion` | rowversion | 并发保护（防两个并发请求互相覆盖 `LastSeenAt`） |

**策略**

| 项 | 值 | 依据 |
|---|---|---|
| 空闲超时 | Admin 120 分钟（`StoreSettings.SessionIdleMinutes` 可配），Customer 30 天 | US-E8-01 明确 120 分钟 |
| 绝对超时 | Admin 7 天，Customer 90 天 | 绝对上限防"永久会话" |
| 验证顺序 | ① 查 `TokenHash` → ② `RevokedAt is null` → ③ `now < AbsoluteExpiresAt` → ④ `now < IdleExpiresAt` → ⑤ Admin: `AdminUser.Status == Active` 且 `SecurityStamp` 未变 | 第 ⑤ 步让"改密即踢下线"无需遍历会话 |
| 滑动续期 | 满足 ①-⑤ 后更新 `LastSeenAt`/`IdleExpiresAt`（节流） | |
| 登出 | `RevokedAt = now, Reason=Logout` + 清 Cookie | US-E8-01「登出后回退按钮无法回到已登出页面」——服务端已撤销，回退只会 401 |
| 改密 / 停用 | revoke 该 subject 全部会话 + 轮换 `SecurityStamp` | INV-AD02 |
| 清理 | `CartExpiryJob` 顺手删 `RevokedAt < now-30d` 或 `AbsoluteExpiresAt < now-7d` | |
| **Session fixation** | 登录成功时先删旧 Session 再建新（不复用 Id/Token） | |

### 6.3 认证流程

```
管理端登录：
  POST /api/admin/auth/login
   → 限流检查（IP + 账号） → 查 AdminUser by 规范化 email
   → AdminUser.EnsureNotLocked(now)                 // 5 次失败锁 15 分钟
   → PasswordHasher<AdminUser>.VerifyHashedPassword
   → 失败：FailedAttempts++（≥5 则 LockedUntil=now+15m）+ 审计 + 统一 AUTH_INVALID_CREDENTIALS
   → 成功：FailedAttempts=0；建 Session（新 Id/Token，CsrfHash 随机）
          Set-Cookie: os_admin_sid（HttpOnly/Secure/Lax/Path=/api/admin）
          Set-Cookie: os_admin_csrf（Path=/）
   → 返回 {id,email,role,permissions[]}

storefront 登录：同构，无 CSRF cookie，Path=/
   → 若存在 os_cart，登录成功后自动 MergeInto（不阻塞登录，失败仅记 warning）
```

**为什么"账号不存在"与"密码错"用同一个错误码 + 相近耗时**：防账号枚举。`VerifyHashedPassword` 对不存在账号也跑一次 dummy hash（固定成本），保证响应时间差 < 20ms。

### 6.5 越权防护的落点

| 场景 | 落点 | 做法 |
|---|---|---|
| **客户 A 读客户 B 的订单** | **Application 查询入口（强制过滤）** | 所有客户态查询必须经 `IOwnedQuery<T>.ForCustomer(customerId)`，它返回**已带 `.Where(x => x.CustomerId == customerId)` 的 `IQueryable`**；仓储/服务不接受"无过滤"的入口。`GetOrderForCustomer(orderNumber)` 查不到 → 抛 `NotFound`（404，**不是 403**），因为 403 等于确认"该订单存在" |
| **游客猜订单号查他人订单** | Application（双因子） | `orderNumber + email` 必须同时匹配；email 比较用 `CryptographicOperations.FixedTimeEquals`（防时序侧信道）；失败统一 `ORDER_NOT_FOUND` |
| **员工调用退款/主题接口** | 端点授权策略 | `perm:refund.write` / `perm:theme.write` → 403 |
| **员工猜测 admin 端 URL** | 同上；另外 admin 前端路由与 API 路径同构，但前端不加载 ≠ 服务端放行 | 集成测试覆盖"Staff 遍历全部 Admin 端点 → 仅矩阵内 200，其余 403" |
| **客户调用 admin 接口** | 两套 Cookie Scheme 分离 | `os_shop_sid` 不会被 `/api/admin/*` 的 scheme 读取（Path 限定 + 不同 scheme 名）→ 401 而非 403（不泄露 admin 端点存在性） |
| **Set-Cookie 作用域越权** | Cookie `Path` 收窄 | 见 §6.1 |
| **cart cookie 伪造** | HMAC 校验 | `os_cart` 含 HMAC，校验不过即视为新建车（不报错） |
| **横向：改 `customerId` 参数** | 服务层忽略请求体中的 `customerId` | `CustomerId` 只从 `ICurrentUser` 取，DTO 里根本没有这个字段 |

**具体代码形态（关键：让"忘记过滤"编译不过）**

```csharp
// Application/Abstractions/IOwnedQuery.cs
public interface IOwnedQuery<T> where T : class
{
    IQueryable<T> ForCustomer(string customerId);   // 实现里强绑 Where(CustomerId == id)
    IQueryable<T> ForAdmin();                        // 只在 perm:* 通过后可用
}
// 仓储不暴露裸 IQueryable，只暴露上面两个入口 + 具名方法（GetByOrderNumberForCustomer 等）
```

### 6.6 CSRF

| 端 | 机制 | 理由 |
|---|---|---|
| Admin（全部写操作） | **double-submit + Origin 校验** | ① `SameSite=Lax` 已拦跨站 POST，但拦不住"同站 XSS"与旧浏览器；② 管理员是高价值目标，双层值得；③ 无状态，不需要每表单发 token |
| Storefront（`/checkout/submit`、`/cart/*`、`/account/*`） | `SameSite=Lax` + **`Origin`/`Sec-Fetch-Site` 校验**（`Origin` 必须是本站；缺失时降级看 `Referer`） | 商城端要兼容"从支付通道 302 回来"的跨站 GET，double-submit 会增加 SSR 表单复杂度；`Lax` + Origin 覆盖 OWASP 推荐的主要场景。**明确取舍记录在案** |
| Webhooks | 不用 CSRF | 无会话，靠签名；且跨站 |

**Admin double-submit 实现要点**
1. 登录时生成随机 `csrf`，`Set-Cookie: os_admin_csrf`（非 HttpOnly，`SameSite=Lax`，`Path=/`），同时 `Session.CsrfHash = SHA256(csrf)`。
2. 所有 `POST/PUT/PATCH/DELETE /api/admin/*` 必须带 `X-CSRF-Token`。
3. 中间件校验（顺序不能错）：① 会话有效 → ② `Origin` 是本站（`Origin` 缺失则拒绝）→ ③ `SHA256(header) == Session.CsrfHash`（`FixedTimeEquals`）→ 否则 `403 AUTH_CSRF_INVALID`。
4. **不豁免**：`/api/admin/auth/login` 也要 Origin 校验（防登录 CSRF），但不要求 CSRF 头（还没有会话）。
5. 改密/登录成功后**轮换** csrf（防 fixation）。
6. 前端：`packages/sdk` 提供 `withCsrf()` 包装，自动从 cookie 读值加到 header——一处实现，杜绝某个页面漏加。

### 6.7 登录防护与限流参数

| 机制 | 参数 | 说明 |
|---|---|---|
| 账号锁定 | 连续 5 次失败 → 锁 15 分钟 | US-E8-05；`FailedAttempts` 在**成功后清零**，锁定期内不累加 |
| 锁定响应 | `423 AUTH_LOCKED` + `details.unlockAt` | 明确告知何时可试，减少客服 |
| 失败响应 | 统一 `401 AUTH_INVALID_CREDENTIALS` | 不区分账号不存在/密码错 |
| 密码策略 | 12–128 字符；不得纯数字；不得在 Top-1000 弱口令集合；`PasswordHasher` 默认迭代（PBKDF2-SHA256, 100k） | US-E8-05；成本因子可通过 options 调，迭代次数版本号写入 hash 前缀（`PasswordHasher` 自带） |
| 密码存储 | `PasswordHasher<AdminUser>` / `<Customer>`，**只复用这一个类** | 不引整套 Identity |
| 重置 token | 32 字节随机，DB 存哈希，30 分钟有效，单次使用 | |
| 时序防护 | 不存在账号也执行一次 dummy verify | |

**限流策略（`Microsoft.AspNetCore.RateLimiter`，分区键与窗口）**

| 策略 | 分区键 | 限额 | 超限响应 |
|---|---|---|---|
| `login` | `ip` + `email`（规范化） | 5 次 / 1 分钟；20 次 / 15 分钟（IP 全局） | `429` + `Retry-After` |
| `password-reset` | `ip` | 3 次 / 10 分钟 | 429 |
| `checkout-submit` | `ip` + `cartId` | 10 次 / 1 分钟（IP）；3 次 / 1 分钟（车） | 429 + `RATE_LIMIT_EXCEEDED` |
| `cart-write` | `ip` | 60 次 / 1 分钟 | 429 |
| `order-lookup` | `ip` | 10 次 / 1 分钟 | 429（防订单号爆破） |
| `refresh-payment` | `orderNumber` | 5 次 / 1 分钟 | 429 |
| `webhook` | `provider` + `ip` | 600 次 / 1 分钟 | 429（允许通道重投） |

## 7. 后台任务清单

**统一执行框架约定（先立规矩）**

| 约定 | 内容 |
|---|---|
| 载体 | `BackgroundService` 一个基类 `PeriodicJobBase : BackgroundService`，提供：启动延迟（默认 10s，避开冷启动迁移检查）、周期 + 抖动（`±10%`，防多任务同秒触发）、`CancellationToken` 联动优雅停机、单次执行耗时与结果日志 |
| 事务粒度 | **扫描在事务外，每条记录一个事务**（`IUnitOfWork.ExecuteAsync`）。一条失败不影响其余条 |
| DbContext | 每条记录用新 scope（`IServiceScopeFactory`），不复用长生命周期 DbContext（避免跟踪膨胀） |
| 批大小 | 每次最多 100 条（可配），处理不完等下一轮，不做"一次清空" |
| 单实例假设 | 不做分布式锁（架构 YAGNI）。**若未来多实例部署，下列任务全部需要 `SELECT ... FOR UPDATE SKIP LOCKED` 或 DB advisory lock**（记录在 §12.1 R4） |
| 开关 | 每个任务独立 `OpenStore:Jobs:<Name>:Enabled`，生产可单独关停（如备份交给外部 cron） |
| 可观测 | 每次执行写一条 `job.executed{job, scanned, succeeded, failed, durationMs}` 结构化日志；失败计数暴露到 `/api/admin/dashboard/summary` |

| # | 任务 | 触发周期 | 做什么 | 幂等性保证 | 失败重试策略 | 对用户可观测的迹象 |
|---|---|---|---|---|---|---|

**为什么把这些做成后台任务而不是同步执行**

| 任务 | 若同步执行会怎样 |
|---|---|
| Outbox | 下单接口等 SMTP（3–10 秒），30% 的下单会超时；且 SMTP 挂了就无法下单 |
| 对账 | 用户点"刷新支付状态"要等通道响应（可能 5–30 秒），AC-07 的"10 秒内纠正"难保证；定时对账更是必须异步 |
| 超时释放 | 依赖"恰好某个请求进来时触发"，用户不访问站点就永远不释放 → 库存永久占用 |
| 购物车/会话清理 | 无请求上下文可挂 |

### 8.1 CorrelationId 与结构化日志

**中间件顺序（`Program.cs`，顺序不可调）**

```
1. UseForwardedHeaders            → 拿到真实 IP 与 scheme（反代后必需）
2. CorrelationIdMiddleware        → 建立/透传 traceId
3. ExceptionProblemDetailsMiddleware → 必须包住后续所有环节
4. SecurityHeadersMiddleware      → 含 HSTS、CSP
5. UseHttpsRedirection（可配）
6. UseRateLimiter
7. UseAuthentication（两套 scheme）
8. UseMiddleware<CsrfMiddleware>  → 仅在鉴权之后（要用 Session）
9. UseAuthorization
10. 端点路由
```

```csharp
// Middlewares/CorrelationIdMiddleware.cs（关键 8 行）
public async Task InvokeAsync(HttpContext ctx, ILogger<CorrelationIdMiddleware> log)
{
    var id = ctx.Request.Headers["X-Request-Id"].FirstOrDefault() is { Length: > 0 and <= 64 } h
             ? h : Activity.Current?.TraceId.ToString() ?? Guid.NewGuid().ToString("N");
    ctx.Items[CorrelationIdKey] = id;
    ctx.Response.Headers["X-Request-Id"] = id;
    using var scope = log.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id });
    await _next(ctx);
}
```

**日志字段（Serilog JSON，字段名固定 → 可 grep）**

| 字段 | 何时有 | 用途 |
|---|---|---|
| `CorrelationId` | 全部 | **主检索键**：一个请求的全部日志同一值 |
| `TraceId` / `SpanId` | 全部（OpenTelemetry 兼容） | 跨服务（SSR → API）串联 |
| `OrderNumber` | 下单之后的全部订单相关日志 | **grep 一个订单号拿到完整链路**（架构 §6 要求 5 分钟内定位） |
| `PaymentId` / `RefundId` / `ProviderTxn` | 支付相关 | 对账 |
| `HoldId` / `VariantId` / `Sku` | 库存相关 | 超卖排查 |
| `CustomerId` / `AdminId` | 已认证 | 越权排查 |
| `UseCase` | 每条用例日志 | `Checkout.Submit` `Order.Ship` |
| `ElapsedMs` | 用例 End | 性能 |
| `Outcome` | 用例 End | `Ok` / `DomainError:CODE` / `Exception:TYPE` |
| `EventType` / `AggregateId` | 领域事件派发 | 事件链路 |
| `Job` / `Scanned` / `Succeeded` / `Failed` | 后台任务 | 任务健康度 |

**用例级日志规范（统一由 `IUseCaseLogger` 输出，避免各服务风格漂移）**

```
INFO  usecase.start   UseCase=Checkout.Submit  CorrelationId=...  CartId=...  ItemCount=2
INFO  domain.event    EventType=PaymentSucceeded  AggregateId=pay_...  CorrelationId=...
INFO  usecase.end     UseCase=Checkout.Submit  Outcome=Ok  OrderNumber=OS-251115-7QK3M2  ElapsedMs=42
WARN  stock.low       Sku=SERVO-...  Available=1  CorrelationId=...
ERROR usecase.end     Outcome=Exception:DbUpdateException  ElapsedMs=31   （附 stack）
```

**禁止**：任何日志中出现完整卡号（`\d{16}` 无命中，AC-15）、密码、Cookie 值、`Authorization` 头、SMTP/支付凭据。`Program.cs` 里挂一个 Serilog `Destructure.ByTransforming` 白名单 + 正则脱敏（`\d{13,19}` → `***`），并且 `RequestLogging` 只记 path/method/status/耗时，**不记 body**（body 里可能有地址与邮箱）。

### 8.2 全局异常 → ProblemDetails 映射

**只有一个地方 catch**：`ExceptionProblemDetailsMiddleware`。端点与服务**一律不 try/catch**（除必须做补偿的场景）。

| 异常类型 | HTTP | `code` | `title` | 说明 |

### 8.3 限流

见 §6.7（策略、分区键、限额）。补充两点：
- **限流器必须在鉴权之前**（否则未登录请求不消耗配额 → 刷登录页无成本）。分区键能拿到 `email` 的是 `login` 策略，用**路径级策略**而非全局策略，靠 `[EnableRateLimiting("login")]` 挂到端点上。
- 限流计数器存内存（`System.Threading.RateLimiting` + `PartitionedRateLimiter`），单实例足够；多实例会失效（同 §12.1 R4）。

### 8.4 安全响应头

| 头 | 值 | 适用 | 说明 |

| `Cross-Origin-Opener-Policy` | `same-origin` | 全部 | |

**storefront CSP**

```
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';      ← 有意的取舍，原因见下
img-src 'self' data: https:;
font-src 'self';
connect-src 'self';
form-action 'self';
frame-ancestors 'none';
base-uri 'self';
object-src 'none';
upgrade-insecure-requests
```

**为什么 storefront 必须允许 `style-src 'unsafe-inline'`（三个具体原因，缺一就会坏）**

1. **主题 token 以内联 `<style>` 注入**：`+layout.svelte` 里 `<svelte:head><style>{tokensToCss(tokens)}</style></svelte:head>`（架构 §5.1.4）。这是"运行时换色不重新编译"的唯一实现方式，改成外链 CSS 会引入一次额外请求 + FOUC（首屏闪白）。
2. **Svelte 5 的过渡/动画在运行时写 `element.style`**：`transition:`/`animate:` 指令产生的内联样式是框架行为，无法在构建期消除；`'unsafe-inline'` 下 `style` **属性**的写入需要 `style-src-attr` 放行（CSP3），因此同时声明 `style-src 'self' 'unsafe-inline'` 覆盖 attr。
3. **图片懒加载占位与 `srcset` 宽高比**：`<img style="aspect-ratio:..."` 用于防 CLS（架构 §5.4.3），动态计算，无法静态化。

**为什么这个取舍可接受**：CSP 的核心防线是 `script-src`，本项目 **`script-src 'self'` 严格不放行任何内联脚本与 `eval`**，因此即使攻击者能注入 `<style>` 也拿不到脚本执行能力；且商品富文本入库前已 sanitize 并**剥离 `style` 属性与 `<style>` 标签**（US-E2-04/07），用户可控内容进不了样式面。
**备选方案（未采用，记录备查）**：per-request nonce（`style-src 'nonce-xxx'`）能去掉 `'unsafe-inline'`，但要求 SSR 每次渲染把 nonce 传给 `.NET` 的响应头（两个进程要共享 nonce），跨进程耦合成本 > 收益。

**admin CSP**（更严，无主题）：`script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'`（`unsafe-inline` 同样因为 Svelte 过渡）。

### 8.5 缓存

**键设计与版本号**


| 数据 | 缓存？ | TTL | 失效方式 | 理由 |
|---|---|---|---|---|
| 分类树 | ✅ | 60 min | `catalog` bump | 慢变主数据，每页导航都要 |
| 属性定义 / 选项 / 属性集 | ✅ | 60 min | `catalog` bump | 筛选项的标签来源，避免 N+1 |
| 商品详情（**不含库存/不含变体可售状态**） | ✅ | 60 s | `catalog` bump | 详情页是最热路径；库存必须单独取 |
| 主题实例（tokens/blocks/texts） | ✅ | 60 min | `content` bump | 每页都要，纯读 |
| i18n 字典与覆盖 | ✅ | 60 min | `i18n` bump | |
| StoreSettings（不含凭据） | ✅ | 10 min | `settings` bump | 注意：**凭据字段永不进缓存**（单独服务读） |
| sitemap XML | ✅ | 60 min | `catalog` bump | 生成成本高、变更少 |
| 商品列表查询结果（含筛选/排序/分页） | ❌ | — | — | 组合爆炸（facet × sort × page）→ 缓存命中率低而内存占用高；靠 EF 投影 + 索引保证 P95 |
| facet 计数 | ❌ | — | — | 随库存/上下架实时变，缓存会给出"筛了没结果"的错值 |
| **库存数字** | ⚠ 仅 `stock:{variantId}` | **5 s** | 写库存时主动 `Remove` | 绝不能进 `catalog` 版本体系（会与商品缓存同寿命）；5 秒是"能接受的最长陈旧"，加购页仍有服务端二次校验兜底 |
| 购物车 | ❌ | — | — | 每人每车，缓存命中率≈0，且带身份 |
| 会话 | ❌ | — | — | 安全 |
| 订单 / 支付 / 退款状态 | ❌ | — | — | 资金类，任何陈旧都不可接受 |
| Admin 任何列表/详情 | ❌ | — | — | 管理员要看到刚改的数据 |
| 任何带 `Set-Cookie` 或已认证的响应 | ❌ | — | — | 防串号 |

**实现要点**
1. 版本号的读取是**一次字段读**（`long` 原子读），不查库 → 命中判断零成本。
2. 写操作 bump 在 **commit 之后**（`UnitOfWork` 的成功回调里），避免"事务回滚了缓存已失效"（这种情况下失效是安全方向，可以不回滚，但统一放 commit 后更简单）。
3. 缓存穿透：对"确认不存在"的 key 存 `null` 占位 30 秒（防爬虫刷不存在的 slug）。
4. **绝不使用 `IMemoryCache` 存可变大对象（如整个商品列表）**，单条上限 256KB，超限直接跳过缓存并记 warn。

**内存预算（v1.3 #19，AC-12：三进程合计 RSS ≤ 2GB 且 30 分钟压测不 OOM）**

| 进程 | 预算 | 约束手段 |
|---|---|---|
| `.NET API` | **≤ 1.2 GB** | `IMemoryCache` 必须设 `SizeLimit`（按条目字节估算，总额 **128 MB 上限**）+ `CompactionPercentage=0.25`；每条目 `Size` 用序列化后长度估算，超 256KB 直接不缓存；`ServerGarbageCollection=false`（单机小内存用小对象堆 GC 更省 RSS）；EF `QueryTrackingBehavior.NoTracking` + 分批 100 条（避免 `ChangeTracker` 累积）；**禁止**把整个商品/订单集合读进内存做 LINQ（必须 `IQueryable` 投影分页） |
| `Node storefront` | **≤ 500 MB** | `--max-old-space-size=384`；SSR 不缓存响应；`load` 里并发请求数受控（同一页最多 3 个并行 API 调用） |
| `SQLite` | **≤ 250 MB** | `PRAGMA cache_size = -64000`（64MB 页缓存）、`journal_mode=WAL`、`mmap_size` 适度 |
| 余量 | ~50 MB | 系统与日志缓冲 |

> **验证方式**：压测跑满 30 分钟后 `ps -o rss` 汇总三进程，断言 ≤ 2GB 且无 OOM Killer 记录（`dmesg | grep -i 'killed process'` 为空）。这条是 `check.sh` 之外的人工/CI 性能门禁，写进 QA 的 AC-12 用例。

## 9. 工程门禁（fail-before-pass）

### 9.1 `scripts/check.sh` 的 12 个步骤

`check.sh` 只做编排，每步是一个可独立运行并返回非 0 的脚本/命令；任一步失败立即 `exit 1` 并打印 `GATE FAILED: <规则名>`（规则名固定，便于 CI 与文档引用）。

| # | 步骤 | 命令（骨架） | 断言什么 | 失败时的输出 |
|---|---|---|---|---|
| 1 | 依赖还原与构建 | `dotnet restore --locked-mode && dotnet build -warnaserror` | 锁定依赖（无飘版本）；**零警告**（`TreatWarningsAsErrors`） | 编译错误/警告列表 |

### 9.2 如何证明门禁"先失败后通过"（客户最关心的部分）

**核心思路：门禁本身要被测试。** `scripts/verify-gates.sh` 会在一个临时 git worktree 里**故意注入 8 处违规**（V1–V8，见下表），逐条运行对应门禁并断言"必须红"。任何一条注入后门禁仍然绿 → 说明该门禁是摆设，脚本本身失败。

| 注入 # | 违规内容（自动 patch） | 期望被拦的步骤 | 期望输出包含 |
|---|---|---|---|
| V1 | `Domain/Shared/Money.cs` 顶部加 `using Microsoft.EntityFrameworkCore;` | 步骤 2（分层） | `Domain must not reference Microsoft.EntityFrameworkCore` |
| V2 | `Domain/Catalog/Product.cs` 加 `using OpenStore.Domain.Ordering;` 并引用一个类型 | 步骤 3（上下文互引） | `Domain.Catalog must not reference Domain.Ordering` |
| V3 | 端点 `Admin/RefundEndpoints.cs` 把 `.RequireAuthorization(Permissions.RefundWrite)` 删掉 | 步骤 4（授权完备性） | `admin endpoint POST /api/admin/refunds has no permission policy` |
| V4 | `Application/Catalog/Dtos/Storefront/StorefrontProductDto.cs` 加 `public Money CostAmount { get; init; }` | 步骤 5（数据隔离） | `StorefrontProductDto.CostAmount leaks admin field` |
| V5 | `assets/industry-templates/womenswear/template.json` 删掉 `defaults.themeId` | 步骤 9（模板 schema） | `/defaults: required property themeId missing` |
| V6 | `themes/base/theme.manifest.json` 的 `blocks` 里加 `"countdown"`（不改 editable.schema.json） | 步骤 10（主题 manifest） | `block "countdown" not declared in editable.schema.json` |
| V7 | `Persistence/Configurations/ProductConfiguration.cs` 改 `HasMaxLength(200)` → `300`（不改迁移） | 步骤 8（迁移漂移） | `模型有未提交的迁移变更` |
| V8 | `Domain/Ordering/OrderStatusMachine.cs` 白名单里加 `PendingPayment → Shipped` | 步骤 6（状态机穷举） | `F1 禁止转换未生效：PendingPayment→Shipped 未抛 ORDER_INVALID_TRANSITION` |

**脚本契约**

```bash
# scripts/verify-gates.sh 关键逻辑（12 行）
set -euo pipefail
for spec in "V1:Layering" "V2:BoundedContexts" "V3:Authorization" "V4:StorefrontDto" \
            "V5:templates" "V6:themes" "V7:migrations" "V8:statusmachine"; do
  id=${spec%%:*}; gate=${spec##*:}
  wt=$(git worktree add -q --detach "/tmp/gate-$id" HEAD && echo "/tmp/gate-$id")
  apply_violation "$id" "$wt"                       # git apply patches/$id.patch
  if run_gate "$gate" "$wt"; then                    # 期望失败
    echo "GATE $id IS A NO-OP: violation not caught"; FAILED=1
  else
    echo "GATE $id OK (caught as expected)"
  fi
  git worktree remove --force "$wt"
done
[ "${FAILED:-0}" -eq 0 ] && echo "ALL GATES PROVEN" || exit 1
```

**这套机制解决什么问题**：它把"我们有架构测试"变成"我们证明了这个架构测试会拦住违规"。客户以后每次修改门禁规则，都能立刻知道有没有把某条规则改成空转——这是"fail-before-pass"的真正含义，也是防止 AI 辅助生成代码逐步侵蚀边界（架构 §7 风险 10）的唯一可执行手段。

## 10. 给下游的交接要点

### 10.1 给前端

**OpenAPI → 类型生成流程**

```
dotnet run --project tools/OpenStore.Tools -- emit-openapi -o api/openapi.json
pnpm -C frontend gen:types            # openapi-typescript api/openapi.json -o packages/sdk/src/types.ts
# 生成物必须提交（check.sh 步骤 11 会 diff 校验）
```
- 只生成**类型**，不生成客户端（架构 §3）。`packages/sdk` 提供 `apiFetch<T>()`：注入 `X-Request-Id`、`X-CSRF-Token`（admin）、`credentials: 'include'`、`Accept: application/problem+json`。
- **两个 app 用两套生成路径**：storefront 只引 `components.storefront.*`，admin 只引 `components.admin.*`（同文件不同 section），物理上避免把 admin 字段带进 storefront 包（`tree-shaking` 不保证，需要靠类型 + 代码审查）。

**错误处理约定（只写一套）**

```ts
// packages/sdk/src/problem.ts
export type Problem = { type: string; title: string; status: number; detail?: string;
                        instance?: string; code: string; correlationId: string;
                        errors?: Record<string, string[]>; details?: unknown };
export function toUiError(p: Problem, t: (k: string, a?: object) => string) {
  if (p.errors) return { kind: 'field' as const, fields: p.errors, message: t('error.validation') };
  return { kind: 'code' as const, code: p.code, message: t(`error.${p.code}`, p.details ?? {}),
           correlationId: p.correlationId, retryable: RETRYABLE.has(p.code) };
}
```
- 所有错误都有 `code`，**前端不解析 `title`/`detail` 的文案**（文案会变，code 不会）。
- `correlationId` 必须显示在错误提示的"详情"里（客服排查的第一条信息）。

**SSR 调 API 的注意事项（storefront）**

| 项 | 要求 |
|---|---|
| 超时 | **2 秒**（`AbortSignal.timeout(2000)`），可配 `API_INTERNAL_TIMEOUT_MS` |
| 降级 | 商品页/分类页超时或 5xx → 渲染 `+error.svelte` 的"暂时不可用"页，**HTTP 状态必须是 503**（不是 200）+ `Retry-After: 30` + `<meta name="robots" content="noindex">`，**绝不白屏、绝不 500 堆栈、绝不渲染 200 的空壳页**（AC-10 负向断言：空壳页被索引比不索引更糟）；`bootstrap` 失败 → 同样 503 错误页，不做"先出骨架再补数据" |
| 不做重试 | SSR 内**不重试**（用户已经在等，重试只会翻倍等待）。重试交给浏览器（用户刷新）或 CDN |
| Cookie 透传 | 用户态请求（`/cart`、`/account/*`）必须把浏览器的 `Cookie` 头透传给 API（`os_cart`、`os_shop_sid`），且**不要**在 SSR 侧缓存这类响应 |
| 并发 | `+layout.server.ts` 与 `+page.server.ts` 的请求用 `Promise.all` 并行，不串串联（bootstrap 与页面数据无依赖时） |
| 缓存头 | 公开页面由 SSR 设 `Cache-Control: public, max-age=60, stale-while-revalidate=300`；带 cookie 的页面设 `private, no-store` |
| 语言 | 所有 API 调用必须带 `locale`（从路由 `params.locale` 取），不要依赖 `Accept-Language` |
| 金额 | 直接渲染 `amount/100` 并按 `Intl.NumberFormat(locale, {currency})` 格式化，**禁止前端做任何金额运算**（合计、税额一律用服务端返回值） |
| `canSell` | 只用 `bootstrap.store.canSell` 控制"去结算"按钮的禁用与提示文案（`canSell=false` 时按钮禁用 + 显示"本店尚未开通支付"）。**不要**在前端推导 canSell（不要读 `provider`/`credentials` 自己算），也不要在本地缓存超过 1 次页面加载 |
| 绝对 URL | 后端返回的所有 URL 字段（`primaryImage.url`、`ogImage`、`canonical`、`trackingUrl`、`paymentUrl`）**都是绝对 URL**，前端不做拼接；构造 hreflang/og:url 时用 `bootstrap.store.publicSiteUrl` + 当前路径（AC-10 要求不随 `Host` 头漂移） |
| 退款展示 | 订单详情页必须分区渲染三个字段：`status`（状态标签）/ `fulfillmentStatus`（物流区块）/ `refundSummary`（退款区块）；`refundSummary.requiresManualSettlement=true` 时提示"退款将由商家线下处理"（US-E7-07） |

**admin（纯 SPA）**
- 登录态判定只靠 `GET /api/admin/auth/me`（401 → 跳登录页并带 `?next=`）。
- 写操作前必须已有 `os_admin_csrf` cookie；`apiFetch` 自动带上，**不要手动拼**。
- 前端菜单按 `permissions[]` 隐藏 —— 但要明确写进注释：**这不是安全边界**，403 才是。
- 长任务（备份导出、批量操作）用 `202 + jobId` 轮询，不阻塞 UI。

**另外必须做的"反向"测试（容易被漏）**
- 无 `Idempotency-Key` 调 `/checkout/submit` → 400（防前端漏发）。

- 重复点击"生成变体" 3 次 → 变体行数不变（`toAdd` 为空）。

## 12. 风险与待确认

### 12.1 风险

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **价格表形态与架构文档不一致** | 架构 §2.4 写的是 `VariantPrice(VariantId, Currency, AmountMinor)` 子表；主理人裁决"不做多币种表，价格表无 Currency 维度"。本文按裁决执行（价格落在 `Variant` 列上） | 二期加多币种需新增子表 + 数据迁移（**不是零成本**）。已在 §0 与 §11#15 显式登记为技术债。**代价可接受**：MVP 单币种，多一层表只增加 join 与迁移面；**但必须让客户知道这不是"只插行"** |
| R2 | **`RefundFailed` 在状态投影中的位置与 US-E7-02 措辞有张力** | 见 §4.0 ⚠ 与 §12.2 Q1 | 实现上是纯函数一处改动；先用本文取向（失败优先暴露）开发，PM 拍板后改一行 |

| R6 | **`TemplateCompiler` 的确定性 Id 一旦改变会让已初始化库与模板对不上** | 若有人改 `DeterministicGuid` 的算法（如换哈希），同一模板重新编译会产出不同 Id | 算法版本写入 `template.json.defaults.compilerVersion`，编译器版本不匹配直接拒绝（`TEMPLATE_COMPILER_VERSION_MISMATCH`）；算法冻结并加注释"禁止修改" |
| R7 | **Smoke 测试依赖 `FakeGateway` 的语义与真实通道不同** | 真实 Stripe 的异步/3DS/部分退款语义更复杂，Fake 全绿不等于真通道全绿 | `IPaymentGateway` 的 Fake 必须实现"延迟回调""受理中→成功""签名错误"三种真实形态；另有一份 `Stripe` 沙箱手工联调清单（10 项）作为发布前人工门禁 |
| R8 | **`RATE_LIMIT` 在反代后取 IP 可能取到反代 IP** | 所有用户共享一个限流桶 → 全站被限流 | `UseForwardedHeaders` 必须配可信代理（只信任 Caddy 的 loopback），且 `X-Forwarded-For` 取最右非可信项；写进部署文档并加一条集成测试断言 |
| R9 | **`canSell` 只靠"测试连接"与"认证类错误"两个信号判定凭据有效性** | 凭据被通道**静默吊销**（不返回 401，而是所有请求失败）时，`canSell` 可能长时间为 true，用户看到能下单但支付必失败 | 缓解：① `PaymentReconciliationJob` 里对连续 3 次失败的通道调用记 `LastTestFailedAt`（把"功能性失败"也纳入信号，但**必须排除用户侧原因**如余额不足）② 管理端仪表盘常驻显示 `lastTestSucceededAt` 年龄，超过 30 天标黄提示"建议重测"③ 若客户要求更强保证，加一个 `PaymentCredentialHealthJob`（每日一次只读探测，成本极低但会引入"定时打通道"的行为，**默认不开**，见 Q8） |
| R10 | **线下退款（`Mode=Offline`）的"通道无退款能力"是编译期/配置期写死的，不是运行时探测** | 若某个通道后来**新增**了退款 API，适配器不改则一直走线下；反之若通道**停用**退款 API 而我们仍以为支持，会得到一堆失败退款 | 缓解：`SupportsRefund` 在适配器里显式声明 + 写进通道对接文档；每次通道升级必查这一项；`RefundFailed` 里 `category=Unsupported` 时管理端提示"该通道可能已不支持退款，请检查适配器能力声明" |
| R11 | **`PublicSiteUrl` 配错会静默污染 SEO**（canonical/og 全错，但页面看起来完全正常） | 站点被搜索引擎按错误 URL 收录，且**已被索引的错误 URL 难以撤回** | ① 向导里"自动探测 + 人工确认"两步（§5.2），确认页显示最终 canonical 样例让商家肉眼检查 ② 首次访问时若 `PublicSiteUrl` 与请求 `Host` 不一致，日志打 `warn publicsite.mismatch`（不阻断）③ 管理端设置页常驻展示"当前 canonical 前缀" |
