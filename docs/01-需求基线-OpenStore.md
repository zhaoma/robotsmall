# OpenStore 需求基线 v1.18

> 定位：单实例可复用电商独立站母版（非多租户 SaaS）。
> 本文是 Phase 1 唯一需求依据。下游架构 / 数据建模 / 前后端 / 测试均以此为准。
> 不含技术选型、不含表结构、不含 API——那些由其他成员输出。
>
> **⚠️ 效力声明**：**只有本文件是需求事实源。** 任何转发的正文、任何 IM 消息里的需求表述、任何摘要，**均不可作为需求依据**；如与本文冲突，一律以本文对应行号为准。本文每次变更都在下方变更记录表登记，**看变更记录即可判断你手上是不是最新版**。
> **⚠️ 结构规则 1｜物理分区**：**正文（§1~§7）只放当前有效结论**，被推翻的句子一律从正文删除、只登记在**附录 B**。因此——**正文可以无条件信任、不必交叉比对**；变更记录与附录 B 是**追溯区，不参与实现**，仅供回答"这句为什么变成现在这样"。
> **⚠️ 转述约束（消息层，比文档层更危险）**：**消息不是事实源，只是"去找哪一行"的指针。**任何人在消息里声明"结论变了 / 需求改了 / 这条作废了"，**必须附文件路径 + 行号（或 AC/W 编号）**；未附的，一律按"摘要、可能已过期"处理，**回文件取**。<br>> 理由：文档之间的复制已被"引用不复制"约束，但**消息转述这一层此前没有任何约束，而它看起来最像"最新裁定"**。已发生的实例：同一批消息里给出"未译语种回退到默认语言 slug（200 + 回退渲染）"，而该方案早已从数据侧文档删除（它会造出"英文 URL 渲染中文正文"，且使 AC-14a 与 AC-14d 永远无法同时为绿）。**转述会保留旧结论，且不保留旧结论的作废标记。**<br>> **⚠️ 结构规则 4｜"状态 → 行为"必须列全对外可见的每一面**：任何状态映射不得只写主响应。本次索引控制的三面是「**HTTP 响应 / sitemap / 结构化数据**」；<br>> **⚠️ 结构规则 5｜编号永不复用**：**S 编号 / W 编号 / AC 编号 / 变更号（`#N`）/ 注入号（`vN`）一经分配，永不复用、永不改写含义、永不重排**；新增一律往后排，中间留空号也不回收。**且编号只能在产物里分配、不得在消息里口头分配**——口头分配不落盘，两个人可以同时认为自己拿到同一个号，而对账时两边都"有理"。**顺延处理**：撞号时**较早分配者保留原号**，较晚者顺延，并在块头写出"原号 → 新号"**以及旧号在全仓的命中位置**（`grep -rn` 的命令与条数），否则下一个人 grep 旧号会拿到另一条含义不同的记录、且看不出拿错了。理由：编号是他人引用你时的**唯一稳定锚点**——重排一次，所有引用都变成错的，**而且错得看不出来**（它还叫 S9，只是意思变了）。这条比"正文禁版本号"更重要：版本号过期至少能凭时间判断，编号被复用则完全不可检测。<br>> **⚠️ 结构规则 3｜正文禁用版本号**：版本号只允许出现在**本文件头**、**变更记录表**与**附录 B**（那里它是被描述的对象）。**正文（§1~§7）不得出现 `v1.x`**——要表达"依据哪条 AC"，只写 `见 §6 AC-xx`。理由：正文里写"与某版对齐"等于复制一份**需要人工失效的缓存键**，与"结论写两处"是同一个病。**并且：正文里任何"依据 / 作废 / 对齐"的表述，只允许引用 AC 编号或台账 W 编号**（`见 AC-11`、`见 W18`）——**版本号与变更号一律不得出现在正文**。理由：AC 编号语义稳定、W 编号永不复用，而版本号与变更号都是**永远在移动的缓存键**。门禁：`scripts/check-doc-version-refs.sh`（扫 `v1\.\d+`，覆盖 `v1.10 #47` 这种形态，不给 `#` 开例外）。
> **⚠️ 结构规则 2｜引用不复制**：下游文档引用验收标准时，**只写"见 AC-xx"或"见 §6.1 Sn"，不复制判定内容**。需要取证细节时回需求文件取。复制是省一次跳转、换永久漂移——本轮 6 处过时文档全部由此产生。

## 1. 场景定义

### 1.1 一句话项目定义

**OpenStore 是一份交给"想自己开店但不想从零写电商"的中小商家的电商独立站源码母版**——商家自行部署一个实例，用配置向导选定行业模板后，得到一套分类树、属性体系、示例商品、主题和语种都已就位、且能真实收款的店铺，之后只需换商品、换素材、换文案即可营业；而母版维护者只需新增"模板数据包"和"主题包"，就能服务下一个完全不同的行业。

> **关于 AI/智能体：本项目全程不引入大模型或智能体。** 安装向导是确定性的配置向导；商品描述、SEO 文案、翻译均由人工填写。理由：跨境电商的小商家对"AI 自动生成商品描述"没有刚性需求，而引入模型的成本（密钥托管、调用费用、输出不可控、合规）远大于收益。若未来要加，唯一合理的切入点是"批量生成 SEO 标题/描述"（高不确定性、低风险、可人工复核），届时再评估，本期明确不做。

### 1.2 三类角色

#### ① 开店方（部署这套母版的商家）

| 诉求 | 痛点 |
|---|---|
| 30 分钟内把店开起来，不要让我读文档、改配置文件、敲命令 | 常见开源电商（Magento / Saleor / Medusa）安装即是一场硬仗：依赖一堆中间件、要手写环境变量、装完是空白后台，商品分类属性全靠自己从零想 |
| 我不懂电商术语，但我知道我卖什么——希望系统先给我一套"像我这种店"的分类和属性 | 现成系统给的是空壳，或者给一套"通用电商"字段（SPU/类目/品牌），装到"桌面机器人配件"这种窄品类上完全不合身 |
| 换个配色、换张 Logo、调一下首页板块顺序，我自己能搞定，别让我找前端 | 主题只能改 CSS 变量或改代码；改完升级主题就全丢 |
| 我卖到国外去，界面和商品都得是英文，别一半中文一半英文 | 多语种要么只翻 UI（商品还是中文），要么要装插件，翻译字段散落在几十个表里 |
| 我要真收钱、真退款，别给我一个"演示支付" | 支付集成往往是最后的坑：只做前端回到 success 页面就算成功，用户关页面就漏单 |

#### ② 终端消费者

| 诉求 | 痛点 |
|---|---|
| 打开链接 1 秒内看到东西，别白屏 | SPA 首屏白屏；分享到微信/推特没有标题没有图（链接抓取器不执行 JS） |

| 不想注册，填个地址就能买 | 强制注册 |
| 付款失败了我还想再试一次，别让我重新填一遍 | 支付失败回到店铺，购物车空了 |
| 我要能查到我的订单到哪了，退款到没到账 | 只能发邮件问客服 |

#### ③ 母版维护者（我方，未来要加行业模板和主题）

|---|---|

### 1.3 核心场景（3 个）

| # | 场景 | 谁 / 何时 / 做什么 / 期望 |
|---|---|---|
| S1 | **冷启动开店** | 商家拿到代码 → 在自己服务器上启动 → 向导 8 步 → 30 分钟内看到一家"像样"的店并完成一笔真实支付 |
| S2 | **日常经营** | 商家每天：上传/编辑商品与库存、处理订单发货、处理退款、微调首页与文案 |

### 1.4 成功标准（可度量，详见 §6）

- 全新环境从解压到首单支付成功 ≤ 30 分钟，全程零命令行、零配置文件编辑。
- 同一份代码用三个不同行业模板各自初始化一次，业务代码零 diff。
- 新增第 4 个行业模板（非创作者执行）≤ 30 分钟完成且不改代码。
- 商品详情页在 JS 不执行的情况下 HTML 内可 grep 到标题/价格/主图/canonical/hreflang/JSON-LD。

## 2. 核心用户旅程

### 2.1 旅程 A：开店旅程（目标 ≤ 30 分钟，含支付联调）

| 步 | 名称 | 商家要提供什么 | 可否跳过 | 谁执行 |
|---|---|---|---|---|
| A0 | 落地启动 | 无。默认 SQLite、零配置，`dotnet run` 或容器启动即可 | 否 | 自动 |
| A1 | 环境预检 | 无（自动检测运行时版本、目录写权限、端口占用、可写磁盘、时区） | 否（不通过则阻断） | 自动 |
| A2 | **选行业模板** | 四选一：桌面机器人配件 / 女装 / 男装 / 空白。**最终提交（A8）之前可反复回到本步改选**，改选即覆盖草稿 | 否（可"空白"） | 商家 |
| A3 | 店铺信息 | 店名（必填）、经营国家/地区（必填，决定税与地址格式）、时区（必填）、客服邮箱（必填，作发件人/退信）、Logo、favicon | Logo/favicon 可跳过 | 商家 |
| A4 | 语言与货币 | 默认语言（zh/en）、是否启用第二语言、基础货币、重量/尺寸单位 | 除默认语言外均可跳过（取地区默认） | 商家 |
| A5 | 税与运费 | 税率模式（单一税率 / 按地区）、税率数值；运费模式（统一运费 / 满额包邮 / 按重量区间） | **可整个跳过**（默认 0 税 + 0 运费） | 商家 |
| A6 | **支付通道** | 通道选择 + 凭据（如 SecretKey/ClientId）+ "测试连接" | **可整个跳过** → 进入演示模式 | 商家 |
| A7 | 管理员账号 | 邮箱 + 密码 + 确认，强度校验 | 否 | 商家 |
| A8 | 模板数据初始化 | 无。进度条展示逐项：分类树 / 属性集 / 示例商品 / 静态页 / 主题 / 文案 | 否（**失败即整库重置后重来**，不做增量续跑） | 自动 |
| A9 | 完成与锁定 | 无。展示店铺地址、管理端地址、凭据保存提醒、下一步清单 | 否 | 自动 |

**向导的强制语义（需求，非技术）**
- **一次性、可重跑、完成后锁定。** 向导只在"未初始化"状态可访问；完成后：页面路由返回 **404**，任何安装接口返回 **409（AlreadyInstalled）**。
- **提交前只是草稿**：A1~A7 的所有输入（含行业模板选择）在 A8 点"开始初始化"之前不落业务数据，可反复改。这一点让"选错模板"变成零成本。
- **失败语义 = 整库重置后重来**，不做增量续跑、不做逐项回滚。失败后展示"本次已写入的部分数据将被清空，是否重置并重新开始"，确认 → 清空 → 回到 A0/A1。
- **逃生口（运维用）**：提供环境变量开关，允许在"已完成"状态下强制重开向导（用于救砖/迁移），启用时必须伴随一次数据库全量重置且有醒目的破坏性提示；具体变量名与安全约束由架构师/部署文档定，需求只要求"存在、可审计、默认关闭"。
- **模板只在初始化时应用一次**，完成后不提供"换模板"。UI 必须在 A2 明确写"模板仅用于生成初始数据，之后可自由修改；提交前可随时改选，也可用空白模板"。
- A5、A6 可跳过的代价必须当场告知："跳过后店铺处于演示模式/无税状态"，并给出补配路径。

**关键摩擦点（A 旅程）**

| # | 摩擦点 | 后果 | 需求侧缓解 |
|---|---|---|---|
| F-A1 | 商家还没开通支付商户号，卡在 A6 | 70% 的人会在这里放弃或走"假支付" | 允许跳过 + 明确的"演示模式"（可浏览、不可下单）+ 管理端常驻黄色横幅 + 一键回到配置页 |
| F-A2 | 商家不理解自己的税务义务 | 选错税率 → 上线后被追税或收错钱 | 提供"我不确定，先用 0%"显式选项，完成页提示"上线前请咨询你的税务顾问" |
| F-A3 | 商家以为要自己建库/改连接串 | 在 A0 就卡死 | 默认 SQLite 零配置；连接串可选，不填即用默认 |
| F-A4 | 域名 / HTTPS / 公网可达 | 支付回调收不到、网站打不开 | 不在向导内做（属部署范畴），但完成页给出检查清单；且必须提供轮询对账兜底（见 E6-03） |
| F-A5 | 初始化中途失败（磁盘满/网络/字体上传失败） | 半初始化状态，用户不敢重试，也不知道该不该重跑 | 失败即整体回到"未初始化"，提供"重置并重新开始"并**清空本次已写入的全部数据**；**不做增量续跑**——半成品数据是最难排查的故障源，重置重跑是唯一可靠的语义 |

### 2.2 旅程 B：购物旅程（落地页 → 收货）

| 步 | 动作 | 期望结果 |
|---|---|---|
| B1 | 从搜索/广告/社交分享点进商品详情或首页 | 首屏 HTML 已含标题/价格/主图，分享卡片有正确标题与图 |
| B2 | 分类页浏览 + 按属性筛选 + 排序 + 分页 | 筛选条件落在 URL 上（可分享可回退），筛选后 URL 可被索引 |
| B3 | 商品详情：图集 → 选变体（1~3 维） | 选中不可用组合时置灰/禁止；价格、库存、主图随选择即时更新 |
| B4 | 加入购物车（游客可加，本地持久化） | 落地页刷新/关浏览器后购物车不丢 |
| B5 | 结算：填邮箱 → 收货地址 → 选运费 → 看订单摘要（商品小计 + 运费 + 税 + 总计） | 下单前一次性看到最终金额，无隐藏费用 |
| B6 | 提交订单 → 跳转支付通道 | 订单状态 `待支付`，库存已被锁定 |
| B7 | 支付成功 | 回到订单成功页，库存转为已扣减，收到确认邮件 |
| B8 | 商家发货 | 收到发货邮件（承运商 + 运单号 + 查询链接），订单状态 `已发货` |
| B9 | 收到货 / 需要退款 | 可凭订单号 + 邮箱查单；退款后状态与邮件一致 |

**分支（必须定义）**

| 分支 | 触发 | 期望行为 |
|---|---|---|
| B-支付失败 | 通道返回失败/卡被拒 | 订单保留 30 分钟可"重新支付"（保留地址与购物车）；前台明确显示失败原因分类（可重试/换卡/联系发卡行） |
| B-支付取消 | 用户关页面或点取消 | 同失败，但提示语不同；不能出现"钱扣了但订单是失败"的状态 |
| B-支付回调丢失 | webhook 未到达（自托管常见：无公网 IP / 防火墙） | 订单详情页"刷新支付状态"能手动物理纠正；后台定时任务自动核对 |
| B-库存不足（加购后） | 他人先买走 | 购物车与结算页显示"仅剩 N 件/已售罄"，允许改数量再下单，不允许静默失败 |
| B-库存不足（提交瞬间） | 并发抢最后一件 | 下单事务内二次校验；失败时明确告知是哪个 SKU 不足，购物车内容保留 |
| B-未支付超时 | 30 分钟未完成支付 | 订单自动取消，库存回补，可发一封"未完成订单"邮件（Should） |
| B-退款 | 消费者联系客服 | 管理员后台对整单或单个订单行发起退款 → 通道退款 → 状态 `已退款/部分退款` → 邮件 → 库存按规则回补 |
| B-退款失败 | 通道拒绝/原路退回失败 | 状态 `退款处理中/退款失败`，管理端可见失败原因，可重试；**不允许静默失败** |

**关键摩擦点（B 旅程）**

| # | 摩擦点 | 缓解需求 |
|---|---|---|
| F-B1 | 变体不可用组合的表达 | 选完才知道没货是最大流失点 → 变体选择器必须预先置灰不可用组合 |
| F-B2 | 支付失败后购物车丢失 | 订单与购物车都必须在跳转支付前完成持久化，返回后可继续 |
| F-B3 | 运费与税在下单后才出现 | 结算页必须一次算清并展示明细行 |
| F-B4 | 游客查单 | 订单号必须可复制、邮件中带直达查询链接（订单号 + 邮箱校验） |
| F-B5 | 多语言下价格/日期/地址格式 | 金额与日期按语言区域格式化，但记账币种不变 |

### E1 安装向导与行业模板

**US-E1-01｜首次启动自动进入向导**（Must）
作为开店方，我要在浏览器打开地址就直接进入向导，而不是看到一个空白站点或报错页。
- G：全新部署，数据库为空，无 lock 标记
- W：访问站点根路径 `/`
- T：307 跳转到 `/setup`，显示第 1 步；管理端 `/admin` 跳转到"系统未初始化"提示页并给出向导入口

**US-E1-02｜环境预检**（Must）
作为开店方，我要在开始填表前就知道环境有没有问题。
- G：已进入向导第 1 步
- W：向导自动执行预检
- T：逐项显示 `运行时版本 / 数据目录可写 / 上传目录可写 / 端口可达 / 时区识别` 五项，每项 通过/失败 + 修复指引；任一项失败时"下一步"按钮禁用，且不写入任何数据

**US-E1-03｜选择行业模板**（Must）
作为开店方，我要四选一决定初始数据，并且看懂每个模板会给我什么。
- G：预检通过
- W：进入模板选择，展示 4 张卡（桌面机器人配件 / 女装 / 男装 / 空白）
- T：每张卡显示"将创建：N 个一级分类 / M 个属性 / K 个示例商品 / 1 套默认主题"；未选任何一张时不可下一步；卡上含固定文案"模板仅用于生成初始数据，提交前可随时改选；选错不影响后续自由修改"；选择结果以**草稿**形式持久化，刷新页面不丢；**提交前可反复回到本步改选，改选直接覆盖草稿**（此阶段尚未写入任何业务数据）

**US-E1-04｜店铺信息、语言与货币**（Must）
作为开店方，我要一次填完店铺基础信息。
- G：已选模板
- W：填写店名、国家/地区、时区、客服邮箱、默认语言、基础货币
- T：店名/国家/时区/邮箱/默认语言为必填；邮箱格式校验；国家变更时若货币未被手动改过则自动跟随该国默认；Logo 与 favicon 可留空并跳过；重量单位默认公制可改；**必须采集站点公网基址 `PublicSiteUrl`（如 `https://shop.example.com`），提供"自动探测"按钮 + 允许手填**，探测值必须由商家确认后才能进入下一步（反向代理/容器环境下自动探测常出错，而 canonical / og:image / hreflang 的**绝对 URL 依赖它**，填错等于整站 SEO 输出全错）

**US-E1-05｜税与运费基础规则（可跳过）**（Must）
作为开店方，我要么现在配、要么明确跳过。
- G：在税与运费步
- W：设置税率（**统一税率数值 + 是否含税开关 + 暂不设置**）与三选一运费模式（统一运费 / 满额包邮 / 按重量区间）。**分类级税率覆盖不在向导内做**，在分类管理页后续设置
- T：选"暂不设置"时写入税率 0 且完成页出现"你尚未配置税率"提醒；"是否含税"开关必须显式选择（影响前台价格展示文案"含税/不含税"）；填了统一运费但不填金额时禁止下一步；跳过后设置页仍可随时修改，修改不影响已生成的历史订单金额。**MVP 不提供按国家/地区税率表、多税辖区、税号校验**（见 §4.2 裁决 4b）

**US-E1-06｜支付通道配置（可跳过）**（Must）
作为开店方，我要能现场验证支付凭据对不对，也能选择先跳过。
- G：在支付步
- W：选择通道 → 填入凭据 → 点"测试连接"
- T：测试连接返回通道账号标识（如商户号）表示成功；失败时显示通道返回的错误码与可读说明；点"暂不配置"后店铺进入演示模式（前台浏览正常、加购正常、**结算按钮禁用并提示"本店尚未开通支付"**），管理端顶部常驻黄色横幅，点击直达该步骤

**US-E1-07｜创建管理员账号**（Must）
作为开店方，我要创建唯一的初始管理员。
- G：在管理员步
- W：填邮箱 + 密码 + 确认密码
- T：密码强度不足（<12 位或纯数字）时禁止下一步并说明规则；两次不一致禁止下一步；邮箱不得与已存在用户重复；创建成功后该账号可立即登录管理端

**US-E1-08｜模板数据初始化、失败重置与完成锁定**（Must）
作为开店方，我要么一次装成功，要么干净地重来；装完之后不能再被误触。
- G：前 7 步完成（全部为草稿态，尚未写入业务数据）
- W：点"开始初始化"
- T：显示分项进度（分类树/属性集/示例商品/静态页/主题与文案），全部成功后跳完成页；**任一项失败则整体回到"未初始化"状态**并提示"本次已写入的数据将被清空，是否重置并重新开始"，确认后清空并回到第 1 步（**不做增量续跑、不做逐项回滚**）；完成页显示店铺地址（可点击打开）、管理端地址、下一步清单（改 Logo / 配支付 / 配运费 / 检查示例商品 / 上传真实商品 / 提交 sitemap）；**完成后 `/setup` 前端页面返回 404（收敛攻击面），所有安装写接口返回 409 且携带稳定错误码 `SetupAlreadyCompleted`（页面不可见、接口可诊断，两者并存）**；提供**默认关闭的环境变量逃生口 `OPENSTORE_ALLOW_SETUP_RESET=true`**（或等价的 CLI 命令）允许强制重开向导（伴随全量数据重置与破坏性二次确认）；**逃生口开启后的状态码按阶段区分**：重置**进行中** → **503 + `Retry-After` + 错误码 `SetupResetting`**（数据库正在重建，服务真的不可用）；重置**完成**（回到 `Draft`）→ 写接口恢复可用、页面重新可访问。**不得用 409 表达"正在重置"**——409 的语义是"已装好、别再试"，用它表达"等一下"会让运维放弃排障

**US-E1-09｜新增行业模板无需改业务代码**（Must，母版价值的验收门）
作为母版维护者，我要只写数据就能支持第 4 个行业。
- G：已交付三个模板的代码基线
- W：新增"宠物用品"模板（分类树 + 属性集 + 12 个示例商品 + 文案），仅新增模板数据文件
- T：`git diff` 中不含任何 `.cs` / `.svelte` 业务文件改动（允许新增数据文件与资源）；全新实例选择该模板可完整初始化；初始化后前台可按宠物属性（如"适用体型""是否可水洗"）筛选。**此项由非模板作者执行，限时 30 分钟。**

### E2 商品与分类（含多属性 / 变体 SKU）

**US-E2-01｜分类树维护**（Must）
作为商家，我要建树状分类并控制前台顺序。
- G：已登录管理端，具商品权限
- W：新增/改名/删除/拖拽排序分类
- T：支持多级（至少 3 级）；删除有子分类或已挂商品的分类时阻止并提示数量；分类名可逐语言填写；排序结果在前台分类导航与筛选侧栏一致；分类有独立 URL slug，slug 全局唯一

**US-E2-02｜属性定义（可容纳完全不同的属性体系）**（Must）
作为商家，我要能定义"兼容型号"这种配件属性和"版型"这种服装属性，且它们是同一套机制。
- G：在属性管理页
- W：新建属性，设置：名称（可翻译）、类型（单行文本 / 多行文本 / 单选 / 多选 / 数值 / 布尔）、是否用于变体维度、是否可前台筛选、是否必填、所属属性组、单位（如 mm/g）、展示顺序
- T：类型一旦被商品使用后不可变更为不兼容类型（如单选→数值），变更入口禁用并提示；标记为"变体维度"的属性在该分类下最多允许 3 个同时启用，超过时保存被拒绝并说明原因；属性名逐语言可填，未填语言回退默认语言

**US-E2-03｜分类绑定属性集与继承**（Must）
作为商家，我要在分类层面决定"这个类目的商品该填哪些属性"，不要每个商品重复选。
- G：已有分类"服装 > T恤"与属性"颜色/尺码/面料/版型"
- W：在该分类上挂载这 4 个属性并设定必填项

**US-E3-05｜语言路径前缀与 hreflang**（Must）
> **已与架构对齐**：**所有**前台页面路径一律带语言前缀 `/{locale}/`，**默认语种也带**（不做"默认语种省略前缀"）。三条理由：① 路径唯一 → 缓存键唯一、无重复内容、hreflang 映射一一对应；② 语言切换 = 替换 pathname 第一段，"停留在当前等价页面"**天然成立**（无前缀方案必须靠路由 id + params 重建 URL，商品详情的变体/筛选参数一丢就跳回首页——这是最容易漏测的失败模式）；③ **决定性的一条**：US-E3-01 允许商家更换默认语言，若无前缀，换默认语言会让**全站 URL 形态翻转**（原无前缀语种变带前缀、原带前缀语种变无前缀），所有已分享链接与已收录 URL 同时失效，需要维护整张重定向表；全前缀下换默认语言只改 `/` 的 302 目标，**零 URL 变更**。**不做"按浏览器语言自动切换站内语言"**（会破坏缓存一致性并干扰爬虫判断），只做根路径 302。
- G：默认语言 zh，已启用 en
- W：访问 `/`、`/zh/product/xxx`、`/en/product/xxx`
- T：`/` 返回 **302** 到 `/zh/`；`/zh/product/xxx` 与 `/en/product/xxx` 均直接返回 200（不互相重定向）；两页面互相输出 `<link rel="alternate" hreflang>` 双向声明并含 `x-default`；**任何前台页面缺少语言前缀时 302 到带前缀的等价路径**；语言切换生成的是可分享的绝对 URL，且停留在当前等价页面

**US-E3-06｜翻译按 CSV 导入导出**（Should）

- G：结算提交成功，订单状态 `待支付`
- W：点击"去支付"
- T：跳转/内嵌到所选通道的支付页，携带订单号与金额；金额必须由服务端按订单记录传递，不得由前端传入；返回地址由服务端生成并签名

**US-E6-02｜支付回调驱动状态机 + 幂等**（Must）
作为商家，订单是否已支付只能由支付通道说了算。
- G：订单 `待支付`
- W：通道回调"支付成功"通知到达
- T：订单变为 `已支付`，按订单行扣减库存（预占转实扣），写一条支付记录（通道交易号唯一）；**同一回调重复投递 5 次，支付记录仍为 1 条、库存只扣 1 次、不重复发邮件**；回调签名校验失败的通知被拒绝并记录；前端"支付成功页"不能改变订单状态（仅展示）

**US-E6-03｜轮询对账兜底**（Must）
作为自托管商家，我的服务器可能收不到回调。
- G：订单 `待支付` 且通道侧已实际收款
- W：在订单详情页点"刷新支付状态"，或后台定时任务运行
- T：通过查询通道订单状态把订单纠正为 `已支付`；纠正过程与回调路径共用同一幂等逻辑，不产生重复支付记录；订单详情页显示"最后核对时间"；定时任务间隔可配置（默认 10 分钟）

**US-E6-04｜支付失败与重试**（Must）
- G：支付被拒
- W：回到订单结果页点"重新支付"
- T：订单仍为 `待支付` 且在 30 分钟有效期内；重试复用同一订单，不重复创建；失败原因按通道错误码归类为"可重试（余额不足/网络）/需换方式（卡被拒）/需联系发卡行"三类展示；超过有效期后重试按钮禁用并提示订单已取消

**US-E6-05｜订单管理**（Must）
作为商家，我要看单、检索、改状态。
- G：已登录管理端，具订单权限
- W：进入订单列表，按状态/日期/金额/客户邮箱筛选，打开详情
- T：列表分页、可按创建时间倒序；详情显示订单行、金额明细、收货地址、支付记录、库存变动、状态时间线、操作日志；允许人工把 `待支付` 改为 `已取消`；不允许把 `已退款` 改回 `已支付`；任何手工状态变更必须填原因并写审计

**US-E6-06｜交易邮件通知**（Must）
- G：已配置 SMTP
- W：完成下单、发货、退款三个动作
- T：分别发出 3 封邮件，含订单号、金额、明细、店铺联系方式；邮件按订单语言发送（下单时记录的语言）；SMTP 未配置时动作不失败，管理端显示"邮件发送失败（未配置 SMTP）"并可重发；邮件模板文案可翻译

**US-E6-07｜演示模式下单拦截**（Must）
> 判定口径见 AC-17：**`canSell` 是派生值**（= 存在可用支付通道），不可手工翻转。
- G：安装时跳过了支付配置（`canSell = false`）
- W：前台点结算
- T：结算按钮禁用并显示"本店尚未开通支付，暂无法下单"；即使构造请求直接调用下单接口，服务端也拒绝创建订单；管理端顶部横幅可直达支付配置页；配置完成并测试通过后 `canSell` 自动转 `true`、横幅消失、结算可用；凭据失效导致连接测试失败时 `canSell` 自动回 `false`。
  **另两条硬要求**：
  ① **`canSell` 必须同时返回 `canSellReason`（`ok / noCredentials / testFailed / channelDisabled`）**，前台按 reason 区分**文案与视觉**：`noCredentials` = 中性提示"本店尚未开通支付"；`testFailed` = **警告样式**"支付通道连接异常，已暂停下单"并引导商家去修。只给一个布尔值，商家会"不知道该去修什么"——僵尸订单风险有一半来自这里。reason 不得泄露凭据内容等敏感信息。
  ② **服务端必须在"结算确认"与"重新支付"两个动作上再校验一次 `canSell`**。前端禁用按钮只是体验，服务端拒绝才是边界；且 `canSell` 可能在页面渲染与提交之间翻转（TOCTOU），不二次校验仍能造出僵尸订单。

### E7 履约与售后

**US-E7-01｜发货**（Must）
- G：订单 `已支付`
- W：填入承运商与运单号，点"标记已发货"
- T：订单变为 `已发货`，记录发货时间；承运商从可维护列表中选（默认含常见快递与国际承运商，可增删）；运单号格式校验（长度/字符集）但不校验真实性；发出含运单号与承运商查询链接的发货邮件；状态变更写审计

**US-E7-02｜取消订单**（Must）
- G：订单 `待支付` 或 `已支付未发货`
- W：管理员取消订单
- T：`待支付` 取消后订单变 `已取消` 并回补库存；`已支付未发货` 取消时必须走退款流程（先退款成功再变 `已退款`），退款失败则保持 `已支付` 并提示；已发货订单不允许直接取消，只能走退款

**US-E7-03｜消费者查单**（Must）
- G：游客下单，仅有邮箱与订单号
- W：访问订单查询页，输入订单号 + 邮箱
- T：校验通过后展示订单状态、明细、金额、物流（运单号 + 承运商链接）；状态文案按订单语言显示；订单号 + 邮箱不匹配时统一返回"未找到该订单"（不泄露订单是否存在）；邮件中的直达链接可免输入打开同一页面

**US-E7-04｜【订单域】退货申请状态流转**（Should）
> **已与架构对齐**：退货申请属**订单域**，只做状态流转与留痕，**不产生任何支付动作**。
- G：消费者在查单页，订单状态 `已发货` 或 `已完成`
- W：点"申请退货"，选择订单行、数量、原因、备注
- T：生成退货申请记录（状态 `待处理`），订单打上"有退货申请"标记；管理端可见并可"同意 / 拒绝（必填理由）"；同意后订单状态不变、仅解锁"发起退款"入口；拒绝后订单状态不变且不可再对该行重复申请同一事由；申请/同意/拒绝各发一封通知邮件；**全程不调用支付通道、不产生退款单**

**US-E7-05｜【订单域】退款单发起与金额校验**（Must）
> **已与架构对齐**：本故事只负责"在订单上生成一张合法的、金额正确的退款单"，**不承诺钱已经到账**（到账见 US-E7-06）。
- G：订单 `已支付`（金额 300）或 `已发货`；其中一行商品单价 100、数量 2
- W：管理员对**整单**发起退款，或对**某订单行**发起部分退款（可指定数量）
- T：退款金额 = 该范围内订单行实付金额之和（含分摊的运费/税按规则处理），**不得超过该订单已收金额减去已退金额**；发起时必填原因；生成退款单（状态 `待执行`，含金额、范围、操作人、原因），写审计；**同一订单行的累计退款金额不得超过其行实付金额**（超出时保存被拒并提示可退余额）；发起后订单状态进入 `退款中`，但**不因本次操作变 `已退款`**

**US-E7-06｜【支付域】退款执行、通道回执与失败重试**（Must）
> **已与架构对齐**：退款执行属**支付域**，**以支付通道回调/查询结果为唯一事实来源**，与支付成功共用同一套幂等与对账机制。
- G：存在一张 `待执行` 退款单
- W：系统向通道发起退款；通道异步回调或查询返回结果
- T：通道返回成功 → 退款单变 `已成功`，订单相应变为 `已退款` 或 `部分退款`，按规则回补库存（默认回补，可勾选"不回补"并必填原因），发退款通知邮件，前台查单页显示退款金额与状态；通道返回处理中 → `处理中`，通过查询更新为最终态；通道返回失败 → `失败` 并记录通道错误原因，**允许重试且重试不产生第二笔退款**（同一退款单幂等）；**同一退款回调重放多次，退款记录仍为 1 条、库存只回补 1 次**；`失败` 状态不允许被人工直接改成 `已成功`

**US-E7-07｜【支付域】通道不支持退款时的线下退款降级路径**（Must）
> **背景**：支付通道未定，且存在"只支持收款不支持退款 API"的通道（部分本地通道如此）。若不定义降级路径，一旦选中这类通道，退款闭环直接断裂、AC-09 无法通过。
> **对齐架构**：`IPaymentGateway` 暴露**能力位**（Webhook / Query / Refund / PartialRefund），管理端展示"当前通道能做什么"，商家不用猜。
- G：当前支付通道的 `GatewayCapabilities` 不含 `Refund`
- W：管理员对订单发起退款（US-E7-05）
- T：系统**不调用**通道退款接口，**`Refund.Status = AwaitingManual`**（内部状态，**订单状态机不新增分支**），并强制要求管理员填写**线下退款凭证号**（如银行流水号/转账单号）+ 退款日期，填写后手动标记 `已成功`；`Provider = manual`、`ProviderRefundId` = 凭证号。
  **对外投影**：消费者侧（订单详情、查单页、通知邮件）统一投影为 `RefundStatus = Processing`，文案"**退款处理中**"，**不向消费者暴露"线下/人工"实现细节**；**运营端**单独展示"线下退款"标记 + 凭证号 + 操作人 + 日期。
  **红线**：金额快照与报表口径必须与线上退款**完全一致**（不得为降级路径另建一套状态或另算一套金额）；审计记录"线下退款 + 凭证号 + 操作人"。
  **能力位为 `PartialRefund` 缺失时**，只允许整单退款，部分退款入口禁用并说明原因。

### E8 管理端通用能力

**US-E8-01｜登录与会话**（Must）
- G：已有管理员账号
- W：访问 `/admin`，未登录；输入正确凭据登录；空闲 2 小时后操作
- T：未登录访问任何管理端页面重定向到登录页，未登录调用任何管理接口返回 401；登录成功后进入仪表盘；会话空闲超时（默认 120 分钟，可配置）后需重新登录；登出后回退按钮无法回到已登出页面

- W：创建一个"员工"角色账号

### E9 非功能（性能 / SEO / 安全 / 备份）

**US-E9-01｜公开页面服务端渲染可索引 HTML + 社交分享卡片**（Must，关键裁决）
> 这是引入 SSR 的**唯一理由**，因此必须写成可验证的验收项，不能停在"用了 SSR 框架"。
作为商家，我要我的商品能被搜索引擎收录、能被微信/Facebook 正确生成分享卡片。
- G：商品已上架
- W：（a）`curl -s https://<店铺>/zh/product/<slug>`（**不执行任何 JS**）；（b）把同一 URL 贴进微信、Facebook、X/Twitter
- T：（a）返回 HTML 中可 grep 到：商品标题、价格（含货币）、主图绝对 URL、可售状态、`<title>`、`<meta name="description">`、`<link rel="canonical">`、`hreflang`、`OG/twitter` 标签、JSON-LD `Product` 含 `offers.price` 与 `availability`；首页、分类页、静态页同样要求正文商品/分类信息在初始 HTML 内。
  （b）**分享卡片必须出现商品标题与商品主图缩略（非空白灰卡）**；`og:title`、`og:description`、`og:image`（1200×630 以上、**绝对 URL**、可匿名访问）、`og:url`、`og:type=product` 全部存在且取值正确；分类页与首页分享卡片同理（用分类名/店名与对应图）。
  （c）**负向要求**：所有绝对 URL 必须基于 `PublicSiteUrl` 生成（**不得用请求 Host 头**）；当后端数据不可用时，商品/分类页必须返回 **503** 或带 `noindex` 的错误页，**严禁返回 200 的空白商品页**——空壳页被索引比不索引更糟。
  **为什么禁用 Host 头（这不是洁癖，是可被主动利用的攻击）**：攻击者构造带伪造 Host 的请求，即可让服务端把 `canonical: https://evil.com/...` 输出到一个可被爬虫访问的 URL 上，**等于把商品页的索引权重整体转让给攻击者**。"探测一下再兜底"不足以防御——`PublicSiteUrl` 必须是配置项，且**优先级高于任何请求头**。

**US-E9-02｜sitemap / robots / 重定向**（Must）
- G：店铺有 100 个已上架商品、8 个分类、3 个静态页
- W：访问 `/sitemap.xml` 与 `/robots.txt`
- T：sitemap 可访问、为合法 XML、条目数 = 已上架商品 + 分类 + 静态页（按语言分别输出并互相 hreflang）；下架商品不出现在 sitemap；**robots.txt 与页面级索引控制必须按 AC-11 的"索引控制矩阵"五档分治（(a) 私有页 / (b1) 筛选参数页 / (b2) 站内搜索 / (b3) 商品详情 / (c) 管理端），且"每档只用一种信号"：`noindex` 与跨 URL 的 `canonical` 不得同时用，`Disallow` 不得与任何前台索引信号同时用；`robots.txt` 全文只剩 `/api` 一条——见 AC-11 说明与 §6.1 判据**；修改商品 slug 后旧 URL 301 到新 URL（保存时记录历史 slug）

**US-E9-03｜性能预算**（Must）
- G：基准数据集 = 10,000 商品 / 50,000 变体 / 每分类 500 商品，单机 2 核 2GHz / 2GB，SQLite，无外部缓存
- W：访问首页、分类页（每页 24 商品）、商品详情页
- T：服务端首字节 TTFB ≤ 500ms（P95）；Lighthouse 移动端模拟下 LCP ≤ 2.5s、性能分 ≥ 70；**筛选条件变化后列表更新 ≤ 800ms（客户端路由局部取数路径；不要求整页刷新路径满足此指标，否则会把"必须整页 SSR 重渲染"写进需求而自缚手脚）**；管理端商品列表 5,000 行分页打开 ≤ 1.5s；稳态三进程合计 RSS ≤ 2GB 不 OOM

**US-E9-04｜安全基线**（Must）
- G：站点已上线
- W：执行下列检查
- T：（1）所有管理接口未登录返回 401、越权返回 403；（2）商品描述注入 `<script>alert(1)</script>` 前台不执行、不破坏布局；（3）支付回调伪造签名被拒；（4）**系统任何位置不存储完整卡号/CVV，库内与日志中均搜不到 16 位连续卡号**；（5）上传仅允许白名单扩展名且不可执行；（6）非 HTTPS 请求重定向到 HTTPS（可配置强制开关）；（7）响应头含 CSP 基础策略、X-Content-Type-Options、Referrer-Policy；（8）管理端与结算接口有基础限流

**US-E9-05｜备份导出与恢复**（Must）
- G：店铺有 500 商品与 200 订单
- W：管理端点"导出备份"，下载一个包含数据库与上传文件的压缩包；在空白环境按文档恢复
- T：导出包内含数据库快照与全部上传文件；恢复后商品数、订单数、图片可访问性与备份时一致；恢复流程不超过 3 条命令（文档内）；导出过程不锁站（可继续浏览）；导出不包含支付凭据明文（凭据需在恢复后重填，文档说明）

**US-E9-06｜图片处理**（Must）
- G：上传一张 3000×3000 的 6MB jpg
- W：前台访问商品列表与详情
- T：自动生成列表缩略（约 400px）与详情（约 1200px）两个尺寸，现代浏览器优先返回 webp；原图不直接用于列表；单张图上传后 10 秒内可访问；图片 URL 稳定（含内容指纹，改图后 URL 变化）

**US-E9-07｜可访问性最低要求**（Should）
- G：完成结算流程
- W：仅用键盘操作
- T：所有表单控件有关联 label；焦点可见；Tab 顺序符合视觉顺序；商品图有必填 alt（上传时未填则保存时警告）；正文文字对比度 ≥ 4.5:1（主题编辑器给出警告）

### 4.2 五个关键裁决（含理由）

#### 裁决 1：多语言是"全部内容可翻译"还是"仅 UI + 商品"？

**结论：全部面向终端用户可见的内容都必须可翻译** —— UI 文案、商品（标题/描述/规格参数值）、分类名、属性名与属性值、静态页、主题内文案、邮件模板、状态文案。
**不需要翻译**：管理端内部字段（员工备注、SKU 编码、内部供应商名）、系统日志、审计原因。

理由：
1. **属性名必须翻译，这是本母版能否用于英文站的分水岭。** 只翻 UI 不翻属性，英文站的筛选侧栏会显示"兼容型号 / 接口类型"——一个英文访客看到中文筛选器，信任直接归零。
2. **分类名必须翻译**，否则英文站的导航是中文。
3. 成本可控的关键在于**范围收敛**：只对"终端用户可见字段"建翻译，管理端内部字段不建。真正贵的是给每个表加 `NameEn/NameZh` 这种列式方案——它会随语种线性膨胀且无法支持第 3 语种；需求上必须约束为"实体 + 语言 → 译文"的通用形态（具体建模归数据建模师）。
4. 中文/英文体量在 MVP 可控：属性名约 60 个、分类约 20 个、示例商品约 36 个、UI 文案约 400 键，一次性人工翻译约 1.5 人日。

**代价与已知取舍**：MVP 会出现"某些字段未译"的状态，因此**必须**有回退策略 + 覆盖率提示（US-E3-04、E3-03），否则英文站会随机出中文而无告警。

**两类文案必须分开管理（已与架构对齐）**

| 类别 | 内容 | 维护方 | 管理端能力 |
|---|---|---|---|
| **UI 文案** | 按钮、提示语、表头、状态词、校验消息 | 开发者（内置键集合） | 商家**只能覆盖个别键的译文**，不能新增键、不能改键名 |
| **业务内容** | 商品名/描述、分类名、属性名与属性选项、静态页、主题内文案、邮件模板 | 商家（后台实体数据） | 每个可译字段**分语言填写**，新增语种自动出空字段（带"未译"标记），零建表变更 |

**URL 形态（已与架构对齐）**：所有前台页面路径一律带语言前缀 `/{locale}/`，**默认语种也带**；根路径 `/` 302 到 `/{默认语种}/`；不做"按浏览器语言自动切换站内语言"。理由：路径唯一 → 缓存键唯一、无重复内容、hreflang 一一对应；自动切换会让同一 URL 返回不同内容，同时破坏缓存与爬虫判断。

#### 裁决 2：变体 SKU 深度——多维矩阵？独立库存？独立图？

**结论：支持，且是 Must，不可裁剪。**
- 支持 **1~3 维**属性组合生成变体矩阵；硬上限 3 维（超过时拒绝并说明原因），防组合爆炸。
- 每个变体拥有**独立 SKU 编码、独立价格、独立库存、独立图片（可选）、独立条码（可选）、独立启用状态**。
- **不支持**：每变体独立富文本描述、独立属性集、独立分类。

理由：
1. 女装/男装的"颜色 × 尺码"是这一品类存在的形式，不是"进阶功能"。砍掉矩阵 = 服装模板不成立 = 母版只能用于配件 = 复用价值归零。
2. 桌面机器人配件虽然多数是单规格，但"兼容型号 × 接口类型"在某些品类（如多规格适配器）就会用到，统一模型比分叉出"简单商品/变体商品"两套模型更省代码（DRY）。
3. 上限 3 维是刻意的 YAGNI 约束：4 维以上（颜色×尺码×材质×长度）在小店几乎不出现，却会让编辑 UI 与管理复杂度陡增。

#### 裁决 3：会员体系——游客下单？积分/等级/优惠券？

| 子项 | 结论 | 理由 |
|---|---|---|
| 游客下单 | **允许**（Must） | 冷启动店铺流量极贵，强制注册是最容易砍掉的转化流失。仅需邮箱即可下单与查单 |
| 账户体系 | **做，但极简**：注册/登录/找回密码/订单列表/单一默认地址 | 复购要靠账户，且账户是"查单"的自然归宿；但多地址簿、消息中心是纯成本 |
| 积分 / 等级 | **不做** | 前提是有复购基数。为零复购的店做积分，等于做一个没人看的排行榜 |
| 优惠券 | **不做**（Deferred） | 优惠券带来"叠加规则、门槛、有效期、限用次数、与退款回冲"一整套计价逻辑，是订单金额复杂度的头号来源；本期订单金额结构保留折扣位（恒 0），二期加券不动结构 |
| 商品评价 | **不做** | 需要审核、反垃圾、图片上传、评分聚合与结构化数据，且冷启动期没有评价 |

**代价**：没有优惠券意味着商家做不了"满减活动"开业促销——这是真实损失，必须让客户知晓并签字确认（见 §7.2 Q5）。

#### 裁决 4：多货币——MVP 就做，还是单货币 + 展示换算？

**结论：MVP 只做单一基础货币（记账 + 展示 + 支付全部同一币种），不做展示换算。**

理由：
1. **展示换算会制造真实纠纷。** "页面显示 €9.9，实际扣款 $11.2"——汇率浮动 + 支付通道换汇费 + 发卡行手续费，三笔叠加后差额可观，是独立站投诉与拒付（chargeback）的常见来源。
2. **多货币会与税务规则乘出组合爆炸**：同一商品在每种货币下都要有价目，税规则、包邮门槛、运费区间都要按币种重算。这对 6~8 周的单人项目是灾难。
3. 三个目标模板（机器人配件 / 女装 / 男装）的典型客户是"本国 + 少量跨境"，单币种 + 一个跨境通道（如 PayPal 自动换汇）已能覆盖。

**但必须做到（零成本的可观测要求）**：
- 安装向导必须选定基础货币；所有价格、订单、退款、报表均携带货币代码并落库；前端格式化按语言区域显示但币种不变。
- 商品价格表结构上按"变体 × 币种"设计（本期只有一行），二期加币种无需改表（具体归数据建模师）。

#### 裁决 4b：税务规则收敛为"统一税率 + 分类级覆盖 + 是否含税开关"

**结论（已与架构对齐）**：MVP 只有三项——① 一个统一税率数值；② 可在**分类**上覆盖该税率（用于"某类商品免税/低税率"）；③ 一个"价格是否含税"的全局开关（决定前台文案与订单金额拆解方式）。
**明确不做**：按国家/地区税率表、多税辖区、B2B 反向征收、税号校验、欧盟 VAT MOSS、美国各州 sales tax。

理由：税制是**按国家无限展开**的领域，任何"半套税制"都比"一套明确的最简税制"更容易出错且更难解释。小店（三个目标模板）的真实诉求是"我知道我收几个点"，而不是"系统帮我算清跨境税"。把它做成最简形态并写进文档边界，比做一半多辖区规则后被商家误用要安全得多。

**代价**：跨境卖家若真有多辖区税务义务，只能靠"分类级覆盖"手工近似，或在支付通道侧处理。此项必须在部署文档里显式写明，避免法律风险被误认为产品责任（见 §7.2 Q4）。

#### 裁决 5：SEO——SSR 还是 CSR？（关键裁决点）

**结论：需求上明确要求"公开商城页面必须服务端渲染出完整可索引 HTML"。这是 Must，不是优化项。纯 CSR 的 SPA 不满足本需求。**

理由（按重要性）：
1. **社交分享的 Open Graph 抓取器一律不执行 JavaScript。** 微信、WhatsApp、X/Twitter、Facebook、Slack、Discord 的链接预览抓取全部是"GET 一次 HTML 然后读 meta 标签"。CSR 站点分享出去的是一张无标题、无图的灰卡片。对独立电商站，这几乎等于断掉社交传播这一条低成本流量渠道——这不是"慢慢被索引"的问题，是"永远抓不到"。
2. **搜索引擎能跑 JS ≠ 能可靠索引。** 渲染排队、超时、二次改写、分页与筛选参数组合的抓取预算问题，都会让商品页长期不被收录。对 SKU 数量少、外链少的新站，收录速度就是生死线。
3. **首屏体验与转化**：白屏 1~2 秒的移动端流失是可以直接观测的收入损失。
4. **反面代价可接受**：SSR 会让前端工程复杂度上升（主题包需在服务端可渲染），但这是本产品的核心矛盾——"要能换主题"和"要能被搜到"都是硬需求，只能两者都要。

**边界（哪些页面不强求 SSR）**：管理端全部、购物车、结算、支付结果页、账户中心 —— 这些不需要被索引，CSR 即可，且能明显降低复杂度。

**必须同时交付的 SEO 配套**（否则 SSR 只解决了一半）：结构化数据 JSON-LD、canonical、hreflang 双向、sitemap 分语言输出、robots、slug 变更 301、语言前缀 URL 策略（§US-E3-05，**全带前缀 + 根路径 302**）。

**验收锚点（必须写死，不能停在"用了 SSR 框架"）**：把商品 URL 贴进微信与 Facebook，预览卡片要出现**正确的商品标题与主图缩略**（`og:image` 为绝对 URL、可匿名访问、≥1200×630）。这是判断"SSR 是否真的落地"最廉价也最不可造假的手段——见 AC-10。

> **给架构师的提示（不是技术选型，是约束）**：这条需求意味着前端框架必须支持服务端渲染，且主题包必须能在服务端被渲染。请据此评估双入口方案。

## 5. 优先级

### 5.1 评分口径

RICE = (Reach × Impact × Confidence) / Effort
- **Reach（1-5）**：该功能被多少条主旅程路径依赖（5 = 几乎每条路径都经过）
- **Impact（1-5）**：缺失时对"能不能开店/能不能收钱"的破坏力（5 = 直接阻断交易闭环）
- **Confidence**：0.5 需求有歧义 / 0.8 方向明确但有欠确认项 / 1.0 已完全确定
- **Effort（1-5，人日档）**：1 = ≤2 天，2 = 3~5 天，3 = 6~10 天，4 = 11~20 天，5 = >20 天

### 5.2 排序结果（按 RICE 降序）

### 5.3 只能做 60% 时先砍哪些

## 6. 可度量验收标准（上线验收清单）

> 每条都可被测试工程师直接执行。全部通过 = MVP 可上线。
> **两条执行前提**：① AC-14 依赖一套"en 100% 已译"的专用 fixture——其内容范围由产品定义（见下方"fixture 四个必备样本"），**由 data-engineer / frontend / backend 三方各交一块**，**属于 MVP 交付物，不是测试临时造数**；② AC-10 的分享卡片检查需真实可外网访问的地址（本地 localhost 无法被微信/Facebook 抓取），部署环境确认前该项只能部分验证（见 Q7）。
>
> **AC-14 的 fixture 分两档装载，验收时按 AC 选档（缺这条会产生假缺陷）**
> 同一个 fixture 无法同时满足"14a 要求 en 零中文"与"14d① 要求某字段回退中文"——只要回退样本在，14a 遍历到那页就必红。因此：**一个数据源 + 一个受控探针开关**（不是两个 fixture 目录，否则两份内容立刻漂移成两套商品；也不是"让 14a 跳过某样本"，跳过逻辑会掩盖真实漏译且下一个人不知道该跳谁）。

| 档 | 装载 | 内容 | 允许跑 |
|---|---|---|---|
| **全译档（默认）** | `fixture load i18n-en-100` | **上一张表所列样本全部在场**，不含回退探针样本 | **AC-14a / 14b / 14c** |
| **回退探针档** | `fixture load i18n-en-100 --probe fallback` | 在全译档之上**仅把指定样本的某字段 en 置为空串**，其他一格不动 | **仅 AC-14d①** |

> **护栏**：① **探针档下不得跑 AC-14a/14b/14c**（否则必红且是假缺陷）；② 脚本必须把 `fixture-mode: full | fallback-probe` 写进输出，**没有这一行则判定结果不可采信**（防止"在哪个档上跑的"事后无从追溯）；③ 探针只能"置空某字段"，**不得新增/删除实体**（否则档间内容漂移）。

筛选/排序 × 分页的交集**（此前未定义，实现曾出现两种自洽读法）：**只要 URL 带任何筛选/排序参数，不论第几页，`canonical` 一律指向该分类页的无参数第 1 页**；**"分页第 2 页起 `canonical` 自引用"仅适用于不带任何筛选/排序参数的分页**。理由：① 归并到 `?page=2` 是错的——`?f.interface=usb-c&page=2` ### 6.1 AC-11「索引控制」的语义断言（判据唯一载体：`scripts/verify-seo-matrix.sh`）

> **本节只规定"必须被断言的语义"，不写具体命令。** 机器判据集中在 `scripts/verify-seo-matrix.sh`（部署侧交付物），它以被测站点地址为入参、逐条断言下列 S1~S11，任一失败即非零退出。
> **为什么不再在需求里写 curl**：同一份清单曾在需求/架构/后端/前端/运维五处各存一份，改一处必漏四处——W9/W12/W14/W15/W16 五条台账全部由此产生。**一份判据、一处维护。**
> **脚本缺失或未覆盖下列任一语义 → AC-11 判为未通过，不得记为"跳过"。**<br>> **但"脚本全绿"不是 AC-11 的充分条件**：AC-11 (b3) 里「替代分类页取最深」这一子句**不在**本脚本的断言范围内（S9 只到 `/c/*` + 落点 200），它由 **fixture 级 E2E** 断言。**AC-11 通过 = 本脚本全绿 且 该子句 E2E 绿**；两处都写"绿"才算，不得以"脚本全绿"单独放行——否则那条子句就是一条**零覆盖**的行为规则。<br>> **规则 4（slug 变更 → 301）的载体已在 S9 内（一对入参）**：S9 的第 4 个对象是「**改过 slug 且仍 `Active`**」的商品——用它的旧地址请求，必须 **301 到新地址**（`--moved-from` / `--moved-to`）。它与「归档商品的历史 slug → 410」是**同一条实现路径的两个分支**（都从 `SlugHistory` 入口、都由「先解析实体、再按状态分派」决定响应），因此**必须成对验、不得分裂成两个编号**：分裂之后改一处忘另一处，而它们本来是一个 `if/else`。<br>> **为什么这一格不能省（它补的是上面那条判据的洞）**：「历史 slug 不得带 `Location`」是**纯禁止项**，而 **`SlugHistory` 完全不实现时，历史 slug 会返回 404——404 本来就不带 `Location`**，于是那条断言一路绿，看起来"验过了"。凡「X 时不得输出 Y」，必须配一条「Z 时必须输出 Y」，且对照组要来自**同一条件为真的另一侧**（这里两个对象入口形态完全相同、走同一个 resolver，唯一差别是实体当前状态）。**只写禁止项，等于给"什么都不做"发了一张通过证。**<br>> **残留风险与兜底**：SlugHistory **完全漏实现**会被 S9 的第 3、第 4 两个对象同时抓住（一个该 410 却 404、一个该 301 却 404）；但"**301 目标路径拼错**"（如分类跳到 `/products/`）在归档分支抓不住 —— 那一侧靠 S9 第 4 个对象的**目标比对**（`Location` 必须等于 `--moved-to`）证明这条机制真的在按 `EntityType` 分派。<br>> **红在哪一侧必须写在判据旁边**：S9 的「落点 200」与「历史 slug 410」两条在补齐前，**AC-11 必然红**——这是**实现缺口**，不是判据过严。**不得为了让 AC-11 变绿而放宽、拆分或删除这两条判据。** 理由：判据长期红之后，下一个人的第一反应是"这条太严"，而不是"这条没实现"，而两者的修法**方向相反**——一个改代码，一个改判据，而后者**便宜且立刻变绿**。<br>> **退出码语义（三方必须一致，否则"红"会被当成"没跑"）**：**`0` = 全部通过**；**`1` = 有断言失败**；**`2` = 前置数据缺失**（找不到断言所需的 fixture 样本、站点不可达等）。**`2` 一律等于"未验证"，而"未验证"按本文件口径就是 AC-11 未通过**——**不得降级为警告、不得标记跳过、不得计为通过率的分母外**。理由：没有样本时脚本若静默变绿，"缺 fixture"就会变成一条永久的假绿通道。

| **S8** | 全局交叉校验（**两条硬红 + 一条不计红的告警**）：<br>红① 任一 URL **不得同时**命中 `Disallow` 与 `noindex`；<br>红② 任一 URL **不得同时**命中 `Disallow` 与**外指** `canonical`；<br>红③ 任一 URL **不得同时**输出 `noindex` 与**跨 URL 的** `canonical`；<br>**告警（不计红、不计入通过条件）**：`noindex` 页面上**自指** `canonical`——**"自指"必须在规范化后判定**：先剔除 `utm_*`/`gclid` 等追踪参数、统一尾斜杠、参数排序，再看是否等于自身 URL；**规范化后仍不相等即按"跨 URL"判红**（否则"看着自指、实则带追踪参数"的写法会被放过） —— 规范上冗余无害（canonical 指向自身，不污染任何其他页面），但**不得**因此去删除它：模板统一输出 canonical 是正常实现，为过门禁而在 noindex 页删 canonical 属无意义改动，且会让页面失去自我描述 | 通过 |
| **S9** | **归档商品页三响应**：`Archived` 且有替代分类页 → **301** 到该分类页；`Archived` 且无替代 → **410 Gone**（**不是 404**）；**同一归档商品的"历史 slug"必须得到完全相同的响应**——用"归档且无替代"那个商品的历史 slug 请求，必须 **410**，**不得 301 到新 slug**（见 AC-11 (b3) 判定顺序）。**对象集** = 「当前 slug」× 2 个归档商品 + 「无替代那个商品的历史 slug」× 1 + **「改过 slug 且仍 `Active` 的商品」的一对（旧地址 → 新地址）**；两个历史 slug 均由 fixture 声明为**固定值**（见 `docs/02` 的 S9 样本行），**缺任一条记录 = S9 前置数据缺失 = rc=2**。钉「无替代 × 历史 slug」这一格的理由：两跳 301 的后果远轻于 `301 → 410`，而两者由同一条实现覆盖（"先按 slug 解析实体、再按状态分派"），钉最坏的一格即可 —— **样本可以苛刻，判据不能苛刻**，但最坏的那条必须钉。**第 4 个对象（`Active` 的旧地址）"不得省略"的理由**：它是第 3 个对象那条**纯禁止项**的对照组——SlugHistory 完全不实现时历史 slug 返回 404、不带 `Location`，禁止项判据照样绿；只有"该 301 的必须 301"能证明这条机制存在。该对象的 `Location` **必须等于 `--moved-to`**（不是"某个返回 200 的页面"：跳到别处时落点照样 200，日志里看不出异常）。**`Location` 只断言到 `/{locale}/c/*` 且落点返回 200，不判"取了哪一层"**（"取最深"由 fixture 级 E2E 断言，见 AC-11 (b3) 的断言层次） | 通过 |
| **S10** | **在售但库存 0 的商品页**：返回 **200** 且结构化数据 `availability=OutOfStock`（**不得 404/410、不得 noindex**）；且**该 URL 仍在 `sitemap.xml` 中**；已归档商品的 URL **不在** sitemap 中 | 通过 |
| **S11** | **管理端 `/admin` 可达（200）且响应带 `X-Robots-Tag: noindex`，且未出现在 `Disallow` 中** | 通过 |

> **S7 的期望是"只有 `/api`"，不是"缺了前台路径"**——这是正确状态，QA 与脚本都不得把"前台没有 Disallow"记为缺陷。
> **S8 是最高优先项**：除 S8 之外的任意两档同时成立时，S8 必须红——它是"指令互相抵消"的总闸。（这里不逐一列举档号：矩阵会扩张，列举必然漏；"除 S8 外全部"才是这条判据真正的语义。）

**六档 × S1~S11 覆盖矩阵（双向必须成立）**

> **为什么要有这张表**：判据收敛到单个脚本之后，**脚本漏一档，那一档就彻底没人管**——以前分散在三份文档里，漏一处还有别处兜。这是单点收敛的内在代价，必须用矩阵对冲。
> **两条硬性约束**：① **每一档至少被一个 S 覆盖**（否则该档没有判据）；② **每一个 S 至少覆盖一档**（否则该条断言没有对象，是空转）。架构侧会在 QA 交回后做反向核对，专找"有 S 但无用例指向"。

| 档 | 场景 | 覆盖它的 S |
|---|---|---|
| **(a)** | 私有页（购物车/结算/支付结果/账户/订单查询/安装向导） | **S1**（noindex + follow）、**S2**（不在 Disallow）、S8 |
| **(b1)** | 带筛选/排序参数的分类页（含带筛选的第 2 页） | **S3**（canonical → 无参数第 1 页）、S7、S8 |
| **(b1∩分页)** | **不带**筛选/排序的分页第 2 页起 | **S4**（自引用）、S7 |
| **(b2)** | 站内搜索 | **S6**（noindex、不输出 canonical、不在 Disallow）、S7、S8 |
| **(b3)-商品** | 商品详情（含 `utm_*`） | **S5**（自引用且不含追踪参数）、S7 |
| **(b3)-归档** | `Archived`：有替代分类 → 301；无替代 → **410** | **S9**、**S10**（不在 sitemap） |
| **(b3)-缺货** | `Active` 且库存 0 | **S10**（200 + `OutOfStock` + **在 sitemap**） |
| **(c)** | 管理端 `/admin` | **S11**（`X-Robots-Tag: noindex` + 不在 Disallow） |

**反向核对（每个 S 至少一个对象）**：S1→(a) · S2→(a) · S3→(b1) · S4→(b1∩分页) · S5→(b3)-商品 · S6→(b2) · S7→(a)/(b1)/(b2)/(b3) 全体 · S8→全体交叉 · S9→(b3)-归档 · S10→(b3)-归档+(b3)-缺货 · S11→(c)。**无空转项。**

**三步判别口诀（必读，本节结论已被误读 4 次）**

第 1 步问「**该不该被收录**」，第 2 步才问「**怎么归并**」，第 3 步**永远不用 `Disallow` 表达"不收录"**。

| 步骤 | 问题 | 答案 → 动作 |
|---|---|---|
| 1 | 这个页面**该不该**出现在搜索结果里 | **不该**（购物车/结算/账户/查单/向导/**站内搜索**）→ `noindex,follow`，**不输出 canonical**，**不 Disallow** |
| 2 | （该收录时）**有没有归并目标页** | **有**（筛选/排序 → 无参数分类页第 1 页，**不论第几页**）→ `canonical` 指目标；**没有**（分类页本页、**无筛选的**分页第 2 页起、商品详情）→ `canonical` **自引用** |
| 3 | 要不要用 `robots.txt` 挡 | **不要**。`Disallow` 的语义是"别抓"，不是"别收录"；被 Disallow 的 URL 若被链接指向，仍以裸链接进结果，且爬虫读不到 `noindex`/`canonical`。**`robots.txt` 全文只留 `/api` 一条** |

> 反例特征（看到就说明读错了）：
> ① 把"筛选/排序"和"站内搜索"合并成"参数一律 Disallow"——两者**唯一共同点只是 URL 里有问号**，但一个是"该收录、只做归并"，另一个是"不该收录、打 noindex"；
> ② 用 `Disallow: /*?*` 图省事——会连 b1 筛选页与 b3 商品详情一起挡掉；
> ③ 给站内搜索同时写 `noindex` 和 `canonical`——`noindex` 优先生效、canonical 被忽略，且多个 noindex 页同时 canonical 到同一目标还可能反向影响该目标收录。

**矩阵违反自检 6 问（做任何 SEO/robots 改动前后各答一遍，任一"是"即为违反）**

1. 我是否给某个页面**同时**加了 `Disallow` 和 `noindex`？→ 是 = 违反（指令互相抵消）
2. 我是否给某个**有 canonical 归并**的页面加了 `Disallow`？→ 是 = 违反（canonical 读不到，归并失效）
3. 我是否写了**通配参数** `Disallow`（`/*?*` / `f.` / `&`）？→ 是 = 违反（必然误伤 b1/b3）
4. 我是否把"带参数"或"参数空间无限"当成了 `Disallow` 的理由？→ 是 = 违反（`Disallow` 从不用于表达"不收录"，见第 3 步）
5. 我是否把 b1 的 canonical 归并标成了"可选/次要/开关默认关"？→ 是 = 违反（它是 AC-11 的 Must 断言）
6. 我是否给某个 `noindex` 页面**同时**输出了 `canonical`（尤其指向别的 URL）？→ 是 = 违反（noindex 优先，canonical 被忽略，还可能污染目标页）

**判据自检 6 问（写任何断言前答一遍。它不隶属上面 6 问——上面问"有没有违反矩阵"，这里问"这把尺子能不能用"）**

> **A 组：定"证明什么"**
> 1. **断言对象是谁？** 页面 URL / JSON 接口 / sitemap 条目 / 响应头 —— **四者不同层**，混一层会同时得到"能过的被判红"与"过不了的被判绿"。
> 2. **取值范围是什么？** 全量 / 样本 / 哪一档 / 是否含参数形态与历史 URL。**取值域不定，样本越精巧，错误实现藏得越深**（归档样本避开"带 slug 历史"的商品，就永远验不出两跳）。
> 3. **退出码语义是什么？** `0` 通过 / `1` 断言失败 / `2` 前置缺失 = **未验证 = 不通过**。
>
> **B 组：定"这道证明本身可不可以用"**
> 4. **载体自己崩了，会不会冒充成"红"？** 脚本崩掉的表现是"输出很少 + 非 0"，**与"有断言失败"一模一样**，人看到非 0 就以为它拦住了东西。所以每条自证必须**同时**断言 `rc` **和**"输出里必须出现的那一行"，两个都满足才算数（若自证只打印一行标题就退出 1，它从未跑完过）。
> 5. **靶点会不会被无关改动悄悄挪走？** 按字典序取"第一个文件"、`ls` 的 `*` 不跨层 —— 注入还在跑，验的已经换了对象，或者**从未执行过一次却报了成功**。靶点写全路径或按内容匹配，**不按"第一个"**。
>
> **C 组：定"两条规则撞上时谁说话"**
> 6. **这条规则与相邻那条规则同时命中时，谁优先？** 实体状态 vs 入口路径、页级 404 vs 参数剔除、`noindex` vs `canonical` —— **两条规则各自都对、合起来没有答案**时，它**不会红**，只是静默"操作了但不生效"，而排查方向会被引到相邻那一层。
>
> **D 组：定"谁去证明"**
> 7. **这条 Must 的判据载体是哪个文件、哪条断言？** 答不出就是**没有载体**。这类规则在文档里**读起来最完整**——状态码、触发条件、"未登记的历史 URL 返回 404 而不是 200"全都写了，唯一缺的是"谁去验"；而它**不红、不不一致、也不需要**，只是**从来没被执行过**。发现途径只有一个：**从别人的用例反查"这条用例的机器载体是谁"**（本轮就是这样发现 AC-11 规则 4 只有一句话、没有 S 覆盖）。
>
> **A/B/C/D 的分工**：A 组覆盖"证明的内容"，B 组覆盖"证明这个动作"，C 组覆盖"两条证明的交点"，**D 组覆盖"有没有人在证明"**——本轮返工全部落在这四格里。

**为什么 `/admin` 用 `X-Robots-Tag` 而不是 `<meta name="robots">`（写清理由，否则后来人会"统一一下"改回去）**
1. `/admin` 是纯静态 SPA，返回的是构建产物的 `index.html`。给构建产物加 SEO 语义属于无关耦合；`X-Robots-Tag` 只需服务端/反代按路径加一行，**不必触碰 HTML**。
2. **`X-Robots-Tag` 对非 HTML 资源（PDF / 图片 / JSON / CSV）同样生效**，而 meta 标签只对 HTML 有效。管理端若将来直接暴露导出类路径，一条响应头能覆盖，meta 覆盖不到。
3. 对 HTML 而言两者**效果相同**——所以选响应头是"不必改 HTML + 能覆盖非 HTML"，**不是**因为 meta noindex 在管理端无效。这一点必须写明，否则会被误读为"meta 无效"然后改错方向。

**私有页为什么用 `noindex` 而不是 `Disallow`**：见 AC-11 正文——`Disallow` 只阻止抓取、不阻止收录，被挡住的 URL 爬虫读不到 `noindex`，最终以"无标题无描述裸链接"出现在搜索结果里。**任何"既要 canonical/noindex 又要 Disallow"的组合都是错的。**
