### 1.1 类型映射裁决（逐条给结论，不留「建议考虑」）

| # | 概念 | C# 类型 | SQLite 存储 | PG 存储 | 裁决与理由 |
|---|---|---|---|---|---|
| T1 | 主键 / 外键 | `Guid` | `TEXT`（36 字符，实测 DDL：`"Id" TEXT NOT NULL CONSTRAINT "PK_x" PRIMARY KEY`） | `uuid` | **`Guid`，应用侧生成（`ValueGeneratedNever`）。** 现有代码就是 `Guid`，**代码不改**（§2 C1/C6 已改判为「文档已过时」）。四条理由见下方「被否决方案」。**外键列类型必须随主键为 `Guid`**：否则出现 `TEXT` 与 `INTEGER` 隐式转换比较（SQLite 容忍、PG 报错）。`long` 在本轮只用于**金额**（`*Minor`）、`ByteSize` 与 **`Version`**（并发令牌是计数器，不是标识）。 |
| T2 | 时间戳（`timestamptz`） | `DateTime`（`Kind=Utc`） | **`TEXT`，格式 = EF 默认 `yyyy-MM-dd HH:mm:ss.FFFFFFF`**（实测写入值 `2026-11-15 10:14:13.1234567`） | `timestamptz` | **裁决：用 EF provider 默认格式，不自定 ISO8601 `T` 格式。** 理由三条：① 该格式定宽、零填充 → 字典序恒等于时间序，`BETWEEN` / `ORDER BY` / keyset 比较全部正确，不需要再多一层函数；② **EF 的参数化查询用的就是这个格式**，自定义 `ValueConverter` 若只改写入侧不改读/比较侧，`WHERE "CreatedAt" >= @p` 会因格式不同而漏行或全表扫（这是最隐蔽的一类线上 bug）；③ 自定 `T` 格式的唯一收益是「人眼友好」，而人眼读到的应该是 API 输出的格式化时间，不是库里的裸值。**因此 `DateTimeUtcConverter` 只允许改 `Kind`（写 `ToUniversalTime()`、读 `SpecifyKind(Utc)`），禁止改 `Format`**，且必须是 `ValueConverter` 而不是 `HasColumnType("TEXT")`。 |
| T3 | `bytea` | `byte[]` | `BLOB` | `bytea` | **M1 无 BLOB 列**（`Session.TokenHash` 用 `TEXT(64)` 小写 hex，见 T9）。规则保留备用：`byte[]` 在两个 provider 上都是原生映射，**无需分支**，未来若加（如缩略图字节）直接映射即可。 |
| T4 | 金额（`decimal` / `bigint`） | `long`（列名以 `Minor` 结尾） | `INTEGER` | `bigint` | **全库禁止 `decimal` 任何列**（02 §5-2）：EF Core 在 SQLite 上把 `decimal` 映射为 `TEXT`，于是 `ORDER BY` 变字典序（`'1000' < '9'`）、范围比较全错，而金额恰恰只做这两件事。金额一律 `long` 最小货币单位 + 同记录单列 `Currency`。 |
| T5 | `bool` | `bool` | `INTEGER` 0/1（实测） | `boolean` | 按 provider 默认，**不写自定义转换器**。副作用必须记住：SQLite 允许写入 `2`，而读回时 `bool?` 得到 `True`（**实测：无 CHECK 的表插入 `2` → EF 读回 `True`，全程零报错**）→ **脏值 `2` 会静默变成 `true`**。所以凡是「语义只有真假」的列，加 `CHECK ("X" IS NULL OR "X" IN (0,1))`（§4.1 CK-6）。 |
| T6 | 枚举 | `enum`（显式 `HasConversion<int>()`） | `INTEGER`（实测） | `integer` | 存数值不存字符串：改枚举名不该触发数据迁移（02 §6.5「重命名枚举值禁止改数值」）。显式写 `HasConversion<int>()` 是为了**堵住**后人加 `.HasConversion<string>()` 的口子。越界值（请求体写 `99`）必须由聚合边界拦（`Product.ChangeStatus` 已有 `Enum.IsDefined` 守卫，M1 其余聚合照此）。 |
| T7 | 字符串 | `string` + `HasMaxLength(n)` | `TEXT`（**长度不强制**，实测 `TEXT` 无长度信息） | `varchar(n)`（超长报错） | 长度约束的「真源」是 `MaxLength` + 领域/DTO 校验（02 §5-12）。**关键纪律：领域层必须自己校验长度**，否则 SQLite 上永远发现不了越界，切 PG 当天才炸。`J` 类列（JSON）例外：不设 `MaxLength` → PG 上落到 `text`。 |
| T8 | JSON 列 | `string`（应用层 `System.Text.Json`） | `TEXT` | **`text`（不用 `jsonb`）** | 02 §3.0 给的是「`jsonb`（或 `text`）」，**裁决取 `text`**：本文规约 JSON 列永不进 `WHERE`/`ORDER BY`（02 §5-6），`jsonb` 的唯一收益（可索引、可查询）在这里是零；而代价是每次用 `jsonb` 就要一次 provider 分支（SQLite 无此类型），且 `jsonb` 会重排 key、丢空白 —— `AuditLog.BeforeJson/AfterJson` 是**审计证据**，要求「原样留证」，被重排就会在争议时说不清「到底是字段顺序不同还是值不同」。唯一 M1 的 JSON 列是 `AuditLog.BeforeJson/AfterJson`。 |
| T9 | Session 令牌摘要 | `string(64)` | `TEXT` | `varchar(64)` | **裁决：TEXT(64) 小写 hex，不是 `bytea(32)`。** 03 §6.2 写 `bytea(32)`，但 02 §3.6 定的是 `S(64)` hex，且 03 自己声明「表由 data-engineer 定稿」。取 hex 的理由：① 排障时可读（会话问题排查要能比对 hash 前缀，`bytea` 得先转码）；② hex 没有「大小写两种表示」问题（`bytea` 若某处写成 `X'..'` 大写字面量，同一 token 会有两个 hash 值）；③ 32B→64B 的体积代价在 `Session`（预计 <10⁴ 行）上可忽略。**强制纪律：`ToString("x2")` 全部小写，写入前断言长度为 64。** |
| T10 | 货币 | `string(3)` | `TEXT` | `varchar(3)` | 按 02 §D11 用 ISO 4217 定长 3 位字符串，**不用枚举整数**：币种会增（二期多币种），枚举整数会让「加币种」变成「加枚举值 + 担心历史行含义漂移」。 |
| T11 | `double`（属性数值） | `double` | `REAL`（实测） | `double precision` | 按 02 §3.1 用 `double` 而非 `decimal`：该列的价值就在 `BETWEEN 10 AND 20` 与 `ORDER BY`，而 `decimal` 在 SQLite 是 `TEXT` → 比较排序全错。金额不走此列，IEEE754 无资金风险。 |
| T12 | 审计尾部 `A` | `DateTime CreatedAt` +（可变表）`DateTime UpdatedAt` | `TEXT NOT NULL` | `timestamptz NOT NULL` | **DDL 里不写 `DEFAULT`**（02 §1.2 / §5-11）：SQLite 的 `CURRENT_TIMESTAMP` 是秒级且格式 `YYYY-MM-DD HH:MM:SS`（无 `T`、无小数秒），PG 的 `now()` 是微秒 + 时区，两者语义不同。值只能由 `SaveChanges` 拦截器从 `IClock.UtcNow` 填。 |

**被否决方案：`long` 自增主键（初稿写过两次，2025 终裁否决，留档防第三次翻案）**

| # | 当初的主张 | 为什么被否决 |
|---|---|---|
| 1 | 「10k 量级下 `TEXT(36)` 的索引比 `INTEGER(8)` 大 3~4 倍」 | **收益不可测**：主键只用于点查与 join，这些路径都有覆盖索引；10k 行上两者的行宽差不到 1MB，换不来任何可观测的 TTFB 改善（AC-12 的性能预算花在 facet 聚合上，不在主键宽度上） |
| 2 | 「改型是 M1 最大一处返工，趁 squash 窗口一次做完」 | **成本确定且大，收益为零**：要动领域层全部 `Guid.Empty` 守卫、全部 DTO、全部测试、两个仓储与映射层；且改型错误会以「SQLite 容忍隐式转换、PG 报错」的形式推迟到切库当天才炸 |
| 3 | 「自增即时间序，可做 keyset 深翻页的 tiebreaker」 | **论据不成立**：本项目的所有排序都依赖显式列（`PublishedAt`/`CreatedAt`/`SortOrder`），从不依赖主键顺序；keyset 的 tiebreaker 只需要「唯一且可比较」，`Guid` 满足（SQLite `TEXT` 字典序稳定、PG `uuid` 有全序）。它不保证「新插入的排在后面」，而本项目没有任何查询需要这件事 |
| 4 | —— | **向前兼容路径存在**：真需要自增序时，加一个 `surrogate long Seq`（保留 `Guid Id` 作主键）是「新增列 + 回填 + 可空→收紧」的非破坏性演进；而此刻把主键从 `Guid` 改成 `long` 是**破坏性重建**（SQLite 重建表、PG 重写全表）。**用一个确定的破坏性变更去换一个不确定的收益，是错的。** |

> **主键统一更正（读本章前必看）**：下面 §1.2~§1.5 的列清单里，凡 `Id` / `XxxId` 行，类型一律是 **`Guid` / `TEXT`（PG `uuid`）**，默认值一栏的「应用侧生成」即 `ValueGeneratedNever`，**PK 不是 `AUTOINCREMENT`**。文中其余提到「自增 / 时间序」的表述一律读作「不适用」。

**命名约定**：持久化记录类统一 `*Record` 后缀（沿用 M0 已建立的 `ProductRecord` 约定），**不改叫 `*Entity`**。理由：同一程序集里 `Product`（领域）与 `Product`（持久化）不能同名，M0 已选 `Record` 并在 `ProductMapping` 里收口映射，M1 换命名要动全部映射与测试，收益为零。

### 3.3 本迁移唯一的生成陷阱：`Product.PrimaryImageId ↔ ProductImage.ProductId` 循环外键

这两张表**互相引用**，而 SQLite 与 PG 处理循环 FK 的机制不同：

| provider | 机制 | 结果 |
|---|---|---|
| SQLite | `CREATE TABLE` 时**不校验**被引用表是否存在（FK 在 DML 时才解析），所以可以先建 `Product` 再建 `ProductImage` | 迁移能过 |
| PG | `CREATE TABLE ... REFERENCES` 指向不存在的表**直接报错**，EF 的 PG 生成器会把其中一条 FK 后置成 `ALTER TABLE ... ADD CONSTRAINT` | 迁移能过（生成 SQL 形态不同） |

**判断：保留循环 FK，不做任何降级。** 理由：① 两个 provider 都能正确生成，只是 SQL 形态不同，这是 EF 的既定行为，不是我们需要绕的坑；② 主图指针必须能被拒绝（`Restrict`），否则删图会让 `Product.PrimaryImageId` 悬空；③ 02 §3.1 已明确否决「用 `ProductImage.IsPrimary` + 部分唯一索引」的方案（那是布尔部分索引 + provider 分支，且改主图要改两行）。
**已知副作用**：插入顺序是「建 `Product` → 建 `ProductImage` → `UPDATE Product SET PrimaryImageId=?`」，即**不能在一个 `INSERT` 里写完**。这属于聚合持久化的正常两段式，`ProductMapping` 需要知道它。
**防呆**：集成测试必须有一条「空库 → 全量迁移 → 断言 24 张表都在」在两个 provider 上各跑一次（02 §6.2 的成对验证），这条会立刻暴露任何建表顺序问题。

## 4. 约束与可移植性风险

### 4.1 CHECK 清单（9 条，逐条标注 provider 语义差异）

> **这张表是 `CK` 的编号与条数的唯一出处。** 02 正文只描述"要什么约束"，不复述条数（`02 §6.1` 已改成指回这里）。两条纪律：
>
> 1. **编号稳定、不许重排。** `CK-1`…`CK-9` 一旦落进提交记录/PR/事故复盘，重排就等于让历史引用换指——和枚举值重排同一个病。删除只能留空号并标注「已移除」，新增只能追加。
> 2. **表头那个数必须能从下面的行数数出来。** 现在是 9 行 = 9 条。行数与表头数字任何一个变了，另一个必须同改。
>
> **「在清单里」≠「已落地」**：本轮（目录 + 库存）实际建成 **4 条**——`CK-1`/`CK-2`（`StockItem`）、`CK-7`（`Category`）、`CK-9`（`ProductCategory`）。`CK-3`/`CK-4`（`ProductVariant`）、`CK-5`/`CK-6`（`ProductAttributeValue`）、`CK-8`（`ProductVariantAxis`）属属性/变体批次，**M1 结束时总数才是 9**。所以 §4.1.1 的门禁命令在中间状态下只能核「已落地的那 4 条各出现恰好一次」，不能核总数 = 9。

| # | 名称 | 表 | 表达式 | SQLite | PG | 差异与说明 |

### 4.1.1 硬规约 R-CHECK：9 条 CHECK 只能声明在 Configuration 里，禁止任何 raw SQL（含门禁）

> 这条规约由主理人从本轮实测证据直接采纳为**门禁规则**，写进 `scripts/check.sh`，PR 违反即红。

| 项 | 规定 |
|---|---|
| **必须** | 所有 CHECK 用 `builder.ToTable("X", t => t.HasCheckConstraint("CK_…", "…"))` 声明在 `Configurations/*.cs` 里（EF Core 7+ 的表级 API） |
| **禁止** | `migrationBuilder.Sql("… CHECK …")`、`migrationBuilder.Sql("ALTER TABLE … ADD CONSTRAINT …")`、启动时执行 `PRAGMA`/DDL 脚本补约束 |
| **为什么禁（三条，任一条都足以否掉）** | ① **会静默丢失**：EF 的 SQLite 迁移在遇到 `DropColumn`/`AlterColumn` 时**重建表**，重建用的是「模型里声明的 schema」→ 手写 SQL 的 CHECK 不在模型里，下一次重建后**约束凭空消失且无任何报错**（测试曾经绿过，某次无关迁移之后就没了）；② **模型漂移不会被发现**：模型里没有 CHECK，`has-pending-model-changes` 永远绿，V2 也查不出「库里应该有、模型里没有」；③ **PG 侧变成两套维护物**（手写 `ALTER TABLE ADD CONSTRAINT` vs SQLite 的重建表），正是 02 §6.2 明令避免的 provider 分叉 |
| **门禁命令（进 `scripts/check.sh`）** | **必须数「迁完之后的库」，不能数脚本文本。** 理由见下方「为什么不能 `grep -c` 脚本文本」：重建表会让同一个约束在脚本文本里出现两次。<br>① `dotnet ef migrations script … -o /tmp/m1.sql`，再 `sqlite3 /tmp/m1.db < /tmp/m1.sql`（空库全量应用）<br>② `sqlite3 /tmp/m1.db "SELECT sql FROM sqlite_master WHERE type='table';" \| grep -o 'CONSTRAINT "CK_[A-Za-z_]*"' \| sort \| uniq -c` → **每一行必须是 `1`**（同名约束在最终 schema 里出现 2 次 = 有一条没被 drop 掉/重建时重复声明）<br>③ 名字集合必须包含「已落地清单」。**中间状态与终态两个数分开写**：本轮（目录 + 库存）已落地 = **4** 个名字；M1 全部批次落地后 = **9**。**不许用一个数同时表达这两件事**<br>④ `! grep -n 'migrationBuilder.Sql' src/OpenStore.Infrastructure/Persistence/Migrations/*.cs \| grep -i 'CHECK\|CONSTRAINT'` → **必须无输出**<br>**为什么不能 `grep -c` 脚本文本（今日实测）**：`grep -c 'CONSTRAINT "CK_' /tmp/m1_full.sql` = **5**，而唯一名 = **4** —— 多出来的 1 次是 `ef_temp_Category` 重建表时把 `CK_Category_Depth` 又写了一遍（同名约束：老定义 1 次 + 新定义 1 次，最终库里只剩 1 条）。脚本里现在有 **2 次重建表**（`ef_temp_ProductCategory`、`ef_temp_Category`），建表语句 **13** 条 = `__EFMigrationsHistory` + 10 张业务表 + 2 张 `ef_temp_*`。所以「脚本文本里数出 5、库里数出 4」不是脚本错了，是**判据数错了对象**——和 `%an`、`rc`、`mtime` 同一族：那个数不度量它声称度量的东西。 |
| **附带好处** | **CK-1~CK-8 内联在 `CREATE TABLE` 里**，因此**完全绕开** SQLite 不支持 `ALTER TABLE ADD CONSTRAINT` 的限制（02 §5-8）。**例外是 CK-9 与 CK-7 的表达式修正**：`CK-9` 是目录批落地之后才裁定的（`M1_ProductCategoryIsPrimaryCheck`），`CK-7` 是目录批落地后按 `02 §3.1` 把下界从 `0` 修到 `1`（`M1_CategoryDepthLowerBound`，名字不变、只改表达式）。这两笔在 SQLite 侧都表现为**重建表**（`ef_temp_ProductCategory` / `ef_temp_Category` → 拷数据 → drop → rename，实测见两份迁移脚本）。这不违反规约（约束仍声明在 Configuration、模型漂移仍可检测、PG 侧同一份模型），但代价要说清：**「9 条全部内联在 CREATE TABLE」不成立**。要让它回到 `CREATE TABLE` 内只能重生成 `M1_Catalog`（会重写已被实测认可的基线 `ad65e6b`，未采纳）；此后新增 CHECK 一律走重建表迁移并在 PR 标注（02 §5-8 纪律）。<br>**重建表的代价已有实测读数**：重建后 `Category` 的两条索引（`IX_Category_Path`、`IX_Category_Parent_Sort`）、自引用 FK（`ParentId → Category.Id` `RESTRICT`）与全部行都还在；重建前插入 `Depth=1/2` 两行，重建后两行原样读出。`ProductCategory` 重建后行与 `UX_ProductCategory_PrimaryPerProduct`、`IX_ProductCategory_Category_Product` 也都在。**这条实测的意义**：重建表最大的风险不是报错，是「约束/索引悄悄没了」——而它这次没发生，是因为约束声明在模型里（R-CHECK 规约），不是因为运气。 |

### 4.2 主理人问的那个问题：`CK_PAV_ExactlyOne` 与 `CHECK (AmountMinor > 0)` 能否由 EF 迁移表达？

**结论：能，零 raw SQL，两个 provider 都进 `CREATE TABLE`。但有一个前提和一个禁令。**

**① 能：用 EF Core 7+ 的表级 CHECK API**（EF 8.0.11 实测存在，`RelationalEntityTypeBuilderExtensions.HasCheckConstraint` 在包里有 4 个重载）：

```csharp
builder.ToTable("ProductVariant", t =>
    t.HasCheckConstraint("CK_ProductVariant_AmountMinor_Positive", "\"AmountMinor\" > 0"));

builder.ToTable("ProductAttributeValue", t =>
    t.HasCheckConstraint("CK_PAV_ExactlyOne",
        "(CASE WHEN \"OptionId\" IS NOT NULL THEN 1 ELSE 0 END" +
        " + CASE WHEN \"NumberValue\" IS NOT NULL THEN 1 ELSE 0 END" +
        " + CASE WHEN \"TextValue\" IS NOT NULL THEN 1 ELSE 0 END" +
        " + CASE WHEN \"BoolValue\" IS NOT NULL THEN 1 ELSE 0 END) = 1"));
```

**本机实测输出**（`Database.GenerateCreateScript()`，EF Core 8.0.11 + SQLite，逐字拷贝。**注**：这两段 DDL 来自验证 CHECK 的临时探针模型，为了最少代码当时把主键写成 `long`；主键类型与本节的 CHECK 结论无关 —— 正式模型主键是 `Guid`，落成 `"Id" TEXT NOT NULL CONSTRAINT "PK_x" PRIMARY KEY`，`CHECK` 部分逐字相同）：

```sql
CREATE TABLE "ProductAttributeValue" (
    "Id" INTEGER NOT NULL CONSTRAINT "PK_ProductAttributeValue" PRIMARY KEY AUTOINCREMENT,
    "OptionId" INTEGER NULL,
    "NumberValue" REAL NULL,
    "TextValue" TEXT NULL,
    "BoolValue" INTEGER NULL,
    CONSTRAINT "CK_PAV_Bool" CHECK ("BoolValue" IS NULL OR "BoolValue" IN (0, 1)),
    CONSTRAINT "CK_PAV_ExactlyOne" CHECK ((CASE WHEN "OptionId" IS NOT NULL THEN 1 ELSE 0 END + CASE WHEN "NumberValue" IS NOT NULL THEN 1 ELSE 0 END + CASE WHEN "TextValue" IS NOT NULL THEN 1 ELSE 0 END + CASE WHEN "BoolValue" IS NOT NULL THEN 1 ELSE 0 END) = 1)
);

CREATE TABLE "ProductVariant" (
    "Id" INTEGER NOT NULL CONSTRAINT "PK_ProductVariant" PRIMARY KEY AUTOINCREMENT,
    "AmountMinor" INTEGER NOT NULL,
    CONSTRAINT "CK_ProductVariant_AmountMinor_Positive" CHECK ("AmountMinor" > 0)
);
```

注意两件事：CHECK 是**命名的**（`CONSTRAINT "name" CHECK (...)`，SQLite 与 PG 都支持命名），所以「违反约束时能识别是哪一个」成立（探针里故意用了短名 `CK_Amount` / `CK_Bool`，正式用 §4.1 的全名）；CHECK 在 `CREATE TABLE` 内部，**因此完全绕开了 `ALTER TABLE ADD CONSTRAINT` 的 SQLite 限制**（02 §5-8 不需要被触发）。**主键部分与正式模型不同**（见上注）：正式模型是 `Guid` → `"Id" TEXT NOT NULL ... PRIMARY KEY`，无 `AUTOINCREMENT`。

**运行时也实测过（4 条，同一个 scratch 工程）：**

| # | 输入 | 实测输出 | 结论 |
|---|---|---|---|
| 1 | 无 CHECK 的表写入 `"BoolValue" = 2`，用 EF 读回 | `True` | **CK-6 要堵的洞真实存在**：SQLite 接受 `2`，EF 读成 `true`，全程零报错（T5 的说法得到证实） |
| 2 | 有 CK_Bool 的表写入 `2` | `SQLite Error 19: 'CHECK constraint failed: CK_Bool'.` | CK-6 生效，**且报错里带约束名** |
| 3 | 有 CK_Amount 的表写入 `0` | `SQLite Error 19: 'CHECK constraint failed: CK_Amount'.` | CK-3 生效；报错带名字正是 CK-1/CK-2 拆成两条的依据 |
| 4 | 有 CK_Amount 的表写入 `1` | 插入成功 | 约束没有过严 |

**② 前提：表必须是「本次迁移新建」的。** `HasCheckConstraint` 只能进 `CREATE TABLE`；对已存在的表加 CHECK，EF 在 SQLite 上只能重建表（这也正是 §3.1 选 squash 的直接原因）。

**③ 禁令：禁止用 `migrationBuilder.Sql("ALTER TABLE ...")` 或 `migrationBuilder.Sql("... CHECK ...")` 来「补」CHECK。** 三条理由，任一条都足以否掉：

1. **会静默丢失。** EF Core 的 SQLite 迁移在遇到 `DropColumn`/`AlterColumn` 时会**重建表**，重建用的是「模型里声明的 schema」。写在 `migrationBuilder.Sql` 里的 CHECK 不在模型里 → 下一次重建后**约束凭空消失，而且没有任何报错**。这是最难查的一类问题：约束曾经存在（测试绿过），某次无关迁移之后就不存在了。
2. **模型漂移不会被发现。** 模型里没有 CHECK，`has-pending-model-changes` 就永远是绿的，V2 校验（§3.4）也查不出「模型说没有、库里应该有」。
3. **PG 侧会分成两条不同的路径。** 手写 SQL 在 PG 上需要 `ALTER TABLE ADD CONSTRAINT`，与 SQLite 的「重建表」成为两套维护物 —— 正是 02 §6.2 明令要避免的分叉。

**④ 三条书写限制**（都是「写错了不报错、只是约束不对」的类型）：

- 表达式是**透传的 raw SQL** → 标识符必须用双引号 `"Col"`（SQLite 与 PG 都认），**禁止 `[Col]`**（SQL Server 方括号：SQLite 容忍、PG 报错）；**禁止任何 provider 特有函数**（`json_extract` / `strftime` / `now()` / `::` 类型转换）。
- `NULL` 语义必须显式（SQL 的 `CHECK` 结果为 `NULL` 时**视为通过**）→ 用 `CASE WHEN x IS NOT NULL THEN 1 ELSE 0 END` 求和，**不要**写 `x IS NULL AND y IS NULL AND ...`（02 §3.1 已给过这个坑）。
- CHECK 一旦上线**不能改**（SQLite 需重建表、PG 需 drop + add），只能新增。所以 8 条必须一次想清楚——表 4.1 就是这次「一次想清楚」的产物。

#### 4.3.3 `AxisSignature` 专项（02 §3.10 的完整落地）

| 项 | 裁决 | 理由 |
|---|---|---|

| 签名样例 | `color=red\|size=m`、`color=navy\|size=l` …（6 变体全表见 02 §3.10）；单规格 = `""` | 排序用 `Ordinal` 而不是默认比较器：后者受区域性影响，同一份数据在不同 locale 的服务器上会算出不同签名（`VariantMatrix` 的注释已写明）。 |
| 唯一索引 | `UNIQUE (ProductId, AxisSignature)`，**不过滤软删** | 与全库「唯一索引不过滤软删」统一（见 §4.3.5）。软删的处理见下条。 |
| 软删变体的处理 | 软删时必须改写签名为 `~{Id}~{原签名}` | 见 D7。`~` 是 ASCII `0x7E`，不会与数字/`;`/`:` 冲突。**改写只发生在「无销量的变体软删」路径上**（有销量的只能停用 `Status=Disabled`，02 §3.1），所以不会影响任何订单（订单行全是快照）。 |
| 写入口 | 只有 `VariantMatrix`（聚合内），**禁止任何代码直接写这一列** | 签名与 `VariantAttributeValue` 是同一事实的两种表示，两处写必然漂移。02 §3.10 已定。 |
| 长度 | `S(400)` | 3 轴 × 每个 `code=optionCode`（各 ≤40 字符上限，实际模板里 ≤10）+ 2 个 `\|` → **通常 <60 字符**，400 有 6 倍以上余量，也足够容纳软删改写（`2 + 36 + 1 + 60`）。SQLite 不校验长度 → **领域必须校验**（`GuardSignature` 已校验 400 ✅）。 |

#### 4.3.4 `Session.TokenHash` 作主键专项

| 项 | 裁决 | 理由 |
|---|---|---|
| 主键 | `TokenHash TEXT(64)` PK，`ValueGeneratedNever()` | 03 §6.2 定「不单列 `Id`」，02 §3.6 一致。EF 必须显式 `HasKey` + `ValueGeneratedNever`（string 主键若不显式声明，行为依赖约定推断，而 C16 已决定不依赖约定）。 |
| 性能 | **接受「TEXT 主键 = 隐式唯一索引 + rowid 回表 = 2 次 B-tree 探测」** | SQLite 的非整数主键表仍是 rowid 表，主键变成一个自动唯一索引 → 每次点查是「索引 seek + rowid 取行」。若改成 `Id INTEGER PK + UNIQUE(TokenHash)`，点查仍是 2 次探测（唯一索引 + 回表），**收益为零**；而 `Id` 会成为第二个「真源」（有人会拿它当会话标识去比较）。会话量预计 <10⁴ 行，两次探测在微秒级。**若未来会话量到 10⁶ 级，再改成「整数 PK + 唯一 TokenHash」，那是纯增量迁移**（§6.5 允许的「加列 + 切读 + 删列」路径），不是现在要付的利息。 |
| 无并发令牌 | **不加 `Version`**（03 §6.2 定稿） | `LastSeenAt` 的节流写是**单行单调 UPDATE**：`UPDATE "Session" SET "LastSeenAt"=@now, "IdleExpiresAt"=@idle WHERE "TokenHash"=@h AND "LastSeenAt" < @nowMinus5min`。影响 0 行的含义是「别人刚写过」——**这是正常并发，不是冲突**。加令牌会让「浏览器同时打 6 个接口」变成随机 409，即用一个假的冲突去换一次可省的写。 |
| 无 `UpdatedAt` | 不设（02 §3.6 本来就没有，与 §1.5 的「可变表有 `UpdatedAt`」形成一处**显式豁免**） | ① 表里已有 `LastSeenAt`，它就是「最后变更时间」，再加 `UpdatedAt` 就是两个真相；② 单调 UPDATE 是**手写 SQL，不经过拦截器** → 声明了 `UpdatedAt` 就必须在每条手写 SQL 里手工维护，漏一处就出现「`UpdatedAt` 早于 `LastSeenAt`」，而这种不一致没有任何约束能发现；③ 03 §2.6 明确 `SessionRecord` 「不是聚合根，由 Auth 服务直接操作」，§1.5 的可变表规约面向聚合实体。**建议把这条豁免写进 02 §1.5 的豁免清单（与只追加表并列）。** |
| 手写 SQL 的边界 | 只允许 `ExecuteUpdate`（EF7+）或 `ExecuteSqlInterpolated`（**必须参数化**）；**禁止字符串拼接** | 04/02 的「直接执行 SQL 改数据不会 bump `Version`」在这里无影响（无 `Version`），但**注入风险**与「SQLite 下格式化时间字面量」的风险仍在：手写 `WHERE LastSeenAt < '2026-11-15T10:14:13'` 会因为格式是空格分隔而**永远匹配不到**（见 T2）。 |

#### 4.3.5 全局策略：**唯一索引一律不过滤软删**

4 张软删表（`Product`/`ProductVariant`/`Category`/`AttributeDefinition`）的唯一键（`Sku`/`AxisSignature`/`Translations(Locale,Slug)`/`Code`/`InternalCode`）**全部不过滤 `IsDeleted`**，只有 `ProductVariant.AxisSignature` 特殊到需要「软删时改写值」（§4.3.3）。

理由（一条策略优于四处例外）：软删商品/分类的 slug、SKU、code 继续**占位**，防止新品复用旧标识造成「旧外链 301 到不相干商品」或「导入撞号串货」；错误信息是明确的（「SKU 已被已删除商品占用」），而**过滤软删的唯一索引会把这个错误变成静默的数据重号**。
例外只为 AxisSignature 开，是因为它的值**不是外部标识**（不对外、不被任何系统引用），改写它零风险；而 SKU/slug/Code 是对外标识，改写它们等于制造两条历史。

### 4.4 `Product` 软删与 SKU 唯一索引如何共存

| 问题 | 答案 |
|---|---|
| 软删商品的 SKU 会被复用吗 | **不会**。`UX_Variant_Sku` 不过滤 `IsDeleted` → 导入/新建撞键，错误信息「SKU 已被已删除商品占用」（02 §3.1 原文就是这个行为）。 |
| 软删商品时翻译行怎么处理 | **保留**。翻译行虽属「可硬删」类（02 §1.3），但**软删商品时绝不能删它们的译文行**：slug 的占位语义完全由翻译行上的 `(Locale, Slug)` 唯一索引承载，删了译文行 = 释放 slug = 旧外链可能指向新商品。物理删除（仅重置/测试路径）时由 FK `Cascade` 一并删。 |
| 软删变体的 `AxisSignature` | 改写为 `~{Id}~{原}`（§4.3.3）—— 这是唯一需要改写唯一键的场景。 |
| 软删商品还能被订单引用吗 | 能：订单行全是快照（`SkuSnapshot`/`NameSnapshot`/`UnitPriceSnapshot`），订单详情**完全不回查 `Product`**（02 §2.1 关键设计点 3）。 |
| 软删后前台行为 | `Status=Archived` → **410**（不是 301、不是 404），02 §1.3 / §4.5 已定。M1 无前台，M2 实现。 |

### 4.5 可移植性风险逐条对到 02 §5

| 02 §5 行 | 风险 | 在 M1 的落点与处置 |
|---|---|---|
| #1 排序规则 | SQLite `BINARY` / PG 按 collation | 规范化列：`EmailNormalized`（小写）、`Slug`（小写）、`Sku`（**全大写**，领域已强制）、`AxisSignature`（纯数字/符号）、`StorageKey`（小写）。**不用 `citext`、不用 `COLLATE NOCASE`**。 |
| #2 `decimal` | SQLite 映射 TEXT → 排序比较全错 | M1 零 `decimal` 列：金额全 `long` minor，属性数值 `double`（T4/T11）。 |
| #3 时间 | 格式/时区语义不同 | 只存 UTC `DateTime`；`DateTimeUtcConverter` 只改 `Kind` 不改 `Format`（T2）；DDL 无 `DEFAULT`。 |
| #4 `LIKE` | SQLite ASCII 不敏感、PG 敏感；`%x%` 不走索引 | M1 只有一处 `LIKE`：`Category.Path LIKE '/1/7/%'`（前缀匹配）。**PG 侧未指定 `text_pattern_ops` 可能不走索引** —— 见下方 R-PG，接受。后台搜索用前缀匹配（M2）。 |
| #5 WAL / 单写者 | SQLite 写事务排队 | 见 §4.6 PRAGMA 清单；M1 写事务保持短（无外部调用在事务内）。 |
| #6 JSON | 行为分叉 | M1 只有 `AuditLog.BeforeJson/AfterJson`，两库都是 `text`，只整体读写（T8）。 |
| #7 自增 | `AUTOINCREMENT` vs `IDENTITY` | **M1 业务表不用自增**：主键统一 `Guid` + `ValueGeneratedNever`（§1.1 T1），所以 `AUTOINCREMENT` / `IDENTITY` 的分叉在本轮不出现。仍禁止任何业务逻辑依赖「主键连续」或「主键即时间序」（订单量统计用 `COUNT(*)`，对外单号随机）。 |
| #8 CHECK | SQLite 不支持 `ALTER TABLE ADD CONSTRAINT` | **本轮已落地的 4 条（CK-1/CK-2/CK-7/CK-9）里，CK-1/CK-2 内联在 `CREATE TABLE`**；`CK-7` 的下界修正与 `CK-9` 是落地后才追加/修正的，走**重建表迁移**（`ef_temp_*` → 拷数据 → drop → rename），见 §4.1.1 的实测读数。清单终态 9 条，见 §4.1。后续新增 CHECK 一律走重建表迁移并在 PR 标注。这是 §3.1 选 squash 的直接原因。 |
| #9 FK 与级联 | SQLite 需 `PRAGMA foreign_keys=ON` | 连接串不写 `Foreign Keys=False`；CI 加一条断言 `PRAGMA foreign_keys` 返回 1（§4.6）。`Cascade` 只用于纯从属行（Translation/ProductImage/ProductVariantAxis/PAV/VAV），其余 `Restrict`。 |
| #10 布尔 | PG `boolean = integer` 报错 | 唯一的布尔部分索引走 provider 分支（§4.3.2）；所有 LINQ 比较走 EF 参数化，SQL 里不写字面量。 |
| #11 DB 默认值 | 秒级/微秒差异 | **M1 全部列都没有 DB `DEFAULT`**（`grep -rn HasDefaultValue Configurations/` 只命中一条注释）。时间列没有 `DEFAULT` 是 §4.6 的纪律；**非时间列也没有**，包括 `IsPrimary`/`Depth`/`SortOrder`。理由不是省事：DB 默认值会让「忘记赋值」静默变成「赋了一个错的值」——`Depth` 必须等于 `Path` 的段数，任何 `DEFAULT`（0 或 1）都只在根节点上恰好正确，在别处**当场通过 `CHECK` 却是脏数据**。所以对照表 §2 的「默认」列记的是**应用侧应赋的值**，不是 DDL 里的 `DEFAULT`，别照着它写迁移。两库一致（都没有），因此这一项在 M1 零分叉。 |
| #12 字符串长度 | SQLite 不强制 | **领域层必须自校验长度**（T7）。这是 M1 最容易漏的一条：SQLite 上永远绿，切 PG 当天全炸。 |
| #13 部分索引 | filter 语法差异 | 3 条部分索引，仅 1 条需分支（§4.3.2）。 |
| #14 覆盖索引 | SQLite 无 `INCLUDE` | `IX_PAV_Facet` 把 `ProductId` 直接放进键（三列复合）→ 达到覆盖效果。 |
| #15 标识符大小写 | PG 未加引号会折小写 | 全部 EF 默认 PascalCase；**`scripts/` 与运维脚本里所有表名列名必须加双引号**。 |
| #16 唯一索引 + NULL | 多 NULL 被允许 | 「至多一条」语义**不用**「唯一索引 + NULL」表达，改用可空 FK 反指（`Product.PrimaryImageId`/`ProductVariant.MainImageId`）；`AxisSignature` 用空串而**不是** NULL（§4.3.3）。 |
| #17 事务隔离 | SQLite 写串行 / PG `READ COMMITTED` | 不依赖隔离级别：靠唯一约束 + `Version` CAS。**禁止 `SELECT ... FOR UPDATE`**（EF 无可移植表达）。 |

**R-PG（新增，02 §5 未列）**：`Category.Path` 上的 `Path LIKE '/1/7/%'` 在 PG 下若用的是非 `C` collation，普通 btree 索引**不会**被 `LIKE` 使用（需要 `varchar_pattern_ops`）。**判断：不指定 opclass，接受 PG 上可能全表扫。** 理由：分类总量是**百级**（02 §3.1 自己写的「需求模板 ~20 个」，硬上限 5 层），全表扫 100 行的成本低于「多一处 provider 专属索引 + 多一份迁移分叉」的维护成本；若未来分类数 >10⁴，再加 provider 专属 opclass 索引（属 02 §6.2 白名单②「少量列类型」的扩展，需评审）。

### 4.6 SQLite 运行时 PRAGMA（物理存储参数，M1 必须落地）

这不是「优化建议」，是**正确性前提**：不开 WAL，`busy_timeout` 也没设的话，两个并发请求就会 `SQLITE_BUSY` 直接 500；不开 `foreign_keys`，所有 FK 都是装饰。

| PRAGMA | 值 | 何时设 | 为什么 |
|---|---|---|---|
| `journal_mode` | `WAL` | 连接打开后（一次性，持久化在库文件里） | 默认的 `DELETE` 模式下读会阻塞写、写会阻塞读 → 单实例电商必然撞锁；WAL 下读写并发（02 §5-5）。 |
| `busy_timeout` | `5000`（ms） | **每条连接**（不持久化，必须每次设） | SQLite 是单写者，写事务排队；不设的话第二个写者**立刻**返回 `SQLITE_BUSY` 而不是等 5 秒。这是最容易漏的一条（02 §5-5 明确点名）。 |
| `synchronous` | `NORMAL` | 每条连接 | WAL + `NORMAL` 是「掉电可能丢最后一个事务、但库不会损坏」的业界默认权衡；`FULL` 会让每次提交 fsync，吞吐掉一个量级；`OFF` 会损坏库。 |
| `foreign_keys` | `ON` | 每条连接 | EF 的 provider 会发，但**若有人手工 `new SqliteConnection` 就漏了**（02 §5-9）→ CI 加断言：`PRAGMA foreign_keys` 必须返回 1。 |
| `cache_size` | `-16000`（约 16MB） | 可选 | M1 库预计 <2MB，收益可忽略；写上是为了给 M2/M3 留基线。**不做 kv 级调优**：DB ≤2GB、峰值 ≤50 RPS 的量级下，调参不如把索引建对（02 末尾的前提声明）。 |

落地位置：连接串（`Data Source=...;Cache=Shared` 之类**一律不写**，共享缓存会引入跨连接锁语义的坑）+ 连接打开回调里统一执行。**固化形式进 M1 DoD**：集成测试断言 4 条 PRAGMA 的实际值（读 `PRAGMA journal_mode` 等），而不是断言「我们调用了设置方法」——后者在重构后可能是空调用。

### 4.7 三个额外裁决

#### A. 并发控制列

**02 §1.4 定了什么**：`long Version`（**统一命名，不叫 `RowVersion`**）+ `IsConcurrencyToken()` + `SaveChanges` 拦截器对 `Modified` 实体自增；不用 `byte[] RowVersion`、不用 PG `xmin`（provider 专有）；需要乐观锁的清单 = `StockItem`（最关键）、`StockHold`、`Product`、`ProductVariant`、`Order`、`Payment`、`Refund`、`Cart`、`StoreSettings`、`SetupState`、`ThemeInstance`、`Customer`、`AdminUser`、`Category`；**`Session` 明确不加**（02 §1.4 末 + 03 §6.2）。

**现有代码有没有**：**没有。** `ProductRecord`/`ProductVariantRecord` 都没有 `Version` 列，`StoreDbContext` 没有拦截器 —— 判定 **改代码**（C5/C7/C11）。

**M1 落点：5 张表有 `Version`**

| 表 | 有 `Version`？ | 理由 |
|---|---|---|
| `StockItem` | **有**（最关键） | `Reserve`/`Commit`/`Release` 都是读-改-写，并发下单必须 CAS；02 §1.4 的「冲突后重试 1 次再报 `STOCK_CHANGED_RETRY`」依赖它。 |
| `Product` | 有 | 两个管理员同时编辑/发布/改价：后写者静默覆盖价格与状态，是管理端最常见的事故。 |
| `ProductVariant` | 有 | 改价与启停并发；且它是 `MinPriceMinor` 投影的输入，覆盖会让投影错。 |
| `Category` | 有 | 拖拽排序 + 移动子树（`Path` 重算）并发会写出不一致的路径。 |
| `AdminUser` | 有 | `FailedLoginCount`/`LockoutUntil` 是读-改-写（并发暴力破解时计数会丢）。 |
| `Session` | **没有** | 见 §4.3.4（单调 UPDATE，影响 0 行是正常并发）。 |
| `StockLedger` / `AuditLog` | **没有** | 只追加、不可变（02 §1.5 的不可变表清单）—— 给只追加表加令牌是纯开销。 |
| 其余 Catalog 表（Translation/Option/Set/MediaAsset/ProductImage/PAV/VAV/ProductCategory/Axis） | **没有** | 02 §1.4 未列。它们的并发由父聚合的 `Version` 保护（改译文/属性值都要先加载并写回父聚合）。**注意**：这对 `AttributeDefinition`/`AttributeOption` 不成立（它们是独立聚合、无 `Version`）—— 按 02 的现状接受（低频管理操作），见 §1.2.8 备注。 |
| `AttributeDefinition` / `AttributeSet` / `AttributeGroup` / `MediaAsset` | 没有 | 同上，02 未列，本文不改。 |

**拦截器行为必须写死**：`Added` → `Version = 1`；`Modified` → `Version += 1`（**只对声明了并发令牌的实体**）。若 `Added` 留 0，首次更新是 `WHERE Version=0`（能工作），但「读过一次再写」与「直接更新」的语义会变得不对称，且 0 与「未初始化」混淆。

**已知限制（写进文档）**：直接用 SQL 改数据不会 bump `Version`；所有写必须经聚合仓储。因此 §4.3.4 里 `Session` 的手写 UPDATE 是**唯一**允许绕过拦截器的地方（因为它没有 `Version`）。

#### B. 软删除 vs 硬删除

| 类别 | M1 的表 | 处置 |
|---|---|---|
| **软删**（`IsDeleted` + `DeletedAt`） | `Product`、`ProductVariant`、`Category`、`AttributeDefinition` | 被历史/订单/报表引用，删掉会让历史页面与统计断裂。**4 张**。 |
| **软删但语义是「停用」**（用状态列，不用 `IsDeleted`） | `AdminUser`(`Status=Suspended`)、`AttributeOption`(`IsActive`) | 状态枚举表达力更强，读侧过滤条件更自然，且停用后仍要能被历史引用（02 §1.3）。 |
| **绝不删除** | `StockItem`、`StockLedger`、`AuditLog` | 账务与审计不可变；两张只追加表仓储**不暴露 `Update`/`Remove`**。 |
| **硬删** | 翻译行（`ProductTranslation`/`CategoryTranslation`/`AttributeDefinitionTranslation`/`AttributeOptionTranslation`）、`ProductImage`（图片绑定） | 无历史价值。图片绑定可硬删：订单行已快照 `ImageKeySnapshot`。`MediaAsset` 由孤儿清理按引用计数回收（M7）。 |
| **条件硬删**（有引用则拒绝） | `AttributeOption`（被值表引用时拒绝）、`Category`（有子分类/商品时拒绝）、`AttributeDefinition`（被引用时拒绝） | 跨表计数判断属领域层（02 §8.1）。 |

**`Product` 软删与 SKU 唯一索引如何共存** → 见 §4.4 全节。一句话：**唯一索引不过滤 `IsDeleted`，SKU/slug/Code 继续占位；只有 `AxisSignature` 在软删时改写值（因为它不是外部标识）**。

**软删表的查询纪律**：全局查询过滤器（`HasQueryFilter`）**不启用**。理由：`Product` 有 3 个读取场景需要「看到软删」（管理端回收站、导入判重报错、slug 占用检查），全局过滤器会让这三处变成「必须写 `IgnoreQueryFilters()`」——把默认行为做反了。改为在仓储方法签名上显式表达（`GetActiveByIdAsync` / `GetIncludingDeletedAsync`），调用点可被 grep 审计。

#### C. `InitialCreate` 是否已含 `Order`/`OrderLine`

**不含。** 实测 `20261115101413_InitialCreate.Up()` 只 `CreateTable` 两张：`Product`、`ProductVariant`，加 3 个索引（`IX_Product_Slug`、`IX_ProductVariant_Product_AxisSignature`、`IX_ProductVariant_Sku`）。`StoreDbContext` 也只有 2 个 `DbSet`。

`OpenStore.Domain/Ordering/` 里的 `OrderStatus`、`FulfillmentStatus`、`RefundStatus`、`OrderStatusMachine` 是**纯领域枚举与纯函数状态机**——无表、无 `DbSet`、无映射、不被 Infrastructure 引用。**这不缺任何东西**，因为 M1 范围（`00` §6.2）不含订单：订单属 **M3**（Cart 持久化、结算、运费税、订单双列状态机）。

**M3 需要新增的表（登记，防 M1 误以为已有）**：`Cart`、`CartLine`、`Order`、`OrderLine`、`OrderStatusHistory`、`StockHold`、`IdempotencyRecord`（7 张，M3）；M4 再加 `Payment`、`Refund`、`RefundLine`、`WebhookEvent`（4 张）。
**唯一与 M1 有耦合的是**：`StockLedger.OrderId`/`OrderLineId` 两列在 M1 就建好（无 FK，见 §1.3.2），M3 只需加 `StockHold` + `唯一 (OrderLineId)`，**不需要改 `StockLedger` 结构**。

## 6. 安全与合规（M1 落点）

| 项 | 裁决 |
|---|---|
| 敏感字段 | `AdminUser.PasswordHash`（**单向**，含参数版本前缀，`PasswordHasher<T>` 产出）；`Session.TokenHash`（`sha256` 小写 hex，库泄露不可反推）；`Session.CsrfHash`；`Session.IpHash`/`UserAgentHash`（**只存 hash**，不存原 IP/UA → 减少 PII，03 §6.2 `IpFirst` 已否，见 X4）。**Cookie 原值永不入库、永不进日志**（AC-15）。 |
| 审计白名单 | `AuditLog.BeforeJson/AfterJson` **按字段白名单**生成（订单状态、金额、地址、库存数字、配置项），**绝不整实体序列化** —— 否则 `PasswordHash`/`TokenHash`/支付密钥会进日志表，直接违反 AC-15「全库与全日志搜不到 `\d{16}`」。M1 的白名单字段：`Product.Status`/`MinPriceMinor`/`MaxPriceMinor`、`ProductVariant.AmountMinor`/`CompareAtMinor`/`Status`、`StockItem.OnHand/Reserved/Sold`、`AdminUser.Role`/`Status`。 |
| 不可改 | `AuditLog`/`StockLedger` 仓储不暴露 `Update`/`Remove`；PG 生产可 `REVOKE UPDATE, DELETE`（SQLite 无此能力，写进部署文档）。 |
| 保留与删除 | `AuditLog` **不自动清理**（US-E8-03），靠备份策略承担；`Session` 由清理任务删 `IdleExpiresAt < now` 或 `RevokedAt < now-30d`；`MediaAsset` 孤儿回收（M7）。 |
| 权限最小化 | `AdminUser.Role` 是枚举（Admin=0/Staff=1），权限点写代码常量（`Application/Common/Permissions.cs`），**不建角色/权限表**（02 §3.6 已裁）。M1 只有 `perm:catalog.product.write` 一个权限点。 |
| 备份排除 | `PaymentGatewayConfig`（M4）按表排除出备份包；M1 无此类表。备份/恢复用 `openstore restore --from <backup>` 一条命令（AC-16，M7）。 |

## 8. 对 backend-engineer 5 项对齐请求的答复

| # | 他的问题 | 答复 |
|---|---|---|
| 1 | `Product.SkuRoot` 列缺失（域/记录里有，表里没有）—— 选 A（新增列）还是 B（从契约删除） | **B：不建列，契约删除**（A2）。见 02 §3.1「为什么不设 SKU 前缀列」。若领域代码里已有 `SkuRoot` 属性，**删掉它**，不要留着当「将来要用」的字段 —— 没有消费者的列会在半年后变成一个没人敢删的谜。 |
| 2 | 主键类型三方不一致（`long` / `Guid` / ULID 示例） | **以 `Guid` 为准**（J4 终裁）：SQLite `TEXT`(36) / PG `uuid`；契约里对外一律是**不透明字符串**，不得出现 ULID 形态的示例（26 字符 base32 会让前端以为可以截断）。领域 `Guid`、记录 `Guid`、DDL `TEXT`、契约 `string` —— 四处一致。 |
| 3 | `Session` 绝对过期默认值冲突（03：Admin 7 天 / Customer 90 天；02：30 天） | **按 03 分档**（X8，02 已改）：Admin 空闲 120 分钟 / 绝对 7 天，Customer 空闲 30 天 / 绝对 90 天。**两个值都不是列**，创建会话时算好写进 `IdleExpiresAt` / `AbsoluteExpiresAt`。管理员空闲期取 `StoreSettings.SessionIdleMinutes`（默认 120，需求 01 §E8 明确「可配置」），其余三个走配置项 `OpenStore:Session:*`。 |
| 4 | Cookie 命名冲突（03 §6.1 `os_admin_sid`/`os_shop_sid`/`os_admin_csrf`/`os_cart` vs 02 §3.6 `os_sf_session`/`os_admin_session`） | **按 03 §6.1**（X7，02 已改）。四个名字：`os_shop_sid`（`Path=/`）、`os_admin_sid`（**`Path=/api/admin`**）、`os_admin_csrf`、`os_cart`。**`Path=/api/admin` 不是可选项** —— 它是「管理员会话不被前台请求带走」的唯一手段。 |
| 5 | 表名 `StockLedger` vs `StockMovement` | **`StockLedger` 是唯一落点**：DDL 表名 `StockLedger`、记录类 `StockLedgerRecord`、领域枚举 `StockChangeType`（**不叫** `StockMovementType`）。附一句：领域实体当前叫 `StockMovement` 可以保留（它表达「一次变动」这个事件），但**持久化与表名必须是 `Ledger`** —— 台账（ledger）强调「只追加、可对账」，而 `Movement` 容易被实现成「可改的当前状态表」。M1 的 `StockLedgerRecord` 仓储**不暴露 `Update`/`Remove`**。 |
