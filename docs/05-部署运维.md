## 0. 一页纸结论（给决策者）

| # | 决策点 | 结论 | 一句话理由 |
|---|---|---|---|
| 1 | 部署单元 | **3 个镜像**：`openstore/api`、`openstore/storefront`、`openstore/caddy`（含 admin 静态产物）+ **1 个业务数据卷 `/data`** | 与架构 §1.2 一致；admin 不打进 api 镜像（见 §2.2） |
| 2 | 数据卷形态 | **bind mount `./data:/data`**，不用 named volume | 商家能看见、能拷走、宿主 cron 能直接打包；named volume 是"看不见的备份死角" |
| 3 | API 对外暴露 | 容器内 `http://+:5080`，宿主 `127.0.0.1:5080:5080`（**只绑 loopback**）+ 云安全组只开 80/443 | "仅内网监听"的具体写法；`0.0.0.0:5080` 一律判为错误 |
| 4 | 内存方案（2C2G） | `api` mem_limit 900M / `GCHeapHardLimit=0x20000000`（512M）；`storefront` 400M / 堆 320M；`caddy` 96M；OS+页缓存 ~400M；合计 ~1.83G，留 10% 余量 | 架构给的 `0x38000000`(896M) 是"托管堆上限"，加上非托管会破 900M 容器上限 —— 必须下调，推导见 §2.5 |
| 5 | SQLite 参数 | `journal_mode=WAL / synchronous=NORMAL / cache_size=-131072(128M) / mmap_size=128M(2G机) / busy_timeout=5000 / temp_store=FILE` | 固化进部署文档，不靠代码默认值（架构 §6 硬要求） |
| 6 | 反代取真实 IP | Caddy **覆盖**写 `X-Forwarded-For {remote_host}`（不追加）+ API 侧 `ForwardedHeaders` 只信任 `172.28.0.0/24` + `ForwardLimit=1` | 不修的后果：全站共享一个限流桶 → 一个人触发 `login` 5次/分钟，全站登录 429（**这是安全 + 可用性双重 bug**） |
| 7 | 迁移执行 | **显式一步**：`docker compose run --rm migrate`（= 架构里的 `dotnet openstore migrate`），启动只做检测 + 503 | 生产自动迁移是事故源 |
| 8 | 发布顺序 | **先迁移后发代码**，且迁移必须 expand-only（只加不删不改）；contract（删列/改名）**延后一个版本** | 单实例没有真零停机（§5.4），但 expand-only 让"回滚镜像"始终可用 |
| 9 | 备份 | DB 走应用内 `DailyBackupJob`（`VACUUM INTO`）；**DB + media + keys 三件套由宿主 cron 打包**（带 `manifest.json` 记录镜像版本与迁移号），保留 14 天 + restic 异地 | keys 丢了加密凭据解不开（硬点）；manifest 让恢复能选对镜像版本 |
| 10 | 一键导出 vs 运维备份 | **不是同一套**：一键导出**不含 keys**（AC-16 要求"不含凭据明文"），只能用于交接/迁移；灾备必须用运维备份 | 混为一谈 = 商家以为导出包是灾备，真出事时支付凭据全废 |
| 11 | 监控 | **不引 Prometheus**：Serilog JSON 文件 + Caddy 访问日志 + 5 条 cron/curl 告警 + 一封每日"晨报"邮件 | 单机 2G，加监控栈的内存成本 > 收益 |
| 12 | 首次暴露风险（**已裁决 P0**） | 加**一次性安装令牌**：≥32 字节随机 → `/data/setup-token.txt`（600）+ 启动日志醒目打印 + 支持 `OPENSTORE_SETUP_TOKEN` 预置；写端点校验失败 403（不区分"未带/错误"）；向导完成即失效。**部署侧更进一步**：Runbook 要求**起站前就把 token 写进 `.env`**，这样"忘了立刻走向导"的时间窗直接归零（§8.1 步骤 4） | 这是全项目唯一"上线即被接管并改收款账户"的直接资金损失风险 |
| 13 | 索引控制 | **admin 静态的 `X-Robots-Tag: noindex` 与 CSP 必须由反代下发**（文件不经应用，应用没机会加头）；storefront 的索引头由应用下发，反代**一个字都不加**。判定只有六档（`docs/01` §6.1），**机器判据的唯一载体是 `scripts/verify-seo-matrix.sh`（S1~S9，含 fail-before-pass 自证）**，本文不复制判据 | 职责按"文件经不经过应用"切；两边都加会出现两条冲突指令。同一份矩阵曾在五处文档各存一份 → 改一处漏四处（§3.6） |
| 14 | 状态码保真 | **反代任何情况下不得把 5xx 改写成 2xx**：禁 `error_page`/`handle_errors` 改写，要维护页就用保留状态码的写法 | 503 被换成 200 的静态页 = 空壳页被收录，比不收录更糟（AC-10 负向断言，§3.7） |
| 15 | 绝对 URL | 所有 canonical/og/hreflang/sitemap 只用 `PublicSiteUrl`，**反代再怎么配也不解决、也不该依赖 Host 头**；反代额外做"未知 Host 直接 404"作为纵深 | 伪造 Host 即可把页面索引权重整体转让给攻击者（AC-10：绝对 URL 必须由 `PublicSiteUrl` 生成） |
| 16 | **域名双源**（已裁决） | **启动时硬比对** `OPENSTORE_DOMAIN_URL` 与 DB `PublicSiteUrl`（规范化后），不一致**拒绝启动**并给可操作错误；`/health/ready` 报 `siteUrl`；首次安装跳过 | 靠文档提醒挡不住 —— 商家只会改一处，症状是"表单全 403"或"canonical 静默错一个月" |
| 17 | **恢复命令**（已裁决） | **`openstore restore --from <backup>` 一条命令 + 2 条验证**；PG 的 5 步封进 CLI（附录 C） | 恢复只会在出事时用，操作者最慌；多步骤手工流程的失败形态是"数据不全"而非报错 |
| 18 | **限流**（已裁决） | **按 HTTP 方法分桶**：`read`(GET/HEAD) 1200/分钟、`write` 60/分钟；**不引入爬虫 IP 白名单** | 爬虫只发 GET；抗刷靠 `write`/`login` 层，放宽 `read` 不降低抗刷能力 |
| 19 | AC-12 验收 | **绑定硬件档位**：小店档 2C2G×≤2k SKU、标准档 2C4G×10k SKU，两档各按全套指标验收 | 用 10k 基准卡 2C2G 等于宣告"2C2G 永远不合格"，销售无法给诚实承诺 |

## 1. 环境分层

### 1.1 四层环境

| 环境 | 数据库 | 主题与静态资源 | 邮件 | 支付 | 日志级别 | 典型用途 | 谁能访问 |
|---|---|---|---|---|---|---|---|
| **dev** 开发 | SQLite 单文件 `./data/dev.db`（删文件即重置） | storefront/admin 走 `pnpm dev`（Vite HMR，无需构建）；主题按工作区包直接加载，改主题 5 秒生效 | `FileDropEmailSender` → `./data/mail/*.eml`（或用 smtpd 容器捕获 :1025/1080，验证真实 SMTP 路径） | `FakeGateway`（含"延迟回调/受理中转成功/签名错误"三种真实形态，后端 R7） | `Debug`（`Microsoft.*=Warning` 压噪） | 日常开发；**零配置冷启动**；黄金链路手工验证 | 开发者本机 |
| **ci** 持续集成 | ① 文件型 SQLite（`/tmp/ci.db`）② Testcontainers `postgres:16`（同一套集成测试跑两遍） | 全量构建两个产物（含 2 个主题、3 个行业模板）；产物仅用于 E2E 与镜像构建 | `FileDrop` | `Fake`（**CI 永不连真实通道**，无凭据可泄露） | `Information` | 门禁、单测、集成、E2E、镜像、漏洞与密钥扫描 | CI runner（无公网入站） |
| **staging** 预发 | 优先 **PostgreSQL**（若 prod 选 PG）；否则同版本 SQLite 文件 | 与 prod **同一镜像 digest** | 商家自有 SMTP 的测试收件地址（或 mailpit 容器 + 人工核对） | **Stripe 沙箱**（真实回调 + 真实验签）；不接生产凭据 | `Information` + `RequestLogging` 开 | 升级演练、迁移预演、主题新增验证、客户验收、回调可达性联调 | 团队 + 客户（可选 Basic 认证闸门） |
| **prod** 生产 | **SQLite（默认，小店）** 或 PostgreSQL（规模化，见 §5.3） | 与 staging 同一镜像 digest（发行包固定 digest 而非 tag） | 商家自有 SMTP | 真实通道（Stripe / 支付宝 / 微信）；未配或失效 → `canSell=false` 演示模式（AC-17） | `Information`（`Microsoft.AspNetCore=Warning`，RequestLogging 只记 path/method/status/耗时，**不记 body**） | 真实营业 | 商家 + 买家（公网 443）；SSH 仅商家 |

**环境差异最小化原则（写死三条）**

1. **同一镜像、同一 compose 文件**跑 staging 与 prod，差异只在 `.env` 与数据卷内容 —— 差别是"变量"不是"版本"，禁止"预发用 compose、生产用 systemd"。
2. **prod 不允许出现 dev-only 的开关**：`FileDrop` 邮件、`Fake` 支付、`OPENSTORE_ALLOW_SETUP_RESET=true`、`Security__ForceHttps=false` 这四项在生产都属于配置事故，Runbook 检查单里逐条勾（§8.3）。
3. **数据不跨环境流动**：生产数据只在生产副本上排查（`cp` 到临时目录起一个只读 api 实例），永不落到开发者本机 —— 里面有客户姓名、地址、邮箱。

### 1.2 dev 环境"零配置启动"（客户冷启动卖点的技术底座）

**目标（对齐 AC-01）**：克隆仓库 → 两条命令 → 打开浏览器就走向导。**不设任何环境变量、不建库、不改配置文件。**

```bash
# 1) 后端（默认值即 SQLite + Fake 支付 + FileDrop 邮件 + /data/media 本地存储）
dotnet run --project src/OpenStore.Api          # → http://127.0.0.1:5080

# 2) 前端（storefront :5173，admin :5199，均通过 Vite proxy 打 /api → 127.0.0.1:5080）
pnpm -C frontend dev                            # → http://localhost:5173/setup
```

零配置能成立，靠的是**后端默认值全部指向"本地可跑"**（`docs/03` §10.3 的默认列）：

| 能力 | 默认值 | 为什么这样默认 |
|---|---|---|
| 数据库 | `Data Source=/data/openstore.db`；dev 下 `OpenStore__DataDir=./data` 由 `appsettings.Development.json` 提供 | 首次启动目录不存在 → 自动创建 → 只有"未安装"状态，不报错 |
| 支付 | `OpenStore__Payments__Provider=None` → 演示模式；向导里选 `Fake` | 不需要任何通道账号即可走完"下单 → 支付 → 发货" |
| 邮件 | `OpenStore__Email__Provider=FileDrop` | 邮件落到 `./data/mail/`，不用申请 SMTP，也不用起捕获端 |
| 文件存储 | `IFileStorage` 本地实现，根 `./data/media` | 无 S3 凭据 |
| HTTPS | `OpenStore__Security__ForceHttps=false`（仅 Development） | 本地 HTTP 直连，不被 307 到 443 |
| CORS | **不需要**：dev 用 Vite `server.proxy`，浏览器看到的仍是同源 | 同源 = 与生产一致的 Cookie `SameSite=Lax` 行为，避免"dev 能跑 prod 挂" |
| 迁移 | 首次 `dotnet run` 前跑一次 `dotnet openstore migrate`（**唯一需要的一步命令**） | 不自动迁移是硬规则；dev 首次提供 `scripts/dev-up.sh` 把 migrate 包进去 |
| 主题 | 工作区包，`import.meta.glob` 自动发现 | 加一个 `themes/xxx/` 目录即出现在后台列表 |

> **诚实的边界**：`dotnet openstore migrate` 这一步在 dev 仍需执行一次（`scripts/dev-up.sh` 已封装）。如果客户要求"真的零命令"，只能在 `Development` 环境开 `OPENSTORE_AUTO_MIGRATE=true` 逃生口，且该变量在 `Production` 下**必须**被代码硬拒（启动日志打 Fatal）。我建议保留这条 CLI 步骤 —— 它同时是生产流程的演练。

## 2. 容器化与编排

### 2.1 api 镜像（ASP.NET Core 8）

```dockerfile
# src/OpenStore.Api/Dockerfile  —— 多阶段、非 root、只带运行期产物
# ---------- build ----------
FROM mcr.microsoft.com/dotnet/sdk:8.0-jammy AS build
WORKDIR /src
# 先只拷 csproj，最大化层缓存命中（NuGet 还原不随源码变更失效）
COPY Directory.Build.props Directory.Packages.props nuget.config ./
COPY src/OpenStore.Domain/*.csproj            src/OpenStore.Domain/
COPY src/OpenStore.Application/*.csproj       src/OpenStore.Application/
COPY src/OpenStore.Infrastructure/*.csproj    src/OpenStore.Infrastructure/
COPY src/OpenStore.Api/*.csproj               src/OpenStore.Api/
RUN dotnet restore src/OpenStore.Api/OpenStore.Api.csproj --locked-mode
COPY . .
RUN dotnet publish src/OpenStore.Api/OpenStore.Api.csproj \
      -c Release -o /app --no-restore \
      -p:UseAppHost=false -p:PublishTrimmed=false -p:InvariantGlobalization=false \
 && dotnet publish tools/OpenStore.Tools/OpenStore.Tools.csproj -c Release -o /app/tools --no-restore

# ---------- runtime ----------
FROM mcr.microsoft.com/dotnet/aspnet:8.0-jammy AS runtime
# healthcheck 需要 HTTP 客户端；aspnet 镜像不带 curl，装一个并清缓存（+2MB）
# sqlite3 CLI 是运维刚需（+2MB）：备份要用 VACUUM INTO、恢复要跑 integrity_check、
# 排障要 select count(*) —— 宿主可能没装 sqlite3，把工具放进镜像才能"一条命令查完"。
# 不装它的代价是：备份脚本必须在宿主装 sqlite3，而"我以为目标机器上有"正是恢复文档最常翻车的地方。
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl tzdata sqlite3 \
 && rm -rf /var/lib/apt/lists/*
# 固定 UID，便于"宿主机 chown 数据目录"这一步在文档里可复制
RUN groupadd -g 10001 openstore \
 && useradd -u 10001 -g 10001 -M -s /usr/sbin/nologin openstore

ENV TZ=Asia/Shanghai \
    ASPNETCORE_ENVIRONMENT=Production \
    ASPNETCORE_URLS=http://+:5080 \
    DOTNET_gcServer=0 \
    DOTNET_GCHeapHardLimit=0x20000000 \
    DOTNET_TieredPGO=1 \
    OpenStore__DataDir=/data \
    OpenStore__MediaDir=/data/media \
    OpenStore__Logging__Path=/data/logs/api-.log \
    OpenStore__Secrets__DpKeysPath=/data/keys

WORKDIR /app
COPY --from=build --chown=10001:10001 /app ./
# 行业模板是"内容资产"，必须进镜像（否则向导第 2 步 500）
COPY --from=build --chown=10001:10001 /src/assets ./assets

USER 10001:10001
EXPOSE 5080
# live 而非 ready：容器重启只该由"进程死了"触发，DB 挂不该重启 API（§7.2）
HEALTHCHECK --interval=30s --timeout=3s --start-period=20s --retries=3 \
  CMD curl -fsS http://127.0.0.1:5080/health/live || exit 1

# 同一个镜像承担两个角色：默认起服务；`migrate` 子命令 = 架构里的 `dotnet openstore migrate`
ENTRYPOINT ["dotnet", "OpenStore.Api.dll"]
CMD ["serve"]
```

**镜像要点（6 条，都不是风格问题）**

1. **单镜像双角色**：`serve`（默认）与 `migrate`/`doctor`（`Program.cs` 按 `args[0]` 分派）。不发行第二个"迁移工具镜像"——否则商家升级时要对两套 tag，必然漂移。
2. **`assets/industry-templates` 必须 COPY 进来**：向导要靠它初始化（AC-02/03/04）。`/health/ready` 里有一条"templates 可读"检查就是为了兜住"打包漏了模板目录"这类事故。
3. **`--no-restore` + 单独 restore 层**：源码改动不触发 NuGet 重下，CI 冷构建 6min → 热构建 90s。
4. **`InvariantGlobalization=false`**：`Money`/日期格式化要靠 ICU，砍掉 ICU 会让 `Intl` 类格式化在服务端退化（中文站点尤其明显）。镜像大 30MB，值。
5. **非 root（10001）**：`USER` 之后容器内无法写 `/app`，只能写 `/data` —— 这顺带守住"运行期不产生未挂载的写入"。
6. **`HEALTHCHECK` 用 `/health/live`**：见 §7.2 的语义分工。

### 2.2 admin 静态产物：**不打进 api 镜像**（结论 + 理由）

**结论**：admin 的 `apps/admin/build/` 打进 **`openstore/caddy` 镜像**（`/srv/admin`），api 镜像里**不含任何 admin 文件**。

| # | 理由 |
|---|---|
| 1 | **SPA fallback 只能有一处实现**：`try_files {path} /index.html` 是反代职责。若 api 也托管静态，就要在 ASP.NET 里再写一份 `MapFallbackToFile`，两处缓存头与 fallback 规则必然漂移（典型症状：`/admin/orders` 刷新 404，但站内跳转正常）。 |
| 2 | **暴露面**：api 只该暴露 `/api/*`（`/health/*` 还被反代屏蔽）。让 `/admin` 穿透到 api 等于把一个"业务进程"变成"静态服务器"，且 `X-Frame-Options`/CSP 变成两处下发（docs/03 §8.4 要求 admin 的 CSP 来自应用侧，静态文件则由反代下发 —— 后者更简单）。 |
| 3 | **发布粒度**：admin 是纯静态、零依赖、改动频繁。放 caddy 镜像里，"只改后台样式"的一次发布 = 重建 ~45MB 的 caddy 镜像；api 镜像（~250MB）与 storefront 镜像不动 → 商家下载量与停机窗口都更小。 |
| 4 | **回滚粒度**：admin 与 api 的契约由 OpenAPI 版本保证，独立 tag 让"后台 UI 出问题只回退 UI"成为可能（默认仍随版本一起发，独立只是能力，见 §4.5）。 |
| 代价 | 多维护一个 Dockerfile（10 行）+ 一次 node 构建阶段。相比上面四条，可忽略。 |

**`openstore/caddy` 镜像**

```dockerfile
# deploy/caddy.Dockerfile
FROM node:22-bookworm-slim AS fe
WORKDIR /fe
RUN corepack enable
COPY frontend/ ./
RUN pnpm install --frozen-lockfile \
 && pnpm --filter admin build          # → /fe/apps/admin/build（含 index.html fallback）

FROM caddy:2.8-alpine
COPY deploy/Caddyfile /etc/caddy/Caddyfile
COPY --from=fe /fe/apps/admin/build /srv/admin
RUN addgroup -g 10002 -S static && adduser -u 10002 -S -G static static \
 && chown -R 10002:10002 /srv/admin && chmod -R a-w /srv/admin
# Caddy 需 root 绑 80/443 与写 /data（证书状态卷）
```

### 2.3 storefront 镜像（SvelteKit adapter-node）

```dockerfile
# deploy/storefront.Dockerfile
FROM node:22-bookworm-slim AS build
WORKDIR /fe
RUN corepack enable
COPY frontend/ ./
RUN pnpm install --frozen-lockfile \
 && pnpm --filter storefront build     # → apps/storefront/build（index.js + client/ + server/）

FROM node:22-bookworm-slim AS runtime
ENV NODE_ENV=production \
    TZ=Asia/Shanghai \
    PORT=3000 \
    HOST=0.0.0.0 \
    NODE_OPTIONS="--max-old-space-size=320" \
    ADDRESS_HEADER=X-Forwarded-For \
    XFF_DEPTH=1
WORKDIR /app
# 只拷产物：不拷 node_modules 全量、不拷源码（adapter-node 产物自带依赖打包）
COPY --from=build --chown=node:node /fe/apps/storefront/build ./build
```

**要点**

| 项 | 选择 | 理由 |
|---|---|---|
| Node 版本 | **22.x LTS，`bookworm-slim`（glibc）而非 alpine（musl）** | ① full-ICU 无差异但 glibc 行为与本地一致；② 商家装第三方排查工具（`curl`/`tar`/`strace`）省事；③ 若未来主题用 native 模块（sharp 等）不会踩 musl 重编译。代价 +45MB，接受。 |
| 堆上限 | `--max-old-space-size=320`（2G 机）/ `384`（4G 机） | 见 §2.5 推导。**注意**：前端文档 §11.2 建议"512MB 内存上限"是 4G 机的余量建议；2G 机上必须按架构 §6 的 400MB 执行，否则三进程互相挤爆（架构风险 12）。 |
| 优雅退出 | `init: true`（compose 注入 tini 作为 PID 1）+ `stop_grace_period: 30s` | `node build/index.js` 直接当 PID 1 时，内核不会替你回收僵尸进程；SvelteKit adapter-node 收到 `SIGTERM` 后停止接新连接并等在飞请求结束。app 侧必须真的监听 `SIGTERM`（前端已实现）。 |
| 环境变量 | `ORIGIN`（SvelteKit 的 CSRF 与绝对 URL 基座）、`PUBLIC_SITE_ORIGIN`、`API_ORIGIN`/`PUBLIC_API_BASE_URL` | `ORIGIN` 配错 → 表单 POST 全 403（SvelteKit 的 CSRF 校验），是首次部署最常见的坑之一，写进 Runbook 检查单。 |
| `ADDRESS_HEADER`/`XFF_DEPTH` | `X-Forwarded-For` / `1` | 让 SSR 拿到真实客户端 IP，再透传给 API（否则 API 侧拿到的是 storefront 容器 IP，**与 §2.6 是同一个 bug 的第二段**）。 |
| 只跑 1 个 node 实例 | 不 cluster | 单实例假设贯穿全局（内存缓存、限流、后台任务都在 api）；SSR 侧多实例会放大内存且无收益。 |

| `memswap_limit == mem_limit` | 允许 swap 的后果是"内存压力下整机卡死 30 秒而不是一个容器被 kill"。宁愿 OOM kill api，也不要拖死 Caddy 让全站 502。 |
| `cpus` | 2 核机器上给 api 1.5 核，避免压测/图片处理时把 storefront 饿死（SSR 2s 超时会立刻表现为 503）。 |
| 容器 stdout 用 `json-file` 轮转 | `/data/logs` 是 **api 的结构化业务日志**；Caddy/Node 的访问日志走 stdout，靠 `docker compose logs` 取。两者分开，互不污染磁盘配额。 |

### 2.6 2GB 内存预算的具体落实（推导，不是拍脑袋）

架构 §6 给的分配是：**.NET ≤900MB + Node ≤400MB + SQLite cache ≤128MB + 系统与反代 ≤400MB**。落到参数上有一个必须点出的矛盾：

> **架构写的 `DOTNET_GCHeapHardLimit=0x38000000`（896MB）是"托管堆硬上限"，不是"进程上限"。** RSS = 托管堆 + JIT/栈/元数据（~120–160MB）+ SQLite 页缓存（128MB）+ ImageSharp 解码缓冲（单张可达 80MB）。堆给到 896MB 时，RSS 峰值会到 1.1GB+，**在 900MB 的容器上限下会先被 cgroup OOM kill，而不是被 GC 拉住**。所以我把托管堆降到 **512MB**（`0x20000000`），让"GC 先于 OOM 发生"。

| 组件 | 参数 | 计算 | 目标 P95 RSS | 容器上限 |
|---|---|---|---|---|
| 内核 + dockerd + journald + page cache | `vm.swappiness=10`，建议 **加 2GB swap 兜底** | 不给 cgroup 限额，靠下面三项总额约束 | 350–450MB | — |
| `caddy` | 默认 GOGC | 静态文件 + 反代，几十个连接 | 30–50MB | 96M |
| `api` | `DOTNET_gcServer=0`（Workstation GC，架构指定）、`DOTNET_GCHeapHardLimit=0x20000000` | 512MB 堆 + 160MB 非托管 + 128MB SQLite cache + 余量 | **650–800MB** | 900M |
| `storefront` | `--max-old-space-size=320` | SSR 单请求峰值 3–8MB（HTML 100–300KB + 当前主题 chunk 28KB + i18n 5KB + 页面数据）；20 并发 ≈ 160MB；堆 320 = 2 倍余量 | 180–300MB | 400M |
| **合计** | | 上限 1.396GB，实测目标 ≤ 1.9GB | | 机器 2.048GB，余量 ~10% |

**SQLite 参数（固化，写在 `Program.cs` 连接字符串或启动钩子，`docs/03` §10.3 要求"部署文档固化"）**

```sql
PRAGMA journal_mode = WAL;          -- 读写不互斥；单写者仍串行
PRAGMA synchronous  = NORMAL;       -- 掉电只丢"最后未 fsync 的事务"，不会损坏库
PRAGMA cache_size   = -131072;      -- 负数 = KiB ⇒ 128MB 页缓存（计入 api 的 cgroup 内存！）
PRAGMA mmap_size    = 134217728;    -- 128MB（2G 机）；4G 机可设 268435456
PRAGMA busy_timeout = 5000;         -- 写锁等待 5s 后报 SQLITE_BUSY，由应用层重试一次
PRAGMA temp_store   = FILE;         -- ★ 不用 MEMORY：大排序会瞬间吃掉几十 MB
PRAGMA foreign_keys = ON;
PRAGMA wal_autocheckpoint = 1000;   -- ~4MB WAL 自动 checkpoint，防止 -wal 无限长
```

> **`synchronous=NORMAL` 的风险边界（要跟商家讲清）**：掉电可能丢"最近几秒已提交的事务"，极端情况下出现"通道侧已收款、本地无订单"。**这正是支付三路径（回调/手动刷新/定时对账）存在的意义**（架构 §5.5）：本地没单也能靠通道侧查询补出结论，不会产生资损。若商家对"丢几秒"零容忍（如日单量极大），改成 `synchronous=FULL`，代价是写延迟 ×3（本地 SSD 上从 ~0.2ms 到 ~0.6ms，本场景可忽略）。**我建议默认 NORMAL，并在 Runbook 里给出改 FULL 的一行说明。**

**mmap 的坑**：`mmap_size` 是 file-backed 映射，理论上可回收，但**在 cgroup v2 下 page cache 计入 `memory.current`**，所以它仍会挤压 900MB 上限 → 2G 机保守设 128MB，不要照抄 256MB。

**ImageSharp 的内存炸弹（必须堵）**：5MB 的 JPEG 可以是 6000×4000 像素，解码成 RGBA = **96MB**/张，3 档尺寸同时处理就是 300MB → 一次上传就能打爆 900MB。**必须**：上传时先 `Image.Identify()` 拿尺寸，**像素数 > 2400 万直接拒**（`IMAGE_TOO_LARGE`），并且串行处理（不并发解码多张）。这一条要写进 §2.1 的镜像环境变量或 appsettings，并由 QA 造一张"5MB / 8000×6000"的图做回归。

**4GB 档位（2C4G）**：`api` mem_limit 1400M / 堆 1G（`0x40000000`）；`storefront` 600M / 堆 384M；`caddy` 128M；SQLite `mmap_size=256M`。其余不变 —— **只改 `.env` 里的三个数**，compose 用变量注入：

```yaml
mem_limit: ${API_MEM_LIMIT:-900m}
```

### 2.6.1 AC-12 的内存验收：如何证明"没被 OOM Killer 杀"（而不是"看着还行"）

AC-12 要求：**三进程合计 RSS ≤ 2GB，连续 30 分钟压测不 OOM、不被 OOM Killer 杀死**。这条的难点不在压测，**在"被杀之后你怎么知道"** —— 被 OOM kill 的典型表现就是"进程莫名重启"，没有证据链会白查几天。所以先装观测，再谈压测。

**（1）OOM 的证据链（三个来源，缺一个就只能猜）**

```bash
# ① 容器级：OOMKilled 标志 + 重启次数（最直接）
docker inspect -f '{{.Name}} OOMKilled={{.State.OOMKilled}} Restarts={{.RestartCount}} ExitCode={{.State.ExitCode}}' \
  $(docker compose ps -q)
# 期望：OOMKilled=false, Restarts=0。ExitCode=137 = 被 SIGKILL（几乎必然是 OOM）

# ② cgroup 级：memory.events 的 oom_kill 计数会一直累加（重启也不清零）
for c in $(docker compose ps -q); do
  echo "$(docker inspect -f '{{.Name}}' $c): $(docker exec $c cat /sys/fs/cgroup/memory.events 2>/dev/null | tr '\n' ' ')"
done
# 期望 oom_kill 0；一旦非 0，说明这个容器在某个时刻确实被杀了

# ③ 内核级：journalctl 里的 OOM 记录（有完整内存快照与"谁杀的谁"）
sudo journalctl -k --since "7 days ago" | grep -iE 'out of memory|killed process' | tail -20
```

> **必须把 ① 的 `Restarts` 与 `OOMKilled` 纳入晨报与告警**：否则"进程每 3 小时重启一次"这种慢性故障会一直存在到商家发现"后台老是掉线"。建议 `watchtower.sh` 增加一条（作为第 6 条告警的候选）：`Restarts > 0 或 OOMKilled=true` → P1。

**（2）30 分钟压测脚本（不引压测工具，用 curl 并行循环就够）**

```bash
#!/usr/bin/env bash
# scripts/soak.sh —— 30 分钟压测 + RSS 采样 + 自动判定（对应 AC-12）
set -uo pipefail
D=${1:-https://localhost}; DUR=${2:-1800}; CONC=${3:-8}; OUT=/tmp/soak-$(date +%s).csv
echo "ts,api_mb,store_mb,caddy_mb,total_mb" > "$OUT"
urls=("$D/zh/" "$D/zh/c/robot-parts" "$D/zh/products/some-slug")
end=$(( $(date +%s) + DUR )); i=0
while [ "$(date +%s)" -lt "$end" ]; do
  for u in "${urls[@]}"; do
    curl -s -o /dev/null -w '%{http_code} %{time_starttransfer}\n' --max-time 10 "$u" >> /tmp/soak-req.log &
  done
  wait
  if [ $(( i % 10 )) -eq 0 ]; then           # 每 10 轮（≈几十秒）采一次内存
    stats=$(docker stats --no-stream --format '{{.Name}},{{.MemUsage}}' \
            | grep -E 'openstore-(api|storefront|caddy)' \
            | awk -F'[,/ ]+' '{print $2/1024/1024}')
    echo "$(date +%s),$(echo "$stats" | paste -sd,)" >> "$OUT"
  fi
  i=$((i+1))
done

# ---- 判定 ----
awk -F, 'NR>1{t=$2+$3+$4; if(t>max)max=t} END{printf "峰值合计 RSS = %.0f MB（上限 2048，预算 1900）\n", max;
        exit (max>1900)}' "$OUT" || { echo "FAIL: 内存超预算"; exit 1; }
awk '{print $2}' /tmp/soak-req.log | sort -n | awk '{a[NR]=$1} END{p=a[int(NR*0.95)];
        printf "TTFB P95 = %d ms（上限 500）\n", p*1000; exit (p>0.5)}' || { echo "FAIL: TTFB 超标"; exit 1; }
grep -qv ' 200$' /tmp/soak-req.log && { echo "FAIL: 压测期间出现非 200"; exit 1; }
docker inspect -f '{{.Name}} OOMKilled={{.State.OOMKilled}} Restarts={{.RestartCount}}' $(docker compose ps -q)
echo "PASS（原始数据：$OUT，单请求明细：/tmp/soak-req.log）"
```

**（2.5）AC-12 必须绑定硬件档位（team-lead 裁决，防"2C2G 永远不合格"的死结）**

AC-12 的基准数据（10k 商品 / 50k 变体 / 每分类 500）本来就是为**规模化店铺**设的，不能拿它去卡入门档硬件 —— 否则等于告诉买 2C2G 的客户"你不达标，请升配"。

| 档位 | 硬件 | 基准数据 | 验收口径 |
|---|---|---|---|
| **小店档** | 2C2G | ≤2,000 SKU / ≤10,000 变体 | AC-12 **全套指标**（TTFB P95 ≤500ms、LCP ≤2.5s、性能分 ≥70、RSS 合计 ≤2GB 不 OOM），但**按小数据量** |
| **标准档** | 2C4G | 10,000 SKU / 50,000 变体 | AC-12 **原口径** |

```bash
# soak.sh 接受"档位"参数，自动选对应数据集与预算（不给参数就按小店档，避免误判）
./scripts/soak.sh --tier small   https://localhost 1800 8   # 2C2G：2k SKU，RSS 预算 1900MB
./scripts/soak.sh --tier standard https://localhost 1800 12  # 2C4G：10k SKU，RSS 预算 3900MB
```

> **销售侧的诚实承诺**：买 2C2G 时给的是"小店档"的性能承诺（按 ≤2k SKU 验收），而不是"可能不达标"。**这比含糊其辞更安全** —— 含糊的后果是客户在 3k SKU 时踩线，然后双方对"当初承诺了什么"各执一词。
> 数据集造法必须写进 `scripts/seed-bench.sh --tier small|standard`，两个档位用**同一份生成逻辑、只改规模**，否则两档结论不可比。

**（3）压测的前提条件（不做就等于没测）**

| 前提 | 怎么造 |
|---|---|
| **10,000 商品 / 50,000 变体 / 每分类 500** | 用 `docs/03` 的种子工具或 SQL 批量插入；**必须造满，10k 与 100 个商品的结论完全不同** |
| **在 2 核 2GHz / 2GB 的真实规格上跑** | 8 核开发机上的结论不可用（GC 行为、并行度全变） |
| 冷/热缓存分别测 | 冷启动后立刻压 5 分钟（缓存未热）→ 再压 30 分钟（稳态）。**冷启动期最容易被 OOM 杀**（分类树 + 模板 + 首屏区块同时加载） |
| 关闭 `VACUUM INTO` 与定时任务干扰 | 压测期间 `OpenStore__Jobs__*__Enabled=false`（除了要测的任务），否则"备份吃 CPU 导致 TTFB 超标"会被误判成性能问题 |
| Lighthouse 移动端 LCP/性能分 | 单独用 Lighthouse CI 跑首页/分类/详情（依赖真实网络节流，不能与压测同时做） |

**（4）超标时先调哪个旋钮（按性价比排序）**

1. `--max-old-space-size` 与 .NET 堆的**比例**（不是总量）：先看 `docker stats` 里谁在涨
2. `PRAGMA cache_size`（128MB → 64MB，牺牲读性能换内存）
3. `mmap_size`（128MB → 64MB，同理）
4. api 的 `cpus`（1.5 → 2.0，减少排队、缩短内存驻留时间）
5. **最后**才是加内存/升档 —— 若 2G 上怎么调都过不去，说明 AC-12 的基准数据量与 2G 不匹配，要回到 PM 讨论（**这可能推翻"2C2G 起"的定位，不是我一个人能拍的**）

### 3.1 完整 Caddyfile

```caddyfile

	email {$ACME_EMAIL:admin@example.com}

	# local_certs

	# 只信任私网来源的 X-Forwarded-* （本机只有我们自己的容器/进程）
	servers {
		trusted_proxies static private_ranges
	}

{$OPENSTORE_DOMAIN:localhost} {
	encode zstd gzip

	# ---------- 安全响应头（全站兜底；CSP 由应用侧下发，避免两处漂移）----------
	header {
		Strict-Transport-Security "max-age=31536000; includeSubDomains"
		X-Content-Type-Options    "nosniff"
		Referrer-Policy           "strict-origin-when-cross-origin"
		Permissions-Policy        "camera=(), microphone=(), geolocation=(), payment=(self)"
		Cross-Origin-Opener-Policy "same-origin"
		-Server
	}

	# ---------- 上传体积：与后端 5MB 图片上限对齐 ----------
	# 5MB 文件 + multipart 边界/其它字段 ⇒ 8MB 足够；超出由 Caddy 直接 413（不进应用，省内存）
	request_body {
		max_size 8MB
	}

	# ---------- 0) 健康探针不对外暴露（仅容器内/宿主 curl 可用）----------
	@health path /health /health/*
	respond @health 404

	# ---------- 1) 安装向导：未安装时 / 会 307 到这里；完成后应用返回 404 ----------
	handle /setup* {
		reverse_proxy {$STOREFRONT_UPSTREAM:storefront:3000} {
			header_up X-Real-IP        {remote_host}
			header_up X-Forwarded-For  {remote_host}
			header_up X-Forwarded-Proto {scheme}
			header_up X-Forwarded-Host {host}
			transport http {
				dial_timeout            3s
				response_header_timeout 30s
			}
		}
	}

	# ---------- 2) admin 静态 SPA（handle_path 去前缀，产物引用 /admin/_app/...）----------
	redir /admin /admin/ 308
	handle_path /admin/* {
		root * {$ADMIN_ROOT:/srv/admin}

		# ★ 这三条必须由反代下发：静态文件不经过应用，应用没有机会加头。
		#   - X-Robots-Tag：AC-11 索引矩阵 (c) 类 —— 允许抓取 + noindex（写 Disallow 反而变裸链接）
		#   - X-Frame-Options：老浏览器兜底（CSP frame-ancestors 已覆盖新浏览器）
		#   - CSP：必须与后端 docs/03 §8.4 的 admin CSP **逐字一致**（见 §3.6"两处下发的漂移风险"）
		#   ⛔ 绝对不要把这几个头挪到站点级（文件顶部那个 header {}）—— 那会给商城端也打上 noindex，
		#      整个店铺从搜索结果里消失。这是本文件最危险的一种"顺手改动"。
		#   ✅ 放在 handle_path 内部还有两个必要理由：① 路径被剥离后 matcher 才对得上
		#      ② 头会覆盖本块所有响应，**包括 try_files 回落出来的 index.html**
		#      （否则 /admin/login 这种前端路由的 200 会裸奔，后台登录页被收录）
		#   注：/admin（无尾斜杠）走上面的 308 重定向，重定向响应不需要该头（不构成可索引页面）
		header {
			X-Robots-Tag          "noindex, nofollow"
			X-Frame-Options       "DENY"
			Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'self'; object-src 'none'"
			-Server
		}

		@immutable path /_app/immutable/*
		header @immutable Cache-Control "public, max-age=31536000, immutable"

		@nofallback path /index.html /
		header @nofallback Cache-Control "no-cache"

		# 其余路径（/admin/orders、/admin/products/123）一律回落 index.html
		# ⚠️ 注意：这个 fallback 只在"文件不存在"时生效，**不会**把 5xx 变成 200（见 §3.7）
		try_files {path} /index.html
		file_server
	}

	# ---------- 3) API（含 webhook 回调路径 /api/webhooks/*）----------
	handle /api/* {
		reverse_proxy {$API_UPSTREAM:api:5080} {
			# ★ 覆盖而非追加：Caddy 默认会把客户端自带的 XFF 保留并在其后追加，
			#   恶意客户端可借此伪造 IP 绕过限流。这里直接覆盖成真实对端地址。
			header_up X-Real-IP         {remote_host}
			header_up X-Forwarded-For   {remote_host}
			header_up X-Forwarded-Proto {scheme}
			header_up X-Forwarded-Host  {host}
			header_up X-Forwarded-Port  {server_port}
			transport http {
				dial_timeout            3s
				response_header_timeout 30s   # 通道调用 3s 超时 ×2 + 落库；>30s 视为挂死
			}
		}
	}

	# ---------- 4) 媒体文件（URL 含内容指纹：StorageKey = 2025/06/{sha256前16}）----------
	handle_path /media/* {
		root * {$MEDIA_ROOT:/srv/media}

			hide .*
		}
	}

	# ---------- 5) 其余全部走 storefront SSR（含 /、/{locale}/*、/sitemap.xml、/robots.txt）----------
	handle {
		reverse_proxy {$STOREFRONT_UPSTREAM:storefront:3000} {
			header_up X-Real-IP         {remote_host}
			header_up X-Forwarded-For   {remote_host}
			header_up X-Forwarded-Proto {scheme}
			header_up X-Forwarded-Host  {host}
			header_up X-Forwarded-Port  {server_port}

		}

	log {
```

### 3.2 四个容易配错的地方（都要有回归断言）

| # | 坑 | 正确做法 | 断言 |
|---|---|---|---|
| 1 | **`handle_path` vs `handle`**：admin 的 SvelteKit `base='/admin'`，产物里引用 `/admin/_app/...`，文件在磁盘上是 `_app/...` | 必须用 `handle_path /admin/*`（去前缀）；用 `handle` + `root` 会 404 全部静态资源 | `curl -I https://d/admin/_app/immutable/entry/app.js` → 200 且 `immutable` |
| 2 | **`/media` 目录层级**：请求 `/media/2025/06/ab12-800.webp`，磁盘是 `/data/media/2025/06/ab12-800.webp` | `handle_path` 去前缀 + `root /srv/media` | `curl -I https://d/media/...` → 200 + `immutable` |
| 3 | **HTML 缓存**：反代若对 HTML 加 `s-maxage`，换主题/改价后用户看不到 | **Caddy 不对 HTML 设任何 `Cache-Control`**，完全交给 SSR 的 `setHeaders`（公开页 `max-age=60, swr=300`；带 cookie 页 `private, no-store`） | 改主色后无痕窗口刷新 ≤5s 生效（AC-13） |
| 4 | **把 admin 的 `X-Robots-Tag` 挪到站点级 `header {}`** | 只在 `handle_path /admin/*` 内部加。站点级会命中商城全部页面 → **整个店铺从搜索结果里消失**，而且这种事故通常要等到"销量下滑"才被发现 | `curl -sI https://域名/zh/ \| grep -i x-robots-tag` → **必须为空**；`curl -sI https://域名/admin/login \| grep -i x-robots-tag` → **必须命中** |

### 3.3 安全响应头与 `style-src 'unsafe-inline'` 的取舍

CSP 由**应用侧**下发（`docs/03` §8.4），Caddy 只补通用头 —— 因为 CSP 需要区分 storefront/admin 且与主题内联样式强相关，放反代会与代码漂移。

**为什么 storefront 必须放开 `style-src 'unsafe-inline'`（三条，缺一即坏）**

1. 主题 token 以**内联 `<style>`** 注入（`+layout.svelte` 的 `tokensToCss`）—— 这是"运行时换色不重新编译"的唯一实现路径；改外链 CSS 会多一次请求 + FOUC。
2. Svelte 5 的 `transition:`/`animate:` 在运行时写 `element.style`，属框架行为，无法构建期消除（需要 CSP3 的 `style-src-attr` 覆盖）。
3. 图片容器用内联 `style="aspect-ratio:…"` 防 CLS（动态值，静态化不了）。

**如何用其它头补偿（这是"取舍"而不是"放弃"）**

| 补偿手段 | 落地 |
|---|---|
| `script-src 'self'` 严格不放行内联与 `eval` | CSP 的核心防线在脚本；**`unsafe-inline` 只开 style，攻击者拿到样式注入也拿不到执行能力** |
| 富文本入库前 sanitize 并**剥离 `style` 属性与 `<style>` 标签** | `docs/03` §8.4；集成测试断言"注入 `<style>*{display:none}</style>` 后前台 HTML 不含该标签" |
| `frame-ancestors 'none'` + `X-Frame-Options: DENY`（admin） | 防点击劫持（样式注入的典型利用场景） |
| `object-src 'none'`、`base-uri 'self'`、`form-action 'self'` | 堵住 `<base>` 劫持与表单外发 |
| `Cross-Origin-Opener-Policy: same-origin` + `Permissions-Policy` | 收缩侧信道 |
| HSTS `preconnect` 前置条件 | **HSTS 只在"域名与证书已稳定"后开启**；首次部署若域名/IP 还在调整，先注释掉，避免把自己锁在 HTTPS-only 里 |

> **Caddy 层不给 storefront 加 CSP**：一旦为了方便在 Caddy 的 site 级 `header {}` 里加 `Content-Security-Policy`，它会**覆盖**应用下发的 CSP（同一响应头只能有一个值），结果是 storefront 与 admin 拿到同一套策略 —— 这正是"两处配置漂移"的典型形态。
> **但 admin 是例外，必须由 Caddy 下发**：admin 是**纯静态文件**，请求根本不经过 api，应用没有机会给它加任何安全头。所以规范是精确的：**每条路径的 CSP 只有一个来源** —— storefront（`/`、`/{locale}/*`）来自应用，`/admin/*` 来自反代，两者互不重叠（§3.6 给了防漂移的检查手段）。

### 3.4 真实 IP 传递（这是修复一个实际 bug，不是优化）

**Bug 形态**：`docs/03` §12.1 R8 已指出 —— 反代后取 IP 若拿到的都是反代地址，`login` 策略的分区键退化为常量，**5 次/分钟** 的登录限额会被一个人用完后全站登录 429；`checkout-submit`、`order-lookup`、`global` 全部同理。更严重的是 `webhook` 的 IP 允许列表（`Security__WebhookIpAllowList`）会完全失效。

**修复需要三段同时正确，缺一段就退化：**

```
浏览器 ──(真实 IP)──> Caddy ──(XFF 覆盖写)──> api
                          └──> storefront(SSR) ──(把 getClientAddress() 放进 XFF)──> api
```

| 段 | 配置 | 说明 |
|---|---|---|
| ① Caddy → api | `header_up X-Forwarded-For {remote_host}`（**覆盖**） | Caddy 默认是追加，会把客户端伪造的 XFF 保留在前段。覆盖写 = 只有一跳可信来源。 |
| ② Caddy → storefront | 同上 + `ADDRESS_HEADER=X-Forwarded-For`、`XFF_DEPTH=1` | SvelteKit `getClientAddress()` 才能拿到真实 IP。`XFF_DEPTH=1` 表示"从右数第一段是最靠近我的代理写入的"。 |
| ③ storefront → api | SSR 发起请求时把 `getClientAddress()` 写进 `X-Forwarded-For` | 否则 API 看到的是 storefront 容器 IP（172.28.0.x），所有 SSR 请求共享一个限流桶。 |
| ④ api 侧 | `ForwardedHeadersOptions { ForwardedHeaders = XForwardedFor\|XForwardedProto\|XForwardedHost, ForwardLimit = 1, KnownNetworks = 172.28.0.0/24 }`（systemd 模式为 `127.0.0.1/32`） | **只信任我们自己的反代/SSR 所在网段**；`ForwardLimit=1` 表示只处理最后一跳。**不要** `KnownNetworks.Clear()` 后全放开（等于把伪造权交给公网）。 |

**验收断言（CI 集成测试 + 部署后手测）**


### 3.5 上传体积与超时（与后端对齐）

| 项 | 值 | 依据 |
|---|---|---|
| 全局 `request_body max_size` | **8MB** | 后端图片上限 5MB（架构 §6 安全⑥）；multipart 开销 + 富文本字段留 3MB 余量 |
| 超限响应 | Caddy 直接 `413`（不进应用） | 保护 900MB 内存：不让 100MB 请求先进 Kestrel 再被拒 |
| `/api/*` `response_header_timeout` | 30s | 通道调用 3s 超时 ×（建意图 + 查询）+ 落库；退款/导出走 202 异步，不会更久 |
| `/setup*`、`/` `response_header_timeout` | 30s | 向导"应用模板"是一个大事务（分类+商品+变体+库存+设置），2GB 机器上 10k 商品量的模板也在 5s 内；30s 是兜底 |
| `dial_timeout` | 3s | 上游容器挂了要快速失败，而不是挂着等 |
| 长任务 | **不用长连接**：导出备份/批量操作返回 `202 + jobId` 轮询（`docs/03` §5.4） | 反代与浏览器都不需要超长超时 |
| 优雅停机 | `stop_grace_period: 30s` | 让在飞的支付结算与 outbox 派发跑完；`BackgroundService` 收到 `CancellationToken` 后停止接新批次 |

### 3.6 索引控制：`Disallow` 与 `noindex` 的分工（AC-11 矩阵的部署侧落点）

**铁律**：`Disallow` 只阻止抓取、不阻止收录。被 Disallow 的 URL 若有链接指向，仍会以"无标题无描述裸链接"进搜索结果，**而此时爬虫读不到页面上的 `noindex`，也读不到 `canonical`** —— 两者叠加是**最差结果**。

#### 3.6.1 切分原则（先读这三条，再看表）

1. **`Disallow` 从不用于表达"别收录"**。它唯一的合法用途是"别抓"，本站只有一条：`Disallow: /api`。
2. **每一档只用一种信号**：该收录的用 `canonical` 归并，不该收录的用 `noindex`，**两者不叠加**。
3. **谁加头**：**文件经过应用的，由应用加；不经过应用的，由反代加。** 按此切就不会出现"两边都加 → 两条冲突指令"。`/admin` 是纯静态产物，永远不经过 Node 也不经过 .NET，所以它的 `X-Robots-Tag` **只能由 Caddy 加** —— 这是 §3.1 里唯一注入索引头的地方。

#### 3.6.2 六档落点（语义见 `docs/01` §6.1，本文只写"谁实现、反代做什么"）

| 档 | URL 形态 | 唯一信号 | 谁实现 | Caddy 动作 | 断言 |
|---|---|---|---|---|---|
| **(a)** 私有页 | `/{locale}/cart`、`/checkout`、`/checkout/result`、`/account/*`、`/orders/track`、`/{locale}/_preview`、`/setup/*` | 允许抓取 + `noindex,follow`，**不输出 canonical** | storefront（`NOINDEX_PATTERNS` **一张模式表**，不逐语种枚举） | **不加任何头** | S1 S2 |
| **(b1)** 筛选/排序 | `/{locale}/c/{slug}?f.x=y[&sort=…]` | 允许抓取 + `canonical` → 无参数第 1 页；**无 noindex** | storefront SSR | 不加 | S3 |
| **(b1∩分页)** 筛选 × 分页 | `…?f.x=y&page=2` | **同样 → 无参数第 1 页**（不是 `?page=2`，也不是自引用） | storefront SSR | 不加 | S3 |
| **(b2)** 站内搜索 | `/{locale}/search?q=` | 允许抓取 + `noindex,follow` + **不输出 canonical** | storefront | 不加 | S6 |
| **(b3)** 商品详情 | `/{locale}/products/{slug}`（含 `utm_*`） | `canonical` **永远自引用**，追踪参数只从 canonical 剔除 | storefront SSR | 不加 | S5 |
| **(c)** 管理端 | `/admin/*`（含 SPA fallback 落到 `index.html` 的所有深链） | 允许抓取 + `X-Robots-Tag: noindex`；**不 Disallow** | **Caddy** | **必须加**（§3.1 已加，且只在 `handle_path /admin/*` 内） | S9※ |

**另有三条不属于分档、但必须断言**：

| 项 | 要求 | 断言 |
|---|---|---|
| 无筛选的分类分页 | 第 2 页起 `canonical` **自引用**（不是第 1 页） | S4 |
| `robots.txt` 本身 | **全文只有 `Disallow: /api` 一条**，不含任何前台路径、不含 `?`/`&`/`*` | S7 |
| 三条信号之间 | 任意 URL **不得**同时命中 Disallow 与 noindex / Disallow 与外指 canonical / noindex 与跨 URL canonical | S8 |

> **本文不再复制 AC-11 的判定正文。** 判据的事实源是 `docs/01` §6.1 的**全部 S 档**（(c) 档 `/admin` 亦已入库，见 3.6.3），机器判据的唯一载体是 `scripts/verify-seo-matrix.sh`。理由不是"省字数"：这张矩阵在 **需求 / 架构 / 后端 / 前端 / 运维** 五处各写过一遍，改一处必漏四处（W9/W12/W14/W15/W16/W20 六条台账全部由此产生）。**本文只做需求文档不做的那两件事**：① 谁实现、反代要不要加头；② 脚本怎么落地、怎么自证它不是橡皮图章。
>

**脚本里三个容易被"优化"掉的取舍（写清理由，防止后人统一一下）**

| 取舍 | 为什么 |
|---|---|
| 跟 302 时**链上任一跳**带 noindex 即算命中 | 被 302 的 URL 自身也可能以裸链接进结果，所以"只看最终页"会漏判；`/{locale}/account` → `/account/login` 就是这种形态 |
| `noindex + 自指 canonical` 记 **WARN 不记红** | `docs/01` §6.1 只明令禁止**跨 URL** 的 canonical；自指属冗余无害。若 PM 要求全禁，把脚本里那行 `warned` 改成 `fail`（一行） |
| sitemap 里**自动发现**而不是写死 URL | 写死 slug 的脚本在换模板/换语言的第一天就失效，而失效的表现是"绿"（`curl` 404 也算断言通过），这是最坏的失效方向 |

**⚠️ 前端联调项（S1 会把这条打成红，请提前处理）**

(a) 类的购物车/结算/账户/查单/向导在 storefront 里是 `ssr = false`。如果 `noindex` 只写在组件的 `<svelte:head>` 里，那么**不执行 JS 的爬虫（以及本脚本）拿到的是没有该标签的 HTML** —— 而 AC-10 的前提正是"不执行 JS 也能读到"。**最省事的解法**：`lib/server/robots.ts` 的 `NOINDEX_PATTERNS` 已经在服务端可用，在 `hooks.server.ts` 里对命中模式的请求统一 `setHeaders({'X-Robots-Tag': 'noindex, follow'})` —— 一行覆盖所有语种、所有 CSR 页面，顺带覆盖非 HTML 资源（与 (c) 档选 `X-Robots-Tag` 而非 meta 是同一个理由）。这也是 §3.6.1 第 3 条原则的正确落法：**文件虽然由 Node 输出，但 header 由 Node 加，不劳 Caddy**。

#### 3.6.4 连带影响：放开筛选抓取 → **限流必须按方法分层**（否则会被"优化"回去）

**因果链是我们自己的决策种下的，写清楚以防下一个人收紧 GET**：

```
需求侧决定「筛选参数页允许抓取 + canonical 归并」（正确：Disallow 会让 canonical 读不到）
   ↓
爬虫会去抓约 15,000 个参数 URL（抓取量从千级升到万级）
   ↓
若只有一个 global 桶（600/min/IP）→ 爬虫吃满 → 429
   ↓
搜索引擎把 429 读作"服务器压力大"，主动降抓取频率
   ↓
商品页收录反而变慢（抓取预算被参数页吃掉，边际收益为负）
   ↓
结论：限流按「请求方法」分层，而不是简单调大阈值
```

**team-lead 裁决：不引入爬虫 IP 白名单，按 HTTP 方法分桶**（`CrawlerCidrs` 已否决）。两个理由记下来防重提：① Googlebot/Bingbot 网段会变 → 白名单过期后要么误放（把伪造者当爬虫）要么误拦（真爬虫被限），等于给静态配置挂一个永不结束的维护任务；② **爬虫与真实用户的区别不在 IP，在请求方法 —— 爬虫只发 `GET`，从不发 `POST`。**

| 策略（`docs/03` §6.7 需按此改） | 适用方法 | 阈值 | 为什么 |
|---|---|---|---|
| `read` | `GET`/`HEAD` | **1200 次/分钟/IP**（20 rps） | 爬虫抓的就是这些；单店真实峰值通常个位数 rps |
| `write` | `POST`/`PUT`/`PATCH`/`DELETE` | **60 次/分钟/IP** | 真实用户不会一分钟下 60 单；**抗刷能力主要靠这层** |
| `login` | 登录端点 | 失败 5 次锁定 | 独立于上面两层 |
| `webhook` | 支付回调 | 独立 + IP 允许列表 | 通道重投可能密集，不能被 `write` 误伤 |

> **抗刷能力并没有因为放宽 `read` 而下降**：真正需要保护的动作（下单/登录/改价/退款/上传）全在 `write`/`login` 层，而爬虫**碰不到这些**。这是结构性划分，不是调参。
> **⛔ 看到"GET 1200/分钟"想收紧的人，先读完上面那条链。** 收紧 `read` 的直接后果不是"更安全"，是"爬虫降速 → 商品页收录变慢"，而这件事**不会报任何错**。

**部署侧三个动作**

1. **不在 Caddy 做 UA 白名单**：UA 可任意伪造，且限流在应用侧（反代拦不住也绕不过），在反代做只会制造"以为放行了其实没有"的错觉。
2. **验收断言（分组独立，不依赖任何 IP 白名单）**：
   ```bash
   # 连续 GET 不应导致第一个 POST 被 429（证明 GET 与写操作不同桶）
   for i in $(seq 1 100); do curl -s -o /dev/null "https://$D/zh/"; done
   curl -s -o /dev/null -w '%{http_code}\n' -X POST "https://$D/api/cart/items"   # 期望 非 429
   # 连续 POST 不应导致 GET 被 429（证明写桶满不影响读）
   for i in $(seq 1 60); do curl -s -o /dev/null -X POST "https://$D/api/cart/items"; done
   curl -s -o /dev/null -w '%{http_code}\n' "https://$D/zh/"                      # 期望 200
   ```
3. **观测**：晨报保留 `429 计数`（§7.4 的判读指引），这是唯一能发现"静默劣化"的手段。
4. **`webhook` 必须从 `write` 里排除**：`POST /api/webhooks/*` 在路由上独立成策略。后端另需处理"双桶叠加"：`write` 60/分钟与端点级 `cart-write` 60/分钟完全重合，要么合并、要么把 `cart-write` 降到 30 让"端点级更严"真实成立（已发后端，见 `docs/03` §6.7 修订）。

**另外三条部署侧纪律**

1. **不要给 storefront 的响应加任何 `X-Robots-Tag`**：Caddy 的 `header` 写在 site 级会命中所有路径，一旦加上就与应用的 per-route 输出打架（同一响应两条不同指令时行为不可预期）。§3.1 只在 `/admin` 的 handle 内加，就是这个原因。
2. **`robots.txt` 与 `sitemap.xml` 必须由 storefront 输出并透传**：走 §3.1 最后的兜底 `handle`，反代**不 rewrite、不缓存、不静态替换**。特别注意别给 `robots.txt` 设长缓存（改 `PublicSiteUrl`、加语种后要立刻生效）。
3. **观测项（上线后 4 周，非阻塞）**：看 Search Console 的抓取统计与已收录页面数，验证"允许抓取参数页"这一决策的实际收益。若出现"参数页吃满抓取预算、商品页收录反而变慢"，**调整方向是给官方爬虫 IP 段放行/放宽限流（`CrawlerCidrs`），不是改回 `Disallow`** —— 改回 Disallow 会连带毁掉 (b1) 的 canonical 归并。注意这条与 team-lead"现在不做 CrawlerCidrs"的裁决**不矛盾**：现在不做是因为方法分桶已经解决了问题；4 周后的观测若证伪，那时才补白名单，且只作为"放宽 read 桶"的补充，不替代分桶。

#### 3.6.5 admin 的 CSP"两处下发"漂移（与索引无关，但同属"两处定义"）

`/admin/*` 的 CSP 现在是 `deploy/Caddyfile` 里的一份字符串 + `docs/03` §8.4 里的一张表，**两份会漂移**（这正是上面 W20 说的同一个病）。**已裁决用两步守，不加 `emit-csp`**（不为一个检查引入永久维护面，Q12）：

1. **源字符串比对**：从 Caddyfile 与后端常量提取 admin CSP 串，规范化后逐字比，不一致即红。**它只能防"改了一处"。**
2. **实际响应断言（必须）**：E2E 请求 `/admin/` 与 storefront 首页，断言各自 CSP 符合预期，**且 admin 的 CSP 必须存在**。这条抓的是"**两处都没写**"—— 字符串比对抓不到这种，因为它比较的是两坨可能同时消失的东西。

### 3.7 状态码保真：5xx **不得**被改写成 2xx（AC-10 负向断言的部署前提）

**这是反代侧最容易踩、且踩了没人发现的一个坑。**

```nginx
# ❌ 灾难写法：503 被替换成一个 200 的静态页
proxy_intercept_errors on;
error_page 500 502 503 504 /maintenance.html;      # 返回 200 → 空壳页被收录
```

```caddyfile
# ❌ 同样灾难：handle_errors 里 rewrite 到静态文件，状态码会变成 200
handle_errors {
    rewrite * /maintenance.html
    file_server
}
```

| 为什么严重 | 说明 |
|---|---|
| 爬虫看到的是"页面正常、只是没内容" | 于是把空壳页**收录**进索引；等你想让它掉出索引要几周，期间用户点进来看到空店 |
| **空壳页被索引比不索引更糟** | AC-10 的负向断言正是为此：禁止 200 的空白商品页 |
| 运维视角的隐性伤害 | 监控探到你返回 200 → `watchtower.sh` 第 1 条告警**永远不响**，你以为站点好好的 |

**正确做法（要维护页时）**

```caddyfile
# ✅ 保留状态码（Caddy 里 {err.status_code} 是占位符，respond 用它当状态码）
handle_errors {
    @down expression {err.status_code} >= 500
    respond @down "店铺维护中，请稍后（{err.status_code}）" {err.status_code}
}
# ✅ nginx 等价：error_page 503 =503 /maintenance.html;    ← 等号后的 =503 是关键
```

**我这份配置为什么天然安全**：§3.1 里**没有** `error_page` / `proxy_intercept_errors` / `handle_errors`；唯一的 fallback 是 `/admin` 内的 `try_files`，它只在"**文件不存在**"时回落 `index.html`，与上游状态码无关。**正确链路是：storefront 探测到 API 不可用 → 自己返回 503（`docs/03` §10.1 的降级约定）→ Caddy 原样透传。**

**部署后必须做的破坏性验收（一条，不可省）**

```bash
# 断开后端，验证 503 活着走到客户端
docker compose stop api
curl -sI https://$D/zh/products/any-slug | head -1     # 期望 HTTP/2 503（★ 绝不能是 200）
curl -s  https://$D/zh/products/any-slug | grep -o '<meta name="robots"[^>]*>'  # 期望含 noindex
docker compose start api && ./scripts/wait-ready.sh
```

**另外两条相关约束**

- **不要给 storefront 上游配主动健康检查来"自动兜底"**：单上游场景下，`health_uri` 失败会让 Caddy 直接返回 502（状态码仍是 5xx，可接受），但它会**掩盖应用自己渲染的 503 错误页**（用户从"友好提示 + 重试按钮"变成"502 Bad Gateway"）。单上游不配健康检查，靠容器 `HEALTHCHECK` + `depends_on` 即可。
- **`Retry-After` 要透传**：应用返回 503 时带 `Retry-After: 30`（`docs/03` §10.1），反代不得覆盖或丢弃该头。

### 3.8 绝对 URL：`PublicSiteUrl` 不靠探测、不靠 Host 头

**需求（AC-10，现行有效）**：所有 canonical / `og:url` / `og:image` / `hreflang` / sitemap 的绝对 URL 必须由 **`PublicSiteUrl` 配置项**生成，**不得使用请求 Host 头**，且 `PublicSiteUrl` 优先级高于任何请求头。

**为什么这是安全问题**：攻击者构造伪造 Host 的请求，服务端就会把 `canonical: https://evil.com/...` 输出到一个可被爬虫访问的 URL 上 —— **等于把商品页的索引权重整体转让给攻击者**。"探测一下再兜底"不足以防御。

**部署侧的四件事**

| # | 事项 | 说明 |
|---|---|---|
| 1 | **向导的"自动探测"值必须由商家确认，不能直接采信** | 反向代理/容器下探测常错：拿到容器内网 IP（`172.28.0.x`）、`http` 而非 `https`、带内部端口（`:5080`）。Runbook 第 8 步显式要求"确认 `PublicSiteUrl` 是 `https://你的域名`（无尾斜杠、无端口）才能下一步" |
| 2 | **域名双源：启动时硬比对，不一致拒绝启动**（★ 见下，这条不能靠文档提醒） | `OPENSTORE_DOMAIN_URL`（部署期，→ storefront 的 `ORIGIN`，影响 TLS/路由/CSRF）与 `PublicSiteUrl`（运行期，DB 设置，影响 canonical/sitemap/OG）是**同一个决定写在了两个地方**。商家换域名时完全可能只改一处 |
| 3 | **反代不参与生成 URL，只做"未知 Host 直接 404"的纵深防御** | §3.1 的 site 地址是具体域名（`{$OPENSTORE_DOMAIN}`），Caddy 对不匹配的 Host 直接 404 —— 伪造 Host 连应用都到不了。注意：**若商家把 `OPENSTORE_DOMAIN` 配成通配/多域名，这层防御就没了**，此时全靠应用侧的 `PublicSiteUrl` |
| 4 | **改 `PublicSiteUrl` 必须立即生效，不许重启** | 它是 DB 设置（向导/后台写入），环境变量 `OpenStore__PublicBaseUrl` 只作初始值兜底。验收见下 |

#### 2.1 域名双源必须是"启动拒绝"，不是"文档提醒"（team-lead 裁决）

**为什么不能靠提醒**：本项目返工全部是"同一个决定被写进两个地方后各自演化"。域名正好是两个地方，且**不一致时的症状是"表单全 403"或"canonical 指旧域名"** —— 前者会被当成权限问题查半天，后者会**静默跑一个月**（站点能开、能下单，只是 SEO 数据全错，等发现时已被索引）。

**要求（后端实现，部署侧依赖）**

- **启动路径上比对**：取 `OPENSTORE_DOMAIN_URL`（或 Caddy 侧 `ORIGIN`）与 DB 的 `PublicSiteUrl`，**规范化后比对**（scheme + host + 端口；**忽略尾斜杠**、忽略大小写、补齐默认端口），不一致则**拒绝启动**。
- **不要降级为 WARN**：警告会被忽略。
- 错误信息必须可操作（照抄即可给商家看）：

```
域名配置不一致：Caddy ORIGIN=https://a.com，PublicSiteUrl=https://b.com
两者必须指向同一站点。请检查 .env 的 OPENSTORE_DOMAIN_URL，
或到管理端「系统设置 → 站点地址」修改 PublicSiteUrl。
```

- **`/health/ready` 也要报告该项**（`checks.siteUrl: "mismatch(a.com≠b.com)"`），这样"启动被拒"之后运维在宿主 `curl 127.0.0.1:5080/health/ready` 就能看到原因，不用翻日志。
- **一个必须放行的例外**：`/setup` 未完成时的首次启动（此时 DB 里还没有 `PublicSiteUrl`）→ 此时应**跳过比对**，不能因为"还没装"就起不来。这也是 `/health/ready` 明确"不检查安装状态"的同一个道理。

**由此带来的运维简化**：换域名 Runbook 的判定点从"人工核对两处"改成"**启动能过 = 配置一致**"（见下方第 2 步）。

**验收（3 条命令，一次性证明"跟随"与"防注入"）**

```bash
# ① 改值后立即跟随（后台把 PublicSiteUrl 改成 https://new.example.com，不重启）
curl -fsS https://new.example.com/zh/ | grep -oE '(canonical|og:url)[^>]*' | head -3   # 应全部是新域名
curl -fsS https://new.example.com/sitemap.xml | grep -o 'https://[^<]*' | sort -u | head  # 全部新域名
# ② 不随 Host 漂移（伪造 Host 应被 Caddy 404 掉）
curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: evil.com' https://$D/zh/            # 期望 404
# ③ 容器内网地址绝不外泄
curl -fsS https://$D/zh/ | grep -cE '172\.28\.|:5080|:3000|http://'                    # 期望 0
```

**域名迁移 Runbook（商家换域名时，30 分钟）**

1. DNS 新域名解析到同一 IP → 等 TLS 自动签发（`curl -I https://new/` 200）
2. **同时改两处**：`.env` 的 `OPENSTORE_DOMAIN_URL`（改完 `docker compose up -d` 生效）+ 后台「系统设置 → 站点地址」的 `PublicSiteUrl`
3. **判定点：启动能过 = 配置一致**（不再人工核对两处）。若两处不一致，api **会拒绝启动**并打印"域名配置不一致：ORIGIN=… PublicSiteUrl=…"；此时 `curl 127.0.0.1:5080/health/ready | jq .checks.siteUrl` 也能看到 mismatch 明细 —— 改完再起
4. 起站后验证"跟随"：canonical / sitemap 已是新域名（下方验收 ①）
5. Caddyfile 增加旧域名 site block，**301 到新域名并保留路径与查询串**：
   ```caddyfile
   old.example.com {
       redir https://new.example.com{uri} permanent   # 301
   }
   ```
6. **不要删旧域名的 301**，至少保留 12 个月（历史外链与已收录 URL 全靠它）
7. 通道后台改回调地址与 `ReturnUrlBase` → 重跑 §8.3-B 回调自检
8. `curl` 抽查 10 个已收录 URL 的跳转链（一条 hop，不出现 301→302 连环）

### 3.9 HTTPS 强制与 Cookie 安全属性（同一个根因，两种症状）

**故障模式（很常见，且难查）**：TLS 终止在 Caddy，app 看到的是 `http`。若 `UseForwardedHeaders` 没生效，`UseHttpsRedirection` 会把每个请求 307 到 https → Caddy 再转成 http 打给 app → **无限重定向循环**（浏览器报 `ERR_TOO_MANY_REDIRECTS`）。同一个根因的另一个症状是：app 认为自己在 http，于是**会话 Cookie 不加 `Secure`**（安全基线不满足，AC-15）。

| 项 | 正确配置 | 说明 |
|---|---|---|
| TLS 终止位置 | **Caddy**（唯一入口） | 证书、HSTS、80→443 都在 Caddy；app 只监听 http:5080 内网 |
| `X-Forwarded-Proto` | Caddy 传 `{scheme}`（§3.1 已配）+ app 侧 `KnownNetworks` 信任它 | **这是 §3.4 同一处配置**：真实 IP 修不好，Cookie `Secure` 与重定向循环也跟着坏。三个症状一个根因 |
| `Security__ForceHttps` | 默认 `true`（架构） | 但只有在 `X-Forwarded-Proto` 被正确读取时才能为 true。**若出现重定向循环，二选一**：① 修 `TrustedProxies`（首选）；② 临时 `ForceHttps=false` 应急（Caddy 已经在做 80→443 强制，不会真的裸奔），并在日志里标 `WARN` |
| Cookie 属性 | `Secure` + `HttpOnly` + `SameSite=Lax`（管理端 `os_admin`、顾客端 `os_shop_sid`）；**不设 `Domain`** | 同域部署下 `Domain` 只会扩大作用域（子域串 Cookie）；不设 = 只对当前主机生效，最安全 |
| `upgrade-insecure-requests` | 只在**真 HTTPS** 环境下有效 | ⚠️ staging 若用 http 自测，storefront CSP 里的这条会让所有资源请求升级到 https 而失败 → 用 `OpenStore__Security__Csp__Storefront` 逃生口去掉它，**但生产必须带** |

**验收（两条，写进 §8.3 检查单）**

```bash
# ① 无重定向循环：一次跳转就到位
curl -sI http://$D/zh/ | head -3        # 期望 1 个 308/301 → https，且 https 响应是 200（不是再一次 307）
curl -sIL http://$D/zh/ | grep -c '^location:'   # 期望 1

# ② Cookie 三属性齐全（登录后看管理端会话 Cookie）
curl -sD- -o /dev/null -X POST "https://$D/api/admin/auth/login" \
     -H 'content-type: application/json' -d '{"email":"…","password":"…"}' \
  | grep -iE '^set-cookie:' | grep -E 'Secure' | grep -E 'HttpOnly' | grep -E 'SameSite'
# 期望：三条都命中；任一缺失 = AC-15 安全基线不满足
```

## 4. CI/CD

### 4.1 阶段与门禁顺序（关键：哪个先跑、什么失败即阻断）

原则：**越便宜越先跑，越能证明"红线存在"越早跑。**

| 序 | 阶段 | 步骤 | 质量门禁（不满足即阻断） | 失败处理 | 耗时 |
|---|---|---|---|---|---|
| 1 | 密钥扫描 | `gitleaks detect --redact` | 命中 0 条 | 阻断；提示轮换 + 加 `.gitleaksignore` 需 PR 说明 | 20s |
| 2 | 后端编译 | `dotnet restore --locked-mode && dotnet build -warnaserror` | 零警告；`Directory.Packages.props` 锁定版本（无浮动版本） | 阻断 | 90s（热）/6min（冷） |
| 3 | **架构门禁** | `check.sh` 步骤 2–5：分层 / 上下文互引 / 授权完备 / storefront DTO 隔离 | 4 个 NetArchTest 分类全绿 | 阻断（**这是母版不腐化的红线，优先级高于单测**） | 60s |
| 4 | 领域单测 | `dotnet test tests/OpenStore.Domain.Tests` | 全绿；覆盖率 `Domain` ≥ 85%（行） | 阻断 | 40s |
| 5 | 迁移漂移 | `dotnet ef migrations has-pending-model-changes` + `migrations script` 非空 | 退出码 0 | 阻断（"改了模型忘提交迁移"= 上线炸库） | 40s |
| 6 | 模板/主题 schema | `tools check-templates && tools check-themes` | 3 模板 + 2 主题全部通过 JSON Schema | 阻断 | 15s |
| 7 | 契约漂移 | `emit-openapi && pnpm gen:types && git diff --exit-code` | 无 diff | 阻断（否则前端静默错位） | 60s |
| 8 | 应用+集成测试 | 文件型 SQLite **与** Testcontainers PG 各跑一遍 | 全绿；`docs/03` §10.2 的 12 条 AC 断言全过 | 阻断 | 6–8min |
| 9 | **门禁自证** | `scripts/verify-gates.sh`（自动注入 8 处违规，断言每一处都被拦） | 8/8 全被捕获；输出 `ALL GATES PROVEN` | 阻断（**客户最看重的机制，见 §4.3**） | 12–18min |
| 10 | 前端 | `pnpm lint && svelte-check && tsc --noEmit && build(storefront) && build(admin)` | 零 error；`svelte-check` 零 error（warning 允许）；首屏 JS ≤120KB gz（构建产物体积断言） | 阻断 | 4–6min |
| 11 | E2E + a11y + **AC-11 索引矩阵** | Playwright 黄金链路（浏览→加购→下单→Fake 支付→后台发货）+ axe（5 个关键页 `critical=0`）+ 三浏览器；**同一套 E2E 站点上跑 `verify-seo-matrix.sh --self-test` 再跑 `verify-seo-matrix.sh http://localhost:8080`** | 全绿；截图/trace 归档；**索引矩阵退出码必须 0**（`docs/01` §6.1：脚本缺失或未覆盖任一语义 = AC-11 判未通过，**不得记跳过**） | 阻断 | 6–8min |
| 12 | 依赖漏洞 | `dotnet list package --vulnerable --include-transitive`；`pnpm audit --audit-level=high` | **High/Critical = 0**；Medium 记录不阻断 | 阻断（High+） | 60s |
| 13 | 镜像构建推送 | `api` / `storefront` / `caddy` 三个镜像，`linux/amd64`（可选 `arm64`） | 推送成功 + 记录 **digest** | 阻断 | 4–6min |

**总时长**：串行约 30min；按 job 并行（1–7 一组、9 独立、10 独立、8 依赖 2、11 依赖 8）**墙钟 ≈ 20min**。`check.sh --fast`（步骤 1–7）≈ 3min，作为 **pre-push hook**。

**为什么 AC-11 索引矩阵挂在第 11 步而不是自己做一步**：它是**唯一必须"起一个真站"才能跑的门禁**（要真实 sitemap、真实筛选链接、真实反代加的 `X-Robots-Tag`），单测和集成测试都验不到。塞进 E2E 是搭便车：站点已经起来了，多花 20 秒。**但它不是"E2E 的附属品"**——E2E 红是"链路断了"，矩阵红是"验收项 AC-11 不通过"，两者在报告里分开命名，避免以后有人把矩阵挪成 `continue-on-error`。

**为什么门禁自证（第 9 步）排在 E2E 之前**：它是最能证明"这套工程体系不是摆设"的一步，而且它**能发现"某个门禁被改成空转"**——这是 AI 辅助开发下最真实的风险（架构 §7 风险 10）。E2E 慢且偶发脆弱，把快的、更有说服力的放前面，反馈更快。

### 4.3 `verify-gates.sh` 在 CI 中的特殊地位

`docs/03` §9.2 定义的机制是**"门禁本身要被测试"**：在临时 git worktree 里注入 8 处违规（V1 分层 / V2 上下文互引 / V3 授权 / V4 DTO 泄露 / V5 模板 schema / V6 主题 manifest / V7 迁移漂移 / V8 状态机），逐条断言"必须变红"。

**部署侧的三条约束（补充后端设计里没写的）**

1. **必须 `fetch-depth: 0`**：脚本用 `git worktree add --detach HEAD`，浅克隆会直接失败。失败信息要说人话：`verify-gates: 需要完整 git 历史（actions/checkout 请设 fetch-depth: 0）`。
2. **必须能并发跑**：worktree 路径用 `/tmp/gate-$$-$id`（含 PID），否则同一 runner 上两个 job 会互删。
3. **失败信息必须指向"哪个门禁是摆设"**，而不是笼统"脚本失败"：输出形如
   ```
   GATE V3 IS A NO-OP: 删掉 refund 端点的权限策略后，授权门禁仍然通过
     → 检查 tests/OpenStore.ArchitectureTests/AuthorizationTests.cs 的反射扫描范围
   ```
   这条信息直接决定"商家/客户能不能相信你的门禁"，比任何测试报告都有说服力。

### 4.4 缓存策略与预期耗时

| 缓存 | 键 | 命中后收益 | 冷启动成本 |
|---|---|---|---|
| NuGet（`setup-dotnet cache: true`） | `**/packages.lock.json` 哈希 | restore 6min → 25s | 首次 6min |
| pnpm store | `frontend/pnpm-lock.yaml` 哈希 | install 3min → 30s | 首次 2–3min |
| Playwright 浏览器 | lockfile 哈希（含 playwright 版本） | install 90s → 10s | 首次 90s（三浏览器 ~400MB） |
| Docker buildx（`type=gha`） | 分层 | 镜像 5min → 90s | 首次 5min |
| `~/.dotnet/tools`（`dotnet tool restore`） | 版本文件 | 20s → 3s | — |

**墙钟预期**：冷缓存（第一个 PR / 换依赖）≈ 32min；热缓存 ≈ 18–20min。若超过 25min（热），视为流水线劣化（通常是 `verify-gates` 或 E2E 抖动），需要当月排期治理。

### 4.5 分支策略与发布触发

| 项 | 规则 |
|---|---|
| 分支模型 | **主干开发**：`main` 常绿 + 短生命周期 `feat/*`、`fix/*`；不设 `develop` |
| `main` 保护 | 必需检查：`secret-scan`、`backend-gates`、`integration`、`gates-proof`、`frontend`、`e2e`（6 项全绿）；至少 1 人 review；禁止 force push |
| **禁止绕过** | 任何人不得跳过 `gates-proof`（哪怕 hotfix）—— 门禁自证只在"信任已被破坏"时才急着绕过 |
| 发布触发 | 打 tag `v1.4.2` → 构建并推送 `1.4.2` / `1.4` / `latest` + 记录 digest；同时生成 **发行包**（见下） |
| `main` 推送 | 推 `edge` tag 镜像（供 staging 自动部署），**不打 latest** |
| 发行包内容 | `docker-compose.yml`、`Caddyfile`、`.env.example`、`scripts/*.sh`、`RUNBOOK.md`、`digests.txt`、`manifest.json`（含 `appVersion` / `latestMigration` / `composeMinVersion`） |
| 商家侧固定 | 发行包与 Runbook 一律用 **digest** 而非 tag（`image: …@sha256:…`），防 tag 被覆盖导致"回滚到同一个 tag 却拿到不同镜像" |

## 5. 数据库迁移与发布

### 5.1 生产迁移流程（必须是显式一步）

```bash
# 0) 迁移前必须备份（自动化：scripts/pre-migrate-backup.sh）
VACUUM INTO '/data/backups/pre-migrate-$(date +%Y%m%d-%H%M).sqlite'

# 1) 停站（写入必须停：SQLite 迁移期间有写并发会锁库；单实例本就要停）
cd /opt/openstore && docker compose stop api storefront

# 2) 显式执行迁移（不随启动自动发生）
docker compose run --rm migrate            # = dotnet openstore migrate

# 3) 校验迁移结果
docker compose run --rm migrate status     # 打印 当前版本 / 期望版本 / 待执行列表（应为空）
sqlite3 data/openstore.db "PRAGMA integrity_check;"   # 必须 ok
# ↑ 若用 Docker 部署，宿主不必装 sqlite3，改走容器：
#   docker compose exec -T api sqlite3 /data/openstore.db "PRAGMA integrity_check;"

# 4) 起新代码
docker compose up -d --wait

# 5) 验证（§8.2 的"上线后检查"）
curl -fsS 127.0.0.1:5080/health/ready | jq .
```

**启动期的行为（已由后端实现，部署侧要理解）**：`Program.cs` 只做"比对 `__EFMigrationsHistory` 最新版本 vs 编译期期望版本"，落后则打 `Fatal` 并把 `/health/ready` 置 503 且给出可读修复指令，**进程继续活着**（崩了就看不到日志）。所以"漏迁移"的表现是**站点能打开但下单 503 + 一条明确的 Fatal 日志**，而不是白屏 —— 这是有意设计。

**唯一例外：域名双源不一致必须拒绝启动**（§3.8 之 2.1）。迁移漂移可以"活着但 503"（因为运维能读日志修），而域名不一致**必须硬失败** —— 它的症状是"能开能下单但 canonical 全错"，属于会静默跑一个月的错误，没有第二次机会。两者的判定差异是有意的，不要统一。首次启动（`/setup` 未完成、DB 无 `PublicSiteUrl`）时跳过该比对。

### 5.2 迁移失败的回滚策略（EF Core 没有自动回滚）

| 情形 | 处置 | 依据 |
|---|---|---|
| 迁移脚本执行报错，事务回滚（SQLite/ PG 的 DDL 都在事务内） | `migrate status` 确认无变化 → 修脚本 → 重跑。**不要 `migrate down`**（生产禁用） | EF 默认每个 migration 在事务内执行 |
| 迁移"成功"但数据被改坏（如加唯一索引时发现重复值 → 部分数据被截断） | **恢复 `pre-migrate-*.sqlite`** + 回退镜像 tag 到上一版本 → 复盘 | 备份是唯一可靠回滚 |
| 迁移中途进程被 OOM kill / 断电 | `integrity_check` 失败 → 恢复备份；成功但版本号半更新 → 用备份恢复（不做手工补 SQL） | 单机无副本，人工推断不可靠 |
| 迁移成功、新代码启动失败 | **回退镜像 tag 即可**（前提：迁移是 expand-only，旧代码能跑在新 schema 上）→ 见 §5.4 | 这是 expand/contract 的全部价值 |

**硬规则**：**生产永久禁用 `dotnet ef database update --migration <older>`（下行迁移）**。理由：下行迁移代码几乎从不被测试，SQLite 的"表重建"路径极易丢数据；有备份就不需要它。CI 里加一条 `check.sh` 断言：`Migrations/` 下不存在 `Down()` 里含 `DropTable`/`DropColumn` 的**新增**迁移（allowlist 旧文件）。

### 5.3 SQLite → PostgreSQL 切换 Runbook（规模化路径）

**触发条件（架构 §6 并发假设）**：写等待 > 200ms 持续出现，或日均订单 > 500，或需要多机。

**前置（这是一项后端交付物，见 §12 Q2）**：`dotnet openstore db-copy --from <sqlite-cs> --to <pg-cs>` —— 用 EF 逐表读 SQLite → 写 PG，按外键拓扑序写入，保留主键与时间戳，`MediaAsset.StorageKey` 不变（媒体文件不动）。

```bash
# 1) 准备 PG（同机 docker，或托管的 PG 实例）
docker run -d --name openstore-pg -p 127.0.0.1:5432:5432 \
  -e POSTGRES_DB=openstore -e POSTGRES_PASSWORD="$PGPASS" \
  -v ./data/pgdata:/var/lib/postgresql/data postgres:16-alpine

# 2) 停站 + 备份（SQLite 三件套）
cd /opt/openstore && docker compose stop api storefront
./scripts/backup.sh --tag pre-pg

# 3) 在空 PG 上建 schema（用 EF 迁移，保证与代码一致）
PG_CS="Host=127.0.0.1;Port=5432;Database=openstore;Username=postgres;Password=$PGPASS"
docker compose run --rm migrate migrate --connection "$PG_CS"

# 4) 搬数据
docker compose run --rm migrate db-copy \
  --from "Data Source=/data/openstore.db" --to "$PG_CS"

# 5) 校验（下面 6 条全过才继续）
#    ① 每张表行数一致 ② max(CreatedAt) 一致 ③ 金额合计一致
#    ④ 抽 20 个订单逐字段比对 ⑤ 商品搜索/筛选各 3 组用例 ⑥ 图片 URL 可访问
./scripts/verify-migration.sh

# 6) 切连接串 + 重启
sed -i "s|^ConnectionStrings__Default=.*|ConnectionStrings__Default=$PG_CS|" .env
docker compose up -d --wait

# 7) 业务验证（比数据库校验更重要）
#    前台：搜索 → 加购 → 下单 → 沙箱支付 → 后台发货 → 退款
#    后台：改商品 → 前台 5s 内可见；改主题 → ≤5s 生效

# 8) 保留旧库只读 7 天，然后改名归档
mv data/openstore.db data/openstore.db.pre-pg.$(date +%F)
```

**校验清单（缺一不可）**

- [ ] `SELECT count(*)` 逐表一致（含 `*Translation` 子表 —— 最容易漏）
- [ ] 金额类：`sum(Order.TotalAmountMinor)`、`sum(Refund.AmountMinor)` 一致
- [ ] `__EFMigrationsHistory` 在 PG 上与 SQLite 的一致
- [ ] `PRAGMA integrity_check`（旧库）与 PG `VACUUM ANALYZE` 都跑过
- [ ] **引导/序号类**：`Order.Number` 序列、`PaymentAttempt.AttemptNo` 在 PG 上不重号（单号唯一索引会立刻暴露）
- [ ] `datetime` 时区语义：SQLite 存 TEXT/Unix，PG 用 `timestamptz` → 抽 5 条对比 UTC 值
- [ ] 双 provider 集成测试在切换后的 `.env` 上跑一遍（`dotnet test` 连的是真实 PG）

**回退**：切回 SQLite 只需把连接串改回 + `docker compose up -d`（PG 期间产生的新数据会丢 → 所以**切换必须在停机窗口内一次完成**，不能"先切一半"。预计 30–60min，含校验）。

### 5.4 零停机发布的现实评估（诚实结论）

**做不到真零停机。** 理由，逐条：

1. **单实例**：只有一个 api 进程，滚不起来（没有第二个实例承接流量）。
2. **SQLite 单写者**：迁移期间必须没有写事务，否则 `database is locked`。
3. **storefront 与 api 契约同步**：SSR 与 API 在同一版本内演进，跨版本并存没有经过测试的组合。

**能做的是"最小停机"（目标 ≤ 3 分钟）**：

```
T+0:00  备份（在线 VACUUM INTO，不停站，~10s）
T+0:10  发维护公告（可选：Caddy 返回 503 + Retry-After，或直接停）
T+0:15  docker compose stop api storefront                      ~5s
T+0:20  docker compose run --rm migrate                         10–90s（增量迁移通常 < 30s）
T+1:00  docker compose up -d --wait                             20–40s（等 healthcheck 通过）
T+1:40  冒烟：ready 200 + 首页 200 + 加购 201                    10s
T+2:00  恢复服务，观察 30min
```

**发布顺序：先迁移，后发代码。** 结论与理由：

| 顺序 | 判断 | 理由 |
|---|---|---|
| **迁移 → 代码（采纳）** | ✅ | 新代码依赖新列/新表，没有它们必崩；旧代码在新 schema 上只要迁移是 expand-only 就照常跑（新列有默认值/可空）。**停机窗口只需覆盖"迁移 + 重启"，不需要"迁移 + 代码 + 数据回填"三件事同时成功。** |
| 代码 → 迁移 | ❌ | 新代码起来会撞 `no such column`，窗口内所有请求 500；且若迁移失败，你手上是"新代码 + 旧 schema"的不可用组合，回滚要退两次。 |
| 两者打包进同一个容器启动脚本 | ❌ | 等于自动迁移，直接违反硬规则 |

**expand/contract 双版本纪律（这条决定了"能不能回滚镜像"）**

| 阶段 | 版本 | 内容 |
|---|---|---|
| Expand | vN | 只加表/加列（可空或有默认值）/加索引（`CREATE INDEX CONCURRENTLY` 于 PG；SQLite 直接建） |
| Dual-write（可选） | vN | 新旧字段同时写；读旧字段 |
| Contract | **vN+1（至少延后一个版本）** | 删旧列/改名/加 NOT NULL/加唯一约束 |

> **一句话规则**：**同一版本内绝不出现"删/改"类迁移。** 这样"回退镜像"永远可用（旧代码 + 新 schema ⊇ 旧代码所需 schema），成本只是多留一版废弃字段。

## 6. 备份与恢复

### 6.1 SQLite 在线备份：`VACUUM INTO`（为什么不能 `cp`）

> **全文命令约定（Docker 部署）**：文中所有 `sqlite3 /data/xxx.db "…"` 都在 **api 容器内**执行，宿主**不需要装 sqlite3**（已打进镜像，§2.1）。建议在宿主加个别名，后面所有排障命令都能直接抄：
> ```bash
> alias osq='docker compose -f /opt/openstore/docker-compose.yml exec -T api sqlite3 /data/openstore.db'
> osq "select count(*) from \"Order\";"
> ```
> 本文为可读性仍按 `sqlite3 /data/openstore.db "…"` 书写，读到就替换成 `osq "…"`（systemd 部署则宿主机本来就有 DB 文件，可直接用）。

```bash
# 在线、一致、不锁站（读事务快照 → 输出一个已整理的完整库）
sqlite3 /data/openstore.db "VACUUM INTO '/data/backups/db-$(date +%Y%m%d-%H%M).sqlite'"

# 立即校验（缺这一步的备份等于没备份）
sqlite3 /data/backups/db-*.sqlite "PRAGMA integrity_check;"   # 必须输出 ok
```

| 为什么 `cp` 不安全 | 具体后果 |
|---|---|
| **WAL 模式下数据在 `-wal` 里** | `cp openstore.db` 会丢掉"最近已提交但还没 checkpoint"的事务 → 恢复后少几小时订单。`cp` 三个文件也不行：非原子的三文件拷贝会拿到**撕裂状态**（主库已 checkpoint 一半、wal 已换） |
| **页级撕裂（torn page）** | 拷贝过程中 SQLite 正在写页 → 备份里有半新半旧的页 → `integrity_check` 报 `database disk image is malformed`，**库直接不可用** |
| **需要停机** | `cp` 要一致性就必须停写；`VACUUM INTO` 不停站 |
| **产物更大** | `VACUUM INTO` 顺带整理碎片，产物比原库小 20–40%，也更快恢复 |

> **`VACUUM INTO` 的唯一代价**：它要读全库并写一份新文件 → 期间磁盘需要 DB 大小 × 1 的额外空间，且 CPU 占用约等于一次全表读（1GB 库约 10–20s）。所以**它跑在 03:00，且在 `DailyBackupJob` 里串行执行、不与图片处理并发**。

**调度（两层，各管一段）**

| 层 | 谁 | 频率 | 产物 | 目的 |
|---|---|---|---|---|
| 应用内 | `DailyBackupJob`（`docs/03` §7 任务 8） | 每 6 小时（建议把默认的"每天 03:00"改为 6h 一次，RPO 从 24h 降到 6h；成本仅 4× VACUUM） | `/data/backups/db-*.sqlite` | 快速单点恢复（"把库回到 3 小时前看看"） |
| 宿主 cron | `scripts/backup.sh` | 每天 03:10 | `/srv/backup/openstore-YYYYMMDD-HHMM.tar.zst`（DB + media + keys + manifest） | **灾备**（整机丢失可重建） |

### 6.2 PostgreSQL 方案

```bash
# —— 备份（运维侧，cron 执行）——
pg_dump -Fc -Z6 -f /data/backups/pg-$(date +%Y%m%d-%H%M).dump "$PG_CS"
pg_restore --list /data/backups/pg-*.dump | head      # 校验：能列出目录即文件完整

# —— 恢复 ——
# ⚠️ 一律用 CLI，不要手敲 pg_restore（原因见 §6.5 / 附录 C.3）：
openstore restore --from /srv/backup/openstore-<ts>.tar.zst
# 手敲的那一步只在这两种情况用：① 只想从 dump 里捞单表（--table=）② 排查 dump 内容
# pg_restore -d "$PG_CS" --clean --if-exists --no-owner /data/backups/pg-*.dump
```

PG 场景额外的两条：① 若 PG 在**另一个容器/实例**上，`backup.sh` 用 `docker compose exec -T pg pg_dump …` 直出到宿主；② PG 自身的 WAL 归档/PITR **本方案不做**（单机小店，RPO 24h 靠每日 dump 足够）—— 若商家要求 RPO < 1h，则升级为 `pgBackRest` + 对象存储，作为增值项。

### 6.3 `/data/media` 与 `/data/keys`

**media（10GB 量级，只增不减）**

```bash
# 硬链接快照式增量（同机多份、几乎不占额外空间）
rsync -a --delete --link-dest=/srv/backup/media-latest /data/media/ /srv/backup/media-$(date +%F)/
rm -f /srv/backup/media-latest && ln -s /srv/backup/media-$(date +%F) /srv/backup/media-latest
# 打包进每日三件套（用 zstd，比 gzip 快 3 倍、小 15%）
tar --zstd -cf /srv/backup/openstore-$(date +%Y%m%d-%H%M).tar.zst \
    -C /data openstore.db media keys
```

> **media 的取舍**：图片是最大的备份体积项。**建议 media 只做"每日 rsync 增量 + 每周一次打包进异地"**，不必每天打进 tar（10GB/天 × 14 天 = 140GB 不现实）。恢复时 media 可以晚于 DB 恢复（缺图不影响下单，只影响展示）。

**keys（< 100KB，但最致命）**

| 项 | 说明 |
|---|---|
| 它是什么 | ASP.NET Data Protection 密钥环（`/data/keys/key-*.xml`），用于加解密**支付凭据 / SMTP 密码 / 会话 Cookie** |
| **丢失后果（写清）** | ① DB 里的支付/SMTP 凭据是**密文**，解不开 → **无法发起支付、无法发信** → 必须让商家重新填一遍凭据（商家手上还不一定有，Stripe 后台能重发，支付宝/微信要找回商户密钥，可能要 1–2 天）；② 所有会话 Cookie 失效（所有人被登出，可接受）；③ **不会丢业务数据**（订单/商品完好） |
| 恢复要求 | **必须与 DB 同一次打包、同一时间点恢复**。混用"上周的 keys + 今天的 DB" → DB 里新写的密文（用新 key 加密）解不开 → 部分凭据失效，且**没有明显报错**，只表现为"支付发起 500"。这是恢复演练最容易踩的坑 |
| 备份加密 | keys 备份包**必须加密**（`age -r <公钥>` 或 `gpg -c`）。它能解密支付凭据，等于"凭据保险箱的钥匙"；明文存放的 keys 备份 = 把所有支付凭据交出去 |
| 泄露处置 | 立即在后台重新填凭据（会生成新密文）→ 删除旧 keys 备份 → 换 SMTP/通道密钥 |

### 6.4 保留策略与异地副本

```bash
# scripts/backup.sh（宿主 cron，03:10）
#!/usr/bin/env bash
set -euo pipefail
D=/opt/openstore; B=/srv/backup; TS=$(date +%Y%m%d-%H%M)
cd "$D"
# 1) DB 一致性快照（应用 job 已产，这里再取一次并校验，避免依赖应用存活）
docker compose exec -T api sh -c "sqlite3 /data/openstore.db \"VACUUM INTO '/data/backups/db-$TS.sqlite'\""
docker compose exec -T api sqlite3 "/data/backups/db-$TS.sqlite" "PRAGMA integrity_check;" | grep -qx ok
# 2) manifest：记录镜像 digest 与迁移版本（恢复时用来选对镜像！）
printf '{"ts":"%s","appVersion":"%s","digest":"%s","migration":"%s"}\n' "$TS" \
  "${OPENSTORE_VERSION}" "$(cat /opt/openstore/.digest 2>/dev/null || echo unknown)" \
  "$(docker compose exec -T api sh -c 'sqlite3 /data/openstore.db "select MigrationId from __EFMigrationsHistory order by MigrationId desc limit 1"')" \
  > "$B/manifest-$TS.json"
# 3) 三件套打包（keys 单独加密）
tar --zstd -cf "$B/openstore-$TS.tar.zst" -C /data openstore.db media keys "$B/manifest-$TS.json"
age -r "$BACKUP_AGE_PUBKEY" -o "$B/openstore-$TS.tar.zst.age" "$B/openstore-$TS.tar.zst"
# 4) 保留 14 天 + 本地一份未加密（便于快速恢复），异地一份加密
find "$B" -name 'openstore-*.tar.zst*' -mtime +14 -delete
find /data/backups -name 'db-*.sqlite' -mtime +14 -delete
# 5) 异地（对象存储 / 另一台机器 / 家里 NAS），restic 加密去重增量
restic -r "$RESTIC_REPO" backup "$B"/openstore-$TS.tar.zst.age --tag openstore
restic forget --keep-daily 14 --keep-weekly 8 --prune
```

**异地副本三档（按商家预算选，Runbook 里给推荐）**

| 档 | 手段 | 成本 | 抗"整机丢失" | 抗"勒索加密" |
|---|---|---|---|---|
| 最小 | 每周手动把 tar 下载到本地电脑 | 0 | ✓ | ✗（同机同网） |
| **推荐** | `restic` → 对象存储（阿里云 OSS / B2 / S3） | ¥1–10/月 | ✓ | ✓（restic 加密 + 只写凭据） |
| 强化 | restic → 另一台机器/NAS（异地/异网） | 一次性硬件 | ✓ | ✓ |

> **`restic` 的另一半价值**：`forget --keep-daily 14 --prune` 让异地副本自动保留策略，且它能**校验**（`restic check`）—— 这是"备份是否可用"唯一自动化的真相来源。建议每周日 `restic check --read-data-subset=5%`。

### 6.5 恢复 Runbook（**1 条恢复命令 + 2 条验证**，≤15 分钟）

> **team-lead 裁决**：原方案 SQLite 3 条 / PG 5 条，现改为**统一 1 条恢复命令** `openstore restore --from <backup>`，把 provider 差异封进 CLI；AC-16 口径改为"**1 条恢复命令 + 2 条验证**"。
> **理由不是好看，是执行时机**：恢复只会在出事时用，那时的操作者最慌、最容易漏步骤。PG 那 5 步里"起 pg / 建空库 / pg_restore / 起站 / 校验"任何一步漏了，症状都是"**数据不全**"而不是"命令报错"—— 这是最难排查的失败形态。SQLite 版之所以可行，恰恰因为步骤少。
> **PG 的 5 步作为该命令的内部实现写在附录 C**（运维需要知道它做了什么，但不需要手敲）。

**前置依赖清单（先跑 `scripts/preflight.sh`，别在恢复现场才发现缺工具）**

| 工具 | 恢复时是否需要 | 来源 |
|---|---|---|
| `docker` + `docker compose` v2 | 需要 | 装 Docker 时自带（5 分钟，**不计入 15 分钟**） |
| `tar` | 需要 | **基础系统自带**（Ubuntu/RHEL 都有） |
| `zstd` | `tar --zstd` 需要 | ⚠️ **Ubuntu server 最小安装可能没有** → `apt install zstd`；**若不能装，备份脚本改用 gzip**（见下） |
| `sqlite3` | **不需要装** | 已打进 api 镜像（§2.1），一律用 `docker compose exec -T api sqlite3 …` |
| `jq` | manifest 解析用 | `apt install jq`（或改用 `grep`，脚本里给了兜底） |
| `age` / `gpg` | 只在"异地加密备份"时需要 | 商家侧按需装 |
| `restic` | 只在异地副本恢复时需要 | 单独装（`apt install restic`） |

```bash
# scripts/preflight.sh —— 缺失即打印确切安装命令，不让商家猜
missing=0
for c in docker tar zstd sqlite3 jq curl; do
  if ! command -v "$c" >/dev/null 2>&1; then
    case "$c" in
      sqlite3) echo "· sqlite3 未装（可不装，会走容器内 sqlite3）" ;;
      *) echo "✗ 缺少 $c → sudo apt-get install -y $c"; missing=1 ;;
    esac
  fi
done
docker compose version >/dev/null 2>&1 || { echo "✗ docker compose v2 缺失"; missing=1; }
[ "$missing" -eq 0 ] && echo "✓ preflight 通过"
```

> **⚠️ 诚实声明 + DoD（team-lead 裁决：这是里程碑项，不是"有空再做"）**
> 本 Runbook 目前是**设计稿，尚未在真机跑过一次**。AC-16 要求"在空白环境按文档恢复 ≤3 条命令、≤15 分钟"，**这个要求只能靠实跑证明，不能靠读文档证明**。
> **M7 里程碑必须真跑一次，并把结果（实测耗时、缺的工具、踩到的报错、命令需要修订处）回填进本节 —— 这是 AC-16 的验收证据，属 DoD 项。** 演练必须在"只有基础系统 + 干净 IP"的机器上做（不是原机、不复用任何残余文件）。
> 在那之前，本节所有命令按"待验证"处理。

**前提**：`preflight.sh` 通过（约 5 分钟，不计入 15 分钟）；拿到 `/srv/backup/openstore-<ts>.tar.zst`。

```bash
# ① 恢复（唯一一条命令；内部按 manifest 选镜像版本、按 provider 分派 SQLite/PG 还原路径）
sudo openstore restore --from /srv/backup/openstore-20251115-0310.tar.zst

# ② 验证一：健康 + 迁移版本匹配 + 域名双源一致
curl -fsS 127.0.0.1:5080/health/ready \
  | jq -e '.status=="ready" and (.checks.migrations|startswith("drift")|not) and .checks.siteUrl=="ok"'

# ③ 验证二：真实下单（★ 这是"恢复成功"的最终定义，不是"服务起来了"）
#    前台加购 → 提交订单 → 测试通道支付 → 后台订单列表出现该单
```

> **`openstore restore` 必须做的事（否则这条命令会变成新的坑）**
> 1. **读 tar 内的 `manifest.json`**：`appVersion` / `digest` / `migration` / `provider`，据此**校验当前镜像版本**；不匹配则**先报错并给出两种处置**（换镜像 tag，或确认后执行迁移），**绝不静默继续**。
> 2. **校验完整性**：DB `integrity_check` / `pg_restore --list`，失败即中止且**不覆盖现有数据**。
> 3. **DB + media + keys 同源校验**（§6.3 的硬点）：三者版本戳必须来自同一次打包，混用会导致"凭据解不开但没有任何报错"。
> 4. **`--dry-run`**：只校验不落盘，恢复现场先跑它。
> 5. **恢复前自动把当前 `/data` 快照到 `/data/backups/pre-restore-<ts>/`**（覆盖前留一手，误操作可回退）。
> 6. 退出码语义固定：`0` 成功 / `2` 版本不匹配 / `3` 完整性失败 / `4` 同源校验失败 —— 脚本与 Runbook 都按这个判。

**恢复后必须做的两步验证（缺一步都不算恢复成功）**

```bash
# A. 机器可判的三项（就绪 + 迁移不漂移 + 域名双源一致）
curl -fsS 127.0.0.1:5080/health/ready | jq .
#    期望 checks.migrations 非 drift*、checks.siteUrl == "ok"

# B. 人可判的两项（缺一不可）
#    B1. keys 正确 —— 后台 → 设置 → 支付 → 「测试连接」必须成功
#        （这是"keys 与 DB 同源"的唯一强判据：能解开加密凭据才算对）
#    B2. 能真的下单 —— 前台加购 → 提交订单 → 测试通道支付 → 后台出现该单
```

**Provider 差异（运维需要知道，但不需要手敲 —— 由 `restore` 内部处理，完整实现见附录 C）**

| 维度 | SQLite | PostgreSQL | 对操作者的可见差异 |
|---|---|---|---|
| 备份产物 | 单个 `openstore.db`（含在同一次 tar 里） | `pg-YYYYMMDD.dump`（`pg_dump -Fc`） | **无**（都在同一个 tar 里） |
| 恢复动作 | 文件落位（`VACUUM INTO` 产物直接可用） | 起 pg 实例 → 建空库 → `pg_restore` | **无**（命令帮你做） |
| 校验 | `PRAGMA integrity_check` | `pg_restore --list` + 行数比对 | **无**（内置） |
| 时长 | 秒级 | 分钟级（1GB dump 约 1–3 分钟） | 只有等待时间不同 |
| 常见坑 | 用 `cp` 只拿到主库（丢 WAL 里的事务、可能撕裂页） | 只恢复文件不 restore dump（"数据不全"而非报错） | **都由命令消除** |

> **这就是把差异封进 CLI 的真正收益**：上表右列全是"无"。操作者不需要知道自己在恢复哪种库，也就不需要记住两套步骤 —— 在出事现场，**少一个需要记住的东西，就少一次"数据不全"**。
> 前置：若商家用 PG，`scripts/backup.sh` 必须把 dump 一起放进同一个 tar（保证 DB + media + keys 同源），`restore` 才能一次还原。

### 6.7 管理端"一键导出"与运维备份的关系（**不是同一套**）

| 维度 | 管理端一键导出（AC-16） | 运维备份（§6.4） |
|---|---|---|
| 触发者 | 商家（后台按钮）→ `202 + jobId` → 下载 zip | 宿主 cron（03:10）自动 |
| 内容 | DB 快照（`VACUUM INTO`）+ media（可选）+ 一个 `README.txt` | DB + media + **keys** + manifest |
| **keys** | **不含**（AC-16 明确"导出包内不含支付凭据明文"，而带 keys 就等于能解出凭据） | **必含**（且加密） |
| 用途 | ① 商家"我的数据我能带走"；② 换机器/换服务商的**迁移**；③ 交接 | ① 灾备；② 回滚；③ 演练 |
| 恢复后必做 | **必须重新填支付/SMTP 凭据**（密文解不开） | 凭据立即可用 |
| 存在哪 | 商家下载到自己电脑 | `/srv/backup` + 异地 |
| RPO | 取决于商家什么时候点 | 24h（DB 6h） |

**结论**：**底层逻辑共用一套**（同一个 `VACUUM INTO` + 同一个打包器，`docs/03` §7 任务 8 已如此设计），**但交付物不同、用途不同、恢复步骤不同**。必须在后台按钮旁写一行小字：

> "此导出用于迁移或自留，**不包含加密密钥**，恢复后需要重新填写支付与邮件凭据。用于灾难恢复请使用运维备份（含 keys）。"

不写这一行，商家一定会在真出事时用导出包恢复，然后在"支付凭据全空、无法收款"上卡一小时。

## 7. 监控与告警（轻量，不引重型平台）

**设计前提**：单机 2GB，装不下 Prometheus + Grafana（那至少 500MB）。所以：**结构化日志 + 一条 cron + 一封晨报**。信号要少，但要能在 5 分钟内定位一个订单的问题（架构 §6 可观测性目标）。

### 7.1 日志

**Serilog 配置（api）**

```csharp
// Program.cs（示意，配置项来自 docs/03 §10.3）
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Information()
    .MinimumLevel.Override("Microsoft.AspNetCore", LogEventLevel.Warning)   // 压掉每请求的框架噪音
    .Enrich.FromLogContext()
    .Destructure.ByTransforming<HttpRequest>(r => new { r.Method, r.Path })  // 白名单，不记 body/header
    .WriteTo.Console(new CompactJsonFormatter())                             // stdout → docker json-file 轮转
    .WriteTo.File(new CompactJsonFormatter(),
        path: cfg["OpenStore:Logging:Path"],                                 // /data/logs/api-.log
        rollingInterval: RollingInterval.Day,
        retainedFileCountLimit: 14,
        fileSizeLimitBytes: 100L * 1024 * 1024,
        rollOnFileSizeLimit: true,
        shared: false)
    .CreateLogger();
```

**为什么用 `CompactJsonFormatter` 而不是 `JsonFormatter`**：前者把自定义属性放在根层（`"OrderNumber":"…"`），后者嵌进 `Properties` 对象（`"Properties":{"OrderNumber":"…"}`）—— 后者让 `grep '"OrderNumber"'` 与 `jq .OrderNumber` 都变别扭。**可 grep 是这套日志存在的唯一理由。**

**日志行样例与字段**（`docs/03` §8.1 的字段表）

```json
{"@t":"2025-11-15T10:22:31.4821330Z","@l":"Information","@mt":"usecase.end UseCase={UseCase} Outcome={Outcome}",
 "CorrelationId":"9f2c1e7d8a4b","TraceId":"…","UseCase":"Checkout.Submit","Outcome":"Ok",
 "OrderNumber":"OS-251115-7QK3M2","CustomerId":1024,"ElapsedMs":42}
```

**检索示例（给商家/客服的"三板斧"）**

```bash
# ① 从一个订单号看完整链路（下单 → 支付确认 → 库存 → 邮件 → 发货）
grep -h '"OrderNumber":"OS-251115-7QK3M2"' /data/logs/api-*.log \
 | jq -r '[."@t", ."@l", .CorrelationId, .UseCase, .Outcome, .ElapsedMs] | @tsv' | sort

# ② 从一次报错里显示的 correlationId 反查所有相关日志（跨 SSR→API）
CID=9f2c1e7d8a4b
grep -h "\"CorrelationId\":\"$CID\"" /data/logs/api-*.log | jq .

# ③ 今天所有失败用例（按 code 聚合，看是哪个错误在涨）
jq -r 'select(."@l"=="Error" or (.Outcome // "" | startswith("DomainError"))) | [.Outcome, .UseCase] | @tsv' \
   /data/logs/api-$(date +%Y%m%d).log | sort | uniq -c | sort -rn | head -20

# ④ 反代侧：最近 1 小时的 SSR 5xx（Caddy 日志走 stdout）
docker compose logs --since 1h caddy | jq -r 'select(.status >= 500) | [.ts, .status, .request.uri, .duration] | @tsv' | head -50

# ⑤ 后台任务健康度（outbox 积压 / 对账失败）
jq -r 'select(."@mt" | startswith("job.executed")) | [.Job,.Scanned,.Succeeded,.Failed,.DurationMs] | @tsv' \
   /data/logs/api-$(date +%Y%m%d).log | tail -30
```

**轮转与磁盘**：`retainedFileCountLimit: 14` + `rollOnFileSizeLimit`（100MB）→ 单日超 1GB 时会分裂成 `api-20251115_001.log`，`grep api-*.log` 的写法必须带通配（上面示例已带）。日志预算 4GB，占 40GB 磁盘的 10%。

**禁止项（安全）**：日志不得出现完整卡号（`\d{16}` 零命中，AC-15）、密码、Cookie 值、`Authorization` 头、SMTP/支付凭据；`RequestLogging` 只记 path/method/status/耗时，**不记 body**（body 里有地址与邮箱）。CI 加一条 grep 断言扫最近的日志 fixture。

### 7.2 健康探针的语义分工

| 端点 | 检查什么 | **为什么不查/要查** | 谁消费 | 失败时 |
|---|---|---|---|---|
| `/health/live` | **什么都不查**，进程能返回即 200 | **故意不查 DB**：DB 挂了重启 API 解决不了问题（SQLite 文件锁、磁盘满、迁移漂移都不是重启能修的），而且重启会丢掉正在处理的 outbox 派发与退款，还会让容器进入"重启 → 马上就绪失败 → 再重启"的循环，把一次故障放大成雪崩 | 容器 `HEALTHCHECK`、systemd `Restart=` | 无响应 → 容器重启（这是唯一该重启的情形） |
| `/health/ready` | ① DB `SELECT 1` ② `__EFMigrationsHistory` 最新版本 == 编译期期望 ③ `MediaDir` 可写（写删探针文件）④ `assets/industry-templates` 可读 ⑤ `themes/*/theme.manifest.json` 可解析 ⑥ **`siteUrl`：域名双源一致（§3.8 之 2.1）** | 这些都是"就算进程活着也提供不了正确服务"的条件。**不检查安装状态**：新部署未初始化也算 ready（否则向导打不开 —— 这是必须的） | 部署脚本 `wait-ready.sh`、cron 告警、`docker compose up --wait` | 503 + 明细 JSON：`{"checks":{"db":"down","migrations":"drift(期望 A 实际 B)","siteUrl":"mismatch(a.com≠b.com)"}}` |
| storefront `/healthz` | 自身 200 + **能打通 `API_ORIGIN/health/ready`** | SSR 是"API 的薄壳"，API 不可用时它在用户眼里就是坏的。让它把上游状态透出来，等于给了一个"端到端可用"信号 | 容器 `HEALTHCHECK`、cron | 503 |

**接入方式**

- 容器：`HEALTHCHECK` 已写在 Dockerfile（live）+ compose（见 §2.4，api 用 live、storefront 用 /healthz）。
- **Caddy 不暴露 `/health/*` 到公网**（§3.1 的 `respond @health 404`）：探针不需要公网，暴露只会被扫描器当情报；同时避免"外部监控依赖站点自身"的循环。
- 部署脚本用 ready 做闸门，而不是 sleep：

```bash
# scripts/wait-ready.sh —— 部署流水线里替代 "sleep 30"
for i in $(seq 1 60); do
  if curl -fsS 127.0.0.1:5080/health/ready >/dev/null 2>&1 \
     && curl -fsS 127.0.0.1:3000/healthz   >/dev/null 2>&1; then echo "ready in ${i}s"; exit 0; fi
  sleep 1
done
echo "TIMEOUT: 未就绪，打印诊断 →"; curl -s 127.0.0.1:5080/health/ready | jq .; docker compose ps; exit 1
```

### 7.3 最小告警集（5 条，cron + curl + 邮件/脚本）

`scripts/watchtower.sh`，宿主 cron `*/5 * * * *`（**用最简单的工具，因为商家要能自己维护**）：

| # | 告警 | 阈值 | 探测方式（可复制） | 级别 |
|---|---|---|---|---|
| 1 | **站点不可用** | 连续 2 次（10 分钟）失败 | `curl -fsS -m 10 -o /dev/null -w '%{http_code}' https://$D/zh/` 非 2xx **或** `curl -fsS -m 5 127.0.0.1:5080/health/ready` 非 200 | **P0**（立即） |
| 2 | **磁盘将满** | `/data` 使用率 **> 85%**（>92% 为 P0） | `df --output=pcent /data \| tr -dc 0-9` | P1（当天处理） |
| 3 | **备份未生效** | 最新备份文件 **mtime > 26h** | `find /srv/backup -name 'openstore-*.tar.zst*' -mmin -1560 \| head -1` 为空 → 告警 | **P1**（备份断档是最贵的静默故障） |
| 4 | **支付确认积压** | 存在 **> 2 小时仍 `PendingPayment`** 的订单 | `docker compose exec -T api sqlite3 /data/openstore.db "select count(*) from \"Order\" where Status='PendingPayment' and CreatedAt < datetime('now','-2 hours')"` > 0 | P1（对账/回调可能整体失效） |
| 5 | **证书将到期** | 剩余 **< 14 天** | `echo \| openssl s_client -connect $D:443 -servername $D 2>/dev/null \| openssl x509 -noout -enddate` | P1（Caddy 会自动续，剩 <14 天说明续期失败：DNS/80 端口/限流） |

```bash
# scripts/watchtower.sh 骨架（40 行，商家能看懂、能自己加规则）
#!/usr/bin/env bash
set -uo pipefail
D=${OPENSTORE_DOMAIN:?}; MAIL=(-s "" ) ; FAIL=0
notify(){ echo "[openstore] $1" | mail "${MAIL[@]}" -s "[OpenStore] $1" "$NOTIFY_EMAIL" || logger "[openstore] $1"; }

# 1) 站点
code=$(curl -s -m 10 -o /dev/null -w '%{http_code}' "https://$D/zh/" || echo 000)
[ "$code" = "200" ] || { FAIL=$((FAIL+1)); [ "$FAIL" -ge 2 ] && notify "P0 站点不可用 HTTP=$code"; }
# 2) 磁盘
pct=$(df --output=pcent /data | tr -dc 0-9); [ "${pct:-0}" -gt 85 ] && notify "P1 /data 使用率 ${pct}%"
# 3) 备份新鲜度
[ -z "$(find /srv/backup -name 'openstore-*.tar.zst*' -mmin -1560 | head -1)" ] && notify "P1 备份超过 26 小时未更新"
# 4) 支付积压（★ sqlite3 在 api 镜像里，宿主不需要装）
n=$(docker compose exec -T api sqlite3 /data/openstore.db \
      "select count(*) from \"Order\" where Status='PendingPayment' and CreatedAt < datetime('now','-2 hours')" 2>/dev/null || echo 0)
[ "${n:-0}" -gt 0 ] && notify "P1 有 $n 笔订单超过 2 小时未确认支付"
# 4b) 容器被 OOM 杀过 / 异常重启（AC-12 的慢性故障入口，见 §2.6.1）
for c in $(docker compose ps -q); do
  st=$(docker inspect -f '{{.Name}} {{.State.OOMKilled}} {{.RestartCount}}' "$c")
  echo "$st" | grep -qE 'true|[1-9][0-9]*$' && notify "P1 容器异常：$st"
done
# 5) 证书
end=$(echo | openssl s_client -connect "$D:443" -servername "$D" 2>/dev/null | openssl x509 -noout -enddate 2>/dev/null | cut -d= -f2)
days=$(( ( $(date -d "$end" +%s) - $(date +%s) ) / 86400 )); [ "${days:-99}" -lt 14 ] && notify "P1 证书剩余 ${days} 天"
exit 0
```

> **为什么只有 5 条**：单机小店的故障面就这五类 —— 站点死了、磁盘满了、备份断了、钱收不到、证书过期。再加就没人看了。**告警的价值 = 有人行动；超过 5 条必然被忽略。**

### 7.4 关键业务指标怎么"不引 Prometheus 也看得到"

| 指标 | 最简取法 | 何时看 |
|---|---|---|
| 今日订单数 / 销售额 | 后台仪表盘 `GET /api/admin/dashboard/summary`；或 `sqlite3 … "select count(*), sum(TotalAmountMinor) from \"Order\" where CreatedAt >= date('now')"` | 每天 |
| **支付成功率** | `select count(*) filter (where Status in ('Succeeded')) * 1.0 / count(*) from Payment where CreatedAt >= date('now')` | 每天；突降 = 通道故障 |
| SSR 5xx 率 | `docker compose logs --since 1h caddy \| jq -r 'select(.status>=500)' \| wc -l` ÷ 总请求数 | 每天 + 告警后 |
| **Outbox 积压** | `select Status, count(*) from OutboxMessage group by Status`（`Pending` 持续增长 = 邮件/通道/派发坏了） | 每天 |
| 订单履约滞后 | 后台"待发货"计数 | 每天 |
| 慢用例 | `jq -r 'select(.ElapsedMs > 1500) \| [.UseCase,.ElapsedMs] \| @tsv' api-$(date +%Y%m%d).log \| sort \| uniq -c \| sort -rn` | 每周 / 用户报慢时 |

**"晨报"（强烈推荐，比任何 Dashboard 都实用）**：cron 每天 08:30 把上面 6 个数字查出来发一封邮件给商家：

```
OpenStore 昨日：订单 12 单 / 销售额 ¥4,320 / 支付成功率 96%（1 笔失败）
待发货 3 单 · 低库存 2 个 SKU · 未确认支付 0 笔
备份：正常（最新 03:10，14 份）· 磁盘 41% · 证书 78 天
SSR 5xx：0 · 429（限流）：3（GET 2 / 写 1）
```

> **429 的判读指引（写进晨报，否则这个数字没人会用）**
> - **先看它落在哪个桶**：晨报拆成 `GET / 写` 两个数。**429 增长且集中在 GET** → 先怀疑爬虫抓取量异常（新收录、被恶意镜像、参数页被暴力遍历），去看 Caddy 访问日志的 UA 与 URL 分布；**不要第一反应去调大阈值**（那会拿抗刷能力换收录，见 §3.6 的因果链）。
> - **写桶出现 429** 才是真的有问题：可能是刷单攻击、也可能是**自家前端有重试风暴**（比如某个请求失败后无限重试）。先查 `UseCase` 与 `CorrelationId`，再考虑调参。
> - **两个桶都不涨但用户报"操作过快"** → 那是 `login` / `checkout-submit` / `refresh-payment` 等**端点级策略**在起作用（`docs/03` §6.7），不是 global 层，去查对应业务日志。

这封邮件让 90% 的问题在变成告警之前就被发现，且零依赖、零额外内存。

### 8.1 版本 A：一键部署（Docker，推荐）

> ### ⚠️ 开始之前：一条必须做的事 + 一个常见误解
> **必须做：起站前就预置安装令牌（步骤 3）。** 生成 `OPENSTORE_SETUP_TOKEN` 写进 `.env`，那么即使有人先访问到 `/setup`，**没有令牌也装不了**。花 10 秒，把"忘了马上走向导"从灾难降级成无害。**这是本 Runbook 最重要的一步，别跳。**
> **常见误解："我先把域名指过来，装完再管安全"** —— 这正是抢注窗口。反过来"先不指域名、装完再指"也不省事：Caddy 的自动 TLS 要域名才能签证书，用 IP 访问根本匹配不到 site block（404），而且**向导里的 `PublicSiteUrl` 只能填最终的 `https://域名`，绝不能填 IP**（填 IP = 全站 canonical/og/sitemap 数据被污染，事后要修数据不只是改配置）。
> **所以正确姿势是**：域名先解析 → **预置令牌** → 起站 → 走向导（输入令牌）→ 完成。Caddy 会在首次请求时自动签发证书，整个窗口被令牌保护。
> **令牌在哪**：预置值在 `.env`（以它为准）；若未预置，首次启动会生成并写到 `/data/setup-token.txt`（600，属主 10001），用 `sudo cat /opt/openstore/data/setup-token.txt` 读，同时启动日志里有醒目打印。向导第一步要求输入。
> **完成向导后**：令牌立即失效，`/setup` 页面返回 **404**、安装写接口返回 **409 `SetupAlreadyCompleted`**（**不是 403，也不是 200** —— 反代不得改写这个状态码，否则运维排障会误判成"被拒"）。

### 8.2 版本 B：手动部署（无 Docker，systemd + Caddy）

> 适用：商家已有 VPS 但不想用 Docker、或环境限制不能跑容器。**代价：升级/回滚要手动换目录（多一步），且必须自己保证 Node 与 .NET 版本。**

**目录布局**

```
/opt/openstore/api/          # dotnet publish 产物（含 assets/）
/opt/openstore/storefront/   # node build 产物
/srv/admin/                  # admin 静态（Caddy file_server）
/data/{openstore.db,media,keys,logs,backups}
/etc/openstore/api.env       # 环境变量（600 root:openstore）
```

**`/etc/systemd/system/openstore-api.service`**

```ini
[Unit]
Description=OpenStore API
After=network-online.target
Wants=network-online.target

[Service]
Type=notify
User=openstore
Group=openstore
WorkingDirectory=/opt/openstore/api
EnvironmentFile=/etc/openstore/api.env
ExecStartPre=/usr/bin/dotnet /opt/openstore/api/OpenStore.Api.dll migrate --check
ExecStart=/usr/bin/dotnet /opt/openstore/api/OpenStore.Api.dll serve
Restart=on-failure
RestartSec=5s
# 内存：与容器 mem_limit 等价（900M），超限只杀这个 cgroup
MemoryMax=900M
MemoryHigh=800M
# 安全加固（只允许写 /data）
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
ReadWritePaths=/data
# 优雅停机：SIGTERM 后给 30s 收尾（Outbox/支付结算）
KillSignal=SIGTERM
TimeoutStopSec=30
# 环境（与容器保持一致的 GC/SQLite 预算）
Environment=DOTNET_gcServer=0
Environment=DOTNET_GCHeapHardLimit=0x20000000
Environment=ASPNETCORE_URLS=http://127.0.0.1:5080

[Install]
WantedBy=multi-user.target
```

> `Type=notify` 需要 app 调 `sd_notify`（`Microsoft.Extensions.Hosting.Systemd` 的 `UseSystemd()`）。**若不做，用 `Type=exec` + `ExecStartPost=/usr/bin/curl -fsS --retry 30 --retry-delay 1 http://127.0.0.1:5080/health/ready`** —— 让 systemd 的启动成功能反映"真的就绪"，而不是"进程起来了"。

**`/etc/systemd/system/openstore-storefront.service`**

```ini

[Service]

User=openstore
```

**Caddy（`/etc/caddy/Caddyfile`，与 §3.1 同一份，只换上游）**

```caddyfile
# systemd 模式：上游是回环地址
API_UPSTREAM / STOREFRONT_UPSTREAM 由 systemd 环境提供，或用 Caddy 的 env：
# /etc/systemd/system/caddy.service.d/override.conf
#   [Service]
#   Environment=API_UPSTREAM=127.0.0.1:5080
#   Environment=STOREFRONT_UPSTREAM=127.0.0.1:3000
```

> **同源退化风险**：systemd 模式下 api 与 storefront 都在 `127.0.0.1`，**API 侧 `KnownNetworks` 必须改成 `127.0.0.1/32`+`::1/128`**（不能沿用 `172.28.0.0/24`，否则真实 IP 修复失效 → 又变成全站一个限流桶）。这是两种部署模式的**唯一差异点**，Runbook 必须标注。

**权限与加固**

```bash
sudo useradd -r -u 10001 -s /usr/sbin/nologin openstore
sudo mkdir -p /data/{media,keys,logs,backups} /opt/openstore/{api,storefront}
sudo chown -R openstore:openstore /data /opt/openstore
sudo chmod 700 /data/keys && sudo chmod 600 /etc/openstore/*.env
sudo chown root:openstore /etc/openstore/*.env
# admin 静态只读、交给 caddy 组
sudo chown -R root:caddy /srv/admin && sudo chmod -R a-w /srv/admin
```

**升级（手动模式的额外一步）**：解包到 `/opt/openstore/releases/1.4.3/` → 迁移 → 切 `api`/`storefront` 的软链接 → `systemctl restart` → 验证 → **保留上一版目录**（回滚 = 把软链接切回去 + `systemctl restart`，30 秒）。

### 8.3 上线前检查清单（两个 Runbook 共用，逐条勾）

**A. 安全与可达性**

- [ ] 只有 22/80/443 对外开放（`sudo ss -lntp` 里 5080/3000 只见 `127.0.0.1`）
- [ ] `https://域名/` 证书有效、`HTTP/2`、自动跳转 HTTPS
- [ ] **安装向导已完成**：`/setup` 返回 **404**；`POST /api/setup/apply` 返回 **409 `SetupAlreadyCompleted`**（★ 未锁定的向导 = 公网任何人都能成为管理员；**409 不是 403，反代不得改写**）
- [ ] `.env` 中 `OPENSTORE_ALLOW_SETUP_RESET=false`
- [ ] **演示模式已退出**：`canSell=true`（后台无黄色横幅，前台"去结算"可点，AC-17）
- [ ] `OPENSTORE_ALLOW_SETUP_RESET`、`Email__Provider`、`Payments__Provider`、`Security__ForceHttps` 四项都不是 dev 值
- [ ] 后台管理员密码非默认、非弱口令；`.env` 与备份目录权限 `600/700`
- [ ] `/health/*` 从公网返回 404（探针不暴露）

**A2. 反代行为（AC-10 / AC-11 的部署侧判据，四条都要当场跑）**

- [ ] **503 保真**：`docker compose stop api` → `curl -sI https://域名/zh/products/任一slug | head -1` 必须是 **503**（**绝不能是 200**）→ 再 `start api`。详见 §3.7
- [ ] **Host 注入不生效**：`curl -o /dev/null -w '%{http_code}\n' -H 'Host: evil.com' https://域名/zh/` → **404**；且正常访问的 `canonical` 里不出现 `172.28.`/`:5080`/`http://`（§3.8）
- [ ] **`PublicSiteUrl` 一致**：`.env` 的 `OPENSTORE_DOMAIN_URL` == 向导里填的 `PublicSiteUrl`（都带 `https://`、都无尾斜杠）；改 `PublicSiteUrl` 后 sitemap/canonical **立即**跟随（不重启）
- [ ] **索引矩阵**：先跑 `scripts/verify-seo-matrix.sh --self-test`（确认闸门本身有效：正样本绿、三个注入各自红），再跑 `scripts/verify-seo-matrix.sh https://域名` **全绿（§6.1 的全部 S 档，退出码 0）**。**不看"大致对"，只看退出码**；退出码 2 表示前置数据缺失（sitemap/可筛选属性），同样算未通过（§3.6.3）
- [ ] **`robots.txt` 全文只有 `Disallow: /api` 一条**（`curl -s https://域名/robots.txt \| grep -i '^disallow:'` 逐条看）—— 出现 `/cart` `/checkout` `/account` `/admin` `/search` 或任何带 `?`/`&` 的规则即为错。**注意："前台一条 Disallow 都没有"是正确的终态，不是漏配**（§3.6.2）
- [ ] **`X-Robots-Tag` 抽查**：`curl -sI https://域名/admin/login \| grep -i x-robots-tag` 必须命中（SPA fallback 出来的 `index.html` 也要带，否则**后台登录页会被收录**）
- [ ] **无重定向循环 + Cookie 三属性**：`curl -sIL http://域名/zh/ | grep -c '^location:'` = 1；登录响应 `Set-Cookie` 含 `Secure`/`HttpOnly`/`SameSite`（§3.9）
- [ ] **限流分桶独立**：连续 100 次 GET 后第一个 `POST /api/cart/items` **不是 429**；连续 60 次 POST 后 `GET /zh/` **仍是 200**（证明 `read`/`write` 两个桶分开，爬虫抓取不会挤掉真实写操作；§3.6）
- [ ] **域名双源一致**：`curl 127.0.0.1:5080/health/ready | jq .checks.siteUrl` == `"ok"`（若不 ok，api 本应拒绝启动 —— 这条同时验证"启动检查在生效"，§3.8 之 2.1）

**B. 支付回调可达性自检（★ 单列，因为这是自托管最容易坏的一环）**

| # | 检查 | 命令 / 动作 | 判定 |
|---|---|---|---|
| 1 | 域名公网可解析 | 手机 4G（不连店内 WiFi）访问 `https://域名/` | 能打开 |
| 2 | 回调路径"能到" | 手机 4G 访问 `https://域名/api/webhooks/payments/stripe` | **405/400 = 能到（好）**；404/超时/连接失败 = **不可达** |
| 3 | 80 端口开放（ACME 用） | `curl -I http://域名/` | 有 301/308 响应 |
| 4 | 云安全组/防火墙放行 80+443 | 控制台核对 + `sudo ufw status` | 放行 |
| 5 | 若有路由器/NAT：端口转发有效 | 从外网 `telnet 域名 443` | 通 |
| 6 | 若用内网穿透（frp/cloudflared/tailscale funnel）：隧道与域名映射存活 | `systemctl status frpc` / `cloudflared tunnel info` | active + 域名映射正确 |
| 7 | 通道后台填了回调地址 | Stripe Dashboard → Webhooks / 支付宝/微信商户后台 | URL 正确、最近一次投递 200 |
| 8 | 验签密钥一致 | 后台"支付设置"里的 Webhook Secret 与通道后台一致 | 一致（不一致表现为回调全 400） |

**结论怎么读（写进 Runbook，避免商家慌）**

> - **全通** → 三条支付确认路径都工作，确认延迟通常 **< 10 秒**。
> - **2 或 6 失败（很常见，自托管常态）** → **功能不缺失**：系统会自动降级为「买家返回订单页刷新」+「后台定时对账」两条路径。**代价只是确认延迟上限变长**：对账间隔**默认就是 2 分钟（120s）**（`OpenStore__Reconciliation__IntervalMinutes`，已按裁决固定为 120，下限 30），即最坏 2 分钟内订单会被自动纠正为已支付。
> - **降级后必须做的两件事**：① **不需要改配置**（默认已是 2 分钟，这是设计选择：自托管回调不可达是常态）；② 把这个数字告知商家（"买家付完钱最多 2 分钟后台才会变已支付，属正常"）。
> - **反向优化**：若回调自检**全通**且商家在意通道 API 调用量，可把 `IntervalMinutes` 上调到 `10`（省 80% 查询）；但**上调后一旦回调无声坏掉，确认延迟就变 10 分钟** —— 建议保持 2 分钟不动，通道查询成本远低于一次客服电话。
> - **绝对不要**因为回调不通就认为"支付不能用" —— 这正是架构 §5.5 三路径设计的原因（US-E6-03 / AC-07）。

### 8.4 Runbook 常见故障速查（Top 6）

### 9.2 主题与模板数据的升级兼容性（商家覆盖值不能丢）

**原理**：`ThemeOverride` 是**子表**（`docs/03` §11 #11 明确"不用 JSON 列"），按 `(ThemeId, TokenKey)` 存商家覆盖值。升级时这张表**完全不参与迁移**，所以"覆盖值丢失"只会由三种情况引起：

| 风险 | 表现 | 检查方法 | 缓解 |
|---|---|---|---|
| ① 主题 `formatVersion` 破坏性变更 | 主题列表显示"不兼容，需升级"，拒绝激活 | `RELEASE-NOTES` 里 `formatVersion: 1 → 2` | 宿主拒绝激活而不是静默降级（架构 §5.1.2）；商家需保留旧主题包 → 提前备份 `frontend/themes` |
| ② 商家覆盖的 token key 在新版 `tokens.json` 里被删/改名 | 覆盖值成为"孤儿"：DB 里还在，但渲染不用 | ```sqlite3 /data/openstore.db "select ThemeId, TokenKey, Value from ThemeTokenOverride"``` 与新版 `tokens.json` 键集比对 | **不删孤儿行**（保留，随时可回滚）；后台在主题编辑器里提示"此配置项已不被当前主题支持"，并提供"清理孤儿"按钮 |
| ③ 首页编排引用了已被删除的区块（`blockKey`） | 首页该区块消失（或整页 500 —— 不可接受） | 查 `ThemeInstance` 的 `content` 里 `blockKey` 集合 vs 新版 `theme.manifest.json.blocks` | 渲染器**跳过未知区块并记 `warn`**，绝不能整页 500（架构 §5.1.6 的失败兜底）；后台标红提示 |
| ④ 行业模板 JSON 变了 | **无影响** —— 模板只在安装时编译一次，已初始化库不重编译；`TemplateCompiler` 的确定性 Id 算法冻结（`docs/03` R6，`compilerVersion` 不匹配直接拒绝） | — | 无需动作（这正是把模板做成"构建期内容"换来的好处） |

**升级前的三条硬检查（写进 Runbook）**

```bash
# 以下 sqlite3 均指容器内执行：docker compose exec -T api sqlite3 /data/openstore.db "…"（见 §6.1 约定）
# ① 覆盖值快照（升级前后 count 必须一致）
sqlite3 /data/openstore.db "select ThemeId, count(*) from ThemeTokenOverride group by ThemeId;"   > /tmp/overrides.before
sqlite3 /data/openstore.db "select ThemeId, count(*) from ThemeInstance;"                        >> /tmp/overrides.before
# ② 孤儿键检测（升级后跑，输出应为空或列出的都是"预期删除"的键）
sqlite3 /data/openstore.db "select TokenKey from ThemeTokenOverride where ThemeId='base';"       > /tmp/keys.used
jq -r 'keys[]' frontend/themes/base/tokens.json | sort                                      > /tmp/keys.defined
comm -23 <(sort /tmp/keys.used) /tmp/keys.defined        # 有输出 = 孤儿键
# ③ 首页区块引用检测
sqlite3 /data/openstore.db "select ActiveThemeId, Layout from ThemeInstance;"   # 人工比对 manifest 的 blocks
```

> **必须让商家明白的一句话**（写进升级说明与 README 顶部）：**"新增主题/修改主题代码是发布行为，不是后台操作"**（架构 §5.1.1）。后台只能"切换已构建的主题、改 token 与文案"；要装一个新主题必须升级版本（`themes/` 是构建期资产）。这一条不写清，商家一定会拿 Shopify 主题市场来对标。

### 9.3 回滚预案

```bash
# 30 秒回滚（迁移为 expand-only 时永远可用）
cd /opt/openstore
sed -i 's/^OPENSTORE_VERSION=.*/OPENSTORE_VERSION=1.4.2/' .env   # 或 image: …@sha256:<旧 digest>
docker compose up -d --wait && ./scripts/wait-ready.sh
```

| 场景 | 回滚动作 | 预计耗时 | 验证 |
|---|---|---|---|
| 新版本功能 bug / 500 增多 | 回退镜像 tag（或 digest）→ `up -d --wait` | **30–60s** | ready 200 + 首页 200 + 下一单成功 |
| 新版本页面样式/主题错乱 | 同上（admin 若独立发布，只需回退 caddy 镜像） | 30s | 无痕窗口看首页与商品页 |
| 迁移已执行且**expand-only** | 直接回退镜像（旧代码能跑在新 schema） | 30–60s | 同上 |
| 迁移已执行且**含 contract（删/改）** | **不可回滚镜像** → 恢复 `pre-upgrade` 备份 + 回退镜像 | **10–15min** | §6.5 三步验证（含下单） |
| 新版本写入的数据旧版本不认（如新枚举值） | 恢复备份（会丢升级后数据）→ 与商家确认"丢多少可接受" | 10–15min | 同上 |
| Caddy/证书问题 | `docker compose restart caddy`；证书由 Caddy 自愈 | 20s | 浏览器无证书告警 |

**回滚的判定阈值（预先约定，避免现场犹豫）**

- `/health/ready` 连续 2 分钟非 200 → 回滚
- 5xx 率 > 5%（连续 5 分钟）→ 回滚
- 出现"无法下单/无法支付"且 10 分钟内定位不到原因 → 回滚
- **数据异常（金额/库存/订单状态）→ 立即回滚 + 停写，先保数据**

### 9.4 哪些升级是"不可回滚"的（事前判断方法）

**判断方法（发布前必跑，写进 release checklist）**

```bash
# 生成"上一版 → 当前版"的 SQL 并扫描破坏性语句
dotnet ef migrations script "$PREV_MIGRATION" "$NEW_MIGRATION" -p src/OpenStore.Infrastructure -o /tmp/delta.sql
grep -nEi '\b(drop\s+(table|column|index)|rename|alter\s+column|set\s+not\s+null|truncate)\b' /tmp/delta.sql
```

- **无命中** → expand-only，可回滚镜像 ✅
- **有命中** → 破坏性，回滚只能靠备份恢复 ❌

| 不可回滚项 | 为什么 | 事前识别 | 缓解 |
|---|---|---|---|
| `DROP TABLE/COLUMN` | 数据物理消失 | 上面的 grep | contract 阶段延后一版，先"停止写入"再删 |
| `RENAME`（表/列） | 旧代码按老名查 → 500 | grep `rename` | 用"新增列 + 双写 + 迁移数据 + 下版删旧列" |
| 类型收窄（`nvarchar(300)→(200)`） | 超长数据被截断，回滚也回不来 | grep `alter column` + 人工看长度 | 不收窄；或先校验无超长数据 |
| **新增唯一索引**（已有重复数据） | 建索引失败或去重掉数据 | 迁移前跑一次 `select … having count(*)>1` | 先清洗再建；清洗前备份 |
| **加密算法/密钥格式变更**（Data Protection、凭据加密） | 新格式密文旧代码解不开 → 支付全废 | RELEASE-NOTES 标记 | 提供"重新填凭据"指引；**backups 里同时保留旧 keys** |
| **`MediaAsset.StorageKey` 命名规则变更** | 旧 URL 全部 404（且 `immutable` 缓存让用户长期看不到新图） | RELEASE-NOTES 标记 | 命名规则变更必须带 URL 重写/文件迁移，且不可回退（缓存已污染） |
| 归档/压缩类迁移（把订单迁到历史表） | 旧代码查不到 → 报表口径变 | 人工 review | 本方案不做表归档（见 §10 风险） |
| **`formatVersion` 升级的主题** | 旧主题包在新宿主下被拒 | 主题 manifest diff | 保留旧主题包 + 允许回退镜像 |

### 11.3 为什么**不需要** Redis / MQ / CDN

| 组件 | 为什么不需要（有具体依据，不是口号） |
|---|---|
| **Redis** | ① 缓存是 `IMemoryCache` + 版本号键（架构 §3 已否决 Redis），单进程 = 进程内缓存就是最优解；② 会话在 **DB 表**（可撤销，`docs/03` §6.2），不在 Redis；③ 限流计数器在内存（单实例足够，`docs/03` §8.3）。**加 Redis = +50–100MB 内存 + 一个单点 + 一套备份策略**，在 2G 机器上是纯负担。 |
| **消息队列** | 外部副作用走 **Outbox 表 + BackgroundService**（同库同事务，任务不丢，`docs/03` §7）。用途只是"异步发邮件/对账/清理"，吞吐量是"每天几十条"。**MQ 解决的是"跨进程/跨机器/高吞吐"的问题，本场景都不存在。** 未来的唯一触发点：需要多实例（那时加 `SKIP LOCKED` 就够，仍不需要 MQ）。 |
| **CDN** | ① 图片本地存储 + `StorageKey` 含内容哈希 → `Cache-Control: immutable`，浏览器缓存已覆盖 95% 流量（`docs/04` §9.5）；② `storefront` 是 SSR，HTML 只 `max-age=60`，CDN 收益有限；③ **国内 CDN 还要单独备案 + 按流量计费**，小店月流量 50–200GB 时 CDN 成本可能超过服务器本身。**接 CDN 是"量起来之后"的运维动作，不是首版必需品**（架构 §7.1 已如此定位）。 |
| **独立搜索** | `LIKE` + 索引 + 标题权重足够（架构 YAGNI），商品 10k 量级；切 PG 后可用 `tsvector`。 |
| **Prometheus/Grafana** | 栈本身 400–600MB，占 2G 机器的 25–30%。用 5 条 cron 告警 + 晨报替代（§7.3/7.4）。 |

## 附录 C. `openstore restore` 的内部实现（运维知道即可，不需要手敲）

> 本附录是 §6.5 那条 `openstore restore --from <backup>` **背地里做了什么**。写它的目的不是让商家照着敲，而是两件事：① 出问题时能判断"卡在哪一步"；② 评审时能确认它没有偷工（尤其第 3、5 步）。
> **命令的外部契约**：`openstore restore --from <tar.zst> [--dry-run] [--force]`，退出码 `0` 成功 / `2` 版本不匹配 / `3` 完整性失败 / `4` 同源校验失败。

### C.1 内部七步（顺序不可调）

| # | 步骤 | 做什么 | 失败时 |
|---|---|---|---|
| 1 | **解包到临时目录** | `tar --zstd -xf` → `/var/tmp/restore-<ts>/`（**不在 `/data` 里原地解**，避免半成品污染现网） | 退出码 3（包损坏/磁盘不足） |
| 2 | **读 manifest 并校验镜像版本** | 比对 `manifest.json` 的 `appVersion`/`migration` 与当前镜像；不匹配则报错并给两种处置（换 tag / `--force` 后迁移） | 退出码 2（**绝不静默继续**：新代码跑旧 schema 会 503 或触发迁移） |
| 3 | **DB+media+keys 同源校验** | 三者版本戳必须来自同一次打包（`manifest.sourceSnapshotId`）。混用 = 凭据解不开且**无任何报错** | 退出码 4 |
| 4 | **完整性校验** | SQLite `PRAGMA integrity_check` / PG `pg_restore --list`；失败即中止，**不触碰现有数据** | 退出码 3 |
| 5 | **现有 `/data` 快照** | 覆盖前把当前 DB/keys 复制到 `/data/backups/pre-restore-<ts>/`（误操作可退回） | 磁盘不足则中止（不要"空间不够也继续"） |
| 6 | **按 provider 分派还原** | 见 C.2 | 见 C.2 |
| 7 | **落位 + 权限 + 起站校验** | `chown -R 10001:10001 /data`；调 `wait-ready.sh` 等 `ready`；打印后续两条验证（§6.5 的 B1/B2） | 退出码非 0，并打印 `health/ready` 明细 |

### C.2 第 6 步的两种分派（这就是原来"5 条手敲命令"被封装掉的部分）

**SQLite（默认，小店）**

```bash
# 内部等价于：
install -o 10001 -g 10001 -m 600 /var/tmp/restore-<ts>/openstore.db /data/openstore.db
# 关键：必须同时处理 -wal/-shm 的残留（旧库的 wal 与新库不配对 → 打开即报错）
rm -f /data/openstore.db-wal /data/openstore.db-shm
rsync -a --delete /var/tmp/restore-<ts>/media/ /data/media/
rsync -a --delete /var/tmp/restore-<ts>/keys/  /data/keys/   # ★ keys 必须与 DB 同源
```

**PostgreSQL（规模化）** —— 原方案里让运维手敲的 5 步，现在由命令内部按序执行：

```bash
# ① 确保 PG 实例在跑
docker compose up -d pg && ./scripts/wait-ready.sh --only pg
# ② 建空库（已存在且未 --force 则报错并提示）
docker compose exec -T pg psql -U postgres -c 'CREATE DATABASE openstore'
# ③ 还原 dump（--clean --if-exists 保证可重入；--no-owner 避免角色不存在）
docker compose exec -T pg pg_restore -U postgres -d openstore \
    --clean --if-exists --no-owner /var/tmp/restore-<ts>/pg-<ts>.dump
# ④ 同时还原 keys 与 media（PG 只管业务数据，媒体与密钥仍在 /data）
rsync -a --delete /var/tmp/restore-<ts>/media/ /data/media/
rsync -a --delete /var/tmp/restore-<ts>/keys/  /data/keys/
# ⑤ 起站并等就绪
docker compose up -d --wait && ./scripts/wait-ready.sh
```

### C.3 为什么值得封成一个命令（判定标准）

| 判据 | 手敲 5 条 | 一条命令 |
|---|---|---|
| 漏一步的症状 | **"数据不全"**而不是报错（起 pg/建库/restore 任一步漏了，站能起、数据少一半） | 不可能漏；每步失败都有固定退出码 |
| 出错时操作者的状态 | 最慌的时候，最需要记 5 件事 | 只需贴一条命令 + 看退出码 |
| 版本不匹配 | 靠人记得先改 `.env` 的 tag（§6.5 旧版的第 ② 步） | 命令读 manifest 自动校验并拒绝 |
| 覆盖前留一手 | 靠人记得先备份 | 内置第 5 步 |
| AC-16 可验性 | "≤3 条命令"无法同时满足 SQLite 与 PG（PG 天然 5 条） | **两 provider 统一为 1 条 + 2 验证** |

> **留一个反向提醒给未来的维护者**：如果哪天有人为了"简单"把这个 CLI 拆回 shell 脚本序列，请回到本表第 1 行 —— 恢复失败的最贵形态是"**看起来成功了但数据不全**"，而它只在多步骤手工流程里出现。
