## 1. 测试策略

### 1.1 分层与配比

| 层级 | 覆盖什么 | 数量级 | 责任/执行 | 自动化目标 |
|---|---|---|---|---|
| **单元（Domain 纯函数 + 前端纯函数）** | `Money`（含 `Allocate` 最大余数法、`MultiplyBy` 舍入、币种不匹配抛异常）、`Pricing` 的 11 步顺序（含税/价外、分类级税率、包邮门槛判 `NetGoods`、`INV-O03` 恒等式）、`VariantMatrix`（笛卡尔积顺序、SKU 推导与截断碰撞、四桶 Plan）、`TemplateCompiler`（3 模板 `verified.json` 快照 + 8 类诊断 JSON Pointer）、`ProjectStatus` 九值投影、`OrderStatusMachine`/`Refund` 状态机穷举、`TokenMap.Merge` 三层、`LocalizedText` 回退链、`Slug`/`Sku` 规范化、`Category` 树不变量、`PaymentFailureClassifier`；前端 Vitest：`buildSeo()`、`canonicalFor()`、`switchLocaleHref()`、`resolveTokens()`、`t()` 回退链、变体可用性计算 | **≈200 条** | 开发写、QA 定判据 | **100% 自动化**；`Domain` 行覆盖 ≥85%（05 §4.1 已定门禁） |
| **集成（`WebApplicationFactory` + 真 DB）** | 跨上下文事务（下单=Order+Hold+Payment 同事务）、库存预占/释放/超卖、**幂等（串行 5 + 并发 5）**、退款分域与线下路径、越权矩阵（遍历端点）、禁止转换矩阵 F1~F14、`canSell` 派生与 TOCTOU、向导锁定、设置变更即时生效、SEO 头部（HTTP 层）、sitemap/robots | **≈70 条 × 2 provider** | QA 主导（后端提供测试钩子） | **100% 自动化**；**这是本项目的主战场** |
| **E2E（Playwright）** | 1 条黄金链路（浏览→筛选→选变体→加购→结算→Fake 支付→查单→admin 发货→退款→查单）+ 5 条 P0 smoke（多语 URL 四条规则、演示模式结算禁用、变体置灰、Staff 越权 403、**穿 Caddy 的 503 保真**） | **1 条 × 3 引擎 + 5 条 × 1 引擎 = 8 runs** | QA | 100% 自动化，**不做视觉回归** |
| **脚本/curl 断言（独立可跑，不算层级）** | §6.1 索引控制矩阵、sitemap 条目数、卡号泄漏扫描、备份包扫描、`OpenAPI` 契约漂移、`verify-gates.sh` | 6 组 | QA 维护 | 并入 `check.sh` 与发布前清单 |
| **手工（不可自动化）** | 冷启动计时、第 4 模板（非作者）、真实通道沙箱、社交分享卡片、邮件真实到达与多客户端排版、主题视觉、a11y 键盘+读屏、恢复演练 | **9 项** | QA + 客户/非作者 | 0%（理由逐条见 §8） |

**为什么配比偏离业界 70/20/10**：本项目的失败模式集中在"事务/幂等/并发/状态机"（错一次就是资损或账不平），而不是 UI 交互错乱。这类缺陷**只能在集成层被抓到**（单测里没有 DB 唯一索引，E2E 里看不到库存三元组）。而 E2E 每增一条，1 个人每月的维护成本约 0.5 人日，**所以卡在 6 条（1 主链 + 5 smoke）**；其中"503 保真"这条是**唯一必须穿反代的用例**，不能退化到集成层（F11）。

### 1.2 哪些必须是单元测试（不允许"顺便集成测一下"）

| 必测单元 | 理由（失败后果） |
|---|---|
| `Pricing.Calculate` | 金额错 1 分 → 对账崩、退款金额对不上、客服无法解释。11 步顺序任一步错都是法律意义上的"应付金额"错 |
| `Money` 全部运算 | 舍入方向错 → 相邻两行差额方向随机；`Allocate` 余数错 → 部分退款出现 1 分差 → 误触发 `INV-O04` |
| `VariantMatrix.Plan` | SKU 生成/碰撞/四桶错 → 重复 SKU、删掉有销量的变体（历史订单显示空） |
| `TemplateCompiler` | 3 模板快照是 AC-02/03 的第一道闸；确定性 Id 算法变更会让已初始化库与模板对不上（03 R6） |
| `OrderStatusMachine` + `ProjectStatus` | 状态机能被 `if` 打洞 = 未付款就能发货（F1，最直接的资损） |
| `Refund` 状态机 | F10/F11b（钱没退标已退 / 无凭证标成功）= 伪造财务事实 |
| `canonicalFor()` / `buildSeo()` | 一处错则整站 canonical 全错，且**线上看不出来**（只有搜索引擎知道），必须靠纯函数断言钉死 |

### 1.3 哪些必须是集成测试（单测证明不了）

| 必测集成点 | 单测为什么证明不了 |
|---|---|
| 回调幂等 **并发 5 次** | 幂等靠 `WebhookEvent` 唯一索引 + `RowVersion` 做仲裁；单测里没有唯一索引，`if(已处理)` 在单测里**永远绿** |
| 不超卖（并发抢最后 1 件） | `INV-S02` 依赖乐观锁 + 真实事务隔离；且必须在 **SQLite 与 PG 各跑一遍**（写串行 vs MVCC） |
| 退款分域（退货申请零通道调用） | "零调用"是对**通道适配器**的断言，必须用可计数的 `FakeGateway` 在 API 层验证 |
| 越权矩阵（遍历全部 admin 端点） | 权限点策略在端点元数据上，只能反射+HTTP 验证 |
| 向导锁定（页面 404 / 接口 409） | 涉及端点注册与前端路由两层，且 AC 明确要求"稳定错误码" |
| 数据不可用 → 503（AC-10 负向） | 是"全局异常中间件是否吞异常"的架构级断言 |
| 设置变更即时生效（`PublicSiteUrl`） | 跨 DB → 缓存 → SSR 输出三段链路 |

### 1.4 明确"不测什么"（YAGNI 体现在测试侧）

| 不做 | 理由 |
|---|---|
| **需求 §4.1 已判 `Out of Scope`/`Won't` 的功能**：商品 CSV 批量导入导出、优惠券/促销引擎、PDF 发票、多仓库、细粒度权限（自定义角色）、后台上传主题 | **测了等于要求实现范围外的功能**。这类"缺陷"我不开单；若客户当场提出，走需求变更（找场景产品策略师），不走测试流程 |
| 视觉回归（截图 diff） | 主题/文案会持续变，截图像素噪声率 >50%，维护成本远超收益；改为"token 断言 + 人工视觉验收"（§8） |
| 全量跨浏览器用例矩阵 | 仅黄金链路走 chromium/webkit/firefox；其余用例只在 chromium 跑。CSS 兼容性由"原生 CSS + 无第三方 UI 库"从源头收敛 |
| UI 组件快照测试 | 22 个原语全部 token 驱动，快照会随主题变红一片，是负资产 |
| 每次 CI 跑压测 | 2C2G 基准机在 CI 里不可得；8 核机器上的数字**不可用**（05 §2.6.1 明确）。压测按版本做（发布前 + 可选 nightly） |
| Fuzz / 完整渗透 | 只做 §5 的 ASVS L1 对应清单（客户是自托管小店，攻击面是"通用扫描器 + 越权"） |
| admin 全部 CRUD 表单校验 | 只测必填/唯一/状态机相关；纯表单格式错误由 FluentValidation 单测覆盖 |
| PDF / 打印排版 | 需求明确 Won't（§4.1） |
| **AI 输出质量评测**（准确率/幻觉率/Prompt 回归/流式中断） | **本项目不引入大模型或智能体**（需求 §1.1 原文："全程不引入大模型或智能体；安装向导是确定性的配置向导"）。故本文件不设"AI 专项测试"章节——设一节然后写"无"是形式主义。若二期引入"批量生成 SEO 文案"，评测集与人工复核的门槛应在**需求评审**阶段定义，而不是现在预写 |
| 移动 App / PWA 离线 | Won't（架构 §7.1） |

### 1.5 回归策略、冒烟集与工作量账（1 人现实约束）

| 集合 | 内容 | 触发时机 | 时长预算 |
|---|---|---|---|
| **冒烟集** | 架构 4 类（分层/互引/授权完备/DTO 隔离）+ Domain 单测 + 迁移漂移 + 模板/主题 schema + 契约漂移 | 每次提交（pre-push hook，`check.sh --fast`） | **≤3 min** |

| **版本集** | 回归集 + 压测 + 内存长跑 + 依赖漏洞扫描 + §8 手工清单 | 每个 release | 1.5 人日 |
| **缺陷回归规则** | 修 P0/P1 的 PR **必须**包含至少 1 条新测试（否则同一 bug 下个版本必复发）。作为 review 检查项，不靠自觉 | 每次修缺陷 | — |

**工作量账（唯一目的：让主理人知道这套方案能不能落地）**

| 工作块 | 人日 | 说明 |
|---|---|---|
| 单测（含 3 模板快照与状态机穷举） | 4.5 | AI 生成用例骨架，人负责断言口径 |
| 集成测试（12 条 + 5 条反向 + 双 provider 适配） | 6.0 | 最贵的一块，占 30% |
| 前端 Vitest + Playwright 5 条 | 3.0 | 含 `data-*` 契约落地与三引擎调试 |
| 压测（造数脚本 + 调优 + 内存长跑） | 2.5 | 造满 10k/50k 数据本身要 0.5 人日 |
| 安全清单（§5） | 1.5 | 大部分是 curl + grep |
| 门禁注入（§3.6 的清单）+ 判据自证（§3.7） | 1.5 | 一次性投入，长期收益最高；判据自证与注入共用同一次 patch 流程，不额外加人日 |

> - **样本纪律**：① `fx-arch-repl` / `fx-arch-orphan` / `fx-arch-repl-cat` / `fx-oos` 与全译档同批装载（不占档位）；**禁止归档 `fx-mug`/`fx-tee`/`fx-tote`/`fx-oos`/`fx-arm`**（各带别的判据，归档会连带把别人的绿变红，而失败信息会指向错误判据）。② **不得为凑"四形态"把一个商品同时改成"改过 slug + 归档"**——期望值会立刻变成"两跳还是直达"，这一格现由⑤（历史 slug）专门钉。③ 断言里的 slug / SKU / 变体码 / 分类 slug **必须能在 `02` §7.3.4 grep 到**，grep 不到判**断言写错**而不是实现写错（前端踩过一次：自编的 `/en/products/zh-only-product` 一路绿，因为那个 URL 本来就不该存在，404 是必然结果）。
> - ✅ **脚本覆盖已补齐（本条原记"两处缺口未修复"，现已作废）**：`verify-seo-matrix.sh` 现有 **5 个 URL 入参**（`--archived-moved` / `--archived-gone` / `--archived-gone-from` / `--moved-from` / `--moved-to`），S9 的**四个断言对象**全部有入参；"归档+有替代"除 `301` 与 `/en/c/*` 外，还会**再取一次 `Location` 断言 200**（`02` §7.3.4 把它算作 S9 判据的一半，这条已实现）。**缺任一入参 → `rc=2` → AC-11 不通过**，`--self-test` 的 v11 / v12 两个注入专门验这一条。

> - **否定式断言（"不在册"）必须能自证"真的扫过"**：`sitemap` 里"某个 URL 不出现"是**找不到就绿**——扫都没扫、或 sitemap 取空，这条照样绿，而绿的原因和"URL 确实不在册"无关。本节的负向断言（归档 URL 不进 sitemap）**靠两件事自证**：① 同节正面断言"缺货商品必须在册"（④）——它绿了才说明 sitemap 真被解析过；② 前置"`sitemap.xml` 里必须同时有 `/{locale}/c/` 与 `/{locale}/products/` 各至少一条"，缺则 `rc=2` 而不是警告。**⚠️ 所以那条前置绝不能降级成警告**：一旦允许空 sitemap，负向断言立刻变成"永远绿"，而且它和"已实现"在输出上无法区分。

### 3.3 并发测试的实现思路（**这一节决定 AC-06/AC-08/AC-19 是否真能验**）

三条硬要求：① 每个并发请求用**独立的 DI scope / DbContext**（同一个 DbContext 会被 EF 串行化，得到假绿）；② 必须**真正同时**起跑（`Task.WhenAll` + `TaskCompletionSource` 屏障，不用 `await` 顺序启动）；③ 断言要落在 **DB 状态**与**副作用计数**上，而不是只看 HTTP 码。

```csharp
// 并发重放 5 次的骨架（≤20 行）—— 关键在 barrier 与独立 scope
var barrier = new Barrier(5);
var tasks = Enumerable.Range(0, 5).Select(_ => Task.Run(async () =>
{
    using var scope = _factory.Services.CreateScope();      // 每个请求一个 scope
    var client = _factory.CreateClient();                    // 独立 HttpClient（独立 cookie/连接）
    barrier.SignalAndWait();                                 // 5 个同时起跑，避免"假并发"
    return await client.PostAsJsonAsync("/api/webhooks/payments/fake", _samePayload);
})).ToArray();
var responses = await Task.WhenAll(tasks);
responses.Should().OnlyContain(r => r.StatusCode == HttpStatusCode.OK);   // 全 200，不能有 500
(await _db.Payments.CountAsync(p => p.OrderId == orderId)).Should().Be(1);
await AssertStockAsync(variantId, onHand: 3, reserved: 0, sold: 1);        // Sold 只 +1
(await _db.Outbox.CountAsync(o => o.DedupeKey == $"order-confirmation:{no}")).Should().Be(1);
```

> `barrier.SignalAndWait()` 必须放在**请求发出前**；把 5 个请求写在一个 `foreach` 里 `await` 是**最常见的假并发**（串行跑完永远是绿的）。
> SQLite 下 5 个并发写会排队（单写者），**仍然要跑**：断言点变成"其余 4 个走唯一冲突分支、无 500、无重复副作用"，这恰好验证了 03 §4.3.2 的"把冲突当正常分支"。

### 3.4 E2E 黄金链路（唯一的一条，1 个人必须养得起）

```
访客 → /zh/（断言 SSR 出的区块内容）
→ /zh/c/robot-parts 勾选 facet（断言 URL 带 f.* 与 sort）
→ /zh/products/{slug} 选变体（断言价格/库存/主图联动 + 不可用组合置灰）
→ 加购 → /zh/cart 改数量 → /zh/checkout 填地址（断言摘要四行）
→ 提交订单（带 Idempotency-Key）→ FakeGateway 支付成功页
→ /zh/orders/track 用订单号+邮箱查单（断言"已支付"）
→ /admin 登录 → 订单详情点"刷新支付状态"（断言仍 1 条支付记录）
→ 填运单号发货（断言前台查单看到"已发货"+运单号）
→ 发起退款（断言先"退款中"，Fake 回调后"已退款"）
→ 前台查单看到"已退款" + 退款金额
```

**它如何不依赖真实通道**：`FakeGateway` 必须是**可编排的**（这是给后端的硬需求，见 §10.1）：
- `CreateIntent` 返回可识别的假跳转 URL，E2E 直接 `goto` 它并"点确认支付"→ 触发内部回调；
- 提供三种真实形态：**立即成功**、**受理中→成功（异步延迟 N 秒）**、**签名错误**；
- 提供 `FaultMode`：`Timeout` / `Decline(card_declined)` / `UserCanceled` / `SupportsRefund=false`；
- 提供**调用计数器**（退款路径要断言"零通道调用"）。

**E2E 稳定性纪律**（否则 1 个人会被 flaky 拖死）：
1. 定位器**只用 `data-testid`**，禁止用文本和 CSS class（文案与主题都会变）；
2. 每个断言前等**明确的业务信号**（`data-order-status="paid"`），禁止 `waitForTimeout`；
3. 全程 1 个 worker（单实例店），并行靠"每 worker 一套独立 compose + 独立端口 + 独立数据卷"；
4. 失败自动归档 trace + 截图 + 当时的服务端日志片段（按 `correlationId` 抓）。

> **输出语汇要对齐（否则两个脚本的"通过"不是同一个意思）**：已交付的 `verify-gates.sh` 逐条打印 `Vn <gate> ok`（注意：**它没有 `--self-test` 参数**，它本身就是全量自证，跑一遍约 2 分半；有 `--self-test` 的是 `verify-seo-matrix.sh` 与 `soak.sh`，别把两者的参数与注入数混着写）（失败为 `NO-OP` / `WRONG-RED` / `ANCHOR-MISSING` / `NO-TARGET`），汇总行 `proven=N failed=M`，**成功时不打"首行摘要"**。本文要求 `verify-test-gates.sh` 打的是 `PROVEN VQn: <用例ID> 变红，输出摘要=<首行>`——**这个形态更强（能看出"红在哪一条断言上"），保留不变**，但它是**计划项**：要两边一致，得让后端在 `verify-gates.sh` 补一行输出。在那之前，**不要把两个脚本的输出格式互相引用**（"上次通过了几条"这类结论快照本来也不入本文）。

### 3.7 判据自身的 fail-before-pass（**需求侧已因缺这一步产出假阳性，务必读完**）

> 背景：需求侧第一版通配禁令写成 `grep -Ei 'Disallow:.*(\?|\*|&)'`，会把**正确**的路径段通配 `Disallow: /*/search` 判成违规（`*` 被一并拦）。若这份判据直接交到 QA 手上，结果是**开出一堆假缺陷，然后全组开始不信验收清单**。判据和门禁一样，必须证明自己会红、也要证明自己不会乱红。

| # | 纪律 | 做法（每条脚本判据交付前必须做） | 反面教材 |
|---|---|---|---|
| PG1 | **不误伤** | 在**当前正确实现**上跑一次，必须绿 | 上面的 `\*` 误伤：把合法路径段通配判红。**凡涉及 `*` 的正则，先问"这是路径段还是查询串"** |
| PG2 | **真能抓** | 在**故意做错的实现**上跑一次，必须红；对应注入见 §3.6 的清单。**找不到对应注入的脚本判据，等于只做了一半** ⚠️ **按本条自己的标准：§3.6 的 VQ 清单尚未实现，所以那些判据现在全部"只做了一半"** | 只验"页面里有没有 canonical 这三个字"，注入 `'self'` 也绿（VQ9 抓不到） |
| PG3 | **只断言 AC 原文的东西** | 断言对外可观测的产物（状态码 / 响应头 / HTML 里的 href 值 / DB 行数），不断言实现细节（函数名、日志文案、CSS class） | 断言"日志里有 error"当作 503 的判据 → 反代改写 200 时仍然绿（VQ14 抓不到） |
| PG4 | **空输出不等于通过** | `grep -c` 无命中时**退出码 1 且打印 `0`**，在 `set -e` 脚本里会被当失败；统一写 `! grep -q …` 或显式比较 `-eq 0` | "必须无输出"类断言写成 `grep -c xxx` → 明明正确却判红，团队开始用 `\|\| true` 糊住，最后连真缺陷也一起放过 |
| PG5 | **HEAD ≠ GET** | 涉及 `X-Robots-Tag` / `Location` / `Content-Type` 的断言，除 `curl -sI` 外必须用 `curl -sD- -o /dev/null`（GET 取头）复验一遍 | 部分框架 HEAD 走不同管线，`curl -sI` 绿、真实 GET 无 `noindex` → 线上被收录，测试却全绿 |
| PG6 | **环境差异要显式** | 断言里凡依赖域名/端口/语言的，一律从变量注入（`S=$PUBLIC_SITE_URL`、`$DEFAULT_LOCALE`），不写死 `localhost:3000` 或 `/zh` | 换默认语种为 en 后整批用例红，被误判成回归 |
| PG7 | **退出码语义要唯一，且只有一个定义点** | 四个门禁脚本的码含义**只在 `docs/05` §4.6 定义**，本文不复述数字含义——复述就是第二份真源，本轮已因此出现四份互相矛盾的说法（同一个 `2` 在一处是"用法错误"、在另一处是"未验证"）。**码的集合是契约 `{0,1,2,3}`，出现集合外的码即违约**：脚本多一个码是脚本违约，不是本表缺一行。判据：CI 只接受"通过"那一个值；**出现 `[ $? -le 2 ]` 或 `\|\| true` 一律按缺陷处理**——那是把"未验证"静默升格成"通过" | 退出码混用后，运维看到红不知道该补环境还是该改实现（按"缺陷"去查代码，而真正该做的是把环境补齐）；更糟的是有人用 `\|\| true` 糊住，真缺陷一起放过 |
| PG8（文档侧，不是脚本判据） | **失效引用的回声** | 发布前扫一遍：凡写着"检查 X 是否存在 / 是否等于 Y"的用例，先确认 **X 今天还在不在**。结论已改、但**引用该结论的句子没改**时，它仍在要求一个已不存在的条件——**这是最容易让正确实现被判红、也最容易让已修好的问题重新变成缺陷的形态**。不在了就二选一：① 删；② 改成"**若重新出现则判缺陷**"（推荐②，它保留了"为什么当初要有 X"的信息，删掉会让下一个人重新提议加一个 X） | ① 指向已闭环条目的备注（备注指向 C9 而 C9 已闭环）；② 要求检查已被删除的开关（原 C3 要求查 `FILTER_CANONICAL='self'`，开关整个消失）；③ 仍按"两套并存"写（同一语义两个字段各写一份） |
| PG9（文档侧，不是脚本判据） | **弱断言伪装成强断言** | 下面三对是同一件事的三个实例：**右边的判据看起来更难写，左边的判据看起来已经覆盖了**。左边的那个**总是先被写上去**，因为它更容易满足。写成左边就等于「以为验过了」。⚠️ **但三种病的药不同**：①② 是**弱化**（验了个更松的条件）→ 加严即可；③ 是**自证**（用被测物验被测物）→ 必须切断数据来源的耦合，光加严没用——**自证的断言在实现正确时也是绿的，它不是「错的断言」，是「永远不会红的断言」** | ① `details.reason ∈ {noCredentials, testFailed, channelDisabled}` **vs** 与同一响应的 `canSellReason` **逐字相等**（值域合法性抓不到「把 `channelDisabled` 映射成 `testFailed`」——两个值都在域内）；② 门禁「通过」 **vs** 结论行**印出检了多少条**、`N=0` 单独成句（`set=∅` 时「每个元素都满足 P」恒真，这个绿与「查了 N 个全过」在退出码上一样）；③ `301` 落到 `/{locale}/c/*` **vs** 期望值**只来自 fixture、不从接口 `targetUrl` 反推**（resolver 取错分类时两边一起错，断言永远绿） |
| PG10 | **判据与实现冲突时的禁止路径** | 判据说「X 不存在」而设计说「X 存在」（或反之）时，**只准两件事**：① 停下来说清冲突并裁决；② 按裁决改判据。**禁止两条捷径**：**改实现去迁就判据**、**删功能让判据变绿**。理由：删掉一个东西永远比实现它便宜，所以只要判据的形式是「不存在」，它就在**持续给「删功能」发通过证**；而删掉的东西往往没有第二个判据守着。判据要落在**行为**上（不可写 / 不可达 / 不暴露），不落在**有无**上 | 本轮实例：`TC-E6-19` 原要求「`StoreSettings` **无该列**」，而 `02` §3.8 有只读投影列 `CanSell`/`CanSellReason`；**正确实现会红在这条判据上**，而最便宜的「修法」是把列删掉——那等于用一条过时判据推翻一条已裁决的设计（删列还一并带走互锁 `CHECK` 与 `bootstrap.store` 读口，**且没有别的用例会红**）。改判据为「**存在但不可写**」后，删列反而红 |

**执行约定**：用例表里"方式=脚本/集成/E2E"的行，交付时必须带一个自证状态：`已自证(PG1,PG2=VQn)` 或 `未自证`。**`未自证` 的判据不得作为放行依据**（可以跑，但红灯不能算缺陷、绿灯不能算通过）。这条与 G8/G12 同源：**门禁和判据都必须证明自己会红。**

### 4.1 基准数据集（**造不满就等于没测**）

| 项 | 值 | 说明 |
|---|---|---|
| 商品 / 变体 | **10,000 / 50,000** | 与 AC-12 原文一致 |
| 分类数 / 每节点**直属**商品 | 20（2 根 + 6 中 + 12 叶，3 级）/ **500** | 20×500 = 10,000，正好铺满。⚠️ **"每分类 500"是"每节点直属 500"，不是"每个分类页有 500 个商品"** |
| **子树商品数（按层级）** | 叶 **500** / 中 **1,500** / 根 **5,000** | 同一个数据集在两条查询路径下差一个量级：`ProductCategory WHERE CategoryId=?`（直属）与 `Category.Path LIKE '/1/7/%'`（子树）。哪一个才是"分类页"的规模，取决于该页含不含子树商品——**这个语义不定，下面三个数会各自按自己那套算，且三份都自洽** |
| 属性 | 每分类属性集 6 个，其中 3 个 `filterable` | 筛选要真能筛出东西 |
| 翻译 | zh + en 双全量 | 翻译表 join 是列表查询的固定成本，不可省 |
| 订单 | 20,000（含各状态） | admin 列表与对账扫描的数据量 |
| 运行规格 | **2 核 2GHz / 2GB / SQLite（WAL）/ 无外部缓存** | 8 核开发机结论不可用（05 §2.6.1） |
| 造数 | `dotnet run --project tools/OpenStore.Tools -- seed-bench --db <sqlite-path> --tier small\|standard`。**已交付**（`seed_version=bench-v1` + 各表行数 + 数据量指纹；`--self-test` 7 项自证） | 可重放：确定性主键、按 slug 幂等；**指纹不符或行数不足则拒绝出报告**（防「用了半套数据出的结论」）。商品与变体两项已能达标，属性集/翻译/订单见本节末的缺口表 |

> **分类页的语义（team-lead 裁定）：分类页含子树商品。** 三条理由：① 用户点父分类的预期是"该分类及其子分类的全部商品"，只显示直属会让 3 级树形同虚设（点根分类只能看到 1/7 的商品）；② 需求侧写的是"分类有独立 URL"+"前台分类导航与筛选侧栏一致"，导航给的是树、页面给的却是节点，两者对不上；③ 若定直属，`Category.Path LIKE` 那条路径就只剩 sitemap/后台在走，而它是最贵的那条——**最贵的路径不该只在一个没人压的入口上被测**。
>
> **AC-12 的读数必须绑定"测的是哪一页"**：不绑的话"TTFB P95 ≤500ms"是一句对某个未知页面说的话。基线页固定在**根分类页**——子树 5,000 个商品待分页 + facet，是叶分类页的 10 倍。**跑叶分类等于把最贵的那页造得和最便宜的一样便宜，然后用它证明系统扛得住。**

**怎么造、怎么判「造满了」**

```sh
# 一次性：工具项目不在 OpenStore.sln 里，门禁步骤 1 的 -warnaserror 不覆盖它。
# 不单独 build 的话，check.sh 步骤 9/10 与下面的 run --no-build 都会跑旧产物。
dotnet build tools/OpenStore.Tools -warnaserror

# 自证（只在系统临时目录造数，结束即删，不碰任何真实库）
dotnet run --project tools/OpenStore.Tools --no-build -- seed-bench --self-test

# 造 AC-12 验收档：10,000 商品 / 50,000 变体 / 每分类 500
dotnet run --project tools/OpenStore.Tools --no-build -- seed-bench --tier standard --db /data/openstore.bench.db

# 小档：1,000 商品 / 5,000 变体（改代码后每次回归跑这一档）
dotnet run --project tools/OpenStore.Tools --no-build -- seed-bench --tier small --db /tmp/bench-small.db
```

退出码只有三个：`0` 成功且核对通过 / `1` 数据不一致（行数≠规格）或自证失败 / `2` 用法错误或前置条件不满足（缺 `--db`、tier 非法、`--db` 命中受保护库、目标目录不存在）。**压测报告只认 `0`**。

「造满了」的判据（缺一条就不许出报告）：

| # | 判据 | 机器判法 |
|---|---|---|
| 1 | 商品数 = 规格 | 输出 `products=` 必须等于 `spec_products=`（standard 下 10000） |
| 2 | 变体数 = 规格 | 输出 `variants=` 必须等于 `spec_variants=`（standard 下 50000） |
| 3 | 每分类 = 规格 | 20 个分类逐个核对 = `spec_products_per_category=`（standard 下 500） |
| 4 | 结论行 | 必须打印 `verdict=OK 造满了（行数 = 规格，每分类 = 规格）`；任一条不满足则打印 `CHECK FAILED: <哪张表差多少>` 且退出码 `1` |
| 5 | 两次可复现 | 同一 tier 在两个空库上跑，`fingerprint=` 必须相同 —— 不同即"主键不确定"，两份报告不可比 |
| 6 | 每商品变体数 = 规格 | `products_with_wrong_variant_count=0`。总数对而分布坏（一个商品挂 10 个、另一个挂 0 个）时总数照样对，但规格选择器在某些商品上会返回空 |
| 7 | 同商品轴签名不重复 | `duplicate_axis_signatures=0`。这一条验的是"DB 唯一索引真的在这份库里"（SQLite 改表要重建表，索引最容易在重建时丢掉） |

**这一项的成立范围必须跟着数据一起说，不能只在文档里说清楚**（报告会被摘出来单独转发）：

> 「每分类 500」当前证明的是**列表数据量**（按 slug 段 `bench-cNN-` 核对，输出行 `category_check_scope=slug-segment`）；**未证明**：`ProductCategory` join 成本、多分类归属时属性并集的成本。——这两项要等 `M1 目录与库存` 的表落地、`VerifyAsync` 改为 join 计数后重跑。

造数命令自己也会打印 `category_check_scope=...` 那一行，就是为了让"看起来支持结论的数"没法被单独带走。

把 `seed_version` / `products` / `variants` / `fingerprint` 四行连同压测结论一起归档：两轮报告指纹不同，第一件事是查"是不是换了数据集"，而不是先怀疑代码退化。

受保护库（两道闸门，命中即 `rc=2` 并打印原因）：文件名等于 `openstore.dev.db`；或解析后的绝对路径等于 `src/OpenStore.Api/appsettings*.json` 里任一条连接串指向的库。造数前校验，**拒绝发生在建库之前**，不留副作用。

实测（本机 8 核开发机，仅证明生成端可用，**不是** AC-12 的运行规格）：small 1,000/5,000 与 standard 10,000/50,000 均一次跑通；standard 全量生成约 10 秒、库文件约 14 MB。

当前生成器相对上表规格的**缺口**（不补齐这三项，"AC-12 基准完整达标"这句话仍说不出口）：

| 规格项 | 现状 | 缺口与代价 |
|---|---|---|
| 商品 / 变体 | ✅ 已达标（10,000 / 50,000，含 2.7% 草稿态用于后台列表） | — |
| 每分类 500 | ✅ 已达标，但分类归属**暂由 slug 段 `bench-cNN-` 表达**（输出 `category_check_scope=slug-segment`） | `M0` 物理表还没有 `Category` / `ProductCategory`（`M1 目录与库存` 才落）。能证明"分类页清单拿到的商品数是 500"，**不能**证明真实分类 join 成本。**`M1 目录与库存` 必须把判据迁走**：目标模型里 `Product` 没有 slug 列，slug 在 `ProductTranslation` 上、唯一索引是 `(Locale, Slug)`（同一商品在不同语种 slug 可不同），所以 slug 段只在默认语种那一行成立；且分类重新归属时 slug 不变，`LIKE` 会**静默给出错的分类**。迁移形态：先建 `Category`，为每个商品建恰好一行 `ProductCategory(IsPrimary=true)`，`VerifyAsync` 改为 join 计数，slug 段只作一次性回填依据 |
| 属性集（每分类 6 个，3 个 filterable） | ❌ 未造 | 无属性表；变体轴只落 `size` / `color` 两维的签名串。筛选多面体的 SQL 复杂度没被测到 |
| 翻译 zh + en | ❌ 未造 | 无翻译表；`Product.Title` 单语。列表页的翻译 join 成本缺测 |
| 订单 20,000 | ❌ 未造 | 无 `Order` 表（`M3 购物车与下单`）。管理端 5,000 行分页与对账扫描仍需等订单模型 |

一条给 `M1 目录与库存` 扩生成器的红线：造 `Archived` 样本时**不得**为了"归档商品不该出现在分类页"而删除、清空 `ProductCategory` 行（含 primary 行）——分类页过滤的是 `Product.Status`，不是关联行；删关联会让"替代分类页"取不到候选，现象是归档商品全部 410，而排查方向会先错两层（见 02 的归档语义）。当前生成器**不造 Archived 样本**（只造 Active + 2.7% Draft），所以现在不涉及；写在这里是因为这是造数侧最容易踩的一次性改动。

### 4.3 断言口径（逐条可判定）

| 指标 | 通过标准 | 判定方式 |
|---|---|---|
| TTFB（首页/分类/详情） | **P95 ≤ 500ms** | k6 汇总或 `soak.sh` 里 `awk` 取 95 分位（**05 §2.6.1 给的是设计稿，脚本已交付但未实跑**） |
| LCP / 性能分 | **LCP ≤ 2.5s 且 ≥ 70** | Lighthouse CI JSON |
| 筛选切换 | **≤ 800ms** | Playwright 打点，20 次 P95 |
| 管理端列表 | **≤ 1.5s** | k6 |
| **内存** | 三进程（api+storefront+caddy/系统）**合计 RSS ≤ 2GB**，连续 30 min **不 OOM、不被 OOM Killer 杀** | ① `docker stats` 采样峰值 ② `docker inspect` 的 `OOMKilled=false` 且 `Restarts=0` ③ `/sys/fs/cgroup/memory.events` 的 `oom_kill == 0` ④ `journalctl -k \| grep -i 'killed process'` 无命中。**四条都要，缺一条就只能猜**（05 §2.6.1） |
| 冷/热缓存 | 冷启动后先压 5 min（缓存未热）再压 30 min | 冷启动期最容易被 OOM 杀，必须单列 |
| 干扰项 | 压测期间关闭备份与定时任务（`OpenStore__Jobs__*__Enabled=false`） | 否则"备份吃 CPU 导致 TTFB 超标"会被误判 |

### 4.4 "无超卖"如何断言（压测里最关键的一条）

**判据不是"HTTP 有没有报错"，而是库存三元的账实相符。** 具体做法：

1. **造一个精确的库存数**：目标变体 `OnHand = 5, Reserved = 0, Sold = 0`（`Available = 5`）。
2. **并发下单 N 次（N=20 > 5）**，全部用独立会话同时起跑（§3.3 骨架）。
3. 断言 5 条：
   - 成功单数 **恰好 = 5**（`201` 计数），失败单数 = 15 且**全部是 `409 INSUFFICIENT_STOCK`**（不是 500、不是 429）；
   - **`OnHand = 5`、`Reserved = 5`、`Sold = 0`**，且 `OnHand - Reserved - Sold >= 0`；
   - **DB 中不存在任何负值**：`SELECT COUNT(*) FROM StockItem WHERE OnHand < 0 OR Reserved < 0 OR Sold < 0` = 0；
   - **流水与三元组账实相符**：`SUM(delta.OnHand)`、`SUM(delta.Reserved)`、`SUM(delta.Sold)` 分别等于当前三个字段；
   - **`Available` 全程 ≥ 0**（在压测脚本里每 200ms 采一次 `Available`，取最小值）。
4. 再补一轮**支付 + 超时**交叉：5 单里支付 2 单、其余超时取消 → `OnHand=5, Reserved=0, Sold=2`，失败单的库存已全部回补（`Release` 流水 3 条）。**口径**：`Available = OnHand − Reserved − Sold`，**`Sold` 是"已支付未发货"、仍占 `OnHand`**（所以支付后 `OnHand` 不变、`Reserved` 减、`Sold` 增）。
4b. **管理员把库存改到 `Reserved + Sold` 以下**（**不是新增 AC**，而是 AC-08 那条"库存不出现负数"不变量的**另一条可达路径**——并发抢购之外，后台改数也能把它破掉，容易漏）：`POST /api/admin/inventory/{variantId}/adjust` 传 `newOnHand < reserved + sold` → **409 `INVENTORY_NEGATIVE_FORBIDDEN`**，且三元组**保持原值不变**（不能"改一半"）。DB 侧另有 `CHECK (OnHand >= Reserved + Sold)` 兜底——断言该约束**真实存在于两个 provider 的迁移里**（SQLite 重建表也要有）。
4c. 并发中途用管理员接口调低到刚好等于 `Reserved+Sold`（合法边界）→ **必须成功**，随后新一轮下单立刻 409 `INSUFFICIENT_STOCK`（边界不许被"保守实现"误拒）。
5. **双 provider 都跑**：SQLite（写串行）与 PG（MVCC）结论必须一致；任一不一致即视为 bug（02 §5 第 5 项）。

> **限流三条的取样纪律（写错取样点，断言会在错误的结论上变红）**
> - **一次请求同时消耗它所属的每个桶各一次**（串行 AND）。所以取样端点必须"只属于被验的那一个策略"：验 `write` 用 `POST /api/storefront/cart`；验端点级桶用各自的端点；`/api/admin/auth/login` **绝不能拿来验 `write` 桶**。⚠️ **"只属于一个策略"是选样本的标准，不是给端点分类的依据**——admin 写端点同时吃 `write` 与 `admin-write`（`write` 的 60 先到），所以"大多数端点只属于一个桶"这个前提**不成立**。正确的说法是：**每个用例显式声明"我要验哪个桶、这个取样点一定会消耗它、且不会在更早的一步被别的桶挡住"**；admin 侧几乎找不到满足后两半的样本点，那里只能靠"验端点级桶时同步断言 `write` 也少了一次"来间接确认串行 AND。
> - **"login 的 POST 也计入 `write` 桶"这条不测**：61 次 login 会在第 7 次被 `login` 桶挡下，永远走不到 `write` 耗尽那一步。要让它可观测，只能给测试环境放开 `login` 桶——而后门一旦存在，"限流可被配置绕过"就变成真风险。**不可观测的断言等于没有断言**，这里记"为什么测不了"，不写一条永远绿的假断言。
> - **`retryAfterSeconds` 跨 429 与 503 是一条统一不变量**（`03` §6.7 已定稿，**有意复用而非巧合**）：**凡响应体里出现 `details.retryAfterSeconds`，该响应必须同时带 `Retry-After` 头，且两值相等。**反向不强制（**带头可以不进体**，例如纯运维面响应），但**一旦进了体就必须与头一致**。所以断言写成**一条参数化**：枚举所有带该字段的响应 → 断言头存在且同值（今天是 `429 RATE_LIMIT_EXCEEDED` 与 `503 PAYMENT_PROVIDER_UNAVAILABLE` / `EMAIL_UNAVAILABLE` 两族；**将来新增第三种带它的状态码会被自动覆盖**，不用再加用例）。理由同右：两个出口说不同话，比少一个出口更糟 
> - **窗口必须是滑动窗口或令牌桶，不得用固定窗口**：固定窗口在边界会出现 2 倍突刺（59 秒打满、61 秒再打满，两秒内实际放行两倍），同一份代码同一个请求序列会**跑两次一绿一红**；而随机失败的门禁最后一定会被 `retry` 或跳过。判据是"**任意 60 秒窗口内 ≤ N**"，不是"每分钟 ≤ N"。**该约束已写进 `03` §6.7 实现约束第 6 条**（明确 `SlidingWindowRateLimiter` / `TokenBucketRateLimiter`，并点名"不要因为 `FixedWindowRateLimiter` 是默认最省事的那一个就用它"）。⚠️ 这条是**实现约束，不是可观测判据**：外部打请求分不出滑动窗口与固定窗口，只能在窗口边界做**定向实验**——在第 59 秒打满、第 61 秒再打，两次都必须被 429；固定窗口会让第二次整批放行。**这个实验要进用例**，否则"窗口类型"就只是一句文档承诺。

### 6.2 AC-01~AC-20 覆盖矩阵（含 AC-14 拆出的 14a~14d；**条数以需求 §6 表行为准，本文不复述**）

> **本列的口径（读这张表前必须先看）**：只登记**此刻就能执行、且跑一次会红**的东西（脚本 / 测试方法 / CI 步骤）。**本列「部分」的读法（只此一种，不许各读各的）**：`部分` 描述的是**现状**——这条 AC 下**若干子判据**已经有了会红的载体；**但它在验收上与「无」等价**：只要还有一处子判据不可判红，这条 AC 就**不得判通过**。另有按「能不能判通过」出的巡检视图把 `部分` 直接记作 `无`——**两张表不矛盾，是同一条规则的两个粒度。**  **用例编号不是载体**——它写的是"该断言什么"，不是"已经有人在跑"。**"计划中"一律记为"无"**：计划中的载体和没有载体，在验收那天**行为完全一样**（都不会红），但报告写法不同，而前一种会让人以为已经有人管了。

## 7. 缺陷分级与发布门禁

### 7.1 缺陷分级（**级别必须绑修复时限，否则分级没有意义**）

| 级别 | 判定标准（满足任一条即命中） | 修复时限 | 是否阻断上线 |
|---|---|---|---|
| **P0** | ① 资损或账不平（超卖、重复扣款、重复退款、退款金额错、库存为负）② 资金/权限安全（越权可读他人订单、伪造回调被接受、卡号落库/落日志、`/setup` 未锁定可接管）③ 主链路不可用（下单、支付确认、发货、查单任一 500）④ 数据不可恢复（备份不可用、迁移失败）⑤ **与 AC 原文直接冲突且无 workaround** | **立即（24 小时内修完 + 全量回归）** | **是**（一票否决） |
| **P1** | Must 故事的 AC 不通过，但**不涉及资损与安全**：多语 URL 某条规则错、索引矩阵违反、AC-14 有中文、`canSell` reason 缺失、主题 5s 生效不达标、性能某一项超 5%~20% | **48 小时** | **是**（除非主理人书面降级为 P2 并登记 workaround） |
| **P2** | Should 故事缺陷、体验问题（文案、排序、空态缺省）、性能超标 <5% | 5 个工作日 | 否（登记已知限制后放行） |
| **P3** | 主题视觉细节、文案措辞、非关键页面样式、`Should` 之外的优化项 | 下个迭代 | 否 |

**分级的三条纪律**

1. **不确定就按高级别报**，由主理人降级并留痕；反之（先报低再升）会漏。
2. **每一级都要写"复现步骤 + 期望/实际 + 证据（correlationId / 截图 / SQL 结果）"**。缺证据的缺陷单在 48 小时后自动关闭——1 人团队没时间追。
3. **P0/P1 修复必须附回归用例**（新增或加强），否则同一 bug 下版本复发（§1.5 已定为 review 检查项）。

> **G8 当前判红（这是事实记录，不是"部分通过"）**：`verify-gates.sh --list` 现列 **9 条**（`V1`–`V8` + `V12`，本轮实跑命令核实）；输出形态是**逐条一行**（`Vn <gate> ok` / `NO-OP` / `WRONG-RED`）+ 一行汇总 `proven=N failed=M`——其中 `NO-OP` 的含义是"注入之后门禁仍然绿"，即那条规则是摆设。后端这 9 条的"本次是否逐条 ok"属**结论快照，本文不记**（要记就记 CI 里那一次的输出）。测试侧 `scripts/verify-test-gates.sh` **不存在**、VQ 条目一条未实现，所以"AC 相关门禁自证"的结论是**未完成**，不是"部分通过"。
> **为什么不拆成"当前可达 9 条 / 落地后全量"两档**：拆出来的第一档会立刻变成实际放行依据——人会跑它、看它绿、签字，而它 **0 条测试侧注入**；第二档则永远在排队，没有任何人有动力把它变成阻塞项，直到验收前一周才发现，那时只剩"延期"或"接受 9/25 覆盖率"两个选项。这与 `rc=2` 是同一个问题：**"没跑"必须显示为"未通过"，不能显示为"部分通过"。** 三态里没有第四态。
> **可以让门禁红着交付，不能让门禁假绿着交付**：红着交付时客户知道缺什么；假绿时没人知道。VQ 要落地就给它里程碑与 owner；排不进就如实记"本期不覆盖"——那是范围决定，可以接受；"部分通过"不是范围决定，是记账错误。

| 7 | 实体在某 locale **无语言行** → 直连 URL **404** | 有语言行但**字段为空** → **200 + 回退** | **相反行为**，fixture 必须各备一个样本（F2/F3）；只有其一，永远分不清"该 404"与"该回退"（TC-E3-14d/14d2） |
| 8 | `read` 桶 100 次 GET 后 POST 不得 429 | `write` 桶 60 次 POST 后 GET 不得 429 | 两个桶**各自计数**（一次请求给它所属的每个桶各记一次，串行 AND）；只测一条时"完全豁免 GET"的实现也能过，而那等于关掉读限流（TC-SEC-21）。**取样端点必须只属于被验的那一个策略**，用 login 验 `write` 桶会红在错误的结论上 |

> 反向纪律：我认为某条 AC 测不了或定义有歧义时，**找场景产品策略师改需求**，不让开发改实现去迁就一条坏 AC，也不自己放宽判定（AC-14 逻辑互斥、AC-11 叠加 robots+noindex 都是需求侧自己改掉的，我去改只会变成第二个"作者自证"）。

### 10.2 给前端：需要的 `data-*` 标记（**E2E 稳定的唯一前提**）

> 纪律：**E2E 定位器只用 `data-testid`**，禁止依赖文本、CSS class、DOM 层级（文案与主题都会变）。

| 标记 | 加在哪 | 用途 |
|---|---|---|
| `data-testid="product-card"` / `data-testid="product-price"` | 列表卡片 / 价格 | 列表断言（名称、价格、售罄标记） |
| `data-testid="variant-option"` + `data-variant-code` + `data-variant-disabled="true"` | 变体选项 | 置灰与可点性（TC-E5-02）；**不要用 `:has-text`** |
| `data-testid="variant-price"` / `"variant-availability"` / `"variant-image"` | 详情页变体联动区 | 价格/库存/主图跟随断言（AC-03/TC-E2-06） |
| `data-testid="add-to-cart"` / `"sold-out"` | 加购按钮 / 售罄态 | 加购链路与售罄断言 |
| `data-testid="cart-count"` | 购物车角标 | 角标与实际数量一致（US-E5-03） |
| `data-testid="checkout-submit"` + `data-can-sell="false"` + `data-can-sell-reason` | 结算按钮 | **AC-17 的文案与视觉分级断言**（`noCredentials` vs `testFailed`）；`disabled` 判断 |
| `data-testid="summary-line"` + `data-line="subtotal\|shipping\|tax\|total"` | 结算摘要四行 | 金额断言（按行取，不靠文案顺序） |
| `data-testid="order-status"` + `data-order-status="pending_payment\|paid\|shipped\|refunded\|..."` | 订单/查单页状态标签 | 黄金链路的业务信号等待点（**替代 `waitForTimeout`**） |
| `data-testid="refund-status"` + `data-refund-processing="true"` | 查单页退款区块 | **TC-E7-13：消费者侧只见"退款处理中"，且不得出现线下字样** |
| `data-testid="facet-group"` / `"facet-option"` + `data-facet-code` / `data-facet-count` | 筛选侧栏 | 筛选点击、计数为 0 不显示（US-E5-01）；AC-14 的侧栏断言 |

| `data-testid="admin-login-email"` / `"admin-login-submit"` | 登录表单 | admin 登录（E2E） |

**另外三条前端契约**：① `data-testid` 一旦上线**不允许重命名**（重命名必须同步改测试，进 review 清单）；② 所有 `t()` 产出的文本元素**必须**带 `data-i18n-key`（漏加会让漏译统计偏低 → **假绿**，这是 AC-14 最隐蔽的失败模式）；③ 加载/空/错误三态要有稳定标记（`data-state="loading|empty|error"`），否则 E2E 只能靠超时。
