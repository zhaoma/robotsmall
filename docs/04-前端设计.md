## 0. 一页结论

| 决策点 | 结论 | 理由 |
|---|---|---|
| 两个前端入口 | `apps/storefront`（SvelteKit + adapter-node + SSR）；`apps/admin`（SvelteKit + adapter-static + `ssr=false`） | 公开站要真 HTML（AC-10），后台无需被索引且零 Node 成本（架构 §5.4） |
| 路由语种策略 | **所有语种都带 `/{locale}/` 前缀**（含默认语种），`/` 302 到 `/{default}/`；**任何缺前缀的前台路径 302 到带前缀的等价路径** | 需求 US-E3-05。附带收益：语言切换 = 换第一段路径，3 行代码，等价页永不丢（US-E3-04） |
| 主题存在形式 | 构建期 pnpm 工作区包 + `import.meta.glob` 静态注册表，运行时选择 | Svelte 组件须经 Vite 预编译，"上传 ZIP"技术上不成立 |
| 编辑表单数据源 | **单一文件** `themes/<id>/tokens.json` 即 JSON Schema（每属性带 `default`、`x-group`、`x-control`、`x-a11y`） | 消除"tokens 值文件 + editable schema 文件"双文件漂移风险（见 §12 偏差 D-2） |
| token 合并位置 | **只在 storefront SSR 侧合并一次**（`resolveTokens`），admin 不做合并、只编辑原始三层 | 合并路径唯一，编辑器预览走 iframe 打 storefront，不存在第二套渲染 |
| 可视化预览 | **同页 iframe**（`/{locale}/_preview?token=`），不做内联预览 | admin 不打包主题组件；iframe 隔离样式且能切页面（§4.5.2） |
| 区块拖拽 | **原生 HTML5 DnD + 上移/下移按钮**，不引库 | 6 个区块的列表，sortablejs ~43KB gz 吃预算且移动端本就要按钮兜底 |
| 购物车状态 | 服务端持久化；SSR 下用 `+layout.server.ts` 读 Cookie → `page.data`；组件树内用 `setContext` 的**工厂函数**，**禁止模块级 `$state` 单例** | 模块单例在 SSR 下多请求共用，会串用户数据 |
| admin 数据获取 | 自建 `createQuery/createMutation`（约 25 行 `.svelte.ts`） | 不引 TanStack Query（Svelte 5 支持仍在演进） |
| 首屏 JS | storefront ≤120KB gz：**零第三方运行时库**，i18n 只发当前语种，主题按 chunk | 见 §9 预算表 |
| `<html lang>` | `app.html` 放占位符 `%openstore.lang%`，`hooks.server.ts` 用 `transformPageChunk` 替换 | SvelteKit 的 `app.html` 是静态的，不能按请求变；US-E3-04 硬要求 |
| 索引控制 | **每档只用一种信号**：不该收录（私有页 + 站内搜索）→ `noindex,follow`、不输出 canonical、不 Disallow；该收录 → 只看"有没有归并目标"（筛选/排序 → 无参数第 1 页；其余自引用）。**`robots.txt` 全文只有 `Disallow: /api`** | 判据见需求 §6.1 `S1~S11`（唯一载体 `verify-seo-matrix.sh`）。`buildSeo()` 用 `assertSingleSignal` 机械拦"noindex × 跨 URL canonical"，不靠人记 |
| 未译语种 | **页级无译文 = 404 + `noindex`，不做跨语种 slug 回退**；切换器仍渲染但带 `data-locale-nav="exact\|fallback-home"`，`hreflang` 只出 `exact`；集合查询由后端按 `translatedIn` 过滤 | AC-14d。回退 200 会造出"英文 URL 渲染中文正文"，并把"页级无译文"与"字段级为空"两种相反行为揉成一个 200，两个 AC 都无法同时绿 |
| 降级与错误 | 后端不可用 → **503 或 `noindex` 错误页**，绝不 200 空壳；`ssr=false` 页的 `noindex` 由 `hooks.server.ts` 写 `X-Robots-Tag` | AC-10 负向断言。CSR 页首字节是同一份 SPA 外壳，`<svelte:head>` 的 meta 在爬虫拿到的 HTML 里不存在 |

### 1.2 两端构建与部署产物差异

| 项 | storefront | admin |
|---|---|---|
| SvelteKit adapter | `@sveltejs/adapter-node` | `@sveltejs/adapter-static`（`fallback: 'index.html'`） |
| `ssr` | 默认开（CSR 页显式 `ssr = false`） | 根 `+layout.ts` 全局 `export const ssr = false` |
| `prerender` | 不开启（数据运行时才有） | `export const prerender = false`（fallback 模式，禁构建期预渲染业务页） |
| 构建命令 | `pnpm --filter storefront build` → `build/`（Node 服务） | `pnpm --filter admin build` → `build/`（纯静态） |
| 运行时 | Node 22 LTS 常驻（`node build/index.js`，`PORT=3000`） | 无；由 Caddy 直接 `file_server` |
| 部署位置 | Caddy `reverse_proxy :3000`（`/` 与 `/{locale}/*`、`/setup`、`/sitemap.xml`、`/robots.txt`） | Caddy `root /srv/admin`，`/admin/*` → `try_files {path} /admin/index.html` |
| 环境变量 | `API_ORIGIN=http://127.0.0.1:5080`、`PUBLIC_SITE_ORIGIN`（**仅向导未完成时兜底**；正式绝对 URL 来自 DB `PublicSiteUrl`） | 无（同源 `/api`） |
| 一次发布 | 两个产物各自构建、同一镜像/同一 compose 版本 | 同左 |

> 关键约束：**SSR 只能经 HTTP 调 API，不直连 DB**（架构 §1.2）。admin 从浏览器直连同源 `/api/*`，靠 Cookie 鉴权。

### 1.3 共享包"源码分发"的具体做法

目标：改 `packages/ui` 里一个 Props，两端 dev server 立刻热更新，**不需要 build、不需要发版**。

```jsonc
// packages/ui/package.json（无 scripts.build）
{
  "name": "@openstore/ui",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "svelte": "./src/index.ts",          // Svelte 专用入口
  "types": "./src/index.ts",
  "exports": {
    ".": { "types": "./src/index.ts", "svelte": "./src/index.ts", "default": "./src/index.ts" },
    "./styles.css": "./src/styles/index.css"
  }
}
```

```ts
// apps/*/vite.config.ts —— 两个必须项，否则 .svelte 会被 esbuild 预打包而报错
export default defineConfig({
  optimizeDeps: {
    exclude: ['@openstore/ui', '@openstore/i18n', '@openstore/theme-runtime', '@openstore/sdk']
  },
  ssr: { noExternal: ['@openstore/ui', '@openstore/i18n', '@openstore/theme-runtime'] }
})
```

- 消费方 `package.json` 写 `"@openstore/ui": "workspace:*"`，pnpm 用符号链接，Vite 解析到真实源文件路径 → 源码直接进编译管线，HMR 生效。
- 必须 `optimizeDeps.exclude`：Vite 的开发期预打包用 esbuild，不认 `.svelte`（会报 "Failed to parse source"），排除后由 svelte 插件接管。
- 必须 `ssr.noExternal`：默认 SSR 把 node_modules 标为 external，Node 直接 `import` 一个 `.ts` 会失败；noExternal 强制走 Vite 的 SSR 转换。
- `@openstore/sdk` 只有 `.d.ts` + 一个 `.ts` 封装，`theme-runtime` 是纯 TS（无 `.svelte`），二者同样零构建。
- CI 只跑 `tsc --noEmit` + `svelte-check`，不产出 dist。`check.sh` 里禁止出现 `packages/*/dist`。

### 1.4 路由约定总览

**storefront**（所有用户可见页面都在 `[locale]` 下；根级只放与语种无关的 4 条）

| 路由 | 说明 |
|---|---|
| `/` | 302 → `/{defaultLocale}/` |
| `/sitemap.xml`、`/robots.txt` | 由 API 动态生成，Node 层代理输出。**`robots.txt` 全文只有一条 `Disallow: /api`，不含任何前台路径**——这是正确状态，不是配置遗漏（需求 §6.1 S7）。**不得**出现 cart/checkout/account（a 类）、**不得**出现 `/*/search`（b2）、**不得**出现 `f.*`/`sort`/`page`（b1）、**不得**出现 `/admin`（c 类走 `X-Robots-Tag`）、**不得出现任何含 `?` 或 `&` 的查询串通配**（`/*?*` 会把 b1 与 b3 一起挡掉，而它们的归并依赖爬虫读到 `canonical`）。sitemap 内所有 URL **均带语言前缀**且互相 hreflang |
| `/setup`、`/setup/{1..8}` | 安装向导；SetupState=Completed 时 `error(404)` |
| `/*`（兜底，首段不是启用语种时命中） | **302 → `/{defaultLocale}/{原路径}`**。US-E3-05 明确"任何前台页面缺少语言前缀时 302 到带前缀的等价路径"。实现：`routes/[...rest]/+page.server.ts` 里 `redirect(302, ...)`，query 原样保留；`/setup`、`/sitemap.xml`、`/robots.txt` 因是更具体的静态路由而优先匹配，不受影响。**必须是 302 不是 301**（302 允许将来改前缀策略而不被浏览器永久缓存） |
| `/{已停用语种}/**` | **404，不 302**。US-E3-01 明确"停用某语言后，前台该语言路径 `/{locale}/...` 返回 404，已有内容保留不删"。不要让停用语种被兜底 302 伪装成有效路径（否则搜索引擎会把 `/ja/*` 当重复内容收录） |
| `/{locale}/` | 首页（主题区块编排） |
| `/{locale}/c/{categorySlug}` | 分类页（slug 全局唯一，故无需父级路径） |
| `/{locale}/products/{productSlug}` | 商品详情（**per-locale slug**）。本语种无译文行 → **404**（不是回退页，见 §7.4）；本语种 slug 改过 → 查 `SlugHistory` 命中 → **301** |
| `/{locale}/search?q=` | 搜索 |
| `/{locale}/pages/{slug}` | 静态页（关于/配送/退换/隐私） |
| `/{locale}/cart`、`/checkout`、`/checkout/result` | CSR 交易链路 |
| `/{locale}/orders/track` | 订单号 + 邮箱查单 |
| `/{locale}/account`、`/account/login`、`/account/register`、`/account/orders/{no}` | 账户中心 |
| `/{locale}/_preview?token=` | 主题编辑器预览（**`X-Robots-Tag: noindex, follow`**、**`Cache-Control: no-store, private`**、不进 sitemap、无 hreflang/canonical、token 30min 有效、失效 404） |

**admin**（无 locale；`/admin` 为 Caddy 挂载前缀，SvelteKit `base: '/admin'`）

| 路由 | 说明 |
|---|---|
| `/login` | 登录（未登录唯一可达） |
| `/` | 仪表盘 |
| `/products`、`/products/new`、`/products/{id}` | 列表 / 新建 / 编辑（Tab：基本信息·变体·图片·属性·SEO） |
| `/categories` | 分类树（拖拽排序） |
| `/attributes`、`/attributes/sets/{id}` | 属性定义 / 属性集 |
| `/inventory`、`/inventory/ledger` | 库存列表 + 调整 / 流水 |
| `/orders`、`/orders/{id}` | 列表 / 详情（发货、取消、退款、状态时间线） |
| `/returns` | 退货申请处理 |
| `/customers`、`/customers/{id}` | 客户 |
| `/content/themes`、`/content/themes/{id}/{brand\|home\|copy\|preview}` | 主题列表 / 编辑器 4 页签 |
| `/content/pages`、`/content/pages/{id}` | 静态页（LocalizedField + 富文本） |
| `/i18n/ui-texts`、`/i18n/content`、`/i18n/coverage` | UI 文案 / 业务内容翻译 / 覆盖率看板 |
| `/settings`（Tab：店铺·税·运费·支付·邮件·会话）、`/settings/users`、`/settings/audit` | 系统设置 / 管理员 / 审计日志 |
| `/not-initialized` | 未初始化提示 + 向导入口 |

## 2. storefront 信息架构与页面清单

> 「SSR」列：**必须 SSR** = 爬虫与 OG 抓取器必须拿到内容；**CSR** = `ssr=false`，不需要被索引。
> SEO 列：`J` = JSON-LD，`C` = canonical，`H` = hreflang 双向 + x-default，`N` = noindex。
> **`无 SEO`** = 只输出 `<title>` + `<meta name="robots" content="noindex,follow">`，**不输出 hreflang / og / twitter / JSON-LD，也不输出跨 URL 的 canonical**（PM 确认：给这 6 类页面做 SEO 是纯浪费）。注意是 `noindex,follow` 而非 `noindex,nofollow` —— 页内链接（去购物车、去逛逛）仍应被跟随（AC-11 规则 a）。另：S8 明确「`noindex` + **自指** canonical」只是告警、不计红，**不许为了过门禁去删它**（这 6 页是 CSR，服务端本来就不承载 canonical，天然不会违规）。

> 这 6 类页面的**反向约定同样要守住**：① 不做任何 SEO 输出（无 canonical / hreflang / og / JSON-LD），只有 `title` + `noindex,follow`；② 不进 sitemap；③ **`robots.txt` 里不得为这些路径写 `Disallow`**。
>
> **③ 是硬约束**：`robots.txt` 的 `Disallow` 只阻止**抓取**、不阻止**收录**。被 `Disallow` 的 URL 若有站内/外链指向，仍会以"无标题无描述裸链接"出现在结果里——而**此时爬虫读不到页面上的 `noindex`**。两者叠加互相打架，得到最差结果（既没挡住收录、又丢了"为什么不索引"的信号）。

### 索引控制：一条判断规则，不是一张结论表

> **判据唯一载体是需求 §6.1 的 `S1~S11`（`scripts/verify-seo-matrix.sh`）。本文只写"前端怎么实现"，不复制断言语义**——同一份清单曾在需求/架构/后端/前端/运维五处各存一份，改一处必漏四处，本项目已因此产生 6 条台账（W9/W12/W14/W15/W16/W20）。需要判据请回需求文件取。
>
> **总规则：每档只用一种信号，绝不叠加。三步判别，每一步都要连"为什么这一步在这里"一起读** —— 原理写清的地方不需要结论表；原理没写清，加十张表也拦不住下一个人重新推导错。
> ① **该不该被收录**？不该（**私有页 + 站内搜索**）→ `noindex,follow`，**不输出 canonical**，**不 Disallow**。
> 　　**为什么先问这一步**：这一问的答案只有"该/不该"，没有中间态。而 `Disallow` 表达的是"别来抓"，**不是"别收录"** —— 被 Disallow 的 URL 若被站内/外链指向，仍会以裸链接进结果，且此时爬虫读不到页面上的 `noindex`，两个指令互相抵消。所以"不该收录"只能用 `noindex` 表达，并且**必须允许抓取**才能让它被读到。
> ② 该收录的话，**有没有归并目标页**？有（筛选/排序 → 无参数分类页第 1 页，不论第几页）→ `canonical` 指目标；没有（分类页本页、**无筛选的**分页第 2 页起、商品详情）→ `canonical` 自引用。
> 　　**为什么第二步才问归并**：canonical 的语义是"这两个 URL 是同一内容"。**有目标才能归并**；没有目标却硬指一个，等于对搜索引擎说谎，还会污染被指的那一页。所以"无筛选的分类页第 2 页"必须自引用 —— 归并到第 1 页会让爬虫把第 2 页之后当作重复页丢弃，**第 2 页之后的商品永远无法被索引，而且不报错**（只表现为"某些商品莫名搜不到"）。
> ③ **要不要用 `robots.txt` 挡**？**不要**。全文只留 `Disallow: /api`。
> 　　**为什么第三步永远是"不要"**：走到这一步说明前两步已经处理完。此时再加 `Disallow` 只会让爬虫读不到第 ①② 步留下的信号，把已经正确的东西弄坏。`robots.txt` 在这个项目里唯一的正当用途是挡**不该被任何爬虫访问的接口**（`/api`），不是挡页面。
>
> **为什么不能让 robots 参与前台**：`Disallow` 的语义是"别来抓"，不是"别收录"，更不是"别传信号"。被 Disallow 的 URL 若被站内/外链指向，仍会以"无标题无描述裸链接"进结果——而**此时爬虫读不到页面上的 `noindex`/`canonical`**，两条指令互相抵消，得到最差结果。**"参数空间有限还是无限"根本不是判据**，它只能用来估抓取量。
> **为什么规则里没有"搜索页用 Disallow"这条**:搜索页的 URL 空间是无限的，但"无限"不是理由——它**不该被收录**，所以归第 ① 档走 `noindex,follow`。**"URL 里带问号"从来不是分类依据**：筛选页带问号却该收录，搜索页带问号却不该收录，两者唯一共同点只是那个问号。
> **`noindex` 与 `canonical` 互斥（跨 URL 时）**：`noindex` 优先生效、canonical 被忽略；多个 noindex 页同时 canonical 到同一目标，还可能反向影响那个目标的收录。所以搜索页**必须**输出"无 canonical"，不是"随便给一个"。这条由 `buildSeo()` 在代码层机械保证（见 §8.1 的 `assertSingleSignal`），不靠人记。**但闸门只拦"跨 URL"**：`noindex` + **自指** canonical 是告警不计红（S8），且不得为过门禁去删它。

> 它**不是**结论快照，所以不随真源改版而失效——"若用 Disallow 会怎样"永远是错的。表里**只写"错误做法 → 后果"，不写判据的完整表述**（任何能直接当规则抄的句子都不许出现在这张表里，那种句子只允许有一个出处：需求 §6.1）。保留它的唯一理由：本轮 4 次复发全是同一个反例没被记住，删掉反例等于让下一个人再推导一遍——而那 4 次已经证明推导会错。

> **实现落点（这张表不写答案，只指路）**：`robotsFor()` 与 `X-Robots-Tag` 注入见本节下方；canonical 计算（含 `MERGE_FILTERED_CANONICAL`）见 §2.1；`assertSingleSignal` 闸门见 §8.1；`/admin` 的响应头由 Caddy 注入，见 §11.2。

> **没有"d 类 未译语种回退页"这一档 —— 页级未译是 404，不是可索引的 200**（AC-14d②）。我一度按"回退到默认语种 slug → 200"写过 d 类与 `fallbackCanonical()`，`docs/02` §4.5 已明确该方案**作废**，理由是它会造出"英文 URL 上渲染中文正文"的页面（重复内容 + 语种错配），且与 AC-14d① 的字段级回退揉成一个 200，使 14a 与 14d② 永远无法同时绿。**区分**：页级无译文 → 404；字段级为空/空白（页面存在）→ 200 + 回退值 + `data-i18n-fallback`，**不产生第二个 URL、也不需要第二个 canonical**。

> **档位命名与架构矩阵对齐（8 行 = 六档 + b3 三态）**：`(a)` / `(b1)` / `(b1∩分页)` / `(b2)` / `(b3)` 在售 / `(b3-缺货)` / `(b3-归档)` / `(c)`。**`b3-缺货` 与 `b3-归档` 必须是两档**：归档 = 内容没了（301/410 + 移出 sitemap），缺货 = 内容在、买不了（**200 + `OutOfStock` + 留在 sitemap**）。混成一档会丢掉 S10 的后半句，而"把缺货商品从 sitemap 摘掉"恰恰是最常见的"看起来合理"的错——断货期结束后回榜要慢数周。

> **`/\*/search` vs `/*?*` 的语法差异（写 robots 时的实操陷阱）**：`Disallow: /*/search` 里 `*` 是**路径段通配**，合法；`Disallow: /*?*` 里的 `?` 是**查询串通配**，语法上允许但语义上灾难（连 b1 与 b3 一起挡）。本项目 `robots.txt` 里这两者**一个都不该出现**——全文只有 `/api`。

> **跨档禁令：挡收录不得动可达性。** 归档用 **410** 而不是"让它 404 消失"、缺货商品**必须 200**、`/admin` **必须可达 200** —— 「让页面打不开」是另一种形式的隐形失败：既没解决收录问题（404/403 的 URL 仍可被链接进结果），又把诊断信息一起丢掉。**可达性与收录是两个轴，用可达性去表达收录意图，等于把两个轴压成一个。**


> **抓取量不必担心到要改方案**：b1 的"筛选页一律归并到主分类页第 1 页"会把筛选组合的长尾收敛掉，实际被索引的只是主分类页及其分页序列。为省这点预算回到 Disallow，等于"既花了抓取预算又没买到归并"，是净亏。
> **`MERGE_FILTERED_CANONICAL` 这类开关的性质**：canonical 归并是 **AC-11 的 Must 断言**，开关只作紧急回滚。**默认必须 ON**；以 OFF 状态提测即 AC-11 不通过，不得记成"次要问题"或"待定"（需求 §6.1 自检第 5 问）。
> **订单查询页（`/{locale}/orders/track`）例外要求**：它是"邮件里的孤儿入口"，必须**未登录可直接访问**（订单号 + 邮箱校验即可），不得因为它在 SSR 应用里就被登录墙或 SEO 要求绑架（US-E7-03）。它不属于 `(auth)` 守卫范围。它是 a 类（`noindex,follow`），但**不能**为此加登录墙。

**a 类 + b2 的 noindex 实现方式（别逐语种枚举）**：用**一张模式表 + 一个函数**判定，而不是写 `/zh/cart`、`/en/cart` 的枚举——加第三种语种时会静默漏掉，而这类漏检没人会发现（页面照样 200、照样被收录）。**站内搜索必须进这张表**，因为它和私有页同属"不该被收录"这一档。

```ts
// apps/storefront/src/lib/server/robots.ts —— 唯一出口
const NOINDEX_PATTERNS = [
  /^\/(?:[a-z]{2}(?:-[A-Za-z]{2,4})?\/)?cart(?:\/|$)/,
  /^\/(?:[a-z]{2}(?:-[A-Za-z]{2,4})?\/)?checkout(?:\/|$)/,
  /^\/(?:[a-z]{2}(?:-[A-Za-z]{2,4})?\/)?account(?:\/|$)/,
  /^\/(?:[a-z]{2}(?:-[A-Za-z]{2,4})?\/)?orders\/track(?:\/|$)/,
  /^\/(?:[a-z]{2}(?:-[A-Za-z]{2,4})?\/)?search(?:\/|$)/,   // ★ 与私有页同档
  /^\/(?:[a-z]{2}(?:-[A-Za-z]{2,4})?\/)?_preview(?:\/|$)/, // ★ 预览页同档（见下）
  /^\/setup(?:\/|$)/                       // 向导无 locale 前缀
]
/** 不该被收录的页 → 'noindex,follow'；其它 → 'index,follow'
 *  绝不要把"带筛选参数"的路径放进这里：筛选页该被收录、只做 canonical 归并 */
export const robotsFor = (pathname: string) =>
  NOINDEX_PATTERNS.some(re => re.test(pathname)) ? 'noindex,follow' : 'index,follow'
```

**⚠️ `ssr=false` 的 a 类页面（购物车/结算/支付结果/账户/查单）必须用响应头，不能用 meta**：这些路由关掉了 SSR，首字节返回的是同一个 SPA 外壳 HTML —— `<svelte:head>` 里的 `noindex` **在爬虫拿到的第一份 HTML 里根本不存在**，只有执行 JS 后才有。所以：

```ts
// apps/storefront/src/hooks.server.ts —— 复用同一张模式表，避免第二份真相
import { robotsFor } from '$lib/server/robots'
export const handle = async ({ event, resolve }) => {
  const res = await resolve(event)
  const r = robotsFor(event.url.pathname)
  if (r.includes('noindex')) res.headers.set('X-Robots-Tag', r)   // 'noindex, follow'
  return res
}
```

- 与 `/admin` 用响应头是**同一个机制**（§11.2），理由也相同：对 HTML 两者效果等价，但响应头**不依赖 HTML 内容**，因此对"没有服务端渲染的页面"和"静态产物"都能覆盖。
- 别把 `noindex` 只写进 `+page.svelte` 的 `<svelte:head>` 就以为完事 —— 这是 a 类页面最容易出的"测试环境看起来对、线上收录没挡住"的缺陷：用浏览器看元素面板能看到 meta，用 `curl` 看不到。

**主题预览页 `/{locale}/_preview?token=` 归 a 类（允许抓取 + `noindex`），不写 Disallow**：token 绑 Session 且 30 分钟过期，**"URL 不可预测"不是 Disallow 的理由**（Disallow 只挡抓取、不挡收录），Disallow + `noindex` 的组合会重演"裸链接进结果"的老坑。它的三条真正约束是：

| 约束 | 值 | 为什么 |
|---|---|---|
| 缓存 | **`Cache-Control: no-store, private`**（两个都要） | **这不只是"内容会变"，是"不能进共享缓存"**：预览 URL 带 token，一旦被 CDN/反代按 URL 缓存，A 商家的草稿页会被 B 商家命中 —— **是数据泄漏，不是缓存策略问题**。单写 `no-store` 在某些中间件上仍可能被共享缓存按 URL 存，`private` 是第二道 |
| noindex 载体 | **`X-Robots-Tag: noindex, follow` 响应头**，不靠 `<svelte:head>` 的 meta | 预览页与 a 类私有页一样可能走 CSR，meta 在首份 HTML 里不存在（见上） |
| 索引侧 | **不进 sitemap**、**不输出 `hreflang`**、**不输出 canonical** | 它不是任何页面的等价页；声明 hreflang 等于把带 token 的 URL 广播给搜索引擎 |
| 失效 | token 无效 → **404**（不泄露存在性），且**不带 `Set-Cookie`** | 404 而非 401/403：后者会告诉探测者"这个页面存在" |

> 另外：**预览页不从站内任何地方链接**（只由 admin 的 iframe 打开），所以它不在"站内链接可达"的传播路径上 —— 这也是它能安心用 `noindex` 而不是更激进手段的前提。

> **必须配一条单测**：遍历 `EnabledLocales` 逐个语种拼出 a 类与 b2 的路径，断言 `robotsFor()` 全部命中 noindex。这条测试的作用是"**新增语种时自动红**"，否则加语种当天就会漏掉一批页面（devops 已把这条列为联调项）。

> 注意实现细节：`ssr = false` 只关"组件服务端渲染"，`+page.server.ts` 的 load **仍会在首请求时于服务端执行**（adapter-node 有服务端，与"adapter-static 纯 SPA 无服务端"是两种情形）。因此 `/setup` 的"完成后 404"守卫放在 `setup/+layout.server.ts` 里 `throw error(404)` 是有效的（US-E1-08 要求）。若某版本行为变化，退路是 `hooks.server.ts` 里对 `/setup*` 统一守卫 —— 本方案已把 setup 状态读进 `event.locals`，两条路都成立。

### 2.1 分类页：筛选状态编码进 URL

```
/{locale}/c/robot-parts?f.interface=usb-c,usb-a&f.price=1000-20000&f.compatibleModel=dji-s1&sort=price_asc&page=2
```

- 参数名 `f.<attributeCode>=<v1>,<v2>`；区间类 `f.price=<minMinor>-<maxMinor>`；布尔 `f.waterproof=1`。
- `sort` ∈ **`price_asc | price_desc | newest`**（数据模型只支持这三种，见 §11.3）；`page` 从 1 开始，**前端不设上限**（原写法"`page ≤ 100` 为硬上限"**已作废**）。
  - **作废理由**：分类页含**子树**（team-lead `eeeb5a9` 裁定，AC-12 基线页钉根分类），根分类 5,000 件 ÷ 24 = **209 页**。夹在 100 ⇒ 第 101~209 页上的 **2,600 件商品翻不到**，而 `total` 报 5,000、`pageCount` 报 209、详情页 200、搜索能搜到——**四个数全对，只有"能不能翻到"这一件事错**。收益侧（防爬）本来就该由 `robots.txt` + 限流承担，不该由分页上限承担。
    - ⚠️ **这四个数的载体分属不同里程碑**：`total` / `pageCount` 在 M1 的接口层，sitemap 与详情页在 M3。**M3 之前"四个数全对"是论证，不是已取得的读数**，不得当作 AC 证据引用（同一形态的教训今天出现过多次：**论证与读数长得一样，但一个是推理、一个是证据**）。
  - 这个错**只在"根分类 + 无任何筛选"这一种形态上咬**：带任何 facet 或价格区间后集合立刻变小，几乎到不了第 100 页——**而那恰好是导航树点进去的默认入口**。所以任何"随手翻两页"的用例都撞不到它，它只会在上线后被买家撞到。
- **翻页的终止条件由 `pageCount` 判，不由 `items: []` 判。** 后端契约（`03 §8.2`，`1688ddc`）：`page < 1` → `400 PAGE_OUT_OF_RANGE`；`page > pageCount` → **`200` + `items: []`**；`page === pageCount` → **非空 `items`**。也就是说 **在单一快照内，空 `items` 只有一个含义：`page > pageCount`**（限定词不能省：跨快照时它还能由"`total`/`pageCount` 与 `items` 不同源"产生，见下面第 ② 支）。前端三支：
  - ① `page >= pageCount` → 真到底（`>` 那一支是用户手改 URL 翻过头，不是错误），文案"没有更多了"，`page` 从 `pageCount` 之后不再渲染"下一页"链接；
  - ①-b `page < 1` 或非整数 → 后端 `400 PAGE_OUT_OF_RANGE`。前端**不要**把这发出去：路由层先把 `page` 规整为正整数（非法即回 `page=1` 并 `replaceState`），否则用户手改一个 `?page=0` 会看到一次错误页而不是列表首页——**参数规整属于前端，越界判定属于后端**，两者别互换；
  - ② **`items` 为空但 `page <= pageCount`**：**单看契约不可能，并发语义下可能**——`total`/`pageCount` 与 `items` 不是同一个快照读出来的（并发下架、缓存分层）时，完全可能给出 `total=5000 / pageCount=209 / page=5 / items=[]`。所以它**不是"防御性分支"**，是**真实形态 + 缺陷信号**两种成因共用一个判据：
    - 处置统一：**不得**写"没有更多了"（那等于把一次截断/不一致翻译成一句**更确定的谎言**：用户看到的是"这家店只有 2,400 个商品"，而实际有 5,000 个），文案写"当前条件下无法继续翻页"；
    - **文案之外必须给出口**：**重试**（可能下一拍就一致了）/ **回第 1 页** / **清筛选**。只写文案不给动作 = 用户卡在一个既不是空态、也不是错误页的空白上，**这比原来的假空态更糟**（假空态至少还有"清除筛选"可点）；
    - 同时上报前端监控：它是"数据不一致"的**唯一可见信号**，成因可能是别人加的夹子，也可能是同源被破坏——**两者处置相同、根因不同，所以只报计数、不猜原因**。**这条计数的预期值是 `0`**，不是"不应为 0"：`03 §5.1` 要求 `total`/`pageCount` 与 `items` **同源**（同一条 SQL 的窗口计数，或同一可重复读事务），所以这组合**按契约不可能出现**，出现即缺陷。**写成"不应为 0"会让它长期非 0 → 一定被静音 → 真夹子跟着被静音**（恒红的约束最后总是被豁免）。
    - 对偶约束（给将来"优化"的人看）：若哪天为了性能要给 `total` 加计数缓存/物化表，那**必须同时改契约与这条计数的预期值**——两件事一起做，**不许只做第一件**，因为只做第一件的效果就是把一条判据悄悄变成噪音。
  - ③ `total === 0` → 真没数据，走空态（见 §11.3 末尾"空态 vs 错误页的判别"）。
  - **`pageCount` 直接用响应给的值，不要自己 `Math.ceil(total / pageSize)` 再算一遍**——两处算同一个数，第二处必然过期（`pageSize` 一旦可配，第二处就悄悄错）。
- **列表页要显示服务端 `total`**（"共 5,000 件"），不要只显示"已加载 N 件"。这不是装饰：它是上面那条截断的**对冲**——数字说 5,000 而翻到第 100 页就没了，人一眼能看出矛盾；只显示"已加载 2,400 件"时，截断长得和"这家店就这么大"一模一样。
- 三项全部由 SSR 读取并传给 API；**页面内所有筛选控件的交互 = 改 URL（`goto(..., { replaceState: false })`）**，从而"可分享、可回退、刷新保持"（US-E5-01）自动成立。
- **筛选页 canonical（team-lead 三选一后裁定为"第三条路"）**：**带筛选/排序参数 → 一律归并到「无参数分类页的第 1 页」，不论第几页**；**不带参数 → 自引用**（含第 2 页及以后）。`sort` 与 `f.*` 同属"筛选/排序参数"。

```ts
// apps/storefront/src/lib/server/seo.ts
const TAG = /^(utm_|fbclid$|gclid$|msclkid$)/   // 追踪参数：永远不算"内容差异"，任何模式下都剔除

/** 归并开关：on = 筛选页归并到主分类页（AC-11 要求）；off 仅作紧急回滚，**off 状态过不了 AC-11** */
export const MERGE_FILTERED_CANONICAL = true

const selfUrl = (url: URL, base: string) => {
  const q = new URLSearchParams(url.searchParams)
  for (const k of [...q.keys()]) if (TAG.test(k)) q.delete(k)
  return `${base}${url.pathname}${q.size ? `?${q}` : ''}`
}

/** 分类页 canonical —— 只有两个分支，禁止任何 `page × filtered` 的组合判断 */
export function categoryCanonical(url: URL, base: string) {
  const filtered = [...url.searchParams.keys()].some(k => k.startsWith('f.') || k === 'sort')
  if (filtered && MERGE_FILTERED_CANONICAL) return `${base}${url.pathname}`   // ← 主分类页第 1 页
  return selfUrl(url, base)                                                   // ← 含 page≥2 自引用
}

/** 商品详情：恒自引用，只剔追踪参数，永不做参数归并 */
export const productCanonical = (url: URL, base: string) => selfUrl(url, base)
```

- **不要为"未译语种"写任何 canonical 分支**：页级未译是 404（不渲染页面，`+error.svelte` 输出 `noindex`），"回退页"这个概念不存在。写了就会有人以为"未译也能访问"，然后 AC-14d② 红。字段级回退发生在**同一个页面内部**，canonical 自引用，不产生第二个 URL。

**★ 调用顺序是硬约束：先判存在性 / 译文，再算 canonical。反过来会静默产生 200。**

```ts
// ❌ 错：先剔参再判存在性 —— 带 utm 的请求会被"救活"成 200
const clean = selfUrl(url, base)            // utm 被剔掉，看起来像个正常的基础 URL
if (await hasTranslation(clean)) render()    // ← 于是本该 404 的未译语种页返回了 200

// ✅ 对：存在性与译文判定在最前；404 之后连 canonical 都不进入
if (!await hasTranslation(locale, slug)) throw error(404)        // 页级无译文 → 404（AC-14d②）
if (product.archived) return redirect(301) /* 或 error(410) */   // S9 三响应
const canonical = selfUrl(url, base)                            // 到这里才谈 canonical
```

> **为什么这条要单独立一条**：`utm_*` 剔除是**为了 canonical 正确**，存在性判定是**为了状态码正确**，两件事共用"处理 URL"这一个动作，所以极容易被写成一条链。写错之后的现象极具误导性——未译语种页返回 200 且页面全是中文（没有译文就回退渲染默认语种内容），于是 `14d②` 报"该 404 却 200"、`14a` 报"出现中文"，**两条一起红**。看现象会去查 i18n 数据，实际是两次判断的先后顺序问题。
>
> 配套断言在 §11.1 的 `F3` 那条（`/en/products/fx-tote?utm_source=wx` 必须 404）：它是**唯一能抓到这个顺序错误**的形态——裸路径无论顺序对错都是 404，测不出任何东西。

**canonical 的适用条件只有一条：`响应 200` 且 `是最终页`。**

| 情形 | 是最终页？ | 输出 canonical？ |
|---|---|---|
| 301（含归档跳转、slug 变更、缺前缀 302 之外的跳转） | 否 | **不输出**（没有正文可谈） |
| 410（归档且无替代） | 否 | **不输出** |
| 404（未译语种 / 未知 slug） | 否 | **不输出** |
| 200 缺货商品（S10） | 是 | **必须自引用**（缺货不是下架，页面是同一个页面） |
| 200 筛选页（S3） | 是 | 按 `categoryCanonical()` 归并 |
| 200 详情 / 静态页 | 是 | 自引用 |

> **为什么写成一个条件而不是三处"是否输出"**：用一个条件解释全部情形，比在三个地方各写一遍不容易漂——**因为下一次加第四种状态时，人会去改这个条件，而不是去改三处**。
> 语义上的理由：`canonical` 的声明是"我是某页的正式地址"。301 没有正文；410/404 是错误页，声明"我是正式地址"在语义上是假的，而且会和状态码互相打架（状态码说"没了"、canonical 说"我在这儿"，搜索引擎的处置不可预测）。
> 注意别把这条读成"错误页什么都不用做"：错误页仍然要 `noindex`（页面 `+error.svelte` 给 meta，CSR 页走 §2 的 `X-Robots-Tag`），**但 `noindex` 解决的是"别收录"，不是"可达性"**——410/404 本来就是可达的，两件事。

**JSON-LD 内部的 URL 也必须绝对、也必须来自 `PublicSiteUrl`（这条最容易漏）**

`Seo{title, description, canonical, hreflang, jsonLd}` 里，`canonical` / `og:url` / `hreflang` 三处我们都强调了绝对，但 **`jsonLd` 对象内部**同样是 URL 出口，一个都不能写相对路径：`@id`、`url`、`image`、`offers.url`、`breadcrumb.item[].item`。

这不是洁癖：`@id` 写成相对路径时，爬虫会按**它自己解析出的 base** 展开。站点一旦有多域名或反代，展开结果就与 `canonical` 不一致 → **"结构化数据声明的 URL ≠ canonical"**，这是 Search Console 里"网页无法编入索引"最常见的成因之一，而且**它不报错，只是不收录**。

**三个 URL 型响应头，明确不用**

- **`Link: <...>; rel="next"` / `rel="prev"`**：一旦与 HTML 的 `<link rel="next">` 并存，就是**又一份要漂移的清单**（本仓库"同一份清单抄三处"已经复发过好几轮）。分页只保留 HTML 里的 `<a href>` 可点链接。
- **`Refresh: 0; url=...`**：302 的劣化版——不可缓存、不进历史、**无法用状态码断言**。留它等于留一条"看不见的重定向"，而 AC-11 的全部价值就在于重定向必须是**可断言的 3xx**。
- **`Content-Location`**：只在"同一内容有多个地址"时才有意义，而这里地址唯一性已由 `SlugHistory` + `PublicSiteUrl` 保证，用了反而制造第二套地址声明。

> **"明确不用"也要写成决定，否则它不是决定，只是没人提过。** 这三条不加限制不会有问题，但没人写下来，下一个人就会加一个，然后没人管口径。

**为什么是这条路，以及为什么不能按页数分叉（这段比代码重要）**

| 方案 | 问题 |
|---|---|
| A：筛选第 2 页自引用（保留 `f.*`） | 第 1 页归并到主分类页、第 2 页却自引用 → **父子指向不同族**，给搜索引擎一组互相矛盾的信号，最坏是两个都不认 |
| B：筛选第 2 页归并到 `?page=2` | `?f=usb-c&page=2` 是"USB-C 结果的第 25–48 个"，`?page=2` 是"全部商品的第 25–48 个" —— **内容不同**。canonical 的语义是"这两个 URL 是同一内容"，这样归并等于对搜索引擎说谎，污染后者 |
| **C（采纳）：带筛选一律归并到主分类页第 1 页** | 前提是"**筛选结果是主集合的子集**" → 筛选页里每个商品必然也出现在无参分类页的某个分页里，**归并不会让任何商品失去被收录的机会**，只是改由主序列收录。代价是筛选页各页都不单独进索引，这个代价该付（指数级重复内容会稀释主分类页权重） |

- **任何 `page` 与 `filtered` 的组合判断都会长出第三种读法**——A/B 之争就是这么来的。所以函数里只允许"有没有筛选"这一个条件。
- 开关只作灰度/回滚：**发布验收必须以 `MERGE_FILTERED_CANONICAL = true` 过 AC-11**；默认关闭等于 AC-11 不通过，不得记成"次要问题"或"待定"（AC-11 判据要求，见 01 §6.1 S3）。

- **分页第 2 页起自引用是最容易漏、也最难发现的一条**：若归并到第 1 页，爬虫会把第 2 页之后当作重复页丢弃，**第 2 页之后的商品将永远无法被索引**。它不报错、不影响用户体验，只表现为"某些商品莫名其妙搜不到"，因此必须有显式断言（§11.1）。
- **不要在这里返回 robots 值**：筛选页的抓取必须放行（否则 `canonical` 读不到，归并失效）。`robots.txt` 全文只有 `Disallow: /api`，见 §2 的索引控制规则。

**变体选择器状态机（这是详情页唯一的复杂点）**：
1. 待选维度顺序 = 商品 `variantAxes` 声明顺序；未选完时价格显示商品级默认价 + 状态"请选择颜色/尺寸"。
2. 每个选项的可用性 = 在"其他已选维度固定"的前提下，是否存在启用且有货的变体；不存在 → 置灰不可点（`disabled` + `aria-disabled`），点击无效且不改变已选。
3. 已选轴变化时，**主动清空"因新选择而不可用"的其他轴已选值**（否则会出现矛盾组合）；清空后给出 `aria-live` 提示。
4. 选完 → 价格、库存、主图、SKU、加购按钮全部切换为该变体值。判定**只用后端给的两个字段**：`stockStatus === 'out_of_stock'` → 按钮变"已售罄"且禁用；数量步进上限 = **`maxOrderQuantity`**（后端给什么用什么，**不要自己算、也不要写死任何常量**）。它的定义是 **`min(99, available)`**（A1 终裁）：`99` 是"防一次加 1000 件"的绝对护栏，**`available` 是服务端真值、不是 `availableQuantity`**——后者在 >5 时是 `null`，而 **`Math.min(99, null)` 在 JS 里得 `0`（`null` 被当 0，不抛错）**，所以写成 `min(99, availableQuantity)` 的结果不是"上限变小"，是**上限变 0**：步进器永久禁用、页面上看起来正是"这商品卖完了"，日志里一句都没有。**一个静默的实现错误伪装成了正常的业务状态**——没人会去查一个"卖完了"的商品为什么卖完了。所以它**确实受库存约束**，只是**约束的形态由后端给成一个大整数**——前端照样不需要推算，但**别再写"与库存无关"**（那是作废口径）。"仅剩 N 件"**仅在 `availableQuantity !== null` 时**渲染（后端只在 ≤5 时给值，>5 一律 `null` —— 真实库存是可被爬取的竞争情报）。
5. `stockStatus === 'out_of_stock'` 或全部变体 `purchasable=false` → 整页仍可访问（SSR 出内容 + JSON-LD `availability: OutOfStock`），**不能 404**（S10：在售但库存 0 必须 200 + `OutOfStock`，且 URL **仍在 sitemap 里**）。
6. **下架分三种响应，不能一律 410**（S9）：`Archived` 且**有替代分类页** → **301** 到该分类页；`Archived` 且**无替代分类页** → **410 Gone**（不是 404，让搜索引擎快速剔除）；未知 slug → **404**。
   **"替代分类页"的判定不归前端**（需求 AC-11 (b3) 已定义死）：= 该商品归档前所属分类中，**当前为 `Active` 且该语种存在译文**的那个分类；多个取**分类树中最深**的一个；一个都不满足 → 视为"无替代"。三条设计意图：① 完全由既有数据推出，**不新增商家侧字段或开关**（不能为解一个问题造一个"只能靠记得改回来"的配置项）；② 取最深而非第一个 —— 父类更宽泛，指向父类会让用户落到几乎不相关的列表页；③ "该语种有译文"是必要条件 —— 否则 301 会指到一个 404 或一个渲染中文的英文页，**那正是被否掉的"回退 slug 链"的变体**。
   前端只消费一个字段：`{ archived: true, redirectTo: string | null }` → **有则 301、无则 410**。**前端绝不自己算"哪个分类还在"**：分类状态判断一旦漏进渲染层，前后端就会各有一套分叉逻辑，早晚不一致。
7. 加购成功后不跳页：`aria-live` 提示 + 购物车角标数字变化 + "去结算"次要按钮出现。
8. **买超由服务端夹取，前端必须以返回值回写并告知**：步进器允许用户按到上限之上（前端不硬拦），提交后后端按可用量夹取并在响应里回传 **`clampedTo`**。前端收到 `clampedTo` 必须做两件事：① 把购物车里该行的数量**改成 `clampedTo`**（不是保留用户输入、也不是静默丢弃）；② 用 `aria-live` 明说"已调整为 N 件"。**静默夹取是最差的一种**——用户以为买到了 10 件，结算页显示 3 件，他会怀疑是不是哪里错了，而这条路径没有任何报错可以查。

> **退款状态对外/对内投影必须分开（已定稿，我上一轮写错过一次）**
> `Refund.Status = AwaitingManual` 是**退款单内部状态**；**订单状态机不新增分支**（订单保持 `退款中`）。**对外投影 `RefundStatus = Processing`**，消费者侧（订单详情、查单页、通知邮件）**统一只显示"退款处理中"**，不暴露"线下/人工"实现细节，更不显示凭证号。
> 理由：消费者看到"线下退款"会困惑——"我刷的卡为什么要线下退？钱打给谁？"；凭证号是内部对账信息，对消费者无意义还暴露内部流程。对消费者只需一件事：**钱在路上**。线下标记 + 凭证号 + 操作人 + 日期**只在 admin 展示**。
> 对前端的后果：**订单状态枚举可以定死**，不必预留"容纳新状态"的扩展结构——新状态在退款单上，不在订单上。这也是"同一事实只能有一个出口"的又一个例子（对外投影与内部状态分开，而不是把内部状态透出去）。

### 4.2 注册表与加载（SSR 下可 await、按主题拆 chunk）

```ts
// apps/storefront/src/lib/themes/registry.ts
import type { ThemeDefinition } from '@openstore/theme-runtime'

// 相对 registry.ts 目录（src/lib/themes）向上 5 级才是 frontend/，再进 themes/
const mods = import.meta.glob<{ default: ThemeDefinition }>('../../../../../themes/*/index.ts')

export const availableThemes = Object.keys(mods).map(p => p.split('/').at(-2)!)

export async function loadTheme(id: string): Promise<ThemeDefinition> {
  const key = Object.keys(mods).find(p => p.split('/').at(-2) === id)
  const load = key ? mods[key] : mods[Object.keys(mods).find(p => p.endsWith('/base/index.ts'))!]
  return (await load()).default          // 缺主题 → 回退 base，永不让整站挂掉
}
```

要点：
- `import.meta.glob` 在**构建期**展开成显式映射：每个主题一个独立 chunk，可静态分析，Node/浏览器同一条路径，SSR 里直接 `await`。
- 路径层级是 **5 个 `../`**（`src/lib/themes` → `src/lib` → `src` → `storefront` → `apps` → `frontend`），架构文档写的 4 个是 off-by-one（见 §12 偏差 D-3）。
- 禁止 `import(\`../themes/${id}/index.ts\`)`：Vite 无法静态分析，生产构建会把全部主题打进主 chunk 且给"运行时任意路径"开口子。
- 同一请求内 `loadTheme` 结果用 `event.locals` 缓存，避免一次渲染里重复 `await`（虽然模块已被模块图缓存，但显式更好读）。
- **admin 不做任何 glob**：主题列表与 token schema 由后端 `IThemeCatalog` 读 `themes/*` 目录后经 `/api/admin/themes` 返回，admin 永不打包主题组件（这也是它能 `ssr=false` 且体积小的原因）。

### 4.3 token 三层合并与注入

```ts
// packages/theme-runtime/src/tokens.ts
export type TokenMap = Record<string, string | number>

export const resolveTokens = (theme: TokenMap, preset: TokenMap = {}, override: TokenMap = {}): TokenMap =>
  ({ ...theme, ...preset, ...override })        // 扁平点分键，后者胜

export const tokensToCss = (t: TokenMap): string =>
  ':root{' + Object.entries(t)
    .map(([k, v]) => `--${k.replaceAll('.', '-')}:${v};`)
    .join('') + '}'

export function schemaDefaults(schema: { properties: Record<string, { default?: unknown }> }): TokenMap {
  return Object.fromEntries(Object.entries(schema.properties)
    .filter(([, p]) => p.default !== undefined)
    .map(([k, p]) => [k, p.default as string | number]))
}
```

注入链路（**唯一路径**）：

```
加载顺序（SSR）：① loadTheme(id).defaultTokens
               ② 行业模板预设（SetupState 里记录的 themeTokens）
               ③ DB 的 ThemeInstance.TokenOverrides
               ④ resolveTokens() → tokensToCss() → 字符串
注入位置：      [locale]/+layout.server.ts 返回 cssText → +layout.svelte
               <svelte:head><style>{cssText}</style></svelte:head>
```

```svelte
<!-- apps/storefront/src/routes/[locale]/+layout.svelte（片段） -->
<script lang="ts">
  let { data, children } = $props()
  const Layout = $derived(data.theme.layouts[data.layoutKey] ?? data.theme.layouts.default)
  const ctx = $derived({ locale: data.locale, tokens: data.tokens, content: data.blocks,
                         t: data.t, url: data.url, site: data.site, nav: data.nav })
</script>

<svelte:head>
  {@html ''}<style>{data.tokensCss}</style>
  <Seo seo={data.seo} />
</svelte:head>

<Layout {ctx}>{@render children()}</Layout>
```

**避免 FOUC 的四条硬规则**
1. token **必须**走 `<svelte:head><style>` 内联，**不得**用 `<link rel="stylesheet" href="/tokens.css">`（多一次 RTT，首屏必然先渲染无样式内容，LCP/CLS 双输）。
2. `<svelte:head>` 在 SSR 阶段被输出到 `<head>`，浏览器解析到 `<body>` 前已拿到变量 → 编辑色值不产生闪烁。
3. 禁止在 token 里放 `@import`、禁止 token 值依赖媒体查询（否则变量在 `:root` 与媒体块里双份定义，来源难追）。响应式差异用**布局类 token + `clamp()`**表达。
4. `tokensCss` 必须由服务端算出并随 HTML 下发；客户端不得再算一次（否则水合前后色值可能不同 → 闪烁）。CSR 页面（购物车等）通过 `page.data.tokensCss` 复用同一份，不重复请求。

**对比度检查的前端实现要点**（admin 侧，`theme-runtime/src/a11y.ts`）

```ts
const lum = (hex: string) => {
  const n = hex.length === 4 ? hex.replace(/^#(.)(.)(.)$/, '#$1$1$2$2$3$3') : hex
  const [r, g, b] = [1, 3, 5].map(i => parseInt(n.slice(i, i + 2), 16) / 255)
    .map(c => (c <= 0.03928 ? c / 12.92 : ((c + 0.055) / 1.055) ** 2.4))
  return 0.2126 * r + 0.7152 * g + 0.0722 * b
}
export const contrast = (a: string, b: string) => {
  const [x, y] = [lum(a), lum(b)].sort((m, n) => n - m)
  return (x + 0.05) / (y + 0.05)
}
```

- 组合来自 schema 的 `x-a11y` 数组 → 新增可编辑项时对比度检查自动覆盖，不用改编辑器代码（数据驱动）。
- 结果**只警告不阻断保存**（US-E4-03 明确"警告但不阻止"），告警贴在对应控件下方 + 页签角标。
- 非法 hex 由 `pattern` 在输入层拦（取色器与 hex 输入框双向同步，非法值不写回 draft）。

### 4.4 布局与区块

**`ThemeDefinition.layouts` 的 8 个 key**

| layout key | 负责页面 | 与页面组件的分工 |
|---|---|---|
| `default` | 首页、静态页、404 | 页头/页脚/容器宽度；首页额外渲染区块编排 |
| `product` | 商品详情 | 双列大图布局；图集与变体选择器位置由主题决定 |
| `category` | 分类页 | 左侧 facet 栏 + 右侧网格（minimal 主题用顶部横向 facet） |
| `search` | 搜索页 | 同 category，但强调搜索框与关键词 |
| `cart` | 购物车 | 单列窄容器 + 摘要侧栏 |
| `checkout` | 结算/支付结果 | 极简（隐藏导航与营销，减少跳出 —— 转化最佳实践） |
| `account` | 账户中心 | 侧边账户导航 + 内容区 |
| `static` | 静态页（关于/条款） | 单列阅读宽度（≤72ch） |

**缺 layout 的回退**：`ctx.theme.layouts[layoutKey] ?? baseTheme.layouts[layoutKey] ?? baseTheme.layouts.default`。storefront 的 `lib/server/theme.ts` 在 load 阶段就把回退**算完**再交给组件（`data.layoutKey` + `data.resolvedLayout`），避免运行时二次 import base。这条让"只改配色的主题"可以只实现 `default` 一个文件（架构 §5.1.2 的向前兼容承诺）。

**`ThemeContext` 完整字段**（在架构 4 字段基础上补齐真实渲染所需，全部只读）

```ts
// packages/theme-runtime/src/types.ts
export interface ThemeContext {
  locale: string                       // 'zh' | 'en'
  bcp47: string                        // 'zh-Hans' | 'en'  给 Intl 与 html lang

  url: (path: string, locale?: string) => string   // 自动带 locale 前缀
  site: SiteInfo                       // 店名/logo/客服邮箱/货币/含税标记/社交链接
  nav: NavNode[]                       // 分类导航树（已本地化）
```

**区块渲染器 + `BlockConfig`**

```ts
export interface BlockConfig {
  blockKey: string                 // 必须 ∈ manifest.blockKeys
  visible: boolean
  order: number                    // 服务端按 order 升序排好再下发
  props: Record<string, unknown>   // 按该区块 propsSchema 校验
}
```

```svelte
<!-- packages/theme-runtime/src/BlockRenderer.svelte -->
<script lang="ts">
  let { blocks, registry, ctx } = $props()
  // 1) 只处理启用的；2) 未知 blockKey 直接跳过（主题降级场景）
  const renderable = $derived(
    [...blocks].filter(b => b.visible).sort((a, b) => a.order - b.order)
      .filter(b => registry[b.blockKey])
  )
</script>

{#each renderable as b (b.blockKey)}
  {@const Block = registry[b.blockKey].component}
  <Block {...b.props} {ctx} />
{/each}
```

- **显隐必须是"不渲染"而不是 CSS 隐藏**（AC-13 硬判据：关闭区块后前台 HTML 中不得出现该区块任何内容）。因此 `visible=false` 的区块在过滤阶段就被剔除，DOM 里连包裹节点都不存在；`hidden`/`display:none`/`aria-hidden` 全都不允许用来实现这个功能。
- 顺序 = 数组顺序（服务端已按 `order` 排好），模板里不再排序 → 输出 HTML 与配置严格一致。
- 未知 `blockKey`（商家配置里有、当前主题没声明）：跳过 + `console.warn`（dev），**不渲染占位块**、不报错。
- 全部区块被关闭：渲染主题的最小组件（`default` layout 的页头 + 空内容 + 页脚），编辑器侧同时给"当前无任何区块，首页会很空"的提示（架构 §7 风险 9）。

### 4.5 可视化编辑器

#### 4.5.1 schema → 表单（token 类型 → 控件映射）

| schema 特征 | 控件 | 说明 |
|---|---|---|
| `type: string` + `x-control: color` + `pattern: ^#hex` | `ColorField`（取色器 + hex 输入 + 最近用色） | 非法 hex 不写回 draft；支持 alpha 关闭（本期不做透明色） |
| `type: string` + `x-control: font` + `enum` | `FontPicker`（系统字体族下拉 + 自定义 woff2 上传） | 上传 ≤40KB、仅 woff2，上传后 `@font-face` 由 runtime 拼接 |
| `type: string` + `x-control: image` + `format: media-ref` | `ImageUploader`（拖放 + 裁切比例提示 + 移除） | 存 media ref 不存绝对 URL（换域名不失效） |
| `type: string` + `x-control: length` + `pattern` | `LengthField`（数字 + 单位下拉 px/rem） | 单位与数值分离校验 |
| `type: number` + `x-control: range` + `minimum`/`maximum`/`multipleOf` | `Slider` + `NumberInput` 双向绑定 | 步进取 `multipleOf` |
| `type: boolean` | `Switch` | — |
| `type: string` + `enum`（无 x-control） | `Select` | 选项 label 从 `x-enumLabels` 取（可译） |
| `type: array` + `items: enum` | `ChipsMultiSelect` | — |
| 无以上特征 → `x-control: text` | `Input` | 兜底，永不出现"无控件可渲染" |
| `x-group` | `<fieldset>` + `<legend>` | 分组标题从 `x-groupLabels`（可译） |
| `if/then`、`oneOf` | **不支持** | 编辑器只支持平面属性集；需要条件表单就说明该配置建模错了 |

**结论：表单完全由 schema 渲染，admin 不写死任何字段。** 主题新增一个 token = 改 `tokens.json`，admin 零改动（架构 §5.1.4 的核心诉求）。未知 `x-control` → 降级为 text 输入并 dev 警告，保证向后兼容。

#### 4.5.2 实时预览：同页 iframe vs 内联预览 → **结论：同页 iframe**

| 判据 | 同页 iframe | 内联预览（admin 内渲染主题组件） |
|---|---|---|
| 能否复用真实渲染逻辑 | ✅ 直接打 storefront 真实路由 | ❌ admin 不打包主题组件（否则 admin 变大 3 倍且引入 SSR 假设），只能抄一份渲染 → **第二套渲染，必漏** |
| 样式隔离 | ✅ 天然隔离；主题 CSS 变量不污染后台 UI | ❌ 主题 `:root` 变量会覆盖后台样式，需 Shadow DOM/CSS 作用域黑魔法 |
| 切页面（首页/分类/商品） | ✅ 换 src | ❌ 要在 admin 里重建整个路由树 |
| 保真度（字体/图片/宽度） | ✅ 移动端/桌面宽度可切 | ❌ 窗口宽度 ≠ 设备宽度断点 |
| 实施成本 | 低（草稿接口 + token） | 高 |
| 已知代价 | 需一次草稿保存往返（debounce 300–400ms） | — |

实现：
1. 点"预览"或在编辑页打开 `PreviewFrame` → `POST /api/admin/themes/{id}/draft-preview` 写入草稿（存临时表/内存，TTL 30min，**绑定当前管理员 session**——满足 US-E4-07"仅对当前管理员可见"）。
2. 返回 `token`，iframe `src = /{locale}/_preview?token=<token>&path=/`。
3. 任一 token 变更 → debounce 400ms → `PUT` 草稿 → `postMessage({type:'refresh'})` → iframe 内部 `invalidateAll()`。
4. `_preview` 路由：**`X-Robots-Tag: noindex, follow`**（响应头，不靠 meta）、**`Cache-Control: no-store, private`**（`private` 不可省：带 token 的 URL 一旦进共享缓存，A 商家的草稿会被 B 命中——这是数据泄漏）、不进 sitemap、**不输出 hreflang/canonical**、不带 `Set-Cookie`；token 失效 → 404（不泄露存在性）。
5. 保存正式生效后，前台 ≤5s 生效（AC-13）靠的是**每次请求都从 API 读 ThemeInstance**，不缓存 token 到进程（或用版本号键缓存，写操作 bump）。

#### 4.5.3 未保存保护与重置粒度

| 场景 | 行为 |
|---|---|
| 页内切换页签（品牌 ↔ 首页 ↔ 文案） | 不提示（draft 在页面级共享，切页签不丢） |
| 路由离开 / 关闭标签页 | `beforeNavigate` + `beforeunload` 弹确认；顶部 `UnsavedBar` 常驻显示"有 N 项未保存" |
| 单项重置（每个控件右侧 ↺） | 二次确认 → **调后端"删除单个 override 键"接口**，不触碰其他项 |
| 页签重置 | 二次确认（写清影响项数）→ **调后端"按前缀批量删除"接口**（如 `color.*`） |
| ⚠️ 禁止 | **不要在前端删 map 里的键再整体 PUT 提交** —— 那会绕过"哪些键被改过"的状态判断（前端不知道 preset 里有没有同名键，删掉 override 后应该回落到 preset 还是主题默认），也容易在并发编辑两个页签时互相覆盖。重置语义必须由后端按"删 override 行"实现（数据模型：`ThemeTokenOverride` 行表） |
| 重置后 | 立即刷新预览；**只清 token/区块/文案覆盖值，绝不动商品/订单数据**（US-E4-05） |
| 主题升级后 | draft 按"键是否仍存在于 schema"修剪：已删除的键丢弃、新增键取默认值展示（不写 override）→ 满足"升级后原有修改保留" |

#### 4.5.4 区块拖拽排序：原生 HTML5 DnD（结论）

| 方案 | 体积 | 移动端 | 键盘可达 | 结论 |
|---|---|---|---|---|
| 原生 HTML5 DnD（`dragstart/dragover/drop`） | 0 | ❌ 不支持触屏 | ❌ | **采纳**，但必须配"上移/下移"按钮 |
| sortablejs | ~43KB gz | ✅ | 部分 | 否决：占 storefront 预算 36%，且 admin 也只有一个 6 行的列表 |
| svelte-dnd-action | ~15KB gz | ✅ | 部分 | 否决：为 6 行列表引依赖，YAGNI |
| 上/下箭头按钮 | 0 | ✅ | ✅ | **必做**（a11y 与触屏的真正兜底） |

实现：`onReorder(from, to)` 单一函数，DnD 与按钮共用；拖拽时显示插入位标线；drop 后立即写 draft（不落库）。**决策门槛写清**：区块数 > 20 或需要跨容器拖拽时才引库。

### 4.6 主题失败兜底（三层，缺一层就兜不住）

| 层 | 场景 | 手段 |
|---|---|---|
| ① 构建期（真正的防线） | 主题组件在 SSR 下访问 `window`/`document`、渲染即抛错 | `check.sh` 用 Node 环境把 8 个 layout × 每个区块用 fixture ctx 各渲染一次（无 DOM），抛错即 CI 红；ESLint `no-restricted-globals: [window, document, localStorage]` 仅对 `themes/**` 生效 |
| ② SSR 运行时 | 已上线的主题在特定数据下渲染崩（历史版本遗漏） | `lib/server/theme.ts` 维护进程内熔断计数：`hooks.server.ts` 的 `handleError` 记 `failures[themeId]`；5 分钟内 ≥3 次 → 该次请求直接改用 base 布局渲染，并在日志打 `theme_fallback` 事件（含 themeId/版本/栈） |
| ③ 客户端运行时 | 水合后某区块交互抛错 | Svelte 5 `<svelte:boundary>` 包住区块渲染，`failed` 片段渲染空（区块消失而不是白屏） |

```svelte
<!-- packages/theme-runtime/src/SafeBlock.svelte -->
<script lang="ts">
  let { name, children } = $props()
</script>

<svelte:boundary onerror={(e) => console.error('[theme-block]', name, e)}>
  {@render children()}
  {#snippet failed(error, reset)}
    <!-- 区块抛错 = 该区块不出现，其余区块与页面继续正常 -->
    <span hidden aria-hidden="true"></span>
  {/snippet}
</svelte:boundary>
```

> **诚实说明一个 SvelteKit 限制**：`<svelte:boundary>` **兜不住 SSR 渲染期抛错**（服务端没有 boundary 机制），所以 SSR 侧只能靠 ① 构建期冒烟 + ② 熔断降级，不能指望组件级 try/catch。这也是"主题必须过 PR review + SSR 冒烟进 CI"不可协商的原因（架构 §5.1.6）。

## 5. 状态管理与数据获取

### 5.1 storefront：`+page.server.ts` load 模式

职责分层（严格单向）：

| 层 | 文件 | 负责 | 不负责 |
|---|---|---|---|
| 站点级 | `[locale]/+layout.server.ts` | locale 校验、主题定义、三层 token 合并、`t()` 构造、站点设置、导航树、购物车摘要、CSRF token | 任何页面业务数据 |
| 页面级 | `{route}/+page.server.ts` | 该页业务数据 + `seo` 对象 + 缓存头 | 主题/翻译装配 |
| 纯函数 | `lib/server/seo.ts` | title/description/canonical/hreflang/og/JSON-LD 组装 | IO |

```ts
// apps/storefront/src/lib/server/api.ts —— 文件在 lib/server/ 下，只会进 SSR bundle
import { API_ORIGIN } from '$env/static/private'   // http://127.0.0.1:5080（仅服务端可读）
import { error } from '@sveltejs/kit'

export class Degraded extends Error {}             // 触发渲染"降级页"而非白屏

export async function get<T>(path: string, init: { fetch: typeof fetch; cookie?: string }): Promise<T> {
  let res: Response
  try {
    res = await init.fetch(`${API_ORIGIN}${path}`, {
      signal: AbortSignal.timeout(2000),
      headers: { accept: 'application/json', ...(init.cookie ? { cookie: init.cookie } : {}) }
    })
  } catch { throw new Degraded(path) }             // 超时/网络错 → 降级
  if (res.status === 404 || res.status === 410) throw error(res.status, 'not_found')
  if (!res.ok) throw new Degraded(path)
  return res.json() as Promise<T>
}
// 浏览器侧另有一个 app/api/client.ts，base 固定 '/api'（同源，自带 Cookie）；
// 禁止把 $env/static/private 写进任何会被打进 client bundle 的文件 —— 构建会直接报错。
```

- **2s 超时 → 降级页**（架构 §5.4.2 要求）：`+error.svelte` 对 503 渲染"店铺暂时不可用，请稍后重试"+ `Retry-After: 30`，**不返回白屏、不返回 200**。AC-12 的 TTFB ≤500ms 靠 API 侧索引与缓存，2s 只是防雪崩兜底。
- 缓存头：首页/分类/商品 `setHeaders({ 'cache-control': 'public, max-age=0, s-maxage=60, stale-while-revalidate=600' })`；购物车/结算/账户 `private, no-store`。
- `$env/static/public` 里的 `PUBLIC_API_BASE` 固定为 `/api`（同源），避免跨域与 Cookie 问题。

### 5.2 admin：自建 `createQuery / createMutation`

```ts
// apps/admin/src/lib/query.svelte.ts
import type { Problem } from '@openstore/sdk'
type Fetcher<T> = (signal: AbortSignal) => Promise<T>

export function createQuery<T>(fn: Fetcher<T>, opts: { immediate?: boolean } = {}) {
  let data = $state<T | null>(null), problem = $state<Problem | null>(null), loading = $state(false)
  let ctrl: AbortController | null = null, seq = 0
  async function run() {
    ctrl?.abort(); ctrl = new AbortController()
    const mine = ++seq; loading = true; problem = null
    try { const r = await fn(ctrl.signal); if (mine === seq) data = r }
    catch (e: any) { if (e?.name !== 'AbortError' && mine === seq) problem = e as Problem }
    finally { if (mine === seq) loading = false }
  }
  if (opts.immediate !== false) queueMicrotask(run)     // 在组件 init 期创建，微任务里起跑
  return { get data() { return data }, get problem() { return problem }, get loading() { return loading },
           refetch: run, cancel: () => ctrl?.abort() }
}

export function createMutation<I, O>(fn: (input: I, s: AbortSignal) => Promise<O>) {
  let loading = $state(false), problem = $state<Problem | null>(null)
  async function mutate(input: I) {
    loading = true; problem = null
    try { return await fn(input, new AbortController().signal) }
    catch (e: any) { problem = e as Problem; throw e }
    finally { loading = false }
  }
  return { get loading() { return loading }, get problem() { return problem }, mutate }
}
```

要点：`AbortController` 每次 refetch 取消上一请求（防"筛选快速切换导致旧响应覆盖新响应"）；`seq` 防乱序；文件必须是 `.svelte.ts` 才能在模块里用 runes；必须在组件初始化期（或 `$effect.root`）创建。

### 5.3 购物车：SSR 下如何不串用户

```
浏览器 ──Cookie: os_cart=<cartId>──► storefront SSR ──HTTP+同一 Cookie──► API
                                        │
                          +layout.server.ts 读 Cookie → 调购物车接口
                                        │
                          page.data.cart（每请求独立）
                                        │
                          +layout.svelte 里 createCartStore(initial) → setContext
                                        │
                          子组件 getContext<CartStore>('cart')
```

```ts
// apps/storefront/src/lib/state/cart.svelte.ts —— 工厂，不是单例
import { getContext, setContext } from 'svelte'
import type { CartSummary } from '@openstore/sdk'

export function createCartStore(initial: CartSummary) {
  let cart = $state(initial)
  let pending = $state(false)
  async function mutate(fn: () => Promise<CartSummary>) {
    pending = true
    try { cart = await fn() } finally { pending = false }
  }
  return { get value() { return cart }, get pending() { return pending },
           set: (c: CartSummary) => (cart = c), mutate }
}
export const CART_KEY = Symbol('cart')
export const provideCart = (c: CartSummary) =>
  setContext(CART_KEY, createCartStore(c))          // 每次组件树初始化新建一份
export const useCart = () => getContext<ReturnType<typeof createCartStore>>(CART_KEY)
```

**规则（写进 ESLint 与 code review 清单）**
1. `$state` **只能出现在工厂函数体内**或组件内；**模块顶层禁止** `let cart = $state(...)`（SSR 下该模块是进程级单例，多请求共用 → 串用户，架构 §3 已点名否决）。
2. 服务端是购物车权威：每次 `+layout.server.ts` 都从 API 读，前端 store 只是"最近一次服务端结果"的展示副本。
3. 写操作（加购/改量/删除）成功后用返回的 `CartSummary` 整体替换，**不在客户端做数量/金额的增减推算**（避免与运费/税/库存漂移）。
4. CSRF：`+layout.server.ts` 下发 `csrf` 到 `page.data`，所有写请求带 `X-CSRF-Token`（同域 + `SameSite=Lax` + 双提交）。
5. 登录后合并匿名车：由后端在登录响应里处理并返回合并后的 cartId，前端只做 `invalidateAll()`。

### 5.4 表格与表单的状态组织（admin 大量 CRUD）

| 状态 | 存放位置 | 理由 |
|---|---|---|
| 列表筛选 / 排序 / 分页 / 关键词 | **URL search params**（`goto('?'+qs, { replaceState: true, noScroll: true })`） | 可分享、可回退、刷新不丢、便于 QA 直接命中某状态；组件只读 `$page.url.searchParams` |
| 列表数据 / loading / 错误 | `createQuery`，key = 序列化后的 searchParams（参数变化时 `refetch`） | 单一数据来源，避免"改了筛选忘请求" |
| 表单 draft | 组件内 `$state`（`let draft = $state(structuredClone(entity))`） | 与实体解耦，取消即丢弃 |
| 表单 dirty | `$derived` 比较 draft vs 原始快照（浅比较 + 数组/对象按 key 序列化） | 不手写 dirty 标记（必漏），派生出来才不会错 |
| 字段级错误 | `Record<path, string>`，来自 ProblemDetails 的 `errors` | 后端返回字段路径，前端直接映射到控件 |
| 多步/多 Tab 表单 | 单页 draft + Tab 只切显示，**不按 Tab 拆保存** | 拆保存会产生"半保存实体"，回滚困难 |
| 弹窗（删除/退款/调整） | 由路由 query 或组件 `$state` 控制；提交中禁用关闭 | 防重复提交 |

### 5.5 明确禁止的做法

| 禁止 | 原因 |
|---|---|
| 模块级 `$state` 存购物车/用户/主题 | SSR 进程内单例，跨请求串数据（安全事故级） |
| storefront 用 `localStorage` 存购物车 | 与服务端权威购物车冲突；匿名车已由服务端 Cookie 承载（架构 §2.4 已否决） |
| 主题组件里 `fetch` / `import('@openstore/sdk')` 的写接口 / 读 `$env` | 主题是"可独立分发的纯渲染层"；一旦能取数就无法保证"主题坏了不坏数据" |
| 主题顶层访问 `window`/`document`/`localStorage` | SSR 直接崩；浏览器 API 一律进 `onMount` |
| 用 CSS `display:none` 实现区块显隐 | AC-13 要求关闭的区块**不出现在 HTML** |
| storefront 复用 admin 的 DTO（含成本价/内部备注） | 安全边界；成本价泄露到前台不可接受（架构 §4.3） |
| 客户端计算金额/税/运费 | 与后端漂移是"最贵的 bug"；只展示服务端算好的 `Money` |
| 用 `navigator.language` 决定格式化 locale | 水合不一致；locale 唯一来源是路由参数 |
| 在 `+page.server.ts` 里把整份商品对象塞进 `data` 再全量水合 | 首屏 JS/序列化体积失控；只传渲染必需字段 |
| admin 引 TanStack Query / 组件库 / lodash | 体积与心智成本 > 收益；已自建 |
| storefront 引任何图表/日期/动画库 | 预算见 §9 |

## 7. 多语种实现

### 7.1 `t()` 完整实现

```ts
// packages/i18n/src/t.ts
export type Vars = Record<string, string | number>
export type Dict = Record<string, string>

export function createT(dict: Dict | undefined, fallback: Dict | undefined,
                        override: Dict | undefined, dev = false) {
  const miss = new Set<string>()
  const t = (key: string, vars?: Vars): string => {
    const raw = override?.[key] ?? dict?.[key] ?? fallback?.[key]
    if (raw === undefined) { if (dev) { miss.add(key); console.warn('[i18n] missing', key) } return key }
    if (!vars) return raw
    return raw.replace(/\{(\w+)\}/g, (m, k) => (k in vars ? String(vars[k]) : m))
  }
  return { t, misses: () => [...miss] }
}
```

- 解析顺序严格为 `DB 覆盖 → 当前语种 → 默认语种 → key 本身`（架构 §5.2.1）。返回 `key` 而不是空串，是刻意的：**空串会让"漏译"静默通过，而 key 在页面上极其刺眼**。
- 变量插值只支持 `{name}` 简单替换，**不做复数/ICU**（中英都不需要，架构 §7.1 明确 YAGNI）。替换缺失变量时保留 `{name}` 原样，便于发现。
- DB 覆盖注入方式：`[locale]/+layout.server.ts` 调 `/api/storefront/i18n?locale=` 拿到 `{ dict, fallbackDict, override }` 三份，服务端 `createT` 后**通过 `ctx.t` 与 `page.data.t` 两条通道下发**。`t` 是函数，**不能进 `data` 序列化**——因此实际做法是：`+layout.server.ts` 只返回三份字典，`+layout.svelte` 里 `createT(...)`，再 `setContext('t', t)` 且塞进 `ThemeContext`。这是刻意设计，避免"函数跨网络"的常见错误。
- 当前语种字典单独打包：`packages/i18n/locales/{code}.json` 用 `import.meta.glob('./locales/*.json', { eager: false })` 按需加载，**不把全部语种塞进首屏**。

### 7.2 locales JSON 组织与 key 命名规约

```
packages/i18n/locales/
├─ en.json      # ★ 源语言（key 的唯一真源）
└─ zh.json      # 必须有与 en 完全相同的 key 集合（CI 校验）
```

命名：`{domain}.{component}.{element}`，全小写，用 `.` 分层，最多 4 段。

| 前缀 | 覆盖 | 示例 |
|---|---|---|
| `common.*` | 通用动作/状态 | `common.action.save` `common.action.cancel` `common.state.loading` |
| `nav.*` `footer.*` | 框架 | `nav.cart` `footer.shippingPolicy` |
| `home.block.*` | 首页区块内置文案 | `home.block.productGrid.title` |
| `product.*` | 商品详情 | `product.variant.selectSize` `product.state.outOfStock` `product.state.onlyFew` |
| `category.*` `search.*` | 列表/搜索 | `category.filter.title` `category.filter.clear` `search.empty.title` |
| `cart.*` `checkout.*` | 交易链路 | `cart.empty.title` `checkout.summary.tax` `checkout.demoBlocked` |
| `payment.*` `order.*` | 支付/订单 | `payment.failed.retryable` `order.status.paid` `order.track.notFound` |
| `account.*` `auth.*` | 账户 | `auth.login.title` `account.orders.empty` |
| `error.*` | 错误/降级 | `error.410.title` `error.degraded.title` |
| `email.*` | 邮件模板（后端渲染，文案键同源） | `email.orderPlaced.subject` |
| `admin.*` | 管理端（第二条 i18n 通道，本期只 zh，但 key 先占位） | `admin.products.title` |

规则：① 不复用同一条文案到不同语义位置（宁可重复字符串，不要耦合 key）；② 不把变量放进 key；③ 不带语种语义的措辞（不要在 key 里出现 `zh`/`en`）；④ key 一旦发布不改名（改名 = 商家覆盖值失效）。

### 7.3 从 `en.json` 生成 key 联合类型

```ts
// packages/i18n/scripts/gen-keys.mjs  —— 由 pnpm i18n:keys 触发，产物进版本库
import fs from 'node:fs'
const flat = (o, p = '') => Object.entries(o).flatMap(([k, v]) =>
  typeof v === 'object' ? flat(v, `${p}${k}.`) : [`${p}${k}`])
const en = flat(JSON.parse(fs.readFileSync('locales/en.json', 'utf8')))
const zh = flat(JSON.parse(fs.readFileSync('locales/zh.json', 'utf8')))
const missing = en.filter(k => !zh.includes(k)).concat(zh.filter(k => !en.includes(k)))
if (missing.length) { console.error('locale key 不一致:', missing); process.exit(1) }
fs.writeFileSync('src/keys.generated.ts',
  `// 自动生成，勿手改\nexport type MessageKey =\n${en.map(k => `  | '${k}'`).join('\n')}\n`)
```

- `t` 的签名收窄为 `t(key: MessageKey | (string & {}), vars?)`：内置键有补全与类型检查，主题/自定义键仍可传任意字符串（`string & {}` 保留补全又不封死）。
- 该脚本同时是 **CI 门禁**：`zh.json` 少键/多键 → 构建失败（防止"英文有、中文没有"的静默漏译）。
- 键从 `en.json` 生成而不是从 zh：源语言是英文（便于未来接入其他语种与 README 一致）。

### 7.4 语言切换：停留在当前等价页面

因为**所有语种都带前缀**（本方案的核心 URL 约定），切换只需换第一段路径：

```ts
// apps/storefront/src/lib/i18n/switchLocale.ts
export function switchLocaleHref(url: URL, target: string): string {
  const seg = url.pathname.split('/')          // ['', 'zh', 'products', 'x']
  if (seg.length > 1 && seg[1]) seg[1] = target // 第一段必是 locale（根路径由 302 兜住）
  return seg.join('/') + url.search + url.hash
}
```

- **只有同一个语种码切换这一段**，query（筛选、分页、排序）与 hash 全部保留 → "停留在当前等价页面"（US-E3-04）。
- **但有前提升级（`docs/02` §3.1 / §8.2 定稿口径）**：per-locale slug，且**页级未译 = 该语种没有这个实体的 URL（404）**，**不做任何跨语种 slug 回退**。所以：
  - 实体 DTO 给 `translatedIn: string[]`（= 存在该 locale 翻译行）与 `slugByLocale`；**`translatedIn` 是"有没有这个语言版本"的唯一判据**。
  - **`slugByLocale` 必须覆盖静态页，不只是商品/分类**：静态页 slug 也是 per-locale —— `/zh/pages/guanyu` ↔ `/en/pages/about`。只覆盖商品会让切换器在静态页上退化成 `fallback-home`（用户点 en 被送回首页），而这是**假降级**：内容明明有英文版，只是 slug 不同。判据很硬：**切换器在静态页上的 `exact` 数量必须等于该页的 `translatedIn` 长度**；如果实现只按商品/分类建映射表，静态页会全量落到 `fallback-home`，而 `fallback-home` 本身是合法取值，**所以断言不会红**。
  - **目标语种无译文行 → 该语种入口仍渲染，但 `href` 指向目标语种首页**（`data-locale-nav="fallback-home"`），**绝不拼一个 404 slug**。
    - 为什么不是"隐藏该语种入口"：用户会以为站点不支持这个语言（顶部切换器只有两三个语种时，"少一个"比"点过去到首页"更让人困惑）。
    - 为什么不是"跳当前语种首页"：那等于点了没反应，最差。
  - **切换器链接必须在 DOM 里可区分（AC-14d③）**：每个 `<a>` 带 `data-locale-nav`，取值只有 `exact`（该语种存在真实等价页，`href` 指向它）/ `fallback-home`（无等价页，`href` = 该语种首页路径）。**这层标记是给 QA 取证用的**——三个概念（切换器链接 / `hreflang` / 404）在 DOM 里都只是一个 `href`，没有标记就无法区分，QA 只能靠猜。
    - **`hreflang` 只允许出现在 `exact` 对应的语种上，`fallback-home` 绝不出现**。两者共用同一份 `translatedIn`，**实现时不许合并成一个函数/一个循环**：共享数据 + 复用循环 → `hreflang` 一定会跟着降级成"给首页也声明了等价页"。
  - **列表/搜索/首页区块等集合查询，后端必须按 `translatedIn` 过滤**（`docs/02` §7.3.4），否则英文列表会产出指向 404 的卡片链接。前端**不做二次过滤**（前端过滤 = 分页与 `total` 全错，且会渲染出"18 件但只显示 3 件"的假象）。
  - 缺口该在**管理端翻译覆盖率看板**里暴露（"这个商品没有英文"），而不是靠前台跳转掩盖。
- 切语种后 `page.data` 全部重新加载（URL 变了，`+layout.server.ts` 重跑），购物车与结算无需重建（cartId 在 Cookie 里，与语种无关）。
- 单语种部署也一样：`[locale]` **永远必填**（即使客户砍掉英文站、只剩 `zh`），路由层不要写"单语种退化分支"——否则将来加语种要改路由结构，且改的瞬间所有已收录 URL 形态翻转。此时语言切换器整体不渲染即可。

### 7.5 `<html lang>`、hreflang、canonical 的输出位置

**`<html lang>`**（SvelteKit 的硬限制：`app.html` 是静态文件，不能按请求改）

```ts
// apps/storefront/src/hooks.server.ts（片段）
export const handle = async ({ event, resolve }) => {
  const seg = event.url.pathname.split('/')[1]
  const loc = await resolveLocale(seg)          // 校验启用语种，非法 → error(404)
  event.locals.locale = loc
  return resolve(event, {
    transformPageChunk: ({ html }) => html.replace('%openstore.lang%', loc.bcp47)
  })
}
```

`app.html` 写 `<html lang="%openstore.lang%">`。用 `bcp47`（`zh-Hans`/`en`）而非短码，便于屏幕阅读器与 `Intl` 正确选择语音/格式。

**canonical / hreflang：一处集中输出**

- 位置：`[locale]/+layout.svelte` 里的单个 `<Seo seo={page.data.seo} site={data.site} />`。
- 数据：每个 `+page.server.ts` 返回 `seo`，由 `lib/server/seo.ts` 的 `buildSeo()` 组装（纯函数、可单测）。**页面无法"忘记"输出 canonical**，因为渲染入口只有一个。
- hreflang 规则：**只对 `exact`（该实体存在该语种翻译行）的语种**输出 `<link rel="alternate" hreflang>`，并始终补 **`x-default` → 默认语种的同一页面（不是首页）**（AC-14d④；缺 `x-default` 语法仍合法，但等于把"默认页是谁"交给搜索引擎猜）。
- **"译文缺失"只有一种形态，canonical 只有一种处理**（我把这里拆成两种过一次，是错的）：
  - **字段级为空/空白**（翻译行存在、某字段为 `NULL` 或全空白）→ 页面**就是**这个语种的版本 → `canonical` **自引用**，回退文本节点带 `data-i18n-fallback="zh"`。**不产生第二个 URL，因此不需要第二个 canonical。**
  - **页级无译文**（没有该语种的翻译行）→ **404 + `noindex`**，页面不存在，没有 canonical 可谈。**不要为它写"回退页 + 归并 canonical"分支**（AC-14d②）。
  - 两者是**相反行为**，混在一起会让 AC-14a（零中文）与 AC-14d②（404）永远无法同时绿。
- **绝对 URL 的唯一来源是 `PublicSiteUrl`（DB 里的站点设置），不是请求的 Host 头**。AC-10 明确要求"改 `PublicSiteUrl` 后 canonical/og:url/hreflang 立即跟随，且**不随请求 Host 头漂移**"——用 `event.url.origin` 会把 Host 注入 / 反向代理配错 / 容器内网主机名直接写进 canonical，这是能让整站 SEO 输出全错的缺陷。读取顺序：`site.publicSiteUrl`（DB）→ 未初始化时的 `PUBLIC_SITE_ORIGIN` 环境变量兜底（仅 `/setup` 向导期间会走到）。`buildSeo()` 只接受一个注入进来的 `base` 参数，**函数内部不允许读 `request`**（这样"忘了传 PublicSiteUrl"会在类型层暴露）。
- **OG 图与 canonical 必须是绝对 URL**（AC-10 硬判据），且 `og:image` 要 ≥1200×630、可匿名访问（微信/Facebook 抓取器不带 Cookie）。

### 7.6 业务内容多语在前端的呈现

兜底链（与 `t()` 完全一致，不可分叉）：

```
字段取值：requestLocale 值 → defaultLocale 值 → 空（不显示该字段，而不是显示 '—'）
实体名/标题：同上（必填字段不允许都空）
属性名与属性选项名：同上（这是英文站体验的分水岭，需求裁决 1）
```

- 前端**不做翻译**，只做取值兜底：DTO 里后端已把兜底算好并带 `translatedIn: string[]`（该实体实际有译文的语种列表），前端用它决定 hreflang 与"未译"提示。
- 兜底命中的 DOM 节点输出 `data-i18n-fallback="{实际来源语种}"`，供 QA 区分"UI 漏译（前端缺陷）"与"业务内容未译（数据未填）"。
- 数字/日期/地址：`Intl.NumberFormat` / `Intl.DateTimeFormat` 用 `bcp47`；地址顺序由国家决定（后端给 `addressFormat` 字段：`lines: string[]`），前端不做国家分支。

### 7.7 AC-14 的自动化判据（前端要提供的标记）

> AC-14 已拆为 **14a 业务内容（data-engineer）/ 14b UI 文案（前端）/ 14c 邮件模板（backend）/ 14d 回退与页级无译文（前端）**。本节只写前端要提供的标记与 14b 的实现，判据正文见需求 `AC-14a~14d`。

**AC-14b 的第一道防线是 CI，不是页面扫描**：`packages/i18n/locales/zh.json` 与 `en.json` 的**键集必须完全一致（缺键、多键都失败）**。它比"抓页面中文"更早、更准——页面扫不到是因为那个键压根没被渲染到，CI 能直接报出来。

```ts
// packages/i18n/scripts/check-keys.mjs（pnpm i18n:check，进 CI 必过项）
const zh = Object.keys(flat(zhJson)).sort(), en = Object.keys(flat(enJson)).sort()
const missing = zh.filter(k => !en.includes(k)), extra = en.filter(k => !zh.includes(k))
if (missing.length || extra.length) { console.error({ missing, extra }); process.exit(1) }
```
`flat()` 与 `gen-keys.mjs` 共用同一个展平函数（否则 CI 与类型定义会各算一套，这点必须同源）。

前端必须提供如下标记，脚本才可测、失败才可定位：

| 标记 | 加在哪 | 脚本用途 |
|---|---|---|
| `data-i18n-key="cart.empty.title"` | 所有"由 `t()` 产出文本"的元素 | 命中中文字符时直接报出 key → 定位到 `en.json` 缺哪条 |
| `data-i18n-fallback="zh"` | 业务内容兜底命中默认语种的节点（商品名/分类名/属性名/静态页正文） | 区分「UI 漏译」（必须修代码/字典）与「内容未译」（数据问题，非前端缺陷） |
| `data-i18n-scope="ui\|content\|theme"` | 三个来源的容器（主题文案 / UI 文案 / 业务内容） | 统计每类的中文字符占比，输出可读报告 |
| `data-i18n-exempt` | 含不该翻的专有名词的节点（型号/品牌/SKU） | 扫描面扩到 `img[alt]`/`[aria-label]`/`[title]`/`input[placeholder]` 后必然出现这类文本。**豁免只认节点标记，不认正则白名单**（白名单一定会被放宽到什么都匹配）；**豁免计数必须上报，K>20 报警**——豁免是逃生口，不是常态 |

**组件层义务（把标记做成透传，而不是每个组件手写）**：`Text`/`Button`/`Link`/`Field` 等原子组件统一接收 `i18nKey`、`exempt` 两个 prop 并透传到 DOM；`img` 走 `Image` 组件的 `altKey`/`exemptAlt`。这样"漏加标记"变成"没用原子组件"，code review 一眼可见。

脚本判据（写进 Playwright，见 §11.1）：
```
扫描面 = 文本节点 + img[alt] + [aria-label] + [title] + input[placeholder]（14a 扩面后必须全扫）
对非 data-i18n-exempt 的节点跑 /[\u4e00-\u9fff]/
不含 fallback 标记的中文命中 → 失败（UI/主题漏译）
含 data-i18n-fallback 的中文命中 → 记为"内容未译"告警
```
> **fixture 分两档，混用会得到假红**：`full`（英文 100% 已译，跑 14a/14b/14c）与 `fallback-probe`（专门跑 14d① 字段级回退）。同一套数据**无法同时满足**"en 零中文"与"某字段回退中文"。**脚本输出必须打印 `fixture-mode: full | fallback-probe`**，没有这一行的结论不可采信——否则下一个人会在探针档上跑 14a，然后去改本来正确的实现。
>
> **只有两档，没有"归档档"。** 归档样本（`fx-arch-repl` / `fx-arch-orphan` / `fx-arch-repl-cat`）与**全译档同批装载、常驻**，它们的 URL 由 `verify-seo-matrix.sh --archived-moved <path> --archived-gone <path> --archived-gone-from <path> --moved-from <path> --moved-to <path>` 参数传入，不从 fixture 目录进。**S10 的缺货样本同构**：URL 由 `--out-of-stock <path>` 传入；**参数缺任一个 → `rc=2` + `PRECONDITION`**（= AC-11 未通过，**不得记"跳过"**）。**不要写 `--probe archive`**（该取值已废止）：`--probe` 的语义约束是"只允许把一格 en 置成空串，**不得新增/删除实体**"，而它必须新增 3 个实体，定义上就冲突。
>
> **为什么这不需要第三个档位**：多一档的正当理由只有一种——**样本违反了某条判据的取值域**。归档样本只是**不在** 14a 的取值域内（它们不在 sitemap，14a 的遍历面是"en 站 sitemap 收录页 + 2 个静态页"，根本扫不到），所以这是**范围问题，不是冲突**。**判据冲突要换档，范围不明要定范围。**
>
> 顺带一条容易写错的：**`fx-arch-*` 在 sitemap 里查不到，但它们在「全译档」里是存在的** —— 别把"不在 sitemap"写成"不存在"，那会让下一个人去加一个不存在的装载步骤。
>
> **配套的可执行判据（写成"语义"而不是"词频归零"）**：
> ```sh
> grep -n "归档档" docs/04-前端设计.md | grep -v "判据" \
>   | awk '{ if ($0 !~ /没有|不存在|不得|已废止/) { print "FAIL: " $0; bad=1 } } END { exit bad }'
> ```
> 本条判据要**跳过自己所在的这几行**（`grep -v "判据"`）——否则"怎么查"这件事本身会被当成"在用"。
> 通过的例子：`只有两档，没有"归档档"`；被抓住的例子：把它当作一个真实档位来用（这种用法**不存在**，
> 写了就是判据要抓的）。
>
> **为什么不是"这个词出现 0 次"**：我为了迁就"字面归零"，曾把"不要写 `--probe archive`"改写成
> "不要再写把 `--probe` 取值成 `archive` 的形态"——**只为了让 `grep` 归零**。句子变难读了，
> 而**难读的防错提示等于没有**。判据该管"有没有在用"，不该管"有没有在提"。
> **让句子去迁就判据，是判据设计有问题，不是句子问题。**

**三个与前端渲染强相关的固定样本（记在这里，免得每次去翻 02/06）**

> **引子：断言写得越宽松，越容易绿，而绿的原因和被测行为无关。**
> 下面三条是同一句话的三个实例：`fx-arm`（豁免没标 → 中文被当漏译）、`fx-tee`（内嵌图被 sanitize 剥掉 → 没有 alt 可扫）、`fx-cat-zhonly`（只在裸路径上拦 → 参数绕开）。它们的共同点不是"容易漏"，而是**漏了之后测试仍然全绿**——因为被测面被悄悄缩小了。凡"这条断言能绿，是因为它没在测东西"，都要在样本层留一个"能证伪它"的样本。

| 样本 | 前端义务 | 漏了会怎样 |
|---|---|---|
| `fx-arm`（F6） | en 标题形如 `Robot Arm 机甲臂-3000`：**型号所在节点必须带 `data-i18n-exempt`**，该中文**不计入** `chinese` 命中 | 豁免护栏失去唯一样本；若改成"硬译型号"则是业务错（型号不可翻） |
| `fx-tee`（F5） | en 富文本描述内嵌一张 `<img>`，**`alt` 必须英文**；前端 sanitize 白名单**不得剥掉内嵌图与 `alt`** | 该断言"绿着但什么都没测到"——图上没有 alt 可扫，扫描面自然 0 命中。这是最隐蔽的一种假绿 |
| `fx-cat-zhonly`（F3b） | 只有 zh 译文的分类：`/en/c/fx-cat-zhonly` 必须 **404**，**不得因"空列表"返回 200**；**带参数同样 404**（`?page=2`、`?f.material=ceramic`——已写进 02 §7.3.4 的 F3b 判据）；它在 zh sitemap、**不进 en sitemap 与 en 分类导航** | 列表页天然有"空列表 200"的兜底路径，与商品详情是两条渲染路径——商品侧改对了不代表这里对。**而实现方最常在裸路径上拦截**，漏掉的恰好是爬虫与用户真会命中的 `?page=2` 形态 |


> **`data-i18n-*` 是测试定位契约，不是实现细节**：已写进 AC-14 原文（"命名变更必须同步测试脚本"）。任何重构不得改名、不得为了"更整洁"把它挪到父节点上；新增文案时漏加 `data-i18n-key` 会导致漏译统计偏低（假绿灯），所以 code review 清单里加一条：**所有由 `t()` 产出的文本元素必须带 `data-i18n-key`**。

> `bare: true` 的页面（上表最后一行那 6 类 + 404/410）由 `buildSeo()` 的 bare 分支只产出 `title` + `robots`，**其余标签一律不生成**。分支在 `buildSeo()` 一处，页面自己无权决定 —— 这样"给 CSR 页做 SEO"这类浪费不可能发生。

**`assertSingleSignal`：把"不许叠加信号"变成代码约束，而不是纪律**

需求 §6.1 的 S8 是最高优先项（任一 URL 同时命中两类信号即为违反）。这类违反**只能靠人记住规则**时必错——本项目已经在同一个点上错了 4 次（W9/W12/W15/W16）。所以在 `buildSeo()` 出口加一道机械闸：

```ts
// lib/server/seo.ts —— 出口处唯一一道闸，页面无法绕过
export function buildSeo(input: SeoInput): Seo {
  const seo = assemble(input)                       // 纯组装，不含判断
  const noindex = seo.robots.includes('noindex')
  const crossUrl = seo.canonical !== undefined && seo.canonical !== seo.selfUrl
  if (noindex && crossUrl) throw new Error('S8: noindex 与跨 URL canonical 不得同时输出')
  return seo
}
```

- **为什么抛异常而不是自动删 canonical**：自动删会把"页面配置写错了"变成静默行为，这类错误要到线上被索引了才发现。构造期就炸，本地第一个请求就会红。
- **只拦"跨 URL"，不拦"自指"**：S8 明确 `noindex` + **自指** canonical 只是告警（规范上冗余无害），**不得**为了过门禁去删它——模板统一输出 canonical 是正常实现，删掉会让页面失去自我描述。所以闸门条件是 `noindex && 跨 URL`，不是 `noindex && 有 canonical`。
- **搜索页是唯一必须"完全无 canonical"的页面**：`buildSeo({ canonical: undefined })` 显式传空，而不是"继承一个默认值"。S6 把它写成了独立断言，所以它不能靠上面那道闸兜。
- **`selfUrl` 必须由 `buildSeo()` 自己算**（`base + pathname`，剔追踪参数），不能由页面传入——否则"自引用"与"跨 URL"无法区分，闸门形同虚设。


### 8.2 JSON-LD 实体与字段

```jsonc
// 商品详情：Product + Offer + BreadcrumbList（三条 <script type="application/ld+json">）
{
  "@context": "https://schema.org", "@type": "Product",
  "name": "兼容 DJI RoboMaster S1 的舵机",
  "image": ["https://shop.example.com/media/p/robot-arm-1200.webp"],   // 绝对 URL
  "description": "……（纯文本，剥离 HTML）",
  "sku": "RB-ARM-BLK",
  "brand": { "@type": "Brand", "name": "店铺自有品牌或商品品牌字段" },
  "offers": [{
    "@type": "Offer",
    "price": "299.00",                    // 字符串 + 两位小数（Google 要求）
    "priceCurrency": "CNY",
    "availability": "https://schema.org/InStock",   // InStock | LimitedAvailability | OutOfStock
    "url": "https://shop.example.com/zh/products/robot-arm",
    "itemCondition": "https://schema.org/NewCondition"
  }]
}
```

| 实体 | 必含字段 | 注意 |
|---|---|---|
| `Product` | `name`、`image[]`、`description`、`sku`、`offers` | 多变体：`offers` 输出数组（每变体一个 Offer，带 `sku` 与 `name`）；本期若只渲染选中变体，则 `offers` 至少含当前变体 + 父商品 `AggregateOffer` 可选（不做，YAGNI） |
| `Offer` | `price`（字符串）、`priceCurrency`、`availability`、`url` | `availability` 由 `stockStatus` 映射（`out_of_stock` → `OutOfStock`，`low_stock` → `LimitedAvailability`，否则 `InStock`）；`availableQuantity` 为 `null` 不影响映射（它只是展示用的截断值，不能反推库存） |
| `BreadcrumbList` | `itemListElement[]`（`position`/`name`/`item`） | 与页面面包屑同源数据，不重复拼装 |
| `Organization` | `name`、`url`、`logo`（绝对 URL）、`contactPoint`（客服邮箱） | 首页与静态页输出；`contactPoint.contactType: "customer service"` |
| `WebSite` | `name`、`url`、`inLanguage`、`potentialAction`（SearchAction） | 首页输出；搜索 URL 模板 `/{locale}/search?q={search_term_string}` |

### 8.3 `curl` 不执行 JS 时 HTML 里必须出现什么（逐条对 AC-10）

| AC-10 要求 | 由谁保证 | 具体做法 |
|---|---|---|
| 商品标题 | SSR 组件输出 `<h1>` + `<title>` | 商品详情页在 `+page.server.ts` 拿到数据即渲染 |
| 价格与货币 | `MoneyDisplay`（SSR 时即调用 `Intl`，输出 `¥299.00`） | 服务端 Node 有完整 ICU（Node 22 full-icu 默认），不依赖浏览器 |
| 主图**绝对 URL** | `ctx.image()` helper 用注入的 `site.publicSiteUrl` 拼绝对（**绝不读请求 Host 头**） | 相对路径会在 OG 抓取器里失效 —— 这是最常被漏的一条；用请求 Host 则会把反代/内网名写进分享卡片 |
| 可售状态 | 变体 DTO 的 `stockStatus` + 页面文案 | "已售罄/仅剩 N 件"必须是 SSR 出的文本，不能等 JS；"仅剩 N 件"仅在 `availableQuantity !== null` 时出现 |
| `<title>` / `<meta name=description>` | `Seo.svelte` | 集中在 layout 一处输出 |
| `rel="canonical"` | `buildSeo()` | 每页必有，绝对 URL |
| 双向 `hreflang` + `x-default` | `buildSeo()` 按 `translatedIn` 生成 | 商品/分类/静态页三类都要有 |
| `og:title` / `og:image`（绝对） | `Seo.svelte` | `og:image` 用 1200×630 裁图或主图 1200 版本 |
| JSON-LD `Product` 含 `offers.price` + `availability` | 页面注入 | 价格用**字符串两位小数**，不要数字类型（Google 报错） |
| 首页/分类页/静态页同样通过 | 同上四类组件 | 分类页要有商品名与价格的 SSR 文本（不能只出骨架） |

### 8.4 必须在 SSR 阶段产出的内容（不能等水合）

- 商品：标题、价格、划线价、库存状态、主图 srcset、面包屑、属性规格表、描述正文（**转义后的 HTML 字符串**）。
- 分类：分类名、商品数量、筛选器标题与选项、前 24 个商品卡片（名/价/图/售罄标记）、分页链接。
- 首页：区块编排产出的实际内容（每个区块的标题与商品/分类数据）。
- 静态页：正文。
- 全部 head 标签与 JSON-LD。
- 页头导航、页脚、语言切换链接、`<html lang>`。

**允许在客户端才有的**：购物车角标数量（SSR 时也给一份，客户端更新）、筛选切换的增量结果、变体切换后的价格/库存、支付结果轮询、账户菜单展开。

### 8.5 分页、404/410

- 分页：`?page=N`，第 N 页页面内输出**可点击的 `<a href>` 分页链接**（`rel=prev/next` 已失效，不输出，架构 §5.4.3）；`page>1` 的 canonical 指向自身；`page=1` 不带 `page` 参数（避免重复 URL）。
- 筛选/排序状态的 canonical 由 §2.1 的 `categoryCanonical()` 单点决定（策略已定稿：`unfiltered` + 第 2 页起自引用），**抓取必须放行**（§2 索引控制规则）。
- 404：未知 slug / 非法 locale / 未知分类 → `error(404)`；`+error.svelte` 输出 `noindex` + 搜索框 + 热门分类（减少跳出）。
- 410：**已归档且无替代分类**的商品用 `error(410)`；**已归档且有替代分类 → 301**（S9 的三分叉，别一律 410）。页面文案区分"商品已下架"与"链接不存在"；410 页面同样 `noindex`，并给"看看同类商品"链接。
- **非 200 一律不输出 canonical / `hreflang`**（S5 口径的推广，也覆盖 404 与 410）：301 没有正文可谈；404/410 是错误页，**声明"我是某页的正式地址"在语义上是假的**，而且会让"该页仍存在"这一信号与状态码互相打架。`X-Robots-Tag` 仍按 §2 的模式表给 `noindex`（错误页不该进索引），但**不要给 410/404 写 `noindex` 就当解决了可达性**——它们本来就是可达的 410/404，两件事。
  > 这条是数据侧明确交回给我的边界（他们只钉状态码，不替 S 矩阵下结论）：**状态码归数据侧，信号（canonical / `hreflang` / `X-Robots-Tag` / sitemap）归前端**。所以"404 要不要输出 canonical"这类问题在数据文档里查不到答案，是设计如此，不是漏写。
- slug 变更 301：由后端在解析 slug 时返回 `redirected: { to: newSlug, status: 301 }`，storefront 收到即 `redirect(301, newPath)`（前端不做历史 slug 表，历史登记在后端）。
- **未登记的旧 slug 必须 404，不能"模糊匹配到近似商品后 200"**（AC-11 规则 4）。前端不做任何 slug 猜测/纠正逻辑（不做大小写归一、不做去掉后缀重试），否则会把"已删除商品"变成一串 200 的错页面，直接污染索引。规则 4（301）与规则 3（缺前缀 302）是两条不同规则，实现上必须分开，QA 也不得合并验证。
- `/{locale}/` 与 `/{locale}`（无尾斜杠）：统一 308 到带斜杠形式（SvelteKit `trailingSlash: 'always'`）。**注意 SvelteKit 的 `trailingSlash` 是全局配置，会影响所有路由** —— 采 `'always'` 后 API 代理路径 `/api/*` 不受影响（不经 SvelteKit），确认后写入 `svelte.config.js`。

## 9. 性能预算落地

### 9.1 storefront 首屏 JS ≤120KB gz 的构成

| 项 | 预算 (gz) | 手段 |
|---|---|---|
| Svelte 5 runtime + 水合 | ~25KB | 无可优化空间，接受 |
| SvelteKit client runtime | ~12KB | 默认 |
| app 自有代码（路由 + 首页/详情组件） | ~35KB | 路由级自动分割；首页区块组件按主题 chunk 懒加载（首屏区块 eager，其余 `{#await import()}`） |
| 当前主题 chunk（含 8 layout + 7 block） | ~28KB | 只有**当前主题**进首屏；另一主题独立 chunk 永不加载 |
| i18n 当前语种字典 | ~5KB | 只发当前语种（`import.meta.glob` 非 eager） |
| `@openstore/ui` 被实际用到的部分 | ~10KB | tree-shaking（源码分发天然支持，按 SFC 粒度） |
| 第三方运行时库 | **0KB** | 见准入清单 |
| 合计 | **≈115KB** | 留 5KB 余量 |

**第三方库准入清单（storefront）**

| 允许 | 条件 |
|---|---|
| 无 | 默认全禁 |

| 需要某能力时 | 替代方案（不许引库的理由） |
|---|---|
| 日期格式化 / 相对时间 | `Intl.DateTimeFormat` / `Intl.RelativeTimeFormat`（内置，0KB） |
| 数字/金额 | `Intl.NumberFormat` + `@openstore/sdk/money`（自写 20 行） |
| 防抖节流 | 15 行自写 |
| 轮播图 | 原生 CSS scroll-snap + 3 个按钮（不引 Swiper ~40KB） |
| 图标 | 内联 SVG（每个 ≤1KB，按需 import，不做 icon font） |
| 日期选择器 | 原生 `<input type=date>`（后台用） |
| 富文本 | admin 引一个编辑器（**唯一豁免**，且只在 admin、只在商品/静态页路由懒加载） |
| 图表 | 不做图表（仪表盘用数字卡） |

**代码分割策略**
1. 路由级自动分割（SvelteKit 默认）。
2. 主题按 chunk（`import.meta.glob` 非 eager）。
3. 首页非首屏区块（如 `newsletter`）用 `{#await}` 动态 import。
4. 购物车/结算/账户全部 `ssr=false` + 路由分割 → 不参与商品页首屏。
5. `@openstore/ui` 的 Modal/Drawer/Combobox 等重组件在需要时才 import（`const { Modal } = await import('@openstore/ui/...')` 的层级别更细时用子路径导出）。

### 9.2 图片

```svelte
<picture>
  <source type="image/webp" srcset="/media/p/x-400.webp 400w, /media/p/x-800.webp 800w, /media/p/x-1200.webp 1200w"
          sizes="(max-width: 640px) 100vw, 400px" />
  <img src="/media/p/x-800.jpg" width="800" height="800" alt={altText}
       loading={priority ? 'eager' : 'lazy'} fetchpriority={priority ? 'high' : 'auto'}
       decoding="async" />
</picture>
```

- 三档宽度由后端 ImageSharp 生成（400/800/1200），**前端不拼 URL 猜尺寸**，`ImageRef` DTO 直接给 `sources[]`。
- `width`/`height` 必须来自 DTO（后端有原图尺寸）→ 容器 `aspect-ratio` 固定，CLS ≈ 0。**这是必须提给 backend 的字段**（见 §11.3）。
- 折叠线上第一屏的 LCP 图 `priority`：`loading=eager` + `fetchpriority=high` + `<link rel="preload" as="image" imagesrcset>`（只在商品详情主图与首页 hero 用）。
- 列表用 400w，详情主图用 800/1200w；`sizes` 必须写对（否则浏览器下最大图）。

### 9.3 字体

- **中文不引 webfont**：`font-family: var(--font-body), -apple-system, "PingFang SC", "Microsoft YaHei", sans-serif`。理由：中文字体子集化后仍有 300KB+，与 120KB JS 预算冲突，且系统字体渲染更好。
- 拉丁字体（可选，主题 token `font.body=inter`）：
  - 自托管 woff2，**只子集 latin**（≤40KB），`font-display: swap`（避免 FOIT，接受一次 FOUT）。
  - `<link rel="preload" as="font" type="font/woff2" crossorigin href="/fonts/inter-latin.woff2">` 放 `app.html`（唯一在 `svelte:head` 之外需要 preload 的资源）。
  - `@font-face` 由 `theme-runtime` 根据 token 值拼接并输出到同一个 `<style>` 里（与 token 同一次注入，避免第二个 RTT）。
- 字号基准 `fontScale` 通过 `html { font-size: calc(16px * var(--fontScale, 1)) }` 实现，主题与后台编辑共用。

### 9.4 为达预算而不做的事（显式清单）

| 不做 | 理由 |
|---|---|
| 客户端路由全量 prefetch | 会把另一条链路（购物车/结算）的 chunk 提前拉下来，首屏 JS 超标 |
| Service Worker / PWA 离线缓存 | 架构 §7.1 明确不做；且缓存策略错误会导致"改了商品看不到" |
| 前端状态管理库、组件库、动画库 | 预算 + 主题契约冲突（Tailwind/组件库已否决） |
| 客户端 Markdown/富文本解析 | 描述由后端输出已净化 HTML，SSR 直出 |
| 图片懒加载库（IntersectionObserver 封装） | 原生 `loading=lazy` 足够 |
| 骨架屏组件库 | 自写 `Skeleton`（20 行） |
| 客户端日志上报 SDK | 错误进服务端日志（后端 Serilog + correlationId）；`window.onerror` 可选打点到 `/api/client-error`（1 行 fetch，后期再加） |
| 首屏字体 icon | 内联 SVG |
| 首页自动轮播（定时器） | 也是 a11y 问题（`prefers-reduced-motion`）；改为手动切换 |
> **但"直出"不等于"原样直出"**：前端仍有一道兜底 sanitize（`{@html}` 之前过一遍），白名单**必须保留 `img` 的 `src/alt/width/height`** 与内嵌图本身——这不是安全偏好，是 AC-14a 的取证前提：`fx-tee` 的 en 描述内嵌一张图，**剥掉 `alt` 会让"属性零中文"断言绿着但什么都没测到**（扫描面里没有可扫的 alt 了）。所以要一并守住：`img[alt]` 在 DOM 里**必须存在**（哪怕为空串也算存在，空串由 14a 的"空白视为未译"口径覆盖）。

### 9.5 其他性能项

- **筛选切换 ≤800ms**（US-E9-03）：`goto` 触发 SSR 数据请求；期间保留旧结果 + 顶部 2px 进度条（不全屏 loading，避免"闪白"）。facet 请求与列表请求合并成**一次** API 调用（见 §11.3 facet 形态），避免两次往返。
- **admin 商品列表 5000 行分页 ≤1.5s**：服务端分页 25/页 + 只投影列表字段；表格不做虚拟滚动（25 行不需要）。
- `Cache-Control`：静态资源 `immutable`（Vite hash），HTML `s-maxage=60`，`/media/*` `immutable`（URL 含内容指纹，US-E9-06）。
- 严格避免布局抖动：所有图片/骨架/广告位容器给定 `aspect-ratio`；Toast 用 `position: fixed` 不占流。

## 10. 可访问性（WCAG 2.1 AA）

### 10.1 键盘可完成加购与结算的路径（必须逐条可测）

| 步 | 键盘操作 | 断言点 |
|---|---|---|
| 1 | `Tab` 到商品卡片 → `Enter` 进详情 | 卡片是 `<a>`，有可见 focus ring |
| 2 | `Tab` 到变体选项组，`←/→` 切换（roving tabindex）或 `Tab` 逐项 + `Space` 选中 | `role=radiogroup` + `role=radio` + `aria-checked`；置灰项 `aria-disabled=true` 且不在 Tab 序列（或用 `aria-disabled` 保留可发现性并有说明） |
| 3 | `Tab` 到数量步进，`↑/↓` 调整 | `role=spinbutton` + `aria-valuenow/min/max` |
| 4 | `Tab` 到"加入购物车"，`Enter` | 结果通过 `aria-live=polite` 播报"已加入购物车" |
| 5 | `Tab` 到页头购物车链接（角标数字有 `aria-label="购物车，3 件"`），`Enter` | — |
| 6 | 购物车页 `Tab` 逐行改数量/删除 | 删除有确认或可撤销（Toast 撤销） |
| 7 | `Tab` 到"去结算" | 售罄时按钮 `disabled` + `aria-describedby` 说明原因 |
| 8 | 结算页 `Tab` 顺序 = 视觉顺序（邮箱→地址→运费→摘要→下单） | DOM 顺序必须与视觉顺序一致（不用 CSS order 打乱） |
| 9 | 提交失败：焦点自动移到第一个错误字段，并 `aria-live` 播报错误数量 | `role=alert` 或 `aria-live=assertive` |

### 10.2 表单与焦点规约

- **所有表单控件必须被 `<Field>` 包裹**（label 关联 + hint + error）；错误用 `aria-describedby` 关联，`aria-invalid=true`。
- 错误摘要在表单顶部（`role=alert`），并提供"跳到第一个错误"的链接。
- 焦点环：`--focus-ring: 0 0 0 3px color-mix(in srgb, var(--color-primary) 40%, transparent)`，`:focus-visible` 才显示；**禁止 `outline: none` 而不给替代**（写进 code review 清单）。
- 模态：打开时焦点进第一个可交互元素，`Tab` 循环限制在模态内，`Esc` 关闭，关闭后焦点回到触发元素。
- 装饰性图片 `alt=""`；商品图 alt 必填（上传时未填保存给警告，US-E9-07）。
- `prefers-reduced-motion: reduce` → 关闭所有过渡与自动播放（含首页轮播）。

### 10.3 主题侧的 a11y 责任边界

| 责任 | 归属 |
|---|---|
| 语义正确（`<button>` 不写成 `<div onclick>`）、标题层级 h1 唯一、`<main>`/`<nav>`/`<header>` 地标 | **主题作者**（`@openstore/ui` 提供 Button/Field 等正确语义件，但不强制主题用） |
| 对比度 ≥4.5:1 | **商家**（token 值决定）→ 由**编辑器告警**兜（不阻断）；主题默认值必须已达标 |
| 焦点可见 | token 提供 `--focus-ring`，**ui 包保证自己组件有焦点样式**；主题自定义的可点元素必须自己加 |
| 键盘可达、不做鼠标专属交互 | **主题作者**；`check.sh` 里对 layout 做"仅键盘"无法自动化 → 由 Playwright 黄金链路兜 |
| 隐藏内容不用 `display:none` 藏可聚焦元素 | **ui 包的 Modal/Drawer 负责**（用 `inert` + `hidden`） |
| 表单 label/错误关联 | **ui 包 `Field` 负责**（强制走 Field 就没有这个问题） |
| `aria-live` 结果播报 | **ui 包 `Toast` + 业务组件的加购/筛选结果** |

> 边界一句话：**"控件级语义"由 ui 包保证，"页面级结构与对比度"由主题作者与商家保证**。主题评审清单（PR 模板）里放 5 条：地标、h1 唯一、无 div 按钮、焦点可见、对比度。

## 11. 给下游的交接要点

### 11.1 给 QA：Playwright 黄金链路 + 三个 AC 的断言

> **断言硬原则：期望值不得取自被测对象的同一响应。**
> 一旦违反，断言会变成同义反复——脚本"逐条 PASS"看起来 11/11 全绿，实际只证明了一件事："服务器返回的东西等于服务器返回的东西"。而这是实现阶段最容易被无意引入的：写断言时手边只有那一个接口，最省事的取期望值方式就是它。
> 具体三条落地：① 期望 URL/状态/文案全部来自 **fixture 声明**；② 涉及跳转时**再取一次落地页**并断言它自己 200（防"301 指对了、目标页 404"）；③ **`Location` 一律逐字比完整绝对 URL**：`expect(loc).toBe(`${publicSiteUrl}/en/c/fx-arch-repl-cat`)`，**不要抽 `.pathname` 去比**。
>
> **为什么这里不能归一（这条是踩反了才改对的）**：我原来用 `new URL(loc, 'https://placeholder.test').pathname` 把域名维度摘掉，理由是"红了之后只剩一个变量"。但 `Location` 一旦定了**绝对且来源 `PublicSiteUrl`**，抽掉域就等于**把 AC-10 最想抓的那个错让掉了**——实现若读的是请求 Host，`pathname` 依然正确、断言依然绿，而"canonical 指向 `172.16.x.x`"这类事故一条都不会被抓住。**契约定了绝对之后，归一不是保护，是弃权。**
>
> 归一的正确适用范围只有"**两头都可能带域名**的字符串比对"（例如把 fixture 里声明的绝对 URL 与响应值比较）。`<a href>` **不需要归一**：切换器与分页的 `href` 本来就该是路径，直接比 `/en/` 即可。
>
> **这条归一同时暴露了一个契约缺口，已回提并由数据侧落到 02 §8.2**：既然 `Location`（301/302 的跳转目标）与 canonical / `og:url` / `og:image` / hreflang 同属"绝对 URL"，**它就必须一律由 `PublicSiteUrl` 生成**，而不是各页面各拼一半。理由两条：① **安全** —— `Location` 被 Host 头注入比 canonical 更直接，一次 301 就能把访客与权重一起送去攻击者站点；② **契约** —— "相对还是绝对"不写死，等于把不确定性转嫁给每一处断言，而转嫁出去的东西没人会系统性补上。

**与 `06` 的交接口径（两份文档不得各说一套）**

本节与 `06` 有 8 处交叉：**翻页三支 / S9·S10 的四形态 / `--out-of-stock` / `FX.oos` / 空态 vs 错误页 / `maxOrderQuantity` / `hreflang` 只出 `exact` / `x-default`**。分工是：**本文是口径源**（设计与断言的"为什么"），**`06` 是执行侧单一写者**（用例编号、跑法、判读表）。

规矩：任一侧改动，另一侧要么同步，要么**明确写"此处不复述，见 `04 §X`"**——**不许两边各写一句相似的话**。理由不是洁癖：`06` 复述 soak 条数返工过两轮，**两份文档各说一套时，红的判据会指向错的那一份**（读者按最近的那份修，而那份不是源）。


**黄金链路（1 条主链，chromium/webkit/firefox 三引擎）**
```
访客 → 首页(SSR 断言) → 分类页勾选 facet(URL 断言) → 商品详情选变体(价格/库存断言)
→ 加购 → 购物车改量 → 结算填地址 → 提交订单 → Fake 支付成功 → 支付结果页
→ /orders/track 用订单号+邮箱查单 → admin 登录 → 订单详情点"刷新支付状态"
→ 填运单号发货 → 前台查单看到已发货 → admin 退款 → 前台查单看到已退款
```


> **联调期一条独立断言：`details.reason` 走"没见过的值"兜底分支的次数必须为 0。**
> 兜底规则本身是对的（见 §11.3：没见过的值走"通用失败 + 重试"，不当成 `CANNOT_SELL` 去引导改配置），但**兜底最大的风险不是兜错，是它静默**——兜错时只是体验变差，没有人会知道"我们一直在兜底"。计数为 0 这条不需要线上埋点，**只需要有人问一次这个问题**；它会在第一次联调就暴露"整侧字段对不上"，而不是等商家投诉"点了重试还是不行"。
> **S10 的"留在 sitemap"是最容易漏的一半**：把缺货商品从 sitemap 摘掉"看起来合理"，实际代价是断货期结束后回榜要慢数周，而 S10 要求它 200 + `OutOfStock` + 仍在 sitemap。**归档则相反**：内容没了，必须移出 sitemap。
> **数据侧只有两个独立事实**：`Product.Status`（`Active`/`Archived`）与库存计数。**「下架」与「缺货」不得共用一个布尔值**（如 `IsAvailable`）——共用之后 301/410 与 200/OutOfStock 无法区分，S9 与 S10 会同时挂。

**三条与数据模型对齐的硬约束（`docs/02-数据模型.md`）**：
1. **库存只有三个字段**：`stockStatus` / `availableQuantity`（**≤5 才给值，否则 `null`**）/ `maxOrderQuantity`（= 步进器上限，**= `min(99, 真实可售量)`**，**不是 `min(99, availableQuantity)`**——后者 >5 时是 `null`，而 `Math.min(99, null)` 得 **`0`**（不抛错），错法是**把上限静默变成 0**，不是"算出 null"（A1；详见 §2.2 商品页第 4 条）；它不是"每行业务策略常量"，也**不等于库存余量**——它是"能一次买多少"的上界）。真实 `OnHand/Reserved/Sold` 是**可被爬取的情报**（`Reserved` 甚至能反推销量与秒杀节奏），截断必须在后端 DTO 层做。前端只按 `availableQuantity === null` 决定是否渲染"仅剩 N 件"；**`maxOrderQuantity` 只喂给步进器的 `max`，绝不渲染成任何文案**（不写"最多可买 37 件"）——因为 `available ∈ [6, 98]` 时 `min(99, available)` 就等于真实可售量，把它印在页面上等于把后端花力气遮蔽的数字补回来（A1 的已知张力，遮蔽在后端做、泄漏别在前端补）——**不要从任何别的字段推算库存，也不要把它放进 SSR `load` 返回值之外的任何地方**（`load` 返回值会随 HTML 序列化到页面里）。
   - **`maxOrderQuantity` 的两条使用纪律（A1 的副作用，数据侧已在 02 §8.2 承认）**：
     - **只当步进器 `max` 属性用，绝不渲染成"最多可买 N 件"这类文案。** 因为 `available ∈ [6, 98]` 时 `min(99, available)` 就**等于真实可售量**，而这一档 `availableQuantity` 恰好是 `null`。把它显示出来 = 绕过 null 遮蔽，**爬虫读 JSON 就能拿到精确库存**，而且这个泄漏是"设计上允许的取舍"带来的，不会被任何截断逻辑挡住。
     - **不要写 `availableQuantity ?? maxOrderQuantity` 这类组合式**（旧口径遗留）。A1 之后 `stepperMax = maxOrderQuantity`，永远是有意义的整数，**不需要兜底**；写了兜底反而会在"后端漏传"时静默算出个错的数。
     - 取舍本身要理解成一句话：**约束优先**——宁可让用户点两下步进器感知边界，也不许他加超了到结算才失败。所以这个泄漏是**主动选的**，不是漏掉的；正因如此，前端更不能额外放大它。
2. **`sort` 只有 `price_asc | price_desc | newest`**；**`page` 不设上限**（"`page ≤ 100` 硬上限"**已作废**，理由见 §2.1：根分类 209 页，截断会静默丢 2,600 件商品）。翻页终止由 **`pageCount`** 判（`page >= pageCount` 即到底），**不得用 `items: []` 判"到底了"**；`items` 空但 `page <= pageCount` 单看契约不可能、**并发下可能**（`total`/`pageCount` 与 `items` 不同快照），处置是"数据不完整 + 上报 + **给出口**"，不渲染"没有更多了"——见 §2.1 的三支判别。搜索结果默认按相关性排序，但**不把 `relevance` 作为可选 `sort` 值暴露**。
3. **`translatedIn` 决定 hreflang**，未译语种不输出该实体的 alternate（见 §7.4/§11.3 末尾的 slug 说明）。

```jsonc
  {
    "code": "waterproof", "label": "可水洗", "dataType": "bool", "control": "toggle",
    "options": [{ "value": "true", "label": "是", "count": 5, "selected": false }]
  },
  { "code": "material", "label": "材质", "dataType": "text", "control": "search",
    "suggestions": [{ "value": "abs", "label": "ABS", "count": 4, "selected": false }] }
]
```

1. **count 必须是"排除自身筛选条件后"的计数（析取式 / disjunctive faceting）。** 否则勾了"USB-C"之后"接口类型"自己的其他选项全变 0、其他属性也可能全 0，用户以为没货可选 —— 这是筛选项最常见的致命设计错误。
2. **只返回 `filterable=true` 且"当前结果集中实际出现过值"的属性**（US-E5-01），按 `展示顺序` 排序；`control` 由 `dataType` + 选项数决定（枚举 → checkbox；>12 个选项 → `select`/抽屉；数值 → range）。`count === 0` 的选项后端已滤掉，前端**不再二次判空**（数据模型侧决定，避免两处各滤一次导致"到底谁滤错了"无法定位）。
3. **属性标签必须已本地化**（`label`、`options[].label`），前端不做翻译（属性名不翻 = 英文站露中文，需求裁决 1）。
4. **一次请求同时返回 items + facets + availableSorts**：分两次请求会让"筛选切换 ≤800ms"（US-E9-03）很难达标。

**F. 其他必须给前端的字段**
- 站点设置：`{ name, logo, favicon, currency, taxIncluded, freeShippingThreshold, supportEmail, canSell(bool), canSellReason, publicSiteUrl, locale:{code,bcp47,isDefault}, enabledLocales[] }`。
  **`publicSiteUrl` 是前端生成所有绝对 URL 的唯一依据**（AC-10：不得用请求 Host 头，防 Host 注入与代理错乱）。校验规则由后端执行、前端同步做即时提示：必须是**绝对 URL（含 scheme + host）且无尾斜杠**；修改后 sitemap / canonical / og:url / hreflang **立即**使用新值（不要缓存到进程，或按设置版本号失效）。
  **`canSell` 必须是只读派生值，不是可直接编辑的设置项**（PM 明确，AC-17）：判定 = ① 已填支付凭据 ② 最近一次连接测试通过 ③ 通道处于启用，三条全满足才 `true`；凭据被清除或失效时**自动**回落 `false`。**管理端不得提供直接翻转 `canSell` 的开关**（否则会产生"通道是错的但前台能下单"的僵尸订单：占库存、要人工取消、还发了确认邮件）。由后端在**支付配置变更时**与**定时健康检查时**重算并落库，不要每次请求现算（会拖慢首页）。前端只读它来禁用结算按钮（US-E6-07）与渲染管理端常驻横幅。
- 分页/列表统一：`total/page/pageSize/pageCount`。
- 错误：一律 `ProblemDetails`（RFC 7807），`errors: { "path": ["msg"] }` 供前端做字段级定位。
- 库存调整、退款、发货等写操作成功后返回**更新后的实体**（省一次刷新请求）。

**G. 与后端契约的对齐（联调前必读，否则字段名对不上）**

| 项 | 契约 | 前端注意 |
|---|---|---|
| `canSell` 位置 | `GET /api/storefront/bootstrap` → `store.canSell`；admin 在 `GET /admin/dashboard/summary` 拿 `canSell` + `canSellReason` | 原稿 `paymentsConfigured` **已删除**。**前端禁止自行推导**（不读 provider/凭据自己算） |
| `canSell` 文案 | `false` → **不渲染**结算按钮（渲染后报错是最差体验）；`canSellReason ∈ ok \| noCredentials` → **中性提示**"本站暂未开通在线支付"；`testFailed` \| `channelDisabled` → **警告样式**"支付通道连接异常，已暂停下单" | 两档视觉层级不同，不能合并成一句话；只给布尔值等于让商家不知道该修哪里（AC-17 ⑥）。**枚举按 AC-17 原文驼峰**，不要写成 `test_failed` |
| 改凭据后 | **`canSell` 立刻变 false**（后端清空 `LastTestSucceededAt`），直到重新测试通过 | 保存凭据成功后**必须引导去点"测试连接"**，否则商家以为配好了、前台却下不了单 |
| 下单被拒（TOCTOU） | **`503 CANNOT_SELL`**，`details.reason ∈ {noCredentials \| testFailed \| channelDisabled}`（**与 `canSellReason` 同一套枚举**，openapi 明文）、`details.fixPath` | 场景：页面已渲染"可结算"，提交时凭据刚被改坏。映射表按 `code` 分支，`details.reason` 只微调文案；`fixPath` 做"去修复"按钮。**必须把它当正常业务结果处理**（不弹"未知错误"、不清空购物车、不重试下单）。**因为它与 `canSellReason` 是同一判定域的两个出口，映射表可以共用一张**——同域共用安全，跨域共用才危险（见下） |
| 支付发起被拒（瞬时） | **`PAYMENT_PROVIDER_UNAVAILABLE`**（503），`details.reason ∈ {providerTimeout \| providerError \| providerRateLimited}`（瞬时域；**成员名已进契约**，见 `openapi` bootstrap `description`。但 `/api/checkout` **端点**尚未进契约，M2/M3） | **瞬时可卖但本次失败**（超时/5xx/限流）→ 处置是**给"重试"**，不引导改配置。文案要说明"订单已创建、暂无法支付"，避免用户以为要重新下单。**它不属于 `canSellReason`** —— 那是稳态事实（现在为什么不能卖），这是瞬时事实（这一次请求为什么失败） |
| 归档商品 | 商品接口对 `Archived` 返回 `{ archived: true, redirectTo: string \| null }`；`redirectTo` 由后端按 AC-11 (b3) 的"替代分类页"定义算好 | **前端纯映射**：`redirectTo` 有值 → `redirect(301)`；为 `null` → `error(410)`。**前端不判断"该 301 还是 410"、也不算"哪个分类还在"** —— 判断权必须在一处，两处判断早晚不一致。**候选分类列表只在 admin DTO 给**，storefront 侧多一个字段就多一条"前端自己算"的路 |
| 退款接口 | **`202`** + `{refundId, status: "Pending"\|"RequiresManualSettlement", mode: "Gateway"\|"Offline", amount}` | **异步**（事务内建单 + Outbox）。admin 必须"提交 → 显示退款中 → 轮询/刷新拿最终态"，**不能假设点完就成功** |
| 订单三字段 | `status`（9 值，列表/标签用）、`fulfillmentStatus`（物流区块）、`refundSummary` | **不要只读 `status`**：9 个状态混了"履约"与"资金"两个正交维度，单字段表达不了"已发货 + 部分退款后继续发货" |
| 退款对外投影 | 消费者侧只给 `refundStatus: processing \| succeeded \| failed` + `refundedAmount` | **storefront DTO 必须剥掉 `requiresManualSettlement` / `offlineVoucherNo` / `settledBy`**（见 01 附录 B W10）。后端契约里"前台显示『退款将由商家线下处理』"的措辞与需求冲突，已回提 |
| 线下退款（admin） | `status==='RefundPending' && requiresManualSettlement` → 填凭证号 → `POST /admin/refunds/{id}/settle-offline`；不填 → `400 OFFLINE_VOUCHER_REQUIRED` | 仅 admin 可见；消费者侧一律"退款处理中" |
| 绝对 URL 分工 | 后端给**绝对**的媒体 URL、`paymentUrl`、`trackingUrl`、`bootstrap.store.publicSiteUrl`，以及**所有 3xx 的 `Location`（含归档 301 的 `redirectTo`）** | **但筛选/分页状态的 canonical 必须前端算**（依赖当前 URL 查询状态，后端不知道）。所以：媒体与业务跳转用后端值；`canonical`/`og:url`/`hreflang` 用 `publicSiteUrl + 当前路径`，**绝不用请求 Host**。两套来源不得混用——混用会出现"商品页 canonical 正确、筛选页 canonical 错域名"。**`Location` 归后端且必须绝对**：`Location` 被 Host 头注入比 canonical 更直接（一次 301 就把访客与权重送走），且"相对还是绝对"若不写死，每处下游断言都得自己做归一 |
| CSRF | `os_admin_csrf` 非 HttpOnly，`packages/sdk` 的 `apiFetch` 已注入 | 页面里**不要手写** CSRF |
| 新增错误码 | `CANNOT_SELL`、`PAYMENT_PROVIDER_UNAVAILABLE`、`OFFLINE_VOUCHER_REQUIRED`、`OFFLINE_FALLBACK_NOT_ALLOWED`、`STOCK_CHANGED_RETRY` | 映射表别漏；`WEBHOOK_*` 前端不处理。**注意 `PAYMENT_UNAVAILABLE` 这个码不存在**（它一度在架构里出现，已清零），正确名是 `PAYMENT_PROVIDER_UNAVAILABLE`。**且 `CANNOT_SELL` / `PAYMENT_PROVIDER_UNAVAILABLE` 目前都不在 `ProblemCode` 封闭枚举里**（`/api/checkout`、`/api/setup` 端点尚未进契约，openapi 明写"等 M2/M3 一起进"）——所以引用它们时一律标注 **未进契约（M2/M3）**，否则有人拿 06 去跑 "`code ∈ enum`" 门禁会把它们判成拼写错误，做成一个永远红的约束 |

> **写法标准一：凡提"原因"，必须带域名**（`canSellReason` 或 `details.reason`），**不许裸写 `reason`**。裸写不算笔误——读者会二选一，而这两个域的处置完全不同（前者"去改配置"，后者"重试/换通道"）。这条是架构师在自己刚写完"两个枚举不要合并"之后立刻写出了一个裸 `reason` 才定的：**知道规则和写的时候用上规则是两件事**，所以标准要落在"写"这一层。
>
> **写法标准二：数据枚举用驼峰，错误码用全大写下划线，两者不得互换。**
> - **数据字段的枚举值**（`canSellReason`、`details.reason`）→ 驼峰（`ok` / `noCredentials` / `testFailed` / `channelDisabled`）。它是 JSON 载荷的一部分，跟着 openapi 与 AC-17 原文。
> - **`code` 的值**（`ProblemCode`）→ UPPER_SNAKE（`CANNOT_SELL` / `STOCK_CHANGED_RETRY`）。它是封闭枚举、对外契约。
> - 同一个词 `reason` 在一处驼峰、在另一处作为 `code` 出现全大写，**这是设计意图，不是不一致**。
> - **本表格自己违反过这条**：上一行写着"枚举按 AC-17 原文驼峰，不要写成 `test_failed`"，紧下方两行的 `CANNOT_SELL` 行却写成了 `PAYMENT_NOT_CONFIGURED / CREDENTIAL_INVALID / PROVIDER_DISABLED`。这不是笔误，是把"错误码用 UPPER_SNAKE"的惯例套到了"数据枚举"上。**知道规则、和写的时候想起来用，是两件事**——所以这条要写成可 grep 的检查项进评审清单，而不是只写在这里。

> **`details.reason` 的归属已定（team-lead 裁决）：两张表，值域不重叠，不合并。**
> - `CANNOT_SELL.details.reason` 问的是"**这个商品现在能不能卖**"（`{noCredentials | testFailed | channelDisabled}`，稳态，处置是**引导改配置**）；`PAYMENT_PROVIDER_UNAVAILABLE.details.reason` 问的是"**支付通道这一次请求为什么失败**"（`{providerTimeout | providerError | providerRateLimited}`，瞬时域，处置是**给"重试"**）。两个判定域——**词表可以不同，拼写风格必须一致**。
> - **判据是一句话："这两个错误能同时为真吗？"** —— 不能。稳态不可卖时根本走不到通道；走到了通道就说明稳态可卖。**互斥的事实不共用枚举。**
> - **同域可以共用、跨域不可共用**：`CANNOT_SELL.details.reason` 与 `canSellReason` 是**同一个判定域的两个出口**（openapi 明文"同一套枚举"），共用一张映射表是安全的；而 `CANNOT_SELL` 与 `PAYMENT_PROVIDER_UNAVAILABLE` 跨域，必须两张表。所以上面说的"两张表"指的是**跨域那两张**，不是把 `canSellReason` 也算成第三张。
> - **合并的代价不是"不整洁"，而是"每个上下文里都有一半值永远不出现"**：前端映射表会多出一堆不可能命中的分支，而这些分支不会被测试覆盖，也就不会被发现是错的。
> - 值域既然不重叠，就**不存在"同一个 reason 在两域含义相同"的情况**，所以没有"文案 key 复用"这回事——每个 reason 各对应一句文案，各自封闭。**将来扩枚举若出现同名不同义，再启用域前缀**，写法跟数据枚举一致（驼峰，如 `productUnavailable`），**不要用 UPPER_SNAKE**——那是 `code` 的写法。
> - **前端不猜、不兜**：`details.reason` 只用于选文案与选处置按钮；**没见过的值一律走"通用失败 + 重试"**，不得因为"不在表里"而当成 `CANNOT_SELL` 引导用户去改配置（那是让用户去修一个不存在的配置问题）。



**空态 vs 错误页的判别（AC-10 负向断言相关）**：API 响应**必带 `total`**。`total === 0` 才是真没数据（渲染空态）；5xx/超时才是错误页。**不要把两者都渲染成空态**——空壳页被索引比不索引更糟。同理：**不要在 SSR 里把 503 改成 200 + 空列表**，反代的可用性告警会因 200 永远不响。

**再加一条同族判别（列表页少一个就够骗过人）**：`total > 0` 但本页 `items` 为空时，**先比 `page` 与 `pageCount`** —— `page > pageCount` 是"翻过头了/到底了"，`page <= pageCount` **单看契约不可能、并发下可能**（后端 `03 §8.2`：`page > pageCount` 才空、`page === pageCount` 非空；但 `total`/`pageCount` 与 `items` 若不是同一快照读的，就会出现这个组合）。两种成因（别人加的夹子 / 快照不一致）**处置相同、根因不同**：走"数据不完整 + **给出口（重试 / 回第 1 页 / 清筛选）** + 上报"，不渲染"没有更多了"，**也不要猜原因**。三条判别各管一件事：`total === 0` 管"真没有"、`page > pageCount` 管"真到头"、5xx/超时管"取不到"。**把它们合成一个 `if (!items.length)` 是最省事也最贵的写法**：三种情况下用户看到的都是空白，而只有一种是真的。

### 12.1.1 引用纪律（本项目已升级为正式规则，写在这里供后来人遵守）

> **任何"结论变了"的表述，必须附「文件 + 锚点串 + 采样时刻」；无法附的一律当"未经验证的转述"处理，不得据此改动实现。**
>
> 只说"我搜了 A 没找到"，不说"文档里没有 X" —— 前者是**取证记录**，后者是**覆盖断言**。

三条配套理解，都是这轮用事故换来的：

1. **转述会保留旧结论，但不保留旧结论的作废标记。** 文档里的旧句至少有台账可查（Wn / D-n），消息里的旧句没有任何痕迹。这就是为什么消息层比文档层更危险——它最像"某人的最新裁定"。
2. **这条规则对主理人的话、对架构师的话、对我的话同等有效。** 收到没附锚点的裁定，正确动作是**回问一句再动手**，而不是"是 lead 说的所以直接改"。
3. **不要把"我读到的版本"当作"当前版本"**。本项目已出现 6 次"读到旧快照后报缺陷"（D-15），两次"照消息实现后与文件冲突"（D-17/D-19）。**回文件取，永远是成本最低的动作。**

**为什么锚点是"可 grep 的唯一串"而不是行号 / 版本号**

- 版本号永远在移动，所以全组禁了"正文写需求版本号"；**行号移得更快** —— 本项目一天内 `03-后端设计.md` 从 2507 涨到 2915 行，本文自己也从 1947 涨到 2100+，**我在同一轮里给出的行号已经全部失效**。
- 行号是**偶然属性**（增删一行就变），锚点串是**语义属性**（改完就消失）。核验只跑一条 `grep`：**还命中 = 没改，不命中 = 改了**。不依赖时间、不依赖叙述、不依赖对方是否诚实。

**报告"已改"的格式（四件套，缺一不算）**

| 项 | 要求 | 形状（**全部用占位符，不填真实串**） |
|---|---|---|
| ① 锚点串 | 改前能唯一命中、改后必定消失的那一段（或改后新增的唯一一段） | `‹被删掉的错误结论›.‹它挂的字段›` |
| ② 改前片段 | 原文关键串（含它被当作**有效**结论使用的那半句） | `‹同上› 问的是"通道现在能不能用"` |
| ③ 改后片段 | 新文关键串 | `‹新写入的判据句›` |
| ④ 实测计数 | 改后跑一次 `grep -c`，把**数字**贴出来（不是"我搜过了"） | `锚点：‹① 的「用法」那一截› → grep -c = 0` |

> **本行是格式示意，不是可核验锚点。** 这四格一律不填真实串，理由有两条，都是实测换来的：
> 1. **填进去就等于重新造出命中。** 这轮我先测得某锚点 `grep -c = 0`，把例子填进表，再测同一个串：`0 → 4`；再填 ③ 那一格，`0 → 1`。**在 `grep` 眼里，"举例"和"继续在用"是同一件事。**
> 2. **正文留有留痕时，"名字"永远清不到 0。** 本文 §11.3 末尾特意保留"这个码不存在"的警示（**作废结论必须留痕**，否则下一个人会用同样的理由把同一个错再犯一次）。所以那个裸码名的命中数是 **2**（警示 1 + 早期版本此处举例 1），而**"用法"那一截是 0**。验收形状必须是**两个数字一起**：用法 `0` + 名字 `N ≥ 1`。
>
> 由此三条操作规则：
> - **锚点串属于报告，不属于正文。** 想留"当时怎么验的"，记**条数与时间**，不复写串。
> - **核验顺序固定 改 → 测 → 报，中间不许插入"把过程写进文档"。** 否则你测的是旧文件、报的是旧数字，而读者拿新文件比对会得出"你没改"——这类声明与编造**对读者不可区分**。
> - **只测一个数时，`0` 有两种可能：「清干净了」和「我把串搜错了」。** 旁边必须有一个"应该不为 0"的读数作对照，才把"搜错"这一支排除掉。

> **一个反直觉的推论：可核验的必须是"当时留下的证据"，不能是"事后重建的证据"。**
> 我一度想给 ②「改前片段」回填一段，因为"我知道它大概原来怎么写"。**这是错的**：事后重建的串有两个毛病 ——
> 1. **它不唯一**：反推出来的句子会命中今天的正文（因为写的就是"现在这段"的近邻），`grep -c` 得 1 而不是 0 → 下一个照抄核验的人会得出"你没改"。
> 2. **它是编的**：而"编"的代价不是这一格，是**这张表从此不再可信**——表里一旦有一格是猜的，读者无法区分哪几格是验过的，整张表的证据价值归零。这与 D-21 是同一个病：**编一个看起来合理的东西，它会一路绿。**
>
> 事后重建的证据有个致命特征：**它和它要证明的那件事，唯一的关系是"作者认为它们有关系"**。而审计要的恰恰是"不依赖作者认为"。
> 所以正确用法是：**改的时候就复制改前那一行**（`git diff` 里有，成本为零），不是事后回想。事后能补的只有 ③（它就在文件里），补不了 ②。
> 补不上时写 **"待补（改时未留原文）"** —— 这五个字是有信息量的：它说明"这里改过，但取证没做"。**空着会让人去问、去补记录；填一段假的就没人再问。**

> **两处"写法不得互换"的硬约束（都是这轮被同一个词绊倒换来的）**
> - **数据枚举驼峰 / 错误码 UPPER_SNAKE**：`canSellReason` 与 `details.reason` 是 **JSON 载荷里的数据字段**（`ok` / `noCredentials` / `testFailed` / `channelDisabled`）；`ProblemCode` 的 `code` 是**封闭枚举、对外契约**（`CANNOT_SELL` / `STOCK_CHANGED_RETRY`）。**两者不得互换写法**——把数据枚举写成 `PAYMENT_NOT_CONFIGURED` 这种形态不是风格问题，是把错误码的命名惯例套到了数据枚举上。
> - **判据一句话**：**`code` 是多个独立字段（各自有名字），可以各有拼写；`details.reason` 是同一个字段名，只能有一种拼写。** 域不同解决的是"哪个值属于哪个域"（语义），字段同名解决的是"解析器要不要先看 `code` 再选词表"（工程成本）——**两个域可以各有一张词表，但拼写风格必须一致**，否则"只写一套 `code → i18n key` 映射"这条就打穿了。
> - **引用尚未进契约的码，必须标注 `未进契约（M3/M4）`**：`CANNOT_SELL`、`PAYMENT_PROVIDER_UNAVAILABLE` 目前都不在 `ProblemCode` 封闭枚举里（`/api/checkout`、`/api/setup` 尚未进契约，前者随 **M3**、后者随 **M5**）。不标注的话，下一个人拿 `06` 去跑 "`code ∈ enum`" 门禁会把它们判成拼写错误，做成一个**永远红的约束**——而恒红约束的真实下场是被加进豁免名单，连带真实缺陷一起豁免。
> - **"成员名进契约" ≠ "端点进契约"，这两件事要分开说。** 词表可以只写在 `description` 里（给人读的），而 `enum` 块是**机器唯一执行的约束**，要等端点真正进契约才有。混起来会同时产生两种误判：以为"词表有了 → 门禁能跑了"（跑不了，没有 `enum` 可对），或以为"端点没进 → 词表是我推的"（推的更要标，但已定稿的就不该再说"待定稿"）。**写清楚是哪一种，别让读者自己猜。**

> **断言里出现的任何实体标识（slug / SKU / 分类 slug / 变体码），必须能在 `02` §7.3.4 的 fixture 清单里 `grep` 到。** `grep` 不到就是编的，不需要再判断。
> 这条不需要靠自觉：它是可执行的——查一下就能定案。本轮我犯了两次（`zh-only-product`、以及给 `fx-arch-repl` 编了一个历史 slug），两次都是"看起来非常合理"的标识。
> **为什么"合理"特别危险**：不合理的东西会被人一眼看穿，合理的东西会一路绿——因为那条 URL 本来就不该存在，404 是**恒真**的，跟实现对不对无关。**绿得毫无信息量。**

> **提交信息必须覆盖该提交的实际改动范围；混入非本人改动时，在信息里写明是哪几处、经谁核实。**
> 这条不是"所有权洁癖"，因为**"谁提交"这个量在本仓库核不出来**——所有人同一个 git 身份。
> 本轮我据"提交信息像我的、内容我没写"推出"有人代我提交"，实际那是我自己提交的；
> 反向也成立：同一个身份下，别人混进我的提交，`git` 也指不出来。
> 所以**能核的只有 `git show --stat` + 逐行 diff**：它告诉你"这个提交里有哪些行变了"，
> 但**不告诉你是谁写的**。因此判据只能建立在"范围声明是否与 diff 一致"上，不能建立在身份上——
> **规则的判据必须落在能核实的量上，否则它只是指责。**
> 配套动作：同一份文件在同一时段由 owner 统一提交；别人要直接写，须在消息里说"我改了哪几行"。
> 目的不是独占，是让"哪几行是谁的"有地方可查——**否则报告里的数字与文件对不上时，分不清谁错。**

> **引提交信息必须用 `git log -1 --format=%B`；`--oneline` 只是主题，不是全文。**
> 这是上面那条的同族错误，我当天就犯了第二次：我据 `git show --stat --oneline 1688ddc` 的输出断言"**该提交信息只写了 `fix(paging)`，未覆盖这部分范围**"，而它的正文里明明有一段**认领**：「由 teammate 落笔，会话在网络超时里断掉，本笔由 lead 按其磁盘上的完成态代提交」。
> **`--oneline` 的输出与"消息只有标题"在屏幕上一模一样**——这跟"计划状态与文件状态在句子里一模一样"是同一个病：**用一个摘要去支撑一句关于全文的断言**。修正后的判据只有一层：**要说"信息里有没有写"，读 `%B`；要说"哪几行属于哪笔"，用 `git log -G`。** 摘要能支撑的结论只有"主题是什么"，仅此一条。

> **定位"这一行属于哪一笔"用 `-G`，不用 `-S`（`-S` 会漏）。**
> `git log -S "<串>"` 是 pickaxe：它匹配的是"**这个串在 diff 里出现次数变了**"。于是三种情况**全漏**：① 串被**移动**到另一处（次数不变）；② 串**改了格式**（`Math.min(99, null)` → `Math.min(99,null)` 少一个空格）；③ 串被包进更长的表达式。
> `git log -G "<正则>"` 匹配的是"**diff 内容匹配这个正则**"，对移动与改格式都敏感。完整形态：
> ```
> git show --stat  <hash>                    # 这笔记了哪些文件（不是"谁的"）
> git log -G'<正则>' --oneline -- <file>      # 这一行出现在哪些提交（对移动、改格式敏感）
> git log -S'<逐字串>' --oneline -- <file>    # 只在"逐字没变"时做交叉确认
> git log -1 --format='%an'                  # 只作辅助，不作判据（单身份仓库里它恒返回同一个名字，方差为 0）
> ```
> 这条是 team-lead 对我的修正——**我原来只写了 `-S`**，而"串被移动"恰好是重排文档时最常见的一种改动，**用错开关会在最该抓到的那一类上静默返回空**。

> **恒真判据不是判据：一个断言如果两种不同实现都能满足，它就不能用来区分这两种实现。**
> 本轮两例：`expect(location).toContain(SITE)`（`SITE` 与测试环境请求 Host 同值 ⇒ "读配置"和"读请求 Host"给出逐字相同的串，它恒真）与 `git log -1 --format=%an`（单身份仓库恒返回同一个名字）。
> **推论**：当你想加一条"防止实现走错源"的断言，先问"错的实现会不会也满足它"。会的，就别加——**写"已知未覆盖"比加一个恒真守门人好**：前者把"没验"摊在明面上，后者把"没验"伪装成"验了"。**一个诚实的空洞会被人补上，一个假的覆盖不会。**

> **判据必须能被"只看它、不看上下文"的人直接执行。** 需要读者先去别处补齐才能用的，不是"写得简洁"，是**没写完**。
> 反例（我自己犯的）：AC-11 规则 4 那一格**参数写了、规则名写了、断言一行没有**——三个部件里两个在，于是它**长得像已经写完了**。它比"判据太松"更难发现：松的判据至少会被读一遍，而**"形似完成"的判据，读者是执行者，他会按已有的部件执行，然后得到一个自己都没意识到不完整的结论**。

> **多人共写的文件禁止整文件 `git add`：必须 `git add -p` 逐 hunk 挑，或至少 `git diff --cached` 逐 hunk 过一遍。**
> **而且"核过 `--cached`"不等于"提交的就是我核的那一版"**：`git diff --cached --stat` 核的是"**将要发生的**事实"，提交取的是"**提交那一刻**的暂存区"，**两者之间有一段不属于任何人的时间**。本轮 `backend-engineer` 就栽在这个窗口里（20:08 核 `--cached` 只有 1 个文件，20:09 那一笔落库时多带了别人 12 行）。
> 可执行的动作只有一条：**`git add <精确路径> && git commit -F <msg>` 放进同一条命令链**，不留窗口；要核"这一笔改了什么"，核 `git show --stat HEAD`（**已发生**的事实），**不核 `--cached`**（**将要发生**的事实）。
> **但这个窗口是双向的，单命令链只关掉一半**：它关掉的是"`add` → `commit`"这一段；"**改 → `add`**"那一段仍在——**别人可以在你 `git add` 之前就把你的工作区改动一并提交掉**。
> 本笔实证（`git log --oneline -1 -- docs/04-前端设计.md` 可见）：我在 §2.1/§12.1.1/§12.3 的三处改动 + 一处新写的约束，被上一笔提交整份带走；我随后那条 `git add && git commit` 直接报 `no changes added to commit` —— **不是提交失败，是"已经没有什么可提交了"**。
> **而且 `git add <path> && git commit` 并不能把提交限定在那个路径上——`commit` 提交的是整个索引。**
> 索引里可能有别人刚 `git add` 的东西（多人共写时这是常态）。本轮我就这样把 `docs/06-测试验收.md` 的 152 行
> 带进了自己的提交（`d3c9b59`，2 files changed）。**内容正确、保留、不 amend**，但范围与信息不符。
> 正确形态是 **`git commit -F <msg> -- <精确路径>`（pathspec 限定）**；要核"这一笔到底含哪些文件"，
> 用 `git show --name-only HEAD`，**这是唯一能回答"我的提交里有没有别人东西"的命令**。
> 反过来也要记住：**`git add` 的粒度解决的是"我放进去什么"，不解决"别人已经在里面放了什么"。**

> 所以补一条**事后判据**（这条不能靠预防，只能靠查）：**提交报"没有可提交的改动"时，不要以为命令写错了，先跑 `git log -1 -- <file>`**——你要声明的那笔范围很可能已经落在别人那一笔里了。此时**不 amend、不重写历史**，按"范围可查"补在下一笔的信息里即可。
> `git diff --cached --stat` **不够**：它只说"几行变了"，不说"哪些主题变了"。本轮 `1688ddc` 就是这样一次提交——`--stat` 显示 `3 files changed` 看起来正常，实际在 `04` 上顺带带走了别人四处未提交的改动（`Math.min(99, null)` 两处、`--out-of-stock` 两处）。**同一个动作当天栽了两次**（另一次是 `719b123` 带走 `docs/06`）。
> 注意：**不要因此立"提交前 `git status` 必须为空"**——多人并行时"status 非空"是**正常的中途态**，而"这是我写的还是别人写的"在同一个 git 身份下分不开。那条规则会把正常状态判成违规，然后被大家跳过；**假失败的门禁最后一定会被关掉**。判据要落在"我暂存了什么"（`git diff --cached`）上，不能落在"工作区干净吗"上。

> **给不出锚点串的，写"待核"，不写"已改"。**
>
> **并且必须"改完再取证"，不能"声明先于动作"**：写"已改"时若用的是**脑子里的计划状态**而不是**文件的实际状态**，两者在多线程改文档时几乎必然不同步。这类声明与"编造"对读者**不可区分** —— 而它攻击的不是事实，是**核验通道**：内容错是数据损坏，可改一处；"已改"不可信是协议损坏，之后每条都要重验，而本项目这轮的"引用不复制""结论变了附锚点"全部依赖"对方说的是真的"。
>
> **这条在本项目已犯 3 次，第 3 次是我在写完本段当天犯的**：我在一条消息里写"参数清单缺的 `?sort=` 已补"，实际数组里没有它——**写在消息层，所以文档层查不到，也不会有人来核**。触发点很有代表性：前两个参数我是照着原文抄的，第三个参数要判断"它属于筛选还是排序、该不该进同一个判据"——**需要判断的那一条，就是漏掉的那一条**。同族现象在"写断言"这一侧叫"越宽松越容易绿"，在"抄判据"这一侧就叫"没抄需要判断的那条"。

| **Q-5** ✅ 已闭环（末次） | 商品 slug 的"per-locale 唯一 + 页级未译" | **页级未译 → 该语种无该实体 URL（404 + `noindex`），不做跨语种 slug 回退**（`docs/02` §4.5、§3.1）；切换器无译文时指向目标语种首页并标 `data-locale-nav="fallback-home"`；`hreflang` 只出 `exact` | 我先后写过两种错法（"必须命中"→"回退渲染 200"），两次都源于**相信了转述消息而不是文件行**。已在 §12.1 记 D-20 |
| **Q-6** | 图片 DTO 是否包含 `width`/`height` 与三档 `sources` | **必须包含** | 缺尺寸 → CLS 无法控（AC-12）；缺 sources → 前端猜尺寸必出错 |
| **Q-7** | 预览草稿（`draft-preview`）落哪里：临时表 / 进程内存 | 进程内存 + TTL 30min 足够（单实例），但重启即失效 | 需后端确认单实例假设；多实例时改临时表 |
| **Q-8** | `trailingSlash` 全局策略（`'always'` vs `'never'`） | **`'always'`**（`/zh/` 而非 `/zh`） | 影响 canonical 一致性；SvelteKit 是全局配置，改一次要全站重定向对齐 |
| **Q-11** ✅ 已闭环 | **"未登记的旧 slug → 404（不得 200 近似匹配）"的固定样本** | 数据侧已在 `02 §3.9` 给出三个 `mustNotExist` 探针：`P-404-a` = `fx-mug-v1`（抓"去掉 -vN 归当前商品"）、`P-404-b` = `fx-kettle-v2`（抓"凡 -vN 一律归当前 slug"）、`P-404-c` = `fx-kettl`（抓前缀/模糊/拼写纠正），外加 **`P-404-d`** = `/zh/products/fx-kettle-v1`（抓查历史表**漏了 `Locale`**，属「组合不存在」，**不是**模糊匹配那一类）。**另有 `P-404-d`，不进 `mustNotExist`**：`fx-kettle-v1` 在 `en` 下是一条**完全合法**的历史行（库里真有 1 行，② 就是拿它验 301 的），而清单的语义是"**哪里都不存在**"——把它塞进清单，校验会要求它 `0` 行，**与数据直接矛盾**，而人遇到"清单说有、库里也有"时最省事的做法是**去把数据删掉**（那会同时打掉 ② 的 301 与 `P-404-b` 的基准）。**承载方式是单独一条断言，不是进清单。清单的语义比清单的整齐更重要。** **04 只钉断言、不复述样本表**，见 §7.7 的 `MUST_NOT_EXIST` 块。**`fx-kettle-v2` 的唯一出处是 `P-404-b`**——先前 `02` 里另一份 `N1/N2` 表与它重复，已并掉（同一文件内部各说一套比跨文件更难发现） | 我原写的"无样本、待补"已作废。**但"不自造串"这条判断本身仍然成立、且被数据侧改进了**：他们给出的探针是"只差一个常见变换、看起来最该被匹配上"的串，并**配了正向锚（`/en/products/fx-kettle` → 200）**——我原来的顾虑（自造 404 一路绿）是对的，但它推不出"不能造"，推得出"**必须造得近似、且必须与正向控制成对**" |
